안녕하세요. 저는 카카오 모빌리티에서 카카오 안드로이드 앱을 개발하고 있는 윌슨입니다. 작년인 2019년도에 저는 카카오 대비해 카카오티의 주차 서비스를 탑재하는 프로젝트를 진행했습니다. 카카오팁 앱 내부에서 제공하던 주차 서비스를 똑 떼어다가 다른 앱에 이식하는 프로젝트였기 때문에 기술적으로나 기획적으로나 도전적인 프로젝트였습니다. 오늘 발표에서 저는이 프로젝트를 진행하는 과정에서 어떤 기술적인 문제가 있었고 그러한 문제들을 어떤 식으로 해결했는지 나눠 보려고 합니다. 비록 안드로이드 앱 개발에 관련된 기술적인 발표이지만 코드는 한 줄도 나오지 않으니 안심하시고 편하게 들어 주시면 좋겠습니다. 우선 우리는 왜 카카오 내비에 카카오 주차 서비스를 이식하기로 결정했는지 이야기해 보겠습니다. 카카오 모빌리티는 우리의 기술로 생활을 움직입니다라는 비전을 바탕으로 다양한 모빌리티 서비스를 제공하고 있습니다. 앱으로 보자면 카카오 내비아 카카오티 이렇게 두 개의 앱을 관리하고 있고 카카오 내부엔 다시 많은 분들이 사용해 보셨을 택시를 비롯하여 대리, 주차, 바이크, 셔틀 등의 서비스를 제공하고 있습니다. 한편으로 이런 다양한 서비스를 개별적으로 제공하는데 그치지 않고 각 서비스들이 서로 유기적으로 결합하여 더 큰 시너지를 낳을 수 있도록 노력하고 있습니다. 카카오 내비가 제공하는 기란내 서비스를 생각해 볼게요. 카카오 내비를 이용하면 운전자는 목적지까지 원하는 조건에 맞는 경로로 빠르게 이동할 수 있습니다. 하지만 목적지에 도착하고 나서 주차할 공간을 찾아야 되는데이 부분은 아직 내비가 제공해 주지 못하고 있습니다. 결국 도착지 근처를 배하면서 주차할 공간을 찾아야 하는 건 여전히 운전자의 몫입니다. 그렇다면 카카오 모빌리티가 제공하는 또 다른 서비스를 이용하면 이런 문제를 개선해 볼 수 있지 않을까요? 이미 카카오티에는 주차 서비스가 있으니이 서비스를 내비에 잘 접목하면 운행의 마지막인 주차까지 스마트하게 마무리할 수 있지 않을까 생각했습니다. 그래서 카카오 내비에 카카오 주차 서비스를 연동해 보기로 마음 먹었습니다. 카카오티 주차를 조금 더 들여다보기로 하죠. 카카오 주차는 사전 예약과 자동 정상 이렇게 두 가지 방식의 서비스를 제공합니다. 사전 예약은 사용자가 자신의 목적지 금방의 주차장을 선택한 후 그 주차장의 이용권을 사전에 구매하는 서비스입니다. 이렇게 이용권을 사전에 구매하면 목적지 금방에 도착해서 주차장을 찾아볼 필요가 없고 또 기껏 주차장을 찾아는데 많차라서 낭패를 겪을 일도 없습니다. 또 다른 서비스인 자동 정사는 사전 예약 없이 일단 주차를 하고 나서 서비스를 신청하는 방식입니다. 이렇게 신청을 할 경우 주차장을 벗어날 때 자동으로 결제가 되기 때문에 힘들게 차단기 앞에서 신용 카드를 꽂거나 군대군데 흩어져 있는 주차비 정산기를 찾아다니지 않아도 됩니다. 자동 정산 서비스를 제공하는 가장 대표적인 곳으로는 에버랜드를 꼽을 수 있습니다. 두 서비스 모두 카카오 내비와 연동했을 때 운전자에게 많은 가치를 제공한다고 생각합니다. 하지만 사전 예약의 경우엔 미리 주차장을 찾고 시간권을 구매하는 과정이 필요해서 빠르게 길한 내를 받고자 하는 현재 내비 사용자의 패턴과는 잘 맞지 않았습니다. 그래서 별도의 예가 없이 바로 사용할 수 있는 자동 정산 서비스를 먼저 내비와 연동해 보기로 결정했습니다. 이렇게 해서 카카오 내비에 카카오 T 주차의 자동 정산 서비스를 연동하는 프로젝트가 시작되었습니다. 2019년 중순에 오픈하는 것을 목표로 해서 카카오 T와 카카오 내비의 여러 담당자들이 협업하여 진행해야 하는 나름 복잡한 프로젝트가 되었습니다. 저는이 프로젝트에서 안드로이드 설계와 구현을 맡았는데요. 가장 먼저 카카오티의 주차 서비스를 SDK로 만들어서 내비 앱에 탑재하기로 결정했습니다. 주차 서비스도 빠르게 개선이 이루어지고 있어서 내비 안에 탑재된 주차 서비스를 지속적으로 업데이트 하기 위해선 SDK 형태로 배포하는 방식이 가장 적합했기 때문입니다. 자, 그럼 기존 카카오에 있던 주차 기능을 어떻게 SDK로 만들 수 있을까요? 저는이 부분을 고민하면서 설계를 시작했습니다. 카카오 T앱은 다음과 같은 모듈 구조를 채택하여 개발했습니다. 택시, 대리, 주차 등 여러 서비스들을 저희는 내부적으로 버티컬이라고 부르는데요. 이런 버티컬들은 각각의 안드로이드 라이브러리 모듈로 구성되어 있습니다. 모든 버티컬은 차량 관리, 결제, 사용자 정보 조회 등의 플랫폼성 기능이 필요합니다. 각 버티컬마다 이런 기능을 별도로 구현하는 건 굉장히 비효율적이어서 플러그인이라는 모듈의 모든 플랫폼성 기능의 인터페이스를 선언하고 버티컬은이 인터페이스를 통해 플랫폼 기능을 사용하도록 구성했습니다. 카카오에 본체라고 할 수 있는 M모듈은 플러그인 모듈에 선언된 인터페이스의 구현체를 제공합니다. 이러한 모듈 구조 덕분에 버티컬 모듈은 M 모듈에 의존하지 않고도 플랫폼 기능을 활용할 수 있습니다. 마지막으로 모든 모듈에서 공통적으로 사용할 수 있을 만한 유틸리티성 코드들을 모아서 베이스 모듈을 만들었습니다. 카카오의 모듈 구조를 봤을 때 SDK에서 그대로 활용할 수 있는 모델들이 몇 가지 보였습니다. 우선 주차 서비스 그 본체라고 할 수 있는 주차 모듈을 재사용해야겠죠.이 모듈만 잘 동작할 수 있으면 사실 개발은 거의 끝난 세미나 마찬가지일 겁니다. 하지만 과연 그게 쉬울까요? 계속 살펴보시죠. 주차 모듈이 동작하려면 주차 모듈이 의존하는 모듈이 필요합니다. 그래서 자연스럽게 플러그인 모듈과 베이스 모듈도 재사용 대상으로 뽑았습니다. 하지만 이렇게 되면 플러그인 모듈의 인터페이스를 실질적으로 구현하는 카카오 T앱으로 따지자면 M모듈에 해당하는 무언가가 필요하게 됩니다. 그래서 SDK에선 M모듈의 역할을 담당할 새로운 모듈이 필요해졌습니다.이 모듈의 이름은 코어 SDK라고 지었습니다. 4 SDK 모듈은 제공해야 하는 기능이 굉장히 많은데 이걸 어떻게 하면 효율적으로 구현할 수 있을지가 관건이었습니다. 크게 두 가지 접근법을 떠올렸습니다. 하나는 조금은 무식하게 M모들의 코드를 일단 통째로 복사하고 SDK에 맞게 뜯어 고치는 방법입니다. 개발자분들 중에 많은 분들은 이렇게 복사에서 붙여 놨는데 거부감을 가질 거라고 생각합니다. 일단 빠르게 만들어 낼 수 있는 장점이 있는 반면에 한번 이렇게 코드를 붙여 넣어서 작업을 하게 되면 나중에 두 개의 모듈을 각자 유지보수해야 하는 부담이 생깁니다. 이런 상황을 흔히 우리는 기술 부채라고 표현하기도 하죠. 조금 더 우아해 보이는 방법은 M모듈을 좀 더 작은 모듈로 나눈 다음 M모듈과 코어 SDK 모듈에서 공유하는 방식입니다.이 방식을 택할 경우 모듈로 분리한 코드를 재사용할 수 있으니 통으로 복사하는 방식에 비해 유지 보수하기가 더 좋습니다. 두 번째 모듈화 방법이 더 좋아 보이긴 하지만 M모듈 자체도 계속 개발되고 있는 와중에 그 모듈을 쪼개고 또 코 SDK 모듈까지 새로 만들기엔 작업이 너무나 커집니다. 그래서 일정 내에 이것까지 진행하기는 어렵다고 판단했습니다. 그래서 조금은 덜 우아하지만 일단은 M모델을 통으로 복사해서 만드는 첫 번째 방법을 택했습니다. 내비와 주차 팀의 요구 사항을 취합하다 보니 주차 모듈의 일부 기능은 SDK에서 다르게 동작해야 했습니다. 최대한 주차 모듈만큼은 코드 수정 없이 그대로 쓰려고 했지만 그게 제 마음대로 되지는 않더라고요. 어쩔 수 없이 새로운 요구 사항을 충족시키기 위해 주차 모듈을 수정한 다음 설정을 통해 기능이 분기되도록 결정했습니다. 그럼이 설정값을 제공할 무언가가 필요해집니다. 처음엔 코어 SDK 모듈에서 주차 모듈에 직접 접근해서 설정을 하려고 했습니다. 하지만 혹시나 나중에 택시 SDK, 대리 SDK까지 만들어야 한다고 생각하면 코어 SDK는 주차 모듈에 직접 의존을 하지 말아야 한다고 생각했습니다. 그래서 설계를 조금 바꿔서 주차 모듈에 직접 접근하여 설정을 하는 역할을 하는 새로운 모듈을 추가했습니다.이 모듈의 이름은 주차 SDK라고 붙였습니다. 주차 SDK 모듈이 등장해서 이제 코어 SDK는 더 이상 주차 모듈에 의존하지 않아도 됩니다. 이렇게 설계된 모듈 구조를 도입하면 주차 기능을 사용하고자 하는 앱은 주차 SDK 모듈에만 의존하게 되면 자연스럽게 코어 SDK 모듈과 주차 모듈의 기능에 접근할 수 있습니다. 자, SDK 모듈 구조는 어느 정도 윤곽을 잡았습니다. 이제 실전인 구현 단계로 들어가 볼까요? 구현 단계 모듈에선 모듈 설계에서 강과했던 문제들이 붉어져 나올 테니까요. 그중 가장 덩치가 컸던 문제 두 가지를 소개해 보겠습니다. 먼저 인증 문제를 살펴보겠습니다. 카카오 TSDK의 거의 모든 기능은 사용자 인증이 필요합니다. 즉 로그인이 필요하다는 얘긴데요. M 로그인로그과 별개로 또다시 SDK 로그인을 해야 한다면 이걸 좋아할 사람은 아무도 없을 겁니다. 따라서 앱에서 로그인한 정보를 이용해 자연스럽게 SDK에서 사용자 인증을 할 방법을 고민해 봤습니다. 다행히 카카오 내비와 카카오 T는 모두 카카오 계정을 기반으로 사용자를 관리하기 때문에 내비에서 로그인한 사용자를 카카오티의 사용자로 매핑하는 것이 가능했습니다. 물론 내비와 카카오티 두 서비스 모두 가입한 사용자에만 하겠죠. 카카오 내비는 억세스 토큰을 SDK에 제공합니다. 그럼 SDK는이 토큰을 SDK 서버에 전달하고 서버간 통신을 통해 최종적으로 카카오티 사용자를 알아냅니다. 아쉽게도이 지점에서 SDK 서버와 내비 서버가 서로 통신해야 하기 때문에 SDK를 사용하기 위해선 연동이 필요하다는 제약이 생겨 버렸습니다. 다음으로 이슈가 될 부분은 푸시였습니다. 자동 정산 서비스는 주차장 입차, 출차 등의 메시지를 사용자에게 푸시로 발송합니다. 앱이 푸시를 보내고 받는 건 우리 모두에게 익숙한데 SDK에서 푸시를 보내고 받아야 한다. 이건 저는 처음이었어요. 여러 가지 방법을 고민해 봤지만 앱을 건너뛰고 SDK가 푸시를 보내고 받을 방법이라는 건 없었습니다. 결국 SDK를 탑재한 내비 앱과 내비 서버에 의존해야만 했습니다. 푸시를 발송해야 할 경우엔 주차 서버가 내비 서버의 푸시 발송 요청 API를 호출합니다. 내비 서버는 이렇게 받은 요청 정보를 FCM 서버에 전달해서 푸시 발성을 요청합니다. 푸시 수신도 간단하진 않았습니다. 푸시를 수신하는 주체는 내비앱이고 알림 내용을 구성하는 건 SDK이기 때문입니다. 우선 내비에비 푸시를 수신하면 SDK에게이 푸시 내용을 전달합니다.
