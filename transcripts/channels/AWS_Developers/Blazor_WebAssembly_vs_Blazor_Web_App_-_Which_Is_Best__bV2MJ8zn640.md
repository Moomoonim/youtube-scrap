Lost between Blazor WebAssembly and Blazor WebApp, the two flavor of the new .NET front-end web framework? This video is for you. It is the first of a series about building modern web application with .NET and AWS in 2024. I'll discuss the different hosting model and the rendering mode of the Blazor web framework. I'll also give you some advice on how you can host your Blazor web application, depending on which hosting model you've chosen. Hi, I'm Francois Bouteruche. I'm a .NET developer for the past 20 years and I love Blazor. I work at Amazon Web Services and help .NET developers to make the best use of AWS services' breadth and depth. So, before the release of .NET 8, the world was deterministic. You could choose between Blazor WebAssembly and Blazor Server. The rendering of your web application would happen in the browser or on the server. With .NET 8, the .NET team has released a new Blazor web application model, Blazor WebApp. It brings support for static server side rendering, interactive server side rendering and hybrid rendering. This new model replaces Blazor Server model. Let's see what that means and how you can deploy Blazor WebAssembly and Blazor WebApp on AWS. Blazor is a component-based front-end framework like Angular, React or Vue.js. Its particularity is that you use C# to create rich interactive UI rather than JavaScript or TypeScript. You can then reuse the same code, implementing your app logic, both server side and client side. Of course the UI is rendered as HTML and CSS for wide browser support, including mobile browser. You can also leverage a full ecosystem of .NET libraries. Before .NET 8, Blazor had three hosting model, Blazor Server, Blazor WebAssembly and Blazor Hybrid. With Blazor Server, as its name suggests, component are render on the servers. UI updates, event handling and JavaScript codes are processed over a SignalR connection using the WebSockets protocol. It mean that the state of each connected clients, more accurately every browser tab, is managed server side. Assets are deployed at the ASP.NET web application. With Blazor WebAssembly, the Blazor application is executed on the client side by a version of the .NET runtime compiled to WebAssembly. Other components, their dependency, and the WebAssembly-based .NET runtime are downloaded to the browser. Components are rendered directly on the browser UI thread. UI updates and event handling occur within the same process. Assets are deployed as static files. With Blazor Hybrid, components are render through a Blazor web view that can be embedded into native client application, built either with .NET Maui, Windows forms, or Windows Presentation Foundation. The .NET team provide a comprehensive table that allow you to decide between the three hosting model. The link is in the description. Starting with .NET 8, the .NET team has refined the Blazor server hosting model. To do so, they've introduced Blazor WebApps model, which can be seen as an evolution of the Blazor Server hosting model. In the previous version, every UI updates or interaction had to be processed server side. It was adding unnecessary server load and network ops. Some components may have no interactivity. When they are rendered, there will be no (indistinct) static server side rendering may be a good option. Some components may not need to access several resources but are highly interactive. Thus, client side rendering is a better option. To provide a smooth experience to your user, you may also want to start with interactive server side rendering first, and then move to client side rendering when the Blazor bundle is downloaded. That's exactly why the .NET team has introduced their rendering modes. You have four different rendering mode, starting with .NET 8. Static Server, which performs static server side rendering, Interactive Server, which performs interactive server side rendering. The UI interaction are processed server side over a real time connection with the browser. With the interactive server side rendering, you don't need to build API endpoints to access server resources. Interactive WebAssembly rendering mode performs client side rendering. As Blazor WebAssembly hosting model, it relies on a version of the .NET runtime built with WebAssembly, which is downloaded with your app. Your .NET code is then executed in the browser security sandbox. You can also interact with JavaScript code. The last one is Interactive Auto, which performs interactive server side rendering initially and then client side rendering after the Blazor bundle is downloaded. Blazor WebApps tries to merge the best of both Blazor WebAssembly and Blazor Server hosting model in one application model. Yet all of them require that you deploy a (indistinct) with .NET application to serve your Blazor WebApps. In a nutshell, if you want to build a fully static single page application running in the browser and leveraging some API endpoints to access the server resources, you should take a look at Blazor WebAssembly. On the other side, if you want to provide a smooth experience to users, address users that don't use modern browsers supporting WebAssembly, or your application need to access server resources, but you don't want to maintain API endpoint, then Blazor WebApps is your go-to. Now, what does it mean in term of deployment on AWS? If you are going down the Blazor WebAssembly route, I would recommend to deploy your application on Amazon S3, our object storage service, and serve it with Amazon CloudFront, our content delivery network. If you are going down the Blazor WebApp route, I would recommend to deploy it to AWS App Runner, our managed container app service as a starting point. If you have specific requirements, you can explore Amazon Elastic Container Service, our container architecture using AWS Fargate, our serverless container execution engine. If you are in love with Kubernetes, you can of course leverage Amazon Elastic Kubernetes service. If your requirements evolve over time, you can learn more on other deployment option on the AWS .NET Developer Center at the link in the description. Stay tuned.
