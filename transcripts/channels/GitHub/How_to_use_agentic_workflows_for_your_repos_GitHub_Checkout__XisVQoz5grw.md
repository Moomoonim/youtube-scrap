"잘 들어, 매일 내 종속성에 대한 Astro의 새 릴리스가 있는지 확인해. 만약 있다면, 변경 로그와 업그레이드 문서를 살펴보고, 호환성을 깨뜨리는 변경 사항을 처리하는 것을 포함하여 마이그레이션 계획을 세운 다음, 업그레이드와 관련된 모든 변경 사항을 포함하는 PR을 생성해 ." Co-pilot이 이 작업을 처리하고, 자세히 살펴보면 알 수 있듯이, 프롬프트에서 시작하여 Co-pilot이 이를 읽고 모든 지침을 따르는 등의 과정을 거칩니다 . 마지막에는 이 워크플로를 포함하는 풀 리퀘스트를 생성합니다. Agentic Workflows에서 실제 워크플로 설명은 마크다운으로 작성되며, 맨 앞에 프런트 매터 블록이 있는 영어 문서입니다 . 에이전트가 아무런 제약 없이 마음대로 행동하도록 내버려 두는 것은 좋지 않기 때문에 여기에 가이드라인을 설정합니다 . 이 워크플로의 목적은 무엇일까요? 바로 업그레이드 검사기입니다. 제 워크플로를 살펴본 것입니다. 이 코드는 제 실제 의존성이 무엇인지 파악했고, 실행될 때마다 NPM에서 해당 항목들을 확인하고 , 변경 로그와 업그레이드 가이드를 검토하여 어떤 버전을 업데이트해야 하는지 파악한 다음 필요한 변경 사항을 적용합니다. 그리고 완료되면 풀 리퀘스트를 생성합니다. 실행 예시를 보여드리겠습니다. 저는 제 개인 사이트에서 이 코드를 실행해 봤는데, 특별히 표나 변경 로그의 주요 내용을 출력해 달라고 요청한 것은 아닙니다. 하지만 만약 사람이 이 작업을 했다면, " Agentic 워크플로를 사용하는 입장에서 이런 사용자 경험이 있으면 좋겠네."라고 이해했을 겁니다. 이번 실행에서는 이 버전에서 저 버전으로, 그리고 저 버전에서 저 버전으로 업그레이드합니다 ." 만약 아무것도 찾지 못했다면, "여기서 할 일이 없으니 작업을 수행하지 않겠습니다."라고 말했을 겁니다. 제 오픈 소스 프로젝트에서도 Dependabot이 PR을 생성해야 할 만한 변경 사항이 있거나 호환성이 확보될 확률이 낮아서 PR을 생성할 필요가 없는 경우 몇 번 알림을 받았습니다. 이런 상황에서 에이전트 기반 워크플로가 어떻게 도움이 될 수 있을지 궁금합니다. 다시 말하지만, 답은 항상 원하는 결과를 영어로 작성하는 것입니다 . 좋습니다. 제 에이전트 기반 워크플로는 Dependabot이 제 저장소에 PR을 생성할 때마다 해당 PR을 살펴보고 저장소가 제대로 작동하도록 추가 작업을 수행하는 것입니다. 예를 들어 빌드를 시도하고, 오류를 찾아 수정하고 , 문서를 검토하는 등의 작업을 수행하는 것이죠. 이 모든 과정은 GitHub Actions를 기반으로 실행됩니다. 마치 이런 것처럼 생각하면 됩니다. GitHub Actions와 Copilot이 합쳐져서 탄생한 결과물이 바로 이것입니다 . 여기서는 에이전트 워크플로의 맨 위를 보고 계시죠 ? 마크다운 파일입니다. 에이전트 워크플로의 컴파일러는 이 마크다운 파일을 실제 Actions 워크플로로 변환하는 역할을 합니다. 이 프런트 매터 부분에서 에이전트가 제어할 수 없도록 지정할 수 있습니다. 예를 들어, 프런트 매터에 'safe outputs' 블록 스탠자가 있습니다. 여기서 에이전트 워크플로는 실행될 때마다 풀 리퀘스트를 하나만 생성할 수 있도록 제한했습니다 . 구체적으로는 하나의 풀 리퀘스트만 생성할 수 있도록 했습니다. 다섯 개를 생성하는 것은 허용되지 않습니다. 또한 아무 작업도 수행하지 않을 수도 있습니다. 워크플로에서 사용할 수 있는 도구도 제한했습니다. 이 워크플로는 웹 페처만 사용할 수 있으며, 인터넷상의 모든 도메인을 가져오는 것은 허용되지 않습니다. 이는 에이전트 루프 외부에서 강제되기 때문입니다. 기본적으로 방화벽을 설치하는 것과 같습니다. 에이전트와 인터넷 사이의 관계 인가요? 이 파일은 직접 편집하신 건가요, 아니면 기본 설정인가요? 사실 제가 직접 작성한 건 아닙니다 . Astro는 정말 훌륭합니다. 그리고 팀에서 사용자들이 실험해 볼 수 있도록 다양한 워크플로를 만들어 놓은 것으로 알고 있습니다. 이것들에 대해 좀 더 자세히 설명해 주시겠어요?
