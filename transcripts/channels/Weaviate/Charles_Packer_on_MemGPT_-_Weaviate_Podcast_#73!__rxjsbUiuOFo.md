MGPT는 대규모 언어 모델을 위한 운영 체제를 구상한 매우 흥미로운 연구 논문입니다. 저희 유튜브 채널에서 이 논문에 대한 리뷰 영상을 제작했는데, 이미 가장 성공적인 논문 요약 영상 중 하나가 되었습니다. 아이디어가 정말 훌륭해서 찰스 님을 인터뷰하게 되어 정말 기쁩니다. 팟캐스트에 참여해주셔서 감사합니다. 네, 코너 님, 저도 기쁩니다. 그럼 이 대규모 언어 모델 운영 체제에 대해 좀 더 자세히 설명해 주시겠어요? 이 연구를 시작하게 된 계기가 무엇이었는지 말씀해주시겠어요? 네, 주로 채팅에 대한 관심에서 시작되었습니다. 사람들이 채팅 목적으로 대규모 언어 모델을 어떻게 사용하는지, 그리고 근본적으로 메모리가 이러한 채팅 애플리케이션이나 챗봇 사용에 어떤 제약을 가하는지에 대한 문제였습니다. 특히 버클리 챗봇 사용자들 사이에서 흔히 볼 수 있는 현상은 수많은 채팅을 동시에 진행한다는 것입니다. 그리고 채팅 기록 창은 새로운 작업이 추가될 때마다 사실상 쓸모없게 되어버립니다. 누군가 뭔가를 하고 싶으면 새 채팅창을 열어서 작업을 하는데, 대부분 습관처럼 그렇게 하게 됩니다. 사용자로서 시간이 지날수록 채팅 품질이 떨어지고, 결국 제자리걸음을 하게 되죠. 차라리 처음부터 다시 시작하는 게 낫습니다. 캐릭터 AI나 이런 엔터테인먼트 채팅 봇도 마찬가지입니다. 대부분의 사용자는 이런 봇과 한 세션 이상 채팅할 거라고 생각하지 않죠. 잠깐 재밌게 채팅하고 나면 그냥 버리는 게 일반적입니다. 채팅을 멈춘 부분부터 다시 시작할 수도 없고요. 하지만 채팅 GPT나 캐릭터 봇을 설계한 사람들이 이런 식으로 만들려고 의도한 건 아닐 겁니다. 단지 사용하는 모델 의 한계일 뿐이죠. 트랜스포머 같은 모델은 근본적으로 컨텍스트 창이 제한적입니다. 이를 해결하기 위해 여러 가지 엔지니어링 작업을 할 수는 있지만, 모델 자체를 근본적으로 바꿀 수는 없습니다. 정말 훌륭한 모델이라면 캐릭터나 오픈아이처럼 정말 멋진 챗봇을 만들 수 있지만, 주고받는 메시지 수가 수십, 수백 개를 넘어서는 안 되죠. 네, MGPGPT가 시작된 계기도 바로 그 메모리 문제 때문이었어요. LLM의 메모리 문제를 해결하려고 노력했고, 이제는 명시적인 메모리 관리, 즉 " 토큰이 4,000개밖에 없습니다. 작업에 중요한 것은 무엇일까요?"라는 메시지를 보여주는 방식으로 해결책을 모색하고 있는 거죠. 이 아이디어가 어떻게 탄생했는지 설명해 주시겠어요? 네, 사실 이 아이디어는 꽤 오랫동안 작업해 왔어요. 여름에 MGPGPT 초기 버전을 챗봇으로 만들었죠. 메모리 관리, 즉 스스로 메모리를 편집하는 기능은 오픈 API에 관련 기능이 추가되면서 자연스럽게 생겨났어요. 메모리 관리에 대한 아이디어를 오랫동안 고민해 왔고, 어떻게 효율적으로 처리할지 고민해 왔거든요. 한동안은 괜찮았는데, 함수가 나왔을 때, 자기 메모리를 스스로 편집하는 것처럼 함수를 이런 용도로 쓸 수 있다는 게 바로 명확하진 않았어요. 하지만 직접 시도해 봤더니 바로 작동했던 기억이 나네요. 이 아이디어를 처음 접했을 때 바로 효과가 있었다는 게 정말 놀라웠어요. 최근에도 그랬고요. 음, 전반적으로 봤을 때, MGPT가 함수 편집을 하거나 메모리를 처리하는 방식은 매우 메타적이고 자기 인식적이라고 생각해요. 제 생각에는 이것이 L 언어 모델 전반의 트렌드를 따르는 것 같아요. 예전에는 사람들이 프롬프트를 사용하고, 프롬프트를 조정하고, 온갖 복잡한 shim 코드를 만들어서 프롬프트와 연동시키려고 애썼죠. 그런데 이제는 rhf와 instruct tuuting을 통해 모델이 점점 더 좋아지면서, 사람들은 기존 코드를 자연어로 변환해서 프롬프트에 넣기만 하면 돼요. GP4에게 뭘 하고 싶은지 알려주면, 복잡한 프롬프트를 사용해서 직접 구현하는 것보다 훨씬 더 잘 해내는 거죠. 암묵적으로, 그리고 mgpt는 그런 방향과 매우 유사합니다. 메모리와 컨텍스트를 처리하기 위해 엄청난 양의 코드를 작성할 수도 있지만, GBD4나 사용 중인 다른 모델에 메모리 제한이 있음을 직접적으로 알려주고 메모리 제한을 인지하도록 할 수도 있습니다. 핵심 기능 세트를 제공받아 메모리 관리 방법을 직접 알고리즘으로 작성할 수도 있습니다. 선택은 여러분에게 달려 있습니다. 하지만 저는 이러한 메타적인 아이디어가 LMS의 발전 방향과 매우 일치한다고 생각합니다. 프로그래밍을 넣고 빼낸 다음 자연어로 변환하여 LM이 원하는 대로 작동하게 하는 것이죠. 메모리 관리 도구에 작업 컨텍스트에 추가하고 벡터 데이터베이스에 쓸 수 있는 API가 있다면 좋을 것 같습니다. 이러한 데이터베이스는 당연히 [음악] we8의 편향성을 가지고 있지만, 운영 체제처럼 시스템 메시지가 " 우리는 ~해야 합니다"라고 알려주는 방식이 일반적인 이해에 부합하는 것일까요? 4,000개에서 3,000개 토큰 정도이고, 그런 다음 개방형 AI 접근 방식에서 이 사전이 '여기 추가 함수가 있습니다', '제거 함수가 있습니다', 또는 '완전히 비우는 함수'와 같은 기능을 하는 거죠. 메모리에 쓰는 것과 관련해서, 그냥 그냥 하는 게 맞나요? 네, 정확히 그런 상황입니다. 그래서 LLM을 더 자각적으로 만들려면, 일종의 주의 분산 수준을 높여야 합니다. 그러면 더 이상 기존 언어 모델이나 챗봇처럼 코딩하는 방식이 아니게 됩니다. 여전히 사용자 입력이 들어가면 에이전트 메시지가 나오고, 일방통행 이거나 양방향이고, 한 번의 홉만 거치는 방식이죠. L 체인 같은 건 여러 홉을 거치기도 하지만, 일반적으로는 사용자 입력이 들어가면 에이전트 메시지가 나오는 이런 고수준 개념입니다. 더 이상 사용자 메시지가 아니라 시스템 메시지, 즉 고급 컴퓨터 운영 체제 메시지입니다. 이 운영 체제 메시지 안에 사용자 메시지가 포함될 수도 있는데, 메시지 유형이 사용자 메시지이고 내용이 이렇다는 것을 나타내는 간단한 JSON 형식입니다. 하지만 우리는 이러한 시스템 메시지, 즉 운영 체제 메시지를 사용하여 토큰 부족 이나 메모리 재구성 시도 실패( 메모리 주소 지정 오류)와 같은 매우 메타적인 경고를 보내기도 합니다. 네, 전반적인 이해는 맞습니다. 네, 그 아이디어 정말 좋습니다. 시스템 메시지를 이렇게 명확하게 구분하는 것은 참신한 발상이라고 생각합니다. 팟캐스트를 준비하면서 주제를 조금 앞서 나가는 것 같기도 하지만, 이렇게 도입하신 인터럽트 개념은 기존의 대부분의 증강 현실 세대와는 상당히 다릅니다. 기존에는 단순히 입력을 가져오는 방식이었지만, 이제는 메시지 입력이든 다른 이벤트 처리든 전체적인 이벤트 처리가 이루어집니다. 토큰이 3,000개 있다는 시스템 메시지가 있고, 문서를 업로드하면 일부 처리가 트리거되는데, 이는 비동기적으로 작동하고 인터럽트도 사용됩니다. 인터럽트에 대해 좀 더 자세히 살펴보는 것이 좋을 것 같습니다. 팟캐스트 초반에 이 부분을 다루는 이유는, 제 생각에 RAG의 운영 체제를 구현하는 핵심은 바로 이러한 비동기 백그라운드 처리라고 생각하기 때문입니다. 말씀하신 것처럼, 우리는 인터럽트를 모든 종류의 메시지, 즉 사용자 메시지가 아닌 메시지까지도 일종의 인터럽트라고 부릅니다. 왜냐하면 메시지는 LM을 실행하도록 트리거하기 때문입니다. RAG 환경에서, 특히 채팅뿐만 아니라 데이터를 처리하는 환경에서는 상상할 수 있는 모든 종류의 인터럽트가 존재합니다. 일반적으로 RAG는 이제 매우 광범위한 용어가 되었으며, 더 이상 검색 증강(Retrieval Augmentation)만을 의미하지 않습니다. RAG 환경에서는 일반적으로 데이터를 삽입하고 질문을 하는 방식이라고 생각합니다. 챗봇은 데이터 업로드가 발생했다는 사실조차 인지하지 못하는 경우가 많고, 데이터는 간단한 접두사 등을 붙여 컨텍스트에 삽입될 뿐입니다. 하지만 MGBT 환경에서는 MGBT를 RAG처럼 활용할 수 있습니다. MGBT 사고방식으로 구축한다면, 언제든지 데이터 저장소에 데이터를 업로드할 수 있고, 데이터 저장소는 MGBT에 "업로드 시작", "업로드 완료", "업로드 위치 확인" 등의 알림을 보낼 수 있습니다.
