## 스크립트

Apogex를 배포하려고 하는데 네트워크 연결 옵션에서 문제가 발생했나요? 피어링 방식과 프라이빗 서비스 연결 방식 중 어떤 것을 선택할지 결정해야 하시나요? 이 비디오에서는 Apogee X의 북쪽 및 남쪽 라우팅 연결 패턴과 네트워크 구성 시 고려해야 할 주의 사항에 대해 설명합니다. 먼저 Apogee가 무엇이며 왜 유용한 제품인지 간단히 살펴보겠습니다. Apogee는 Google Cloud의 네이티브 API 관리 플랫폼으로, 모든 사용 사례(음악 포함)에 맞는 API를 구축, 관리 및 보호하는 데 사용할 수 있습니다 . Apogee는 고성능 API 프록시를 제공하여 백엔드 서비스에 일관되고 안정적인 인터페이스를 구축할 수 있도록 지원합니다 . Apoge는 Google Cloud 인프라 관리형 서비스입니다. 이 서비스는 Google에서 관리하는 전용 VPC에 배포되며, 프라이빗 서비스 연결, VPC 피어링 또는 둘 다를 사용하여 네트워크에 연결할 수 있습니다. 둘 다라는 건 무슨 뜻일까요? Apogee는 Apogee로 향하는 북쪽 방향 트래픽과 Apogee에서 나가는 남쪽 방향 트래픽에 대한 네트워크 패턴을 가지고 있습니다 . 그리고 이러한 네트워크 패턴들을 조합하여 트래픽을 라우팅할 수 있습니다. 먼저 가장 일반적인 북쪽 방향 Apogee 네트워크 패턴을 살펴보겠습니다. PSC를 사용하는 경우 Apogee에서 제공하는 서비스 연결에 연결된 PSC NEG를 통해 애플리케이션 로드 밸런싱으로 연결하도록 선택할 수 있습니다 . 로드 밸런싱은 트래픽 패턴에 따라 외부 또는 내부일 수 있으며 , 글로벌, 지역 또는 지역 간 로드 밸런싱이 가능합니다 . 애플리케이션 로드 밸런서를 사용하면 Apogee에 연결을 설정하는 데 사용할 자체 인증서를 가져올 수 있습니다. PSC 엔드포인트를 통해 직접 연결할 수도 있습니다. 하지만 이는 내부 트래픽 패턴에만 해당되며 Apogee에서 제공하는 자체 서명 인증서를 사용해야 합니다. VPC 페어링을 사용하는 경우, 프록시를 실행하는 네트워크 브리지와 로드 밸런서를 사용하는 유사한 패턴이 있습니다. 로드 밸런싱은 외부 또는 내부일 수 있으며, 글로벌, 지역 또는 지역 간 로드 밸런싱이 될 수 있습니다. 이제 남쪽 방향 패턴으로 넘어가겠습니다. PSC 피어링을 선택하든 VPC 피어링을 선택하든 관계없이 존재하는 두 가지 패턴이 있습니다. 첫 번째는 인터넷 송출과 관련된 것입니다. Apogee는 Apogee 테넌트 VPC 내의 cloudnat을 통해 인터넷상의 API 대상으로 직접 트래픽을 내보낼 수 있습니다 . 이렇게 하면 필요한 경우 대상 방화벽 에 사용할 수 있는 알려진 IP 주소가 사용됩니다 . 두 번째 패턴은 Google API 대상과 관련이 있습니다. Apogee를 사용하여 Gemini 또는 BigQuery와 같은 Google API 기반 서비스를 호출하는 경우 Apogee 테넌트 VPC에 비공개 Google 액세스가 구성되며 Apogee는 이러한 API를 직접 호출합니다. PSC만 사용하는 경우 API 대상은 프로듀서 서비스로 노출되어야 합니다. API 앞에 내부 로드 밸런서를 배치해야 합니다. 로드 밸런서의 버전은 중요하지 않으며, Apogee가 배포된 지역과 로드 밸런싱에 사용되는 지역만 일치하면 됩니다. 그런 다음 PSDNAT 서브넷을 사용하는 서비스 연결을 통해 서비스를 노출합니다 . Apogee에서 엔드포인트 연결이 서비스 연결을 가리키도록 구성합니다. 로드 밸런서 뒤에서 API 대상은 모든 유형의 컴퓨팅 서버리스 네거티브 서버, PSC 또는 온프레미스나 다른 퍼블릭 클라우드에 있는 API 대상을 가리키는 하이브리드 네거티브 서버가 될 수 있습니다. 선택한 로드 밸런서 와 백엔드 유형이 호환되는지 확인하기만 하면 됩니다 . 이 패턴의 확장은 상당히 복잡해질 수 있습니다. 따라서 애플리케이션 로드 밸런서의 URL 맵을 사용하여 단일 로드 밸런서 에서 여러 API 대상을 노출하는 것을 고려해 보세요 . 이 패턴의 확장이 너무 어렵다고 판단되면, PSConly를 사용하는 또 다른 방법은 NCC 환경에 보안 웹 프록시를 배포하고 , 서비스 연결을 통해 보안 웹 프록시를 노출하고, Apogee에서 엔드포인트 연결을 구성한 다음, Apogee의 글로벌 포워드 프록시가 이 엔드포인트 연결을 가리키도록 설정하는 것입니다. 이제 보안 웹 프록시는 Apogee에서 발생하는 모든 트래픽을 프록시하고, 보안 웹 프록시가 배포된 VPC의 DNS를 사용하여 API 대상 위치로 트래픽을 전송합니다. 이 옵션은 라우팅 오버헤드를 단일 남행 서비스 설정으로 단순화합니다. 이제 VPC 피어링 남쪽 방향 패턴으로 넘어가겠습니다. Apogee를 NCC 허브에서 프로듀서 스포크로 구성해야 한다는 점을 꼭 기억하세요 . 이렇게 하면 NCC가 Apogee 테넌트 VPC의 모든 경로를 전파하게 됩니다 . 프로듀서 스포크가 구성되면 Apogee는 컴퓨팅 엔진 VM, 로드 밸런서를 통해 노출되는 서비스, 심지어 인터커넥트 또는 VPN을 통해 연결된 온프레미스 또는 다른 퍼블릭 클라우드의 서비스 등 모든 VPC 내의 모든 유형의 API 대상으로 라우팅할 수 있습니다 . Apogee에서 PSC 피어링과 VPC 피어링, 또는 둘 다를 선택하는 경우 어떤 의미가 있을까요? 가장 먼저 고려해야 할 사항은 IP 소비량입니다. 피어링 기반 연결을 위해 Apogee는 인스턴스당 SL22 및 SL28 시터를 필요로 합니다 . 이러한 범위는 연결된 네트워크 전체에서 고유해야 합니다. PSC를 사용하면 IP 중복으로 인한 복잡성이 완전히 제거됩니다. 두 번째 요인은 라우팅 운영 오버헤드입니다. API 대상별로 PSC 프로듀서 서비스를 설정하는 것은 상당한 노력이 필요할 수 있습니다. VPC 피어링은 직접 라우팅을 사용하기 때문에 그러한 번거로움을 없애주지만, IP 사용량이 많아지는 단점이 있습니다 . 세 번째 요인은 비용입니다. 보안 웹 프록시를 사용하는 PSC 남쪽 연결 모델은 IP 공간을 절약하고 라우팅 운영 오버헤드를 단순화하려는 경우 훌륭한 옵션이지만 추가 비용이 발생합니다. 한때 주요 결정 요인이었지만 더 이상 그렇지 않은 중요한 세부 사항 하나를 짚어보자면, 바로 DNS 피어링입니다. 최근까지 Apogee의 PSC 배포 환경에서는 DNS 피어링이 지원되지 않았습니다. 하지만 더 이상 그렇지 않습니다. PSC 및 VPC 피어링 옵션 모두 DNS 피어링을 지원합니다 . 그럼 핵심 요약을 정리해 보겠습니다. 먼저, PSSE, VPC 피어링 또는 둘 다의 조합 중에서 어떤 것을 선택할지는 사용자의 고유한 Apogee 배포 환경에서 무엇이 가장 중요한지 판단하는 것은 사용자에게 달려 있습니다. 배포 옵션을 결정했으면 북쪽으로 향하는 네트워크 패턴을 파악하고 해당 패턴에 가장 적합한 네트워크 구성 요소를 배포하십시오. 내부 와 외부, 지역별 요구사항, 장애 조치 패턴 등을 고려하십시오. 마지막으로, 대상 API가 호스팅되는 위치에 적합한 남쪽 방향 네트워크 패턴을 결정하십시오 . 해당 API가 인터넷에 있는지 , Google API인지, Google VPC에 호스팅된 API인지, 아니면 온프레미스 또는 멀티클라우드 환경에 호스팅된 API인지 생각해 보세요. 이 영상이 마음에 드셨다면 좋아요와 구독 부탁드립니다. 자세한 내용은 설명란의 문서를 참조하여 Apogee 사용에 필요한 모든 정보를 확인하세요. 다음에 또 봐요.
