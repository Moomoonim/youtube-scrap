스테이징은 학습 및 평가 실행과 최종 배포 사이의 중간 단계입니다. 실무자가 " 새로운 후보 모델이 출시될 예정인데, 이러한 스테이징된 모델들을 저장하고 후보 모델과 관련된 모든 워크플로우를 관리할 수 있는 모델 레지스트리가 필요합니다."라고 말한다고 가정해 보겠습니다. 왼쪽은 데이터 과학 연구 중심이고, 오른쪽은 제품을 실행하고 운영하기 위해 수행되는 모든 작업입니다. 모델 레지스트리의 목표는 모델이 왼쪽에서 오른쪽으로 이동할 때 이러한 작업을 중앙 집중화하는 지점이 되는 것입니다. 제가 좀 더 자세히 이야기하고 싶었던 것은, 우리가 여기서 바퀴를 새로 발명하는 것인지, 아니면 다른 워크플로우에서 이미 본 적이 있는 것인지입니다. 가장 좋은 예는 소프트웨어에서 이 문제를 어떻게 해결하는가입니다. 모델 레지스트리를 생각해 보면 용어에서 유사점을 발견할 수 있을 것입니다. 마치 Docker Hub와 같은 컨테이너 레지스트리와 같습니다. 개발자가 이 컨테이너 레지스트리에 이미지를 게시하면 누구나 해당 이미지를 다운로드하고 사용할 수 있습니다. 물론 그렇게 할 수 있는 적절한 권한이 있어야 합니다. 몇 가지 유사점을 더 살펴보자면, 이미지 버전 관리 및 태깅이 있습니다. 각 컨테이너 이미지는 버전이 지정되고 고유한 태그를 갖습니다. 이는 애플리케이션이나 서비스 의 버전 간 차이를 구분하고, 필요한 경우 특정 버전을 배포하거나 롤백할 수 있도록 하는 데 매우 중요합니다. 이미지 배포를 통해 다양한 환경에 컨테이너 이미지를 배포할 수 있습니다. 협업과 관련해서도 비슷한 맥락으로, 이제 팀들은 표준화된 컨테이너 이미지를 공유하고 협업할 수 있습니다. 모델 레지스트리와 관련된 두 가지 주요 사항을 더 자세히 살펴보겠습니다. 컨테이너 레지스트리를 액세스 제어 및 CICD와의 통합에 사용하는 패턴을 볼 수 있습니다. 오른쪽 하단에 있는 또 다른 예시는 소프트웨어 세계에서 익숙한 또 다른 유형의 레지스트리입니다. 파이썬 패키지 레지스트리와 유사하게, 파이썬 라이브러리의 공개 레지스트리가 있으며, 이를 통해 파이썬 패키지 배포가 용이해집니다. 개발자는 EAS를 통해 라이브러리를 쉽게 공유하고 레지스트리 에 게시할 수 있으며, 파이썬 커뮤니티의 누구나 이를 사용하고 설치할 수 있습니다. 이 두 가지 예시와 모델 레지스트리에서 살펴본 게시 및 사용 패턴을 통해 이러한 모든 것들의 공통점은 무엇이며, 이러한 소프트웨어 솔루션은 무엇을 가능하게 할까요? 개발자가 코드를 빌드하고 패키징하여 사용 가능한 버전의 코드를 필수 저장소에 게시할 수 있도록 지원합니다. 그러면 소비자 측( 개발팀 또는 운영팀)에서 이러한 모델을 직접 사용할 수 있습니다. 이 경우에는 코드를 직접 사용하지만, 모델 레지스트리에서는 모델을 직접 사용할 수 있습니다. 이제 엔터프라이즈 팀이라고 가정하고, 머신러닝 엔지니어들이 모델을 프로덕션 환경에 배포하고 있다고 생각할 때, 모델 레지스트리라는 도구에 왜 관심을 가져야 하는지, 그리고 가장 중요한 이점은 무엇인지에 대해 자세히 이야기해 보겠습니다. 팀의 모델 CICD 워크플로에 CICD를 구현했을 때의 주요 이점과 장점을 살펴보겠습니다. 첫 번째는 실험의 복잡성을 추상화하는 것입니다. 왼쪽 스크린샷에서 볼 수 있듯이, CICD는 프로젝트 수준에서 생성되는 모든 모델 체크포인트를 저장하는 아티팩트, 즉 제품을 보여줍니다. 여러 번의 실행이 있고, 각 실행 내에서도 수백 개의 체크포인트가 생성될 수 있습니다. 따라서 프로덕션 환경에 배포할 가능성이 있는 체크포인트를 선별하여 게시하는 방법이 필요합니다. 최신 모델을 확인하려는 MLOPS 엔지니어, 팀 리더 또는 제품 관리자가 수백 개의 체크포인트를 일일이 살펴보고 어떤 체크포인트를 프로덕션 환경에 배포해야 하는지 파악하는 데 시간을 낭비하지 않도록 하기 위함입니다. 두 번째는 거버넌스와 제어에 관한 것입니다. 프로덕션 환경에 배포된 모델에 대해 누가 언제 이 모델을 배포 했는지와 같은 질문에 답할 수 있게 됩니다. 그들이 홍보하는 것은 정확히 어떤 버전의 데이터 세트를 사용했는지, 모델 학습 전에 어떤 후처리가 이루어졌는지 등입니다. 실제 사용자에게 제공될 모델은 적절한 승인 없이 배포될 경우 훨씬 더 큰 영향을 미칩니다. 단순히 학회 논문을 발표하는 것보다 훨씬 더 많은 위험이 따릅니다. 제가 예시로 들고 싶은 것은 저희와 긴밀히 협력하고 있는 고객사 중 한 곳입니다. 이 회사는 대규모 엔터프라이즈 고객으로, 대규모 생성형 AI 모델을 실제 운영 환경에 배포하고 있습니다. 법무 및 규정 준수 팀으로부터 요구 사항을 받았는데, 배포되는 모든 모델의 출처를 추적하여 라이선스가 부여되었거나 공개된 데이터 세트에서 학습되었음을 입증해야 합니다. 또한, 해당 회사가 특정 데이터 세트에서 이러한 생성형 모델을 학습할 수 있는 권한을 가지고 있음을 증명해야 합니다. 바로 이 부분에서 데이터 계보가 매우 중요해집니다. 이 슬라이드에서 보셨듯이, 이것은 하나의 사례에 불과하지만, 더 많은 것을 고려해야 합니다. 규정 준수, 보안 또는 감사 팀의 누구든 " 이 모델은 현재 운영 중입니다. 제가 직접 역추적해서 모델 학습에 사용된 데이터 세트가 라이선스를 받았는지 확인할 수 있어야 합니다. 그래야 나중에 법적 문제가 발생하지 않으니까요."라고 말할 수 있어야 합니다. 그리고 제가 고객들과 이야기할 때 자주 언급하는 재미있는 이야기가 있는데, 저희가 정기적으로 만나는 많은 고객들이 제품 사용 초기에 가장 어려워하는 질문 중 하나가 "운영 중인 모델이 있는데, 어떤 스냅샷의 데이터가 사용되었는지 모르겠습니다."라는 것입니다. 이것이 바로 거버넌스와 제어 측면입니다. 마지막으로 모델 배포 가속화에 대해 이야기해 보겠습니다. 이는 처음에 봤던 그림과 관련이 있는데, 왼쪽에는 실험 단계가 있고 오른쪽에는 운영 단계가 있습니다. 일반적으로 대기업에서 이러한 상황을 볼 수 있습니다. 팀에는 실험을 수행하는 다양한 그룹이나 유형의 사람들이 있고, 이러한 모델을 프로덕션 환경에 배포하는 사람들도 있습니다. 페르소나에 대해서는 다음 슬라이드에서 좀 더 자세히 살펴보겠지만, 여기서 중요한 것은 모델 레지스트리가 없으면 매우 느리고 답답하며 문제가 발생하기 쉬운 인수인계 지점입니다. 그래서 " 잘못된 모델을 배포한 것 같아요", " 잘못된 파일을 보냈습니다", "이 새로운 모델이 준비된 줄 몰랐어요", " XYZ라는 사람이 배포 준비가 되었다고 해서 배포했어요"와 같은 불안한 질문이나 의견이 쏟아집니다. 실무자들이 이러한 수동 프로세스, 즉 MLOP 팀에 인수인계하는 데 시간을 많이 소비할수록 모델 개선 작업에 투자할 시간이 줄어듭니다. 그리고 MLOP 측에서도 마찬가지입니다. 그들은 적절한 모델을 찾고, 혹시라도 잘못된 모델이 배포되는 실수를 방지하기 위해 롤백하는 데 많은 시간을 소비합니다. 결국, 사용자들이 현재 최적의 모델을 사용하는 데 시간이 오래 걸릴수록 팀에게는 손실이 발생합니다. 왜냐하면 사용할 준비가 된 새로운 모델이 있으니 최대한 빨리 서비스에 배포해야 하기 때문입니다. 제가 언급했던 페르소나에 대해 조금 이야기하자면, 이 강좌에 참여하는 분들 중에는 가중치 및 편향 생태계의 다른 부분에 익숙한 분들도 계실 거라고 생각합니다. 레지스트리에 대해 한 가지 주목할 점은 제가 앞서 언급했듯이 새로운 페르소나를 도입한다는 것입니다. 레지스트리는 머신러닝 실무자, 즉 실험 추적, 실행 로깅 모델을 정기적으로 사용하는 사람들과 모델을 배포하는 운영팀 사이의 연결 고리입니다. 따라서 새로운 페르소나 중 하나는 머신러닝 실무자입니다. MLOPS 팀은 이 인수인계를 담당하고 있으며, 어떤 모델이 가장 적합한지, 그리고 제가 그 모델을 배포할 준비가 되었는지에 대한 답을 제시할 수 있어야 합니다. 그다음에는 제가 고객 사례에서 언급했던 규정 준수, 법률, 보안 관련 이해관계자들이 있습니다. 이들에게는 계보가 매우 중요합니다. 모델의 전체 이력, 사용된 구성 요소, 즉 메타데이터, 사용된 라이브러리, 사전 처리 과정 등을 모두 추적할 수 있어야 한다는 확신을 원합니다. 마지막으로, ML 담당자, 예를 들어 임원이나 리더는 팀이 작업 중인 모든 모델을 한눈에 보고 싶어 합니다. 실험 단계는 매우 복잡하고, 그 부분은 구현 세부 사항에 가깝습니다. 사람들이 실제로 보고 싶어 하는 것은 게시된 버전입니다. 여기에 제품 관리자를 포함한 몇몇 다른 사람들도 있습니다. 이것이 제가 속한 분야이며, PMS로서 저희는 현재 또는 지속적으로 이러한 부분을 고려하고 있습니다. 음, 저기요, 팀에서 작업 중인 모델에 대한 문서, 최신 성능 정보, 예상 출력값 등은 어디에 있나요? 이런 모든 문서와 모델 카드 작업도 이 페르소나에 필요하죠. 하밀에게 제품 데모와 API 시연을 맡기기 전에, 먼저 이게 얼마나 쉬운지 알려드리고 싶었어요. 엔터프라이즈 모델 관리의 모든 기능과 중요한 측면들을 설명드리면서, 복잡하게 설정할 것 같다고 생각하실 수도 있겠지만, 제가 장담하건대, 이 모든 걸 로그로 기록하고 모델을 연결하는 데 단 한 줄의 코드만 있으면 됩니다. 가중치와 편향을 설치하고 실험을 시작하는 것까지 포함하면 세 줄이면 충분해요. 그럼 이제 하밀에게 마이크를 넘기고, 제품 자체와 API들을 함께 살펴보고, 다음 순서로 넘어가서 다음 내용을 이야기해 보겠습니다. 워크플로우 자동화를 통해 효율적인 모델 관리를 구현하고, 이 모델 관리 기능을 CICD 파이프라인에 연결합니다.
