안녕하세요, 저는 EDB의 솔루션 아키텍트인 보리스 메히아스입니다. 이번 발표에서는 포스트그레스(PostgreSQL)에서 JSON 데이터 타입을 최대한 활용하는 방법을 보여드리겠습니다. 어떤 분들은 이 데이터 타입을 어려워하고, 심지어는 '악마' 라고 생각하며 JSONB의 'B'가 '괴물'을 의미한다고 여기기도 합니다. 하지만 이 데이터 타입을 잘 다루면 데이터베이스 스키마에 최적화된 형태로 활용할 수 있고 , 저처럼 여러분도 이 데이터 타입을 좋아하게 될 것입니다. 포스트그레스 SQL의 JSON은 두 가지 유형이 있습니다. 가장 기본적인 JSON과 JSONB입니다. 많은 분들이 이 JSONB에서 '괴물'이라는 생각을 하게 됩니다. 마치 악의적인 동작을 하는 것처럼 보이기 때문입니다. 하지만 실제로 사용법을 배우면 그렇게 어렵지 않습니다. 약간의 이해와 주의만 있으면 됩니다. 이번 발표에서는 구문 관련 내용이나 복잡한 JSON 쿼리가 아닌, 쉽고 간결한 JSON 데이터 타입 사용법을 보여드리겠습니다 . 핵심은 JSON을 사용하는 목적에 맞게 데이터 스키마를 설계하는 것입니다. 그렇다면 JSON은 왜 필요할까요? 사람들이 JSON을 사용하려는 이유는 무엇일까요? 제 생각에 사람들이 JSON을 사용하는 가장 큰 이유는 단순히 애플리케이션에서 JSON 객체를 사용하기 때문만은 아닙니다. 바로 스키마의 자유로움 때문입니다. 자유는 보통 부정적인 의미로 받아들여지곤 합니다. 헤비메탈 음악이 자유 와 같은 주제를 다루는 이유도 바로 그 때문이라고들 하죠. 하지만 사실 우리가 추구하는 것은 바로 자유입니다. 데이터의 자유로움이 무엇인지 좀 더 자세히 설명해 드리겠습니다. 이미지, 문서, 비디오 등의 컬렉션이 있다고 가정해 보세요. 각 객체는 이름과 생성 날짜 같은 속성을 가지고 있지만, 객체 유형에 따라 메타데이터도 다릅니다 . 예를 들어, 이미지는 높이와 너비라는 고유한 값을 가지는데, 이는 이미지에만 해당되는 값이지 PDF 파일에는 적용되지 않습니다. 하지만 어떤 사진들은, 휴대폰으로 찍었 거나 나중에 추가한 경우, 사진이 찍힌 위치를 나타내는 위도와 경도를 가지고 있기도 합니다. 예를 들어, 이 사진은 우연히도 제가 칠레에서 처음으로 메탈 밴드 공연을 본 장소에서 찍은 것입니다. 또 다른 예로, 슬로닉이 포스트그레스에 대해 이야기하는 인터뷰 영상의 OGG 컨테이너 파일이 있는데, 마침 제가 가장 좋아하는 메탈 노래 중 하나가 나온 시기와 일치합니다. 우리가 앞으로 이야기할 내용을 더 잘 이해할 수 있도록 사용 사례를 살펴보는 것이 좋습니다. 저는 메탈 음악을 잘 알고 있기 때문에 다시 한번 메탈 음악을 예로 들어보겠습니다. 이제 메탈 밴드를 설명하는 JSON 객체를 살펴보겠습니다. 메탈 밴드를 데이터베이스에 저장하여 검색하고 모든 데이터를 해당 밴드와 연결하려면 식별자와 밴드 이름이 필요합니다. 이 예시에서는 스웨덴 메탈 밴드 Ambush를 사용하겠습니다. Ambush 는 좀 독특한 음악 장르를 가지고 있습니다. 전통적인 헤비메탈의 새로운 물결을 보여주는 밴드라고 할 수 있죠. 2013년에 결성되어 현재까지 활동 중입니다. 그들의 노래는 악, 오컬트적인 내용 뿐만 아니라 반전체주의적인 메시지도 담고 있습니다. 좀 긴 단어지만, 그들이 추구하는 음악 스타일을 잘 나타냅니다. 제가 Ambush에 대해 말씀드린 이 정보는 다른 밴드에 대해서는 완전히 다르게 구성될 수 있습니다. 바로 이런 이유로 JSON 객체를 사용하면 자유롭게 정보를 표현할 수 있는 것입니다. 이제 이 JSON 객체들을 데이터베이스에 저장하여 정보를 찾아야 합니다. 여기서 JSON 객체 가 우리의 구조에 적합한지 확인해 보겠습니다. 테이블을 만들 건데요, 얼마 전에 친한 친구와 종이와 펜의 유용성에 대해 이야기를 나눴습니다. 저는 데이터 스키마를 먼저 종이와 펜으로 그려보고, 그 다음에 코드로 구현해 봅니다. 이 경우, 저는 'bands'라는 테이블, 즉 엔티티를 가지고 있으며, 이 엔티티는 단 하나의 JSON 객체만 가지게 됩니다. 자, 이제 이 메탈 밴드는 그냥 밴드 이름을 가진 JSONB 객체 하나만 갖게 될 겁니다. 여기서 또 하나 추천할 점은, 보통 공용 스키마는 너무 흔해서 사용하지 않는다는 겁니다. 그래서 'Metal'이라는 스키마를 만들었는데, 실제로 테이블 자체가 훨씬 보기 좋습니다. 이게 바로 메탈 밴드 테이블입니다. 그렇죠? 좋습니다. 이렇게 객체가 있고, 각 밴드를 고유하게 식별하고 싶다고 했습니다. 이름으로 식별하는 건 좀 어려울 수 있습니다. 예를 들어 'Ambush'라는 이름의 밴드를 검색하면 여러 개가 나오니까요. 제가 좋아하는 밴드는 'Ambush Sweden'인가 하는 이름입니다. 그래서 고유한 식별자, 즉 숫자가 필요합니다. 사람들이 '하지만 이 데이터 타입은 고유성을 제공하지 않잖아요?'라고 말하는데 , PostgreSQL에서는 가능합니다. PostgreSQL에서 `metal.bands` 테이블에 고유 인덱스를 생성한다고 가정해 보겠습니다 . 여기서 괄호 안에 이중 괄호가 있고, `band` 속성에 이중 화살표가 있습니다. 이는 해당 필드 안으로 들어가 텍스트를 추출한다는 의미입니다. "id" 필드에 있는 텍스트는 고유해야 합니다. 따라서 이 JSON 컬렉션에는 중복이 발생하지 않으므로 매우 좋습니다. 이는 관계형 속성의 부족함을 어느 정도 해소해 줍니다. 이것만으로는 충분하지 않지만, 적어도 이렇게 할 수 있다는 점은 좋습니다. 이제 앨범을 살펴보겠습니다. 메탈 밴드는 라이브 콘서트를 하는데, 이는 가장 중요한 요소 중 하나이지만, 앨범으로 음악을 녹음하기도 합니다. 이 경우, Ambush 밴드의 최근 앨범 3개가 있습니다. 앨범들은 발매 연도가 다르고, 밴드, 아니, 앨범이라는 개념을 가지고 있습니다. 그리고 밴드 자체에 대한 아이디어도 언급하는데, 한 밴드가 여러 앨범을 내는 것은 전형적인 구성이죠. 그래서 종이에 그려보면 다음과 같습니다. 이제 여기서 조금 복잡해지는데, 바로 여기서 한계가 드러납니다. JSON 객체로 앨범과 밴드를 어떻게 연결해야 할까요? ID는 고유하게 만들 수 있지만, 외래 키는 사용할 수 없습니다 . 그런데 우리는 외래 키가 필요합니다. 그래서 이 문제를 해결하기 위해, 고유 ID를 기본 키로 만들 겁니다. 즉, 기존처럼 테이블을 만드는 대신, 하나 의 큰 정수형 속성(기본 키)을 가진 테이블을 만들고, 이 속성 을 JSON 객체 밖으로 옮길 겁니다. 이것이 바로 첫 번째 원칙입니다. JSON 객체 밖에 두는 것이 더 유용한 정보는 그렇게 해도 괜찮습니다. 자, 이제 제가 할 일은 메탈 앨범 객체를 만드는 것입니다. JSON 객체로 만들 필요도 없죠. 모든 앨범에는 ID, 즉 밴드 ID가 있으니까요. 보시다시피, 이 ID는 외래 키로 사용됩니다. `references metal.bands(id)`처럼요. 그리고 앨범 제목과 발매 연도도 포함됩니다. 그다음에는 앨범을 참조하는 곡들을 객체로 만들 거나, 모든 곡을 담은 별도의 객체를 만들 수도 있습니다. 객체의 형태는 원하는 대로 정하면 됩니다. 자 , 이제 이 다이어그램 에서 앨범과 해당 앨범을 녹음한 밴드 사이의 참조 관계를 명확하게 볼 수 있습니다 . 좋습니다 . 물론 세상에는 자기주장이 강한 사람들이 많고 , 앨범 리뷰를 쓰는 사람들도 있습니다. 그중에는 매우 유용한 리뷰도 있죠. 하지만 우리는 음악에 대해 객관적으로 이야기하고 싶어 하는 사람들, 단순히 "이 밴드는 형편없다"라고 하는 사람들이 아닌 사람들에 대해 이야기해 볼 겁니다 . 그럼 이 앨범을 살펴볼까요? 이건 한 밴드, 한 앨범에 대한 예시입니다. 죄송합니다. 스웨덴의 떠오르는 신예 밴드가 최신 앨범인 'The Evil in All Dimensions'에서 그 어느 때보다 더 사악하다는 내용입니다 . 여기서 흥미로운 점은 리뷰 자체에 ID가 있지만, 앨범 ID를 참조한다는 것입니다. 이 ID를 기본 키로 사용하면 외래 키로 참조 할 수 있어 유용할 것입니다 . 그런데 두 번째, 아니 마지막, 죄송합니다, 필드 두 개를 보세요. 점수는... 실수 또는 실수형 숫자, 그리고 0에서 1 사이의 값이 있고, 그 다음에는 리뷰 내용이 들어갑니다 . 리뷰 내용 은 매우 긴 텍스트일 수 있습니다. 이 부분은 나중에 다시 살펴보겠습니다. 먼저 처음 두 개의 ID를 JSON 객체에서 추출하여 기본 키와 외래 키로 사용하겠습니다. 여기서 ID는 앨범이고, 앨범은 다른 앨범을 기본 참조합니다. 그리고 전체 리뷰 내용이 담긴 객체가 있습니다. 이제 설계가 완료되었고, 매우 보기 좋은 관계형 엔티티 관계 다이어그램이 만들어졌습니다. 이 다이어그램은 데이터의 고유성과 무결성을 설정하는 데 매우 유용하다고 생각합니다 . 이제 각 테이블에서 JSON 객체를 어떻게 사용하는지 살펴보겠습니다. 인덱스를 생성해야 합니다. 전체 스캔만 하면 너무 느려지고 RAM에 너무 많은 데이터가 로드되기 때문입니다. 따라서 인덱스를 생성하고, 경우에 따라 인덱스를 사용하여 쿼리를 해결할 수 있습니다 . 자, 그럼 사용할 수 있는 인덱스 몇 가지를 살펴보겠습니다. 문서에는 JSON이나 배열처럼 복합적인 값이 있을 경우 GIN을 사용하라고 나와 있습니다. 마치 술집에서 토닉을 마시려면 GIN을 주문하는 것처럼, 복합적인 값에는 GIN을 사용하는 겁니다. GIN은 역 인덱스(Inverted Index)의 약자입니다.
