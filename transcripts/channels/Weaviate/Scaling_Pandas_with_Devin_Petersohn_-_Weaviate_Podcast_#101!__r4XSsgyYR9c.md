UC 버클리에 입학하셨을 때, 특히 데이터 프레임 확장 문제에 관심을 갖게 된 계기는 무엇이었나요? 네, 저는 버클리에서 유전체학 연구를 시작했는데, 특히 분산 시스템의 컴퓨터 과학 응용 분야에 관심이 많았습니다. 그래서 방대한 양의 데이터를 분석하고, 그로부터 통찰력을 얻는 연구를 시작했죠. 예를 들어, 거대한 DNA 컨소시엄 같은 곳에서 말이죠. 지금 여러 가지가 통합되고 있는데, 예를 들어 백만 재향 군인 프로그램 같은 것도 있고, 의료 기록 과 유전체 데이터를 결합하는 프로그램도 많이 있습니다. 이런 것들을 분석하는 것은 빅데이터 유전체학에서 정말 중요한 문제입니다. 저는 이 문제에 정말 관심이 많았고, '빅데이터 유전체학 으로 암을 해결할 수 있겠다'라고 생각했죠. 그런데 실제로는 더 근본적인 문제들을 발견했습니다. 과학자들과 함께 일하면서 과학자들이 소프트웨어 엔지니어들과는 다른 가치관을 가지고 있다는 것을 깨달았습니다. 과학자들은 문제를 해결할 때 자신의 생산성과 시스템에 대한 이해도를 더 중요하게 생각합니다. ' 이게 더 빨리 돌아가나?' 같은 건 별로 신경 쓰지 않죠. 실제로 제가 경험한 바로는, 사람들이 사용하는 것보다 훨씬 빠른 소프트웨어를 만들어도 과학자들은 별로 신경 쓰지 않습니다. 특히 생물학처럼 연구가 몇 주 또는 몇 달 만에 끝나는 분야에서는 더욱 그렇습니다. 동물을 연구하는 데는 몇 년이 걸릴 수도 있지만요. 동물을 연구하고, 새로운 동물을 낳는 것과 같은 일을 하는 데에는 지연 시간이 필요하지 않았습니다. 하지만 제가 알아차린 것은 그들이 자신들의 방식 과 능력을 유지하는 데 매우 신경을 쓴다는 것이었습니다. 모든 것이 그들의 생산성에 달려 있었죠. 그래서 저는 데이터 프레임도 비슷한 방식으로 작동한다는 것을 알게 되었습니다. 데이터 과학자들은 본질적으로 과학자와 같습니다. 데이터를 분석하고 데이터에서 통찰력을 얻으며, 자신의 생산성과 업무 능력을 중요하게 생각합니다. 어쨌든, 제가 물리 과학 분야에서 데이터 분석을 시작하면서 데이터 분석 전반, 데이터 과학, 그리고 데이터 과학자들이 업무 규모를 확장할 때 직면하는 어려움이라는 더 큰 문제를 보게 되었습니다. 네, 그게 다입니다. 여정의 일부라고 할까요? 정말 멋지네요. 특히 제게 가장 인상 깊었던 한 구절이 있었는데요, 카네기 멜론 대학교에서 파텔 박사님 과 파보 박사님이 진행하신 데이터베이스 시리즈 말인데요, 데이터 과학자와 데이터베이스 전문가를 결합하는 것에 대해 이야기하셨잖아요. 아마 많은 분들이 이 두 분야를 잘 이해하지 못하시는 것 같아요. 한쪽은 데이터 분석, 데이터 탐색, 머신 러닝 모델 구축에 집중하고, 다른 한쪽은 분산 데이터 시스템, 트랜잭션 등에 집중하죠. 이 두 분야를 결합한다는 게 중요한 것 같아요. 그래서 팬더 데이터프레임이 SQL과 같은 일반적인 관계형 데이터베이스 시스템보다 왜 그렇게 느린지 좀 더 자세히 알아보고 싶어요. 네, 데이터프레임은 보통 데이터베이스의 로컬 복사본으로 사용되고, 데이터는 대부분 데이터베이스나 CSV 같은 플랫 파일에서 시작하죠. CSV에 대해서는 나중에 다시 이야기해 볼게요. 사람이 읽기 쉽다는 장점이 있잖아요. 데이터 과학과 데이터 엔지니어링, 그리고 배치 처리 방식에는 큰 차이가 있습니다. 판다는 주로 대화형으로 사용되지만, SQL은 대화형으로 사용하기가 훨씬 어렵습니다. SQL을 사용해 본 사람이라면 누구나 알겠지만, SQL 쿼리를 조금 작성하고 테스트한 다음 결과를 확인하고 '좋아, 괜찮네'라고 생각하며 계속해서 코드를 추가하고 구축해 나가는 방식입니다. 반면 데이터 프레임은 좀 더 점진적으로 데이터를 구축해 나갈 수 있습니다. 제가 좋아하는 비유는 데이터 프레임을 푸드코트에, 데이터베이스/QL을 미슐랭 스타 레스토랑에 비유하는 것입니다. 미슐랭 스타 레스토랑을 떠올려 보세요. 메뉴판에 없는 음식을 주문할 수 없고, 멋지게 차려입고 들어가야 하며, 모든 것이 엄격하게 정해져 있습니다. 모든 손님은 동일한 경험을 하고, 레스토랑 측에서 의도한 경험을 할 수 있도록 체계적으로 구성되어 있습니다. 네, SQL도 마찬가지예요. 데이터베이스를 만든 엔지니어들이 의도한 경험을 제공하게 되죠. 그래서 SQL에서 할 수 있는 작업에 제약이 생기는 거예요. 물론 그게 꼭 나쁜 건 아니지만요. 데이터프레임과 비교해 보자면, 데이터 프레임을 푸드코트라고 생각해 보세요. 푸드 코트에서는 원하는 대로 조합할 수 있잖아요. 콘도그에 아이스크림을 얹고 싶다면, 뭐든지 할 수 있죠. 저도 그렇게 해 본 적 있는데 재밌어요. 하지만 데이터프레임과 SQL은 목적이 완전히 달라요. 데이터프레임이 제공하는 유연성이 정말 필요하다면 데이터프레임을 사용하고 그 안에서 작업하는 게 좋겠죠. SQL은 구조와 그 구조를 유지하는 데 중점을 두는 언어예요. 이렇게 선별된 경험을 제공한다고 표현하는 게 적절할 것 같아요. 그래서 제가 지금 묻고 싶은 건, 데이터프레임에서 SQL로의 전환에 관한 거예요. API와 실행 엔진을 분리하는 것에 대해 이야기해 볼까요? 그리고 Modin이 Pandas 아래에서 어떻게 작동하는지 좀 더 자세히 살펴볼 수 있을 것 같아요. 제가 이해한 바로는, 교수님 강의에서 Pandas는 단일 스레드, 단일 노드 방식인데 이제 분산 처리가 필요하다고 하셨잖아요. 솔직히 제가 이해한 건 그 정도입니다. 그리고 관계 대수 연산자 같은 것들이 핵심 기본 요소들과 관련되어 있다고 들었는데, 그런 부분에 대해 좀 더 자세히 알아볼 수 있을까요? 네, 물론이죠. Modin은 제가 박사 과정 때 개발한 시스템 이고 오픈 소스입니다. Pandas의 API와 유사하게 설계되었죠. 제가 앞서 언급했던 것처럼 과학자와 데이터 과학자들은 다른 어떤 지표보다 자신의 생산성에 집중하는 경향이 있는데, 그런 점을 고려하면 그들에게도 기존에 사용 하던 것과 동일한 API를 제공하는 것이 이상적이라는 점을 다시 한번 말씀드려도 될까요? 그렇게 하면 그들은 같은 종류의 인체공학적 설계를 사용할 수 있습니다. 왜냐하면 그렇게 하면 사용자는 실행 과정에 대해 걱정하지 않고 자신의 흐름을 계속 유지할 수 있기 때문입니다. 우리는 많은 시스템에서 이러한 방식을 사용합니다. 예를 들어 C 언어를 작성할 때 어셈블리 언어를 굳이 생각하지는 않습니다. 컴퓨터 과학에는 다양한 추상화 계층이 있지만, 제가 보기에 부족했던 것은 데이터 시스템 위에 놓이는 언어 계층이었습니다. Modin을 예로 들면, 많은 사람들이 Modin을 Panda API와 같은 것으로 생각하지만, 제 생각에는 그것이 Modin 의 가장 흥미로운 부분은 아닙니다. 가장 흥미로운 부분은 아키텍처와 여러 API를 여러 실행 엔진에 대해 대상으로 지정할 수 있는 기능입니다. Snowflake에서도 이러한 작업을 수행했습니다. Ponder가 Snowflake에 합류하기 전 오픈 소스 Modin에서는 Ray와 Dask를 사용했고, Ponder는 Panda API를 Snowflake 및 다른 데이터베이스에 대해 대상으로 지정하는 작업을 진행했습니다. Modin은 데이터 과학자들에게 소프트웨어 엔지니어링 원칙을 제공하고, 시장에 부족했던 추상화 기능을 추가하는 데 중점을 두고 있습니다. 그래서 Modin은 단순히 Pandas와 상호 작용하는 시스템이라기보다는 컴파일러에 더 가깝다고 할 수 있습니다. 물론 대부분의 최종 사용자는 Modin을 Ray, Dask, Snowfake 등과 같은 도구에서 사용할 수 있는 Pandas API로 인식할 것입니다. 이 부분을 좀 더 자세히 살펴보고 싶었습니다. Pandas에는 고수준 API가 있는데, 이를 Dask나 Ray에서 제공하는 API로 분해해야 합니다. Dask에 대한 질문은 나중에 하도록 하겠습니다. 이러한 API 매핑은 관계형 대수 중간 표현 언어(RAL)를 직접 개발한다고 말씀하셨는데, 그 의미를 좀 더 자세히 설명해 주시면 좋겠습니다. 네, 맞습니다. 제 프로젝트의 일환으로, 박사 과정 연구 중 제가 참여했던 것 중 하나는 데이터 프레임 대수 설계였습니다. 데이터 프레임 대수는 데이터베이스와 같은 관계형 대수와 선형 대수 행렬의 결합이라고 할 수 있습니다. 이 두 가지를 결합하면 각각과는 다른 결과물이 나오지만, 데이터 프레임에서 행렬로, 또는 데이터 프레임에서 데이터베이스로 변환하는 것도 가능합니다. 즉, 이러한 대수를 개발하면서 데이터 프레임 데이터 모델도 함께 개발하게 됩니다. 하지만 이러한 핵심적인 추상화, 즉 기본 원리부터 시작하는 방식은 데이터베이스에서 데이터 프레임을 어떻게 구현할 수 있는지 이해하는 데 매우 중요합니다. 데이터베이스가 데이터 프레임의 기능을 모두 수행하지 않을 수도 있지만, 최종 사용자에게 보여주는 방식에 따라 데이터 프레임처럼 보이게 할 수 있습니다. 최종 사용자 입장에서는 차이가 없어 보이죠. 이러한 추상화 계층이 사용자 기대치와 생산성을 충족하는 데 도움이 되는 이유입니다. 예를 들어, 예를 들어 Snowflake와 같은 백엔드 라이브러리는 순서가 지정되어 있지 않지만, 데이터 프레임은 순서가 지정되어 있습니다. 처음 다섯 줄을 출력할 때 일반적으로 매번 동일한 다섯 줄이 출력될 것으로 예상하지만, 데이터베이스에서는 그렇지 않습니다. ` SELECT STAR`와 같은 쿼리를 실행하면 매번 다른 순서로 결과가 출력될 수 있습니다. 따라서 우리는 데이터에 순서를 부여하고 내부적으로 많은 최적화를 수행하여 이러한 동작을 모방합니다. 데이터베이스나 Snowflake를 처리하는 방식은 Ray나 Dask를 처리하는 방식과 매우 다릅니다.
