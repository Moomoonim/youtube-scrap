To understand HNSW, imagine that you're walking into a library and you're looking for a book, but you only have a brief description of the content of that book. HNSW works in a similar way to this building a multi-layered graph where each vector is a node. The idea is that the graph has a hierarchical structure where the top layer has fewer nodes that are more broadly connected and each lower layer has more nodes with increasingly specific connections. When a query is performed, HNSW starts from an entry point in the top layer and navigates down through the graph progressively moving from broader to more specific connections. At each layer, the algorithm searches through the nearest neighbors of the current node to find the best path forward. It continues this process, refining search as it moves down through the layers of the graph until it reaches the lowest level where it selects the final nearest neighbors. This way, Quadrant avoids having to do brute search across all of our vectors, narrowing down the search space by a significant amount, making search still very precise, but also fast. Now, imagine your query vector is the embedding of the sentence that we saw before, striped blue shirt made of cotton. The search begins at the entry point in the top layer of the graph where the nodes are more loosely grouped by broad categories like clothing or accessory items. The algorithm will search for a neighbor that's closer to our query vector than our current node. If it finds one, it repeats the process. If that's the best note that it could find in that layer, it descends to the next layer and repeats the process. Each time our search becomes more refined, narrowing down our results from clothing to shirts and then other characteristics like blue and striped. When it reaches the layer zero or the final layer, it's able to retrieve from our vector database the result that matches our query vector the closest. in this case was cottonmade meridism chart. We can fine-tune how our HNSW graph is built by fine-tuning a few parameters to balance search speed with accuracy, memory usage, and also the time that it takes to build the index. The M parameter controls the number of connections per node in the graph. You could think of it as how many paths each node can maintain with its neighbors. Increasing the M parameter creates a denser graph where each node is connected to more neighbors which improve search accuracy because then you have more pathways to traverse when searching for the nearest neighbors. This will make it less likely that you will miss relevant vectors to your query. However, this also increases the memory usage and also the indexing time since more connections have to be maintained. Reducing the M parameter makes the graph sparer, reducing the memory usage and speeding up insertion. However, the search quality will probably decrease since we have fewer paths available for traversal. Usually, the M parameter stays at a range from 8 to 64 and the trade-offs of it is accuracy and memory efficiency. When we add a new vector to our HNSW index, our goal is to integrate it within our existing structure efficiently without losing accuracy and preserving performance. In quadrant, this assignment happens during the indexing process and it helps keep the graph navigable and balanced. One important factor influencing this process is the EF construct parameter. It controls how thoroughly the graph is built when inserting a new vector by controlling the number of nearest neighbors considered during insertion. Setting a higher EF construct means that more neighbors will be evaluated, creating a more comprehensive and accurate graph. However, this also makes the indexing process slower and more computationally demanding. On the other hand, if we lower the EF construct, we're going to speed up our indexing process. However, the graph will be built with less optimal connections which can affect our search accuracy. So, choosing the right EF construct is a matter between choosing a balance between indexing speed and graph quality. For most cases, values between 100 and 500 work well, but the more complex your data gets, the higher the EF construct that you might want to consider.
