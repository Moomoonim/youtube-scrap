## 스크립트

안녕하세요, 저는 마이크로소프트 Azure Database for PostgreSQL 팀의 수석 PM인 Varun Dhawan입니다. 오늘은 데이터 아키텍처 패턴의 대대적인 변화와 모든 것을 담는 데이터베이스로 부상하고 있는 PostgreSQL에 대해 이야기해 보겠습니다 . 그럼 , PostgreSQL의 모든 것을 담는 데이터베이스 부상 에 대해 알아보겠습니다 . 소셜 미디어, 모바일, AI 혁명으로 데이터가 폭발적으로 증가하면서 대부분의 데이터 시스템은 이제 OLTP 시스템과 OLAP 시스템으로 나뉘게 되었습니다. OLTP 시스템은 쓰기에 최적화되어 있고 , OLAP 시스템은 스캔, 집계 및 보고에 최적화되어 있습니다. 이로 인해 ETL 또는 ELT 파이프라인을 통한 지속적인 데이터 이동에 어려움이 발생하고 , 지연 및 오류 발생 지점이 생깁니다. 이것이 바로 스택 복잡성의 진정한 문제입니다. 그렇다면 데이터 시스템이 어떻게 이렇게 복잡한 문제로 발전하게 되었는지 살펴보겠습니다. OLTP 시스템에서 OLAP 시스템으로, 그리고 그 사이의 모든 시스템 으로 데이터를 옮길 때 , 저는 이를 '데이터 이동세'라고 부릅니다. OLTP 데이터베이스에서 OLAP 데이터 웨어하우스, Redis 캐시, Elastic Cluster, 벡터 스토리지로 데이터를 옮길 때마다 데이터 이동세가 발생하고, 결국 취약한 데이터 파이프라인이 구축됩니다. 모든 파이프라인은 최종 일관성 문제 를 야기하는데, 모든 파이프라인이 항상 완벽하게 동기화되는 것은 아니기 때문입니다 . 게다가, 이러한 시스템들을 거치면서 데이터가 여러 번 변환되는 과정에서 발생하는 직렬화 및 역직렬화 비용도 발생합니다. JSON 데이터를 관계형 테이블로 다시 변환하는 과정을 생각해 보세요. 이러한 파이프라인의 디버깅은 더욱 어려워지는데, 오류가 단일 지점이 아닌 분산 시스템 경계를 넘어 발생하기 때문입니다. 그렇다면 이러한 데이터 스택은 개발자의 일상 업무에 어떤 의미를 가질까요? 바로, 실제 데이터의 출처를 파악하는 데 많은 시간을 투자해야 한다는 것입니다. OLTP든, OLAP든, 캐시든, 여러 불안정한 파이프라인에 걸쳐 데이터를 결합하려면 종종 비정규화 와 사전 집계가 필요하며, 환경이 다중 상태 일관성을 재현하지 못하기 때문에 테스트가 어려워집니다. 결국 개발자의 시간, 즉 개발 시간이 실제 기능 개발에 투입되지 못한다는 뜻입니다. 이로 인한 비즈니스 손실은 엄청납니다. Redis와 Stripe의 보고서를 살펴보면, 74%가 여러 개의 데이터베이스를 사용하고 있습니다. 결과적으로 개발자 시간의 50%, 다시 말해 50%, 거의 절반에 해당하는 시간이 파이프라인 유지 관리에 낭비 되고 새로운 기능 개발에는 투입되지 못합니다. 이는 오늘날 개발자들이 가장 불만스러워하는 부분 인 복잡한 기술 스택으로 이어집니다. 비용은 인프라에만 있는 것이 아니라, 이러한 파이프라인을 유지 관리하고 디버깅하고 문제를 해결하는 데 소요되는 엔지니어링 시간에도 있습니다 . 여기 있는 통계 자료들을 보면 공감되는 부분이 많고, 여러분도 한 번쯤은 느껴봤을 법한 이야기라고 생각합니다. 자, 그렇다면 데이터 스택은 어떻게 이렇게 복잡해졌을까요? 과거에는 새로운 데이터 요구사항이나 데이터 유형이 생길 때마다 특화된 데이터베이스를 추가하는 것이 일반적인 생각이었습니다. 하지만 오늘날에는 통합 데이터베이스를 선호하는 추세입니다. 새로운 도구나 아키텍처를 바로 도입하기보다는, 데이터 아키텍트들은 기존 방식이 과연 PostgreSQL이 얼마나 많은 데이터를 처리할 수 있을지 의문을 제기하고 있습니다. 고도로 전문화된 데이터 스택의 운영상의 어려움을 더 잘 이해하기 위해 재미있는 상황을 상상해 보세요. 바쁜 레스토랑 주방을 떠올려 보세요. 이 주방에서 각각 의 특화된 데이터베이스는 식재료를 보관하는 특별한 냉장고와 같습니다 . 손님 이 가장 많은 바쁜 날에는 어떻게 될까요? 주방장은 각기 다른 식재료가 들어 있는 여러 냉장고 사이를 정신없이 뛰어다니게 됩니다 . 누군가는 캐시에서 필요한 재료를 꺼내기 위해 Redis에 접속하기도 합니다. 누군가 검색 결과를 얻기 위해 Elasticsearch로 달려가고 , MongoDB를 뒤져서 몇몇 문서를 가져옵니다. 이처럼 파편화된 주방 모델 때문에 셰프는 요리하는 시간 대부분을 냉장고를 뒤지고 재료를 테이블로 가져오는 데 허비합니다. 마치 개발자가 파이프라인을 탐색하고 데이터를 이동시키고 실제 데이터 소스 를 찾는 데 시간을 허비하며 정작 기능을 개발하는 데 집중하지 못하는 것과 같습니다 . 결국 음식 제공이 지연 되어 고객이 불만족스럽게 레스토랑을 떠나는 경우가 발생합니다 . 여러 시스템을 사용할 때 우리는 이러한 대규모 데이터 이동 비용을 지불해야 합니다. 그 결과 제품과 고객 모두 피해를 입습니다. 이것이 바로 복잡한 기술 스택을 사용하는 데 따르는 실제 비용과 복잡성입니다. 과거에는 각 데이터 시스템이 특정 데이터 작업이나 데이터 접근 패턴에 특화되어 있었습니다. 예를 들어 검색을 생각할 때는 역인덱스를, 분석을 생각할 때는 컬럼 형 스토리지를 사용하여 방대한 보고서를 더 빠르게 처리하고, 캐시는 빠른 데이터 접근을 위한 것이고 , 인메모리 키-값 저장 방식도 있었습니다. 이러한 현상이 부분적 으로는 모든 요구 사항을 충족할 만큼 정교하고 확장 가능하며 유연한 단일 데이터 저장소 또는 데이터베이스가 없었기 때문이기도 합니다 . 그 때문에 우리는 이러한 고도로 파편화된 시스템을 사업 비용의 일부로 받아들여야 했습니다. 하지만 이제 Postgres 덕분에 상황이 바뀌고 있습니다. 통합 데이터에 대한 열망이 점점 강해지고 있습니다. Postgres는 확장 가능한 프레임워크, 플러그형 인덱스 유형, 사용자 정의 데이터 유형 지원 덕분에 다양한 데이터 접근 패턴을 지원할 수 있습니다 . 개발자 커뮤니티는 Postgres를 신뢰하고 있으며, 이는 제 말뿐만이 아니라 개발자 커뮤니티의 투표 결과에서도 분명히 드러납니다. 2025년 Stack Overflow 개발자 설문조사 결과를 살펴보겠습니다. % 이상의 개발자가 Postgres를 주요 데이터베이스로 사용한다고 답했습니다. 즉, 애플리케이션 요구 사항이 있을 때 가장 먼저 찾는 데이터베이스가 Postgres라는 것입니다. 58% 이상의 사용자가 PostgreSQL을 긍정적으로 평가했는데, 이는 실제로 한두 가지 데이터 요구 사항 이상에 PostgreSQL을 사용하고 있다는 것을 의미합니다. 예를 들어 문서 관리, 전체 텍스트 검색, 벡터 컴퓨팅 등에 활용하고 있다는 것이죠. PostgreSQL은 현재 전 세계에서 가장 많이 사용되는 데이터베이스입니다. 놀랄 일도 아니죠. 그렇다면 이러한 패턴 변화와 개발자들이 PostgreSQL을 선호하는 이유는 무엇일까요 ? 저는 그 핵심이 개발자들이 던지는 간단한 질문 하나로 귀결된다고 생각합니다. " 동기화를 멈출 수 있는 것은 무엇일까? 언제쯤 복잡한 작업을 멈추고 본격적으로 작업에 집중할 수 있을까?" PostgreSQL은 이 질문에 완벽하게 답하며, 이 모든 질문에 답할 수 있는 비장의 무기를 가지고 있습니다. 바로 확장성입니다. PostgreSQL은 10년이 넘는 역사를 자랑 하지만, 그 기반 위에 세워진 핵심 원칙은 바로 확장성입니다. PostgreSQL은 단일 목적에만 국한된 경직된 도구로 설계되지 않았습니다. PostgreSQL은 처음부터 새로운 데이터 유형, 새로운 인덱스 패턴, 새로운 함수, 새로운 데이터 접근 패턴을 수용하도록 설계되었습니다 . 따라서 엄밀히 말하면 단순한 데이터베이스가 아니라 전체 데이터 플랫폼입니다. 지금까지 PostgreSQL의 확장성이 이러한 다양한 데이터 접근 패턴을 처리하는 데 어떻게 도움이 되는지 설명했습니다 . 이러한 패턴 들은 기존에는 특정 전문 데이터베이스에서 처리되었습니다. 이제 몇 가지 예시를 살펴보겠습니다. 다음 슬라이드에서는 개발자들이 파이프라인 간에 데이터를 동기화하는 실질적인 방법을 몇 가지 보여드리겠습니다 . 먼저 문서부터 시작해 보겠습니다. 테이블에 저장된 관계형 데이터 외에도 비정형 및 반정형 문서에 접근해야 하는 애플리케이션이 있다고 가정해 보겠습니다. JSON을 생각해 보세요. JSON이라고 하면, 처음에는 관계형 데이터베이스에서 벗어나 MongoDB나 Cassandra 같은 NoSQL 데이터베이스와 같은 완전히 별도의 데이터 시스템을 구축하고 싶다는 생각이 들 수 있습니다. 하지만 PostgreSQL은 JSON 및 JSONB 데이터 타입을 통해 유연한 스키마 지원을 기본적으로 제공하여 비정형 및 반정형 문서를 매우 빠르게 저장하고 완벽하게 쿼리할 수 있도록 해줍니다. JSONB는 바이너리 저장소이므로 일반화된 역인덱스(GIN)와 함께 사용하면 JSON 문서에 대한 빠른 포함 및 경로 쿼리가 가능합니다. 이제 검색 기능을 살펴보겠습니다. 이제 소스 데이터 또는 테이블 데이터가 있는 바로 그 위치에서 전체 텍스트 검색에 접근할 수 있습니다. PostgreSQL의 기본 기능인 전체 텍스트 검색(FTS)은 토큰화에 tsvector를, 검색 조건에 tsquery를, 빠른 조회를 위해 GIN 인덱스를 사용합니다. tsvector는 전체 텍스트 검색에 최적화된 완전히 새로운 데이터 타입이라는 점을 기억하세요 . 즉 , Solr이나 Elastic 같은 별도의 전용 검색 시스템을 구축할 필요 없이 PostgreSQL을 검색에 활용할 수 있다는 뜻입니다. 캐싱은 어떨까요? 복잡한 애플리케이션 데이터 스택에서 복잡한 캐싱 계층이나 데이터베이스 앞에 Redis를 사용하는 경우는 거의 본 적이 없습니다 . 하지만 PostgreSQL을 사용하면 캐싱 요구 사항에도 PostgreSQL을 활용할 수 있습니다 . PostgreSQL의 언락 테이블을 사용하면 WAL 로깅을 생략하고 쓰기 복잡성으로 인한 오버헤드를 줄일 수 있습니다. 영구성이 중요하지 않은 임시 데이터에 적합합니다. 캐시 데이터 는 언락 테이블에 저장됩니다 . 데이터베이스가 재시작되거나 장애 조치가 발생하더라도 테이블 데이터는 손실될 수 있습니다. 하지만 캐시된 데이터이므로 메인 테이블에서 복원할 수 있습니다. 이러한 기능을 구체화된 뷰 및 부분 인덱스와 결합하여 고급 캐싱 패턴을 구현할 수도 있습니다. 따라서 완전한 인메모리 데이터베이스를 호스팅하는 추가 인프라 없이 캐시된 데이터 성능을 얻을 수 있습니다 . 즉, Redis 동기화 계층을 완전히 추가할 필요가 없습니다. 자, 그럼 백그라운드 작업은 어떨까요? 여러 데이터베이스를 사용하는 경우, SELECT 쿼리를 작성했거나 저장 프로시저에 포함시킨 후 , 매일 새벽 1시 와 같은 특정 시간에 저장 프로시저를 실행 하여 보고서를 생성해야 하는 요구 사항이 얼마나 자주 발생할까요? 기존에는 이러한 스케줄러를 실행하기 위해 별도의 플러그인 이나 파이프라인( 예: Unix 또는 Linux 환경의 cron)을 사용했습니다. 하지만 PostgreSQL 환경에서는 백그라운드 작업을 cron 작업으로 실행하기 위해 데이터베이스를 벗어날 필요조차 없습니다 . pg_cron 확장 기능이 데이터베이스 내에 내장되어 있어 외부 데이터 스케줄러를 사용할 필요가 없습니다. 따라서 별도의 설정을 할 필요가 없습니다. pg_cron 확장 기능을 사용하면 스케줄링 로직을 테이블 데이터 바로 옆에 배치하여 지연 시간을 줄일 수 있습니다. 또한 pg_cron 확장 기능을 사용하여 배치 작업, 정리 작업, 집계 파이프라인을 예약할 수 있습니다. 시계열 데이터가 있는 경우는 어떨까요? 예를 들어, 타임스탬프 데이터가 포함된 로그, 이벤트 또는 메트릭의 지속적인 스트림을 생각해 보세요 . 날씨 앱이나 주식 시세 추적 앱과 같은 월가 관련 앱이 좋은 예입니다 . 이런 경우 InfluxDB, M3와 같은 시계열 데이터 전용 데이터베이스가 필요하다고 생각할 수 있습니다 . 하지만 PostgreSQL에는 다양한 고급 확장 기능이 있으며, 그중 하나가 TimescaleDB입니다. TimescaleDB는 파티셔닝을 위한 하이퍼테이블을 제공하고 , 시간에 따른 자동 청킹 기능을 제공하며, IoT 센서 나 DevOps 워크로드처럼 대량의 시계열 데이터를 처리하는 데 최적화된 추가 중심 워크로드에 적합합니다 . ACID 규칙을 위반하지 않고 Postgres 데이터베이스에 데이터를 저장할 수 있습니다. 그리고 제가 가장 좋아하는 부분은 공간 데이터 유형이나 위치 데이터를 다룰 때 PostGIS가 단연 최고라는 점입니다. PostGIS는 기하, 지리 유형과 같은 공간 데이터 기능을 추가하고, GiST의 R-트리 인덱스라는 특수 인덱스를 사용하여 공간 쿼리를 더 빠르게 실행합니다. 거리 계산, 교차점 찾기, 지오펜싱과 같은 고급 공간 기능도 지원합니다 . 따라서 단순히 위도와 경도 사이의 기본 계산을 수행하는 간단한 플러그인이 아닙니다 . 고급 공간 작업을 수행할 수 있는 매우 심층적인 공간 시스템입니다. PostGIS Plus를 Postgres 데이터베이스 위에 실행하여 Uber나 DoorDash와 같은 정교한 차량 공유 앱을 구축할 수도 있습니다. PostGIS는 Postgres를 강력한 공간 데이터베이스로 변환합니다. 이제 2026년입니다. 이제 모두가 알고 있지만 언급하지 않는 인공지능(AI)에 대해 이야기해 보겠습니다. AI 앱을 구축할 때 벡터 데이터는 관계형 데이터 바로 옆에 있어야 합니다. 왜 그럴까요? 벡터는 실제로 테이블에 이미 저장된 데이터에서 파생된 차원을 나타내기 때문입니다. PostgreSQL에 오랫동안 탑재되어 온 pgvector 확장 기능을 사용하면 데이터베이스 내에서, 즉 실제 데이터 바로 위에서 의미론적 검색을 수행할 수 있습니다. 벡터 임베딩을 소스 데이터와 가까운 곳에 유지함으로써 관계형 데이터베이스와 벡터 저장소 데이터베이스 간의 데이터 복제 비용과 일관성 문제를 방지할 수 있습니다 . 또한 대규모 벡터 데이터 처리 요구 사항이 발생할 경우, Azure Database for PostgreSQL Flexible Server는 DiskANN과 같은 고급 벡터 인덱스를 제공하여 기본적으로 제공되는 HNSW 및 IVFFlat과 같은 벡터 인덱스보다 벡터 워크로드 성능을 크게 향상시켜 줍니다 . 지금까지 PostgreSQL을 거의 모든 요구 사항에 사용할 수 있는 만능 데이터베이스라고 말씀드렸지만, 특정 용도에 특화된 데이터베이스를 절대 사용하지 말라는 의미는 아니라는 점을 다시 한번 강조하고 싶습니다 . 제가 말씀드리고 싶은 것은 PostgreSQL부터 시작 하고 필요할 때만 특화하라는 것입니다. 예를 들어 시맨틱 검색 애플리케이션의 경우, 데이터와 벡터가 같은 테이블에 함께 있을 때 PostgreSQL 우선 접근 방식이 가장 효과적입니다 . 실시간으로 운영 인사이트를 빠르게 얻어야 하고, 무엇보다 관리해야 할 시스템 수를 줄여야 할 때 유용합니다. 최고 수준의 하이브리드 검색이나 대규모 비정형 필터링이 필요한 경우에는 특화된 벡터 데이터베이스가 필요할 수 있습니다 . Azure AI Search와 같은 것을 벡터 저장에 사용할 수도 있습니다. 즉, 매우 특별한 요구 사항에만 해당됩니다. 그래프는 어떨까요? 최근 매우 인기 있는 데이터 유형입니다. 다행히 PostgreSQL을 사용한다면 PostgreSQL을 벗어나지 않고도 데이터 위에 그래프를 구현할 수 있습니다. Apache AGE Extension을 사용하면 Cypher 쿼리 기능 과 SQL을 결합하여 PostgreSQL 데이터베이스 내에서 완벽한 그래프 환경을 구축할 수 있습니다. 그래프 쿼리를 실행하고, 노드와 가중치를 계산하고 , 모든 복잡한 계산을 수행할 수 있습니다. 그리고 마지막으로, OLTP 시스템을 보유하고 있다면 대부분의 경우 보고 및 쿼리 요구 사항을 충족하기 위해 OLAP 시스템도 필요합니다. 기존에는 앞서 몇 슬라이드에서 언급했듯이 OLTP 시스템에서 OLAP 시스템으로 데이터를 이동하는 데 비용이 발생했습니다 . 하지만 이제 PostgreSQL을 사용하면 데이터를 이동하지 않고도 OLTP 시스템 내에서 바로 분석을 실행할 수 있습니다 . 새로운 pg_duckdb 확장 프로그램을 사용하면 PostgreSQL 내에서 바로 OLAP 분석을 실행할 수 있습니다. 따라서 별도의 ETL 파이프라인도 필요 없고, 데이터 중복도 없으며, 지연 시간도 없습니다. 자세한 내용은 아래를 참조하십시오. 이 슬라이드들을 쭉 살펴보시면, 제가 지금까지 설명한 내용은 하나의 PostgreSQL 인스턴스에서 다양한 데이터 유형, 인덱스, 확장 기능, 그리고 여러 가지 기능을 모두 사용할 수 있다는 것 입니다. 기술적으로는 놀라운 기능처럼 들리지만, 만약 PostgreSQL 데이터베이스의 리소스 한계에 부딪히게 된다면 어떻게 될까요 ? 특정 하드웨어에서 실행되는 단일 PostgreSQL 인스턴스로는 할 수 있는 일이 한정적이라는 것을 깨닫게 될 것 입니다 . 제가 묻고 싶은 것은, PostgreSQL의 단일 노드 제한을 넘어서는 경우 어떻게 해야 할까요 ? 바로 Citus 확장 기능을 사용하면 PostgreSQL을 분산 데이터베이스로 만들 수 있다는 것입니다. 수평 샤딩된 데이터베이스라고 생각하시면 됩니다. Citus 확장 기능을 사용하면 데이터를 여러 노드 에 분산시키고 쿼리를 병렬화할 수 있습니다 . 그림에서 보시는 것처럼 Citus 확장 기능을 사용하면 Citus 코디네이터 노드와 여러 개의 워커 노드를 구성할 수 있습니다. 이 모든 구성 요소는 애플리케이션에 대해 단일 클러스터처럼 작동합니다. 더 좋은 점은 Azure Database for PostgreSQL Flexible Server를 사용하는 경우 Citus를 Elastic Cluster와 함께 관리형 서비스로 사용할 수 있다는 것입니다. 참고로, 이는 Azure Database for PostgreSQL Flexible Server에 대한 설명으로 자연스럽게 이어지는 좋은 계기가 되었습니다. 지금까지 PostgreSQL을 모든 용도의 데이터베이스로 활용하는 것에 대해 이야기해 왔습니다. 하지만 실제로는 이러한 대규모 시스템을 유지 관리하는 데 드는 수고를 덜고 싶을 것입니다 . 바로 이러한 목적을 위해 Azure Database for PostgreSQL Flexible Server가 개발되었습니다. Azure Database for PostgreSQL Flexible Server를 사용하면 운영상의 부담을 덜 수 있습니다. 완전한 오픈 소스 커뮤니티 PostgreSQL을 제공하며 , 관리형 안정성, 고가용성, 재해 복구를 위한 읽기 복제본, Microsoft Entra ID 지원을 통한 엔터프라이즈급 보안이 완벽하게 통합되어 있습니다. 보안 측면에서 Azure Database for PostgreSQL Flexible Server는 암호화된 연결, 프라이빗 엔드포인트, 고급 암호화, TLS 및 TDE를 지원하여 가장 엄격한 엔터프라이즈 보안 요구 사항을 충족합니다 .
