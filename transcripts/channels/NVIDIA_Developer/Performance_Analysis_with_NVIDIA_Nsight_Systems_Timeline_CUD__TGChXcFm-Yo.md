When doing performance measurements,&nbsp; it can be useful to think about how fast the&nbsp;&nbsp; code could possibly run. In this example code,&nbsp; all the data must be transferred to the GPU,&nbsp;&nbsp; a kernel must run on all of it, and all&nbsp; of it needs to be transferred back to the&nbsp;&nbsp; CPU. Looking at the streams, it's clear that&nbsp; the kernel completes faster than the memory&nbsp;&nbsp; transfers. And this GPU has only one copy&nbsp; engine for each direction. So for this code,&nbsp;&nbsp; the memory transfer is the bottleneck of the&nbsp; performance: The fastest that the algorithm could&nbsp;&nbsp; ever run is limited by how long it takes to copy&nbsp; all the data in one direction. How long is that?&nbsp; Hover over one of the memcpys. The transfer time is 3.132&nbsp; milliseconds. Nsight Systems shows four transfers.&nbsp;&nbsp; Because the memory transfer is the bottleneck in&nbsp; this example, 12.528 milliseconds is the fastest&nbsp;&nbsp; that this code could run. At Nvidia, we call this&nbsp; upper limit on performance our "speed-of-light". This first attempt took a total of around&nbsp; 36 milliseconds. That means this first&nbsp;&nbsp; attempt ran at….. [16 seconds]… 35% of the&nbsp; speed-of-light. Looking at that timeline of the second attempt&nbsp; again, it appears that the total time to run the&nbsp;&nbsp; algorithm is the sum of all the memcpys from&nbsp; host to device, plus one final kernel run,&nbsp;&nbsp; plus one final memcpy back to the host. Chopping&nbsp; up memcpys into more pieces won't make the memcpy&nbsp;&nbsp; run any faster because the sum of the memory&nbsp; transfers will still be the same. However,&nbsp;&nbsp; the final memory transfer has poor latency&nbsp; hiding because it doesn't overlap any other&nbsp;&nbsp; kernels nor transfers. This is a hint&nbsp; that chopping up the data into smaller&nbsp;&nbsp; chunks may decrease the time that the GPU&nbsp; is under utilized and that will save us&nbsp;&nbsp; some time. This is an improvement&nbsp;&nbsp; on the 70% from before! This leaves just&nbsp; 16.5% room for improvement. More streams&nbsp;&nbsp; might improve performance but, on the other&nbsp; hand, performance might decrease again due&nbsp;&nbsp; to the overhead of switching between all&nbsp; the streams. Other techniques like data&nbsp;&nbsp; compression and prefetching data into the&nbsp; cache might improve performance further.
