## 스크립트

안녕하세요, 저는 AWS의 Herard입니다. 안녕하세요, 저는 IPC의 Ano입니다. 이것은 제 [음악] 아키텍처입니다. 보시다시피, 여기에는 음성 스트리밍 분석 아키텍처가 있습니다. 왜 이것을 구축했나요? 어떤 문제를 해결하기 위한 것인가요? 기본적으로 IPC는 수천 개의 회선으로 구성된 거대한 글로벌 음성 네트워크를 보유하고 있습니다. 네, 맞습니다. 이 회선들은 전 세계 트레이더들이 서로 소통하는 데 사용됩니다. 저희는 Conexus 플랫폼을 통해 음성 통신을 지원합니다. 트레이더들이 서로 대화할 때, 대화 내용을 텍스트로 변환하고 싶어하고 해당 솔루션을 구독하는 경우, 이 아키텍처가 작동하게 됩니다. 이 아키텍처에서 저희는 IPC 세션 컨트롤러에서 AWS Chime SDK를 사용하여 음성 데이터를 전송합니다. Chime SDK에서 음성 데이터 스트림은 AWS Kinesis로 전달됩니다. Kinesis는 음성을 5초 단위로 버퍼링한 다음 텍스트 변환 도구로 전송합니다. 동시에 음성 스트리밍이 시작되는 즉시 이벤트 브리지도 실행됩니다. 이를 통해 Lambda 함수를 실행할 수 있습니다. 이 시스템의 뒷부분은 기본적으로 이벤트 기반 아키텍처입니다. 즉, 음성 데이터는 Kinesis 스트림으로 입력되고, 다른 한편으로는 Bridge가 작동하여 Lambda 함수를 실행하고, ZIP 연결에서 메타데이터를 추출하여 텍스트 변환 솔루션으로 전송합니다. 이렇게 하는 이유는 아키텍처의 왼쪽 부분에 수천 줄의 데이터가 있기 때문에 올바른 대화 내용이 올바른 고객에게 제공되도록 해야 하기 때문입니다. 보안, 고객 개인 정보 보호, 거래 및 음성 통신의 모든 측면은 우리에게 매우 중요합니다. Lambda 함수는 정보를 텍스트 변환 솔루션으로 전달하고, 텍스트 변환 솔루션은 Kinesis에 버퍼링된 5초 분량의 데이터를 텍스트로 변환하여 Kinesis 데이터 스트림으로 전달합니다. Kinesis 데이터 스트림에서는 Amazon Kinesis Firehost를 사용하여 데이터를 추출하고 S3 버킷에 패키징 파일로 저장합니다. 데이터는 S3 버킷에 저장되며, 데이터가 생성되는 즉시 해당 고객에게 전달됩니다. 데이터는 S3 버킷에 저장되고, AWS Lamb이라는 도구가 데이터를 보강합니다. 이 도구는 다양한 타사 시스템과 내부 IPC 시스템에서 정보를 가져와 데이터를 보강한 후 MongoDB Atlas에 푸시합니다. 데이터가 Atlas에 저장되면 애플리케이션에서 바로 사용할 수 있습니다. MongoDB Atlas에 데이터가 도달하면 모든 고객이 사용하는 웹 애플리케이션인 IPC 포털에 표시할 수 있습니다. 따라서 녹취록은 포털에서 거의 실시간으로 볼 수 있으며, 사용자가 말한 내용이 포털에 표시되기까지 약 15초에서 20초 정도의 지연 시간이 소요됩니다. 동일한 데이터는 API 게이트웨이를 통해 제공되므로 이를 기반으로 트레이더 데스크톱 애플리케이션을 구축할 수 있습니다. 이러한 데스크톱 애플리케이션 중 일부는 Conexus UNG 터렛에서 실행될 수 있습니다. 즉, UN 플랫폼은 애플리케이션을 지원하며, AWS의 API 게이트웨이가 중요한 역할을 합니다. 가장 큰 장점은 이 전체 아키텍처가 무한대로 확장 가능하다는 것입니다. 정말 강력하고 효율적입니다. 이 시스템을 구축하는 데 많은 시간이 걸렸고, 확장성이 매우 뛰어나며 가격 또한 매우 합리적이라고 생각합니다. 네, 좋습니다. 제가 이해하기로는, 이 시스템에는 여러 음성 연결이 있는데, 그것들이 ZipTrunk인가요? 네, 맞습니다. 음성이 플랫폼을 통해 스트리밍되고, 최종적으로 트레이더들이 활용하는 데이터 인사이트가 생성되는 거죠? 네, 맞습니다. 이 시스템은 트레이더의 업무 흐름을 더욱 효율적으로 만들어 줄 것으로 기대됩니다. 네, 그럼 그 효율성에 대해 좀 더 자세히 설명해 주시겠어요? 이 플랫폼을 통해 고객들이 얻는 이점은 무엇인가요? 우선, 중요한 것은 메모 기능입니다. 트레이더는 어제 또는 30분 전에 상대방에게 무슨 말을 했는지 확인할 수 있습니다. 포털에서 어떤 내용이 기록되었는지 바로 확인할 수 있죠. 또한, 규정 준수 측면에서도 유용합니다. 규정을 준수하는 담당자는 수천 줄에 달하는 대화 내용을 모두 기록해 두어야 합니다. 따라서 이 시스템은 규정 준수 업무를 훨씬 수월하게 만들어 줄 것으로 기대됩니다. 저희는 점점 더 많은 앱을 개발하고 있습니다. 규정 준수 측면에서 이점이 있고, 주문 관리 시스템에 주문을 입력할 때 특정 시간 내에 입력해야 하는 법률이 있기 때문에 이 시스템은 이러한 요구 사항을 충족하는 데 도움이 될 수 있습니다. 대화 내용이 무언가를 사고파는 것이기 때문에, 우리는 무엇을 사고팔았는지, 얼마를 사고팔았는지와 같은 정보를 추출할 수 있습니다. 이러한 정보는 녹취된 텍스트에 포함되어 있으므로 추출하여 적절한 시스템으로 전달할 수 있습니다. 따라서 이 시스템은 다양한 사용 사례에 적용될 수 있으며, 궁극적인 목표는 트레이더의 업무를 더 쉽고 효율적으로 만드는 것입니다. 네, 이해가 됩니다. 그렇다면 이 아키텍처의 미래는 어떨까요? IPC의 관점과 고객의 관점에서 보면, 저희의 대형 고객사 중에는 수백 명의 트레이더가 IPC를 하루 종일 사용하고 있습니다. 만약 트레이더들이 대화를 녹취하여 S3 버킷에 저장한다면, 우리는 그 위에 다양한 유형의 애플리케이션을 구축할 수 있을 것입니다. 예를 들어 트레이더의 활동을 모니터링하는 애플리케이션도 만들 수 있겠죠. 적절한 시기에 적절한 금융 상품으로 거래하는 것, 즉 거래 가격대가 최적의 가격대였는지 아는 것만으로도 다음 날 더 나은 결과를 위해 무엇을 할 수 있을지 분석할 수 있습니다. 고객이 필요로 한다면 AI를 적용할 수도 있습니다. AI는 매우 강력하기 때문에 수집된 데이터는 매우 유용하며 고객과 IPC 모두에게 무궁무진한 가능성을 열어줍니다. 이러한 종류의 데이터는 이전에는 녹취 서비스를 이용하기 전까지는 얻을 수 없었습니다. 즉, 5초, 10초, 15초 정도의 지연 시간 내에 쉽게 구성하고 사용할 수 있는 데이터가 아니었습니다. AWS 플랫폼을 사용하기 전까지는 말이죠. AWS 플랫폼은 매우 견고하며 사용 경험이 매우 좋았습니다. 관련 문서도 많아서 개발자와 테스터 모두 다양한 솔루션을 빠르게 익히고 테스트할 수 있었습니다. 네, API 덕분에 음성 스트리밍 아키텍처를 구축하신 방식이 정말 멋지네요. AI 서비스도 활용하셔서 고객 경험을 개선하고 계신다니 정말 감사합니다. 이 아키텍처를 공유해주셔서 진심으로 감사드립니다. [음악]
