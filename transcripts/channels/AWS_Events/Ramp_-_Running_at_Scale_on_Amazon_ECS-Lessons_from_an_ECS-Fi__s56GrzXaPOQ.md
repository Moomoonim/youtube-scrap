Aurora Postgres는 공유 스토리지 계층을 사용하여 여러 Postgres 서버 또는 복제본 간에 데이터를 공유합니다. 저희의 주요 애플리케이션, 즉 핵심 애플리케이션은 서로 다른 다섯 개의 PostgreSQL 복제본과 통신합니다. 그러니까 한 명은 주요 작성자이고 나머지 네 명은 읽기 전용 사용자입니다. 오로라 스토리지 계층은 서버와 마찬가지로 3개의 가용 영역에 분산 및 복제되어 있으며, 공유 스토리지 시스템 덕분에 모든 복제본에서 복제 지연이 거의 없습니다. 이러한 결합된 클러스터를 통해 전체 클러스터에서 초당 최대 백만 건의 쿼리 처리량을 달성할 수 있습니다. 음, 네 개의 주요 읽기 복제본 외에도 별도로 구성된 BI 복제본이 있습니다. 이 시스템은 하드웨어 구성이 약간 다르고 대규모 분석 쿼리 처리에 최적화되어 있습니다. 또한 내부 BI 및 분석 사용 사례를 애플리케이션과 분리하여 리소스 나 데이터베이스 캐시 공간을 두고 서로 경쟁하지 않도록 하는 데에도 큰 도움이 됩니다. 저희 API 작동 방식과 관련하여 꼭 이야기해 보고 싶은 것 중 하나는 자동 스케일링이 API 트래픽 증가에 얼마나 도움이 되었는지입니다. 몇 년 전 제가 처음 일을 시작했을 때는 자동 확장 기능을 전혀 사용하지 않았습니다. 당시에는 필요한 규모가 작아서 비용 절감 효과가 크지 않았기 때문입니다. 저희는 해당 두 API 서비스에서 약 20~30개의 API 작업만 실행했기 때문에, 필요 여부와 관계없이 동일한 금액을 지불했습니다. 저희는 트래픽이 증가함에 따라 피크 시간대에는 820개 이상의 ECS 태스크로 확장하고, 밤에는 20개로 축소합니다. 따라서 자동 확장을 통해 트래픽 변동에 따른 비용을 크게 절감할 수 있습니다 . 저희가 처음 사용했던 자동 스케일링 알고리즘은 ECS를 이용해 설정하기가 매우 간단했습니다. 저희는 AWS 애플리케이션 자동 스케일링을 활용하여 " 이 ECS 서비스의 CPU 사용률을 60~65% 정도로 유지하고 싶다"는 목표 추적 알고리즘을 설정할 수 있었습니다. 그러다가 하루 중 트래픽이 증가하면 소형 인스턴스의 CPU 사용률이 65%를 넘어가고, ECS는 자동으로 더 많은 작업을 불러옵니다. 업무일이 끝나갈 무렵 CPU 사용률이 낮아지면 자동으로 규모가 축소됩니다. 음, 사실 저희 고객들이 동부 시간으로 업무 시작 시간에 Ramp에 너무 빨리 로그인하는 바람에 자동 스케일링이 동부 시간 오전 9시경에 서비스를 충분히 빠르게 확장하지 못하는 경우가 있다는 것을 발견했습니다. 그리고 최근 ECS는 기존 자동 스케일링 규칙 위에 구축되어 시스템이 평소에 어떻게 확장되는지 학습하고 트래픽이 증가하기 전에 서비스 에 ECS 작업을 선제적으로 추가할 수 있는 예측 자동 스케일링 알고리즘을 출시했습니다 . 그리고 기본적으로, 우리가 가끔 아침에 호출기에서 받던 알림음의 자동 크기 조정 기능은 이제 아침에 출근할 시간임을 알려주는 알람 시계 역할만 하게 되었습니다 . 음, 저희 업무의 모든 부분이 이러한 API를 통해 처리되는 것은 아닙니다 . 저희는 백그라운드에서 비동기 적으로 처리해야 하는 작업이 많아서, 그 과정이 조금 더 비용이 많이 들고 시간이 오래 걸립니다 . 그래서 초기에는 파이썬 개발자들 사이 에서 매우 인기 있는 Celery라는 프레임워크를 사용했는데, 이는 RabbitMQ를 기반으로 구축되었습니다. 아, 그리고 이 모든 것도 ECS에서 실행되고 있습니다 .
