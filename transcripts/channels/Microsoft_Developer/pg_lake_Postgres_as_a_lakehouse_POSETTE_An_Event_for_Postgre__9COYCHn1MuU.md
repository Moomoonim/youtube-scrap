## 스크립트

안녕하세요 여러분, 저는 마르코 슬롯입니다. 오늘 제 발표는 pg_lake에 관한 것입니다. pg_lake는 PostgreSQL을 데이터 레이크 및 레이크하우스의 세계와 연결하는 오픈 소스 확장 프로그램입니다. pg_lake를 사용하여 객체 스토어의 데이터를 가져오고, 쿼리하고, 내보내는 방법과 Iceberg와 같은 테이블 형식 및 Parquet과 같은 파일 형식을 사용하여 빠른 분석을 수행하는 방법에 대해 이야기하겠습니다. 자, 그럼 pg_lake: PostgreSQL을 레이크하우스로 사용하는 방법에 대해 알아보겠습니다. 그런데 레이크하우스란 무엇일까요? 솔직히 이 프로젝트를 시작했을 때 저도 레이크하우스라는 용어를 잘 몰랐습니다. 들어본 적은 있지만 정확히 무엇을 의미하는지는 몰랐죠. 마케팅 용어처럼 들리기도 하지만, 사실 데이터 분야와 분석 분야에서 일어나고 있는 중요한 아키텍처 트렌드를 가리키는 말이기도 합니다 . 지난 수십 년 동안 대부분의 기업은 데이터를 두 가지 방식으로 구성해 왔습니다. 보통 한 가지 방식만 사용하는 것이 아니라, 두 가지 방식을 모두 사용하는 경우가 많습니다. 첫 번째는 데이터 레이크입니다. 데이터 레이크는 객체 스토리지와 유사한 방식으로, 로그 파일, CSV 파일, Parquet 파일 등 다양한 파일을 수집합니다. 데이터 레이크는 데이터 쓰기가 매우 간편하며, 어떤 애플리케이션이든 파일을 추가할 수 있습니다. 일반적으로 저장 용량에 제한이 없고, 스토리지 비용도 저렴합니다. 하지만 파일 형식이 제각각 이거나 분석에 최적화된 형식이 아닐 수 있기 때문에 데이터 처리 과정이 복잡하고 시간이 오래 걸릴 수 있습니다. 그럼에도 불구하고 데이터 레이크는 접근성이 좋고 상호 운용성이 뛰어난 데이터 저장 계층입니다. 두 번째는 데이터 웨어하우스입니다 . 데이터 웨어하우스는 데이터를 테이블 형태로 구조화하여 열과 데이터 유형을 정의 하고 조인을 통해 데이터를 효율적으로 처리할 수 있도록 합니다. 데이터 웨어하우스는 훌륭한 모델이지만, 데이터 구조화에 어느 정도 노력이 필요하고 특정 클라이언트와 SQL 구문을 사용해야 한다는 단점이 있습니다. 따라서 데이터 레이크보다 접근성이 떨어집니다. 데이터 레이크하우스는 기본적으로 두 가지 아키텍처를 결합한 것입니다. Azure Blob Storage나 Amazon S3 같은 객체 저장소에 데이터를 저장하지만, 데이터 웨어하우스처럼 열과 데이터 유형을 가진 테이블 형태로 구조화하여 SQL 쿼리를 실행할 수 있습니다. 객체 저장소에 파일로 저장하고 수정할 수 있는 특정 테이블 형식이 정의되어 있으며 , 스키마 변경도 가능합니다. 그중 가장 유명하고 널리 사용되는 형식은 Iceberg입니다. pg_lake의 핵심 구성 요소이기 때문에 Iceberg에 대해 더 자세히 살펴보겠습니다 . Iceberg는 기본적으로 개방형 테이블 형식입니다. 파일들을 하나의 테이블로 그룹화하고 , 테이블의 현재 스키마, 이전 버전, 파일 관련 통계 등을 정의 하는 프로토콜과 형식을 제공합니다 . Iceberg 는 오픈 소스 사양으로, 커뮤니티 주도로 개발되고 있습니다. 따라서 다양한 엔진들이 Iceberg 테이블 쿼리 및 작성을 지원하고 있으며, 이를 통해 동일한 데이터에 대해 여러 엔진을 사용할 수 있습니다. 데이터를 한 번 저장하면 다양한 엔진을 사용할 수 있습니다. 또한 이러한 테이블에서 트랜잭션을 수행할 수 있어 매우 강력하며 스키마도 변경할 수 있습니다. 파티셔닝 과 같은 데이터 웨어하우스에서 일반적으로 볼 수 있는 중요한 기능 들을 데이터 레이크 위에 구현했습니다. pg_lake는 기본적으로 이러한 기술을 PostgreSQL에 통합한 것입니다. 첫째, Iceberg라는 네이티브 테이블 형식을 지원하여 PostgreSQL에서 Iceberg 테이블을 생성하고 쿼리, 업데이트 또는 기존 Iceberg 테이블을 가져올 수 있습니다. 또한 Parquet 파일, CSV 파일, JSON 파일 등 다양한 파일 형식을 가져오고 내보내고 쿼리할 수 있는 원시 데이터 레이크에도 연결하여 SQL을 통해 매우 쉽게 작업할 수 있습니다. Iceberg 또는 Parquet 파일을 사용하는 경우, DuckDB라는 다른 쿼리 엔진에 쿼리의 일부를 위임하여 해당 테이블에 대한 분석 쿼리를 매우 빠르게 실행할 수도 있습니다 . 그리고 마지막으로, pg_lake의 가장 강력한 장점 중 하나는 이러한 작업들을 매우 간편한 방식으로 수행할 수 있다는 점이라고 생각합니다. 일반 SQL과 트랜잭션을 사용하여 이러한 작업을 수행할 수 있습니다. 이를 통해 데이터 레이크에서 데이터를 지속적으로 가져와 PostgreSQL에 수집 하거나 Iceberg에 아카이빙하는 비교적 간단한 데이터 파이프라인을 구축할 수 있습니다 . 발표 후반부에 몇 가지 예시를 보여드리겠습니다. pg_lake는 작년 11월에 Apache 라이선스 오픈 소스 프로젝트로 발표했지만, 그 역사는 좀 더 깁니다. 2024년 초에 시작하여 그 해에 Crunchy Data에서 개발하고 Crunchy Data 제품에 추가했습니다. 그리고 11월에 초기 Iceberg in PostgreSQL 제품에 추가했습니다. 그러다가 작년 6월에 Snowflake에 인수되었습니다. Snowflake 내에서 pg_lake는 새로운 의미를 갖게 되었는데, 첫째로 오픈 소스 프로젝트가 되었고, 둘째로 Snowflake PostgreSQL 서비스의 핵심 구성 요소가 되었으며 , PostgreSQL과 데이터 레이크 , 그리고 Snowflake와 다른 엔진 간의 상호 운용성 에 더욱 중점을 두게 되었습니다 . 자, 이제 좀 더 구체적인 예를 들어볼까요? 지금까지는 딱딱한 이야기였으니 SQL을 살펴보겠습니다. pg_lake를 사용하면 파일에서 직접 테이블을 생성할 수 있습니다. 파일의 형식, 열, 데이터 유형 등을 지정할 필요가 없기 때문에 매우 간편합니다 . CSV 파일의 헤더를 분석하여 테이블을 자동으로 구성해 줍니다. 따라서 원시 파일을 쉽게 쿼리할 수 있습니다. COPY 명령어를 사용하여 해당 테이블에 데이터를 추가할 수도 있습니다. CSV 파일 이나 Parquet 파일의 URL을 지정할 수 있습니다. 데이터 양이 많아서 PostgreSQL에 직접 로드하고 싶지 않을 수도 있습니다. 이럴 때는 와일드카드를 사용하여 특정 파일 또는 파일 집합을 가리키는 외부 테이블을 생성할 수 있습니다 . 이 방법은 매우 유용합니다. *.parquet 접두사를 사용하는 새로운 Parquet 파일이 추가되면 해당 테이블에 자동으로 반영되기 때문입니다. Parquet 형식으로 데이터를 저장하는 또 다른 장점은 해당 테이블을 쿼리할 때 쿼리의 일부를 DuckDB에 위임할 수 있다는 점입니다. DuckDB 는 PostgreSQL보다 훨씬 빠릅니다. 또한 PostgreSQL에서 데이터를 내보낼 수도 있습니다 . 쿼리를 실행하고 결과를 객체 스토리지로 내보내기만 하면 됩니다. 이는 매우 유용한 기능으로 , PostgreSQL이 한 애플리케이션에서 작성된 데이터를 가져와 처리한 후 다른 애플리케이션으로 내보내는 파이프라인을 구축할 수 있게 해줍니다. 웹 애플리케이션이나 모바일 앱에서 해당 데이터를 직접 가져올 수도 있습니다. 따라서 PostgreSQL은 전체 데이터 아키텍처에서 허브 역할을 하게 됩니다. 하지만 파일을 다루는 것은 처음에는 쉽지만, 파일 수가 많아지고 파일마다 내용이 조금씩 달라지기 때문에 항상 까다롭습니다 . 파일 이름 지정 체계를 변경 하거나, 새 파일에 열이 추가되거나, 이름이 바뀌거나, 데이터 유형이 달라지는 경우가 종종 발생합니다. 이러한 상황에서 데이터를 테이블 형식으로 정리하는 것이 매우 유용합니다. Iceberg는 기본적으로 Parquet 파일 모음을 메타데이터 파일 계층을 통해 구조화하는 방식입니다. 이 메타데이터 파일 은 현재 테이블에 포함된 Parquet 파일 세트를 설명합니다. 예를 들어, 특정 Parquet 파일이 다른 Parquet 파일에서 삭제된 내용을 설명한다고 명시할 수 있습니다 . 또한 Parquet 파일에 대한 통계 정보를 저장하거나 제공할 수 있으므로, 해당 메타데이터 파일을 읽는 엔진은 특정 쿼리를 위해 데이터 파일을 직접 읽을 필요가 없습니다. pg_lake와 같이 Iceberg에 쓰기 작업을 수행하는 엔진은 이러한 쓰기 작업을 데이터 파일( 일반적으로 Parquet 파일)과 해당 데이터 파일을 참조하는 메타데이터 파일 로 변환합니다 . 최상위 메타데이터 파일에는 테이블의 현재 버전 정보가 담겨 있으며 , 스키마와 현재 스냅샷 정보가 포함되어 있고 파일의 최신 버전을 가리킵니다. 따라서 이 메타데이터 파일을 통해 테이블에 어떤 내용이 있는지 정확히 파악할 수 있습니다. 하지만 이러한 테이블에서 실제로 트랜잭션을 수행하려면, 이러한 파일이 저장되는 객체 저장소는 적합하지 않습니다. Iceberg는 PostgreSQL처럼 트랜잭션 메커니즘을 직접적으로 지원하지는 않습니다. 그래서 Iceberg에서는 데이터베이스, 보통 카탈로그라고 부르는 것을 사용하여 이 문제를 해결합니다. 카탈로그는 API를 제공하는 데이터베이스와 같 으며, 메타데이터 파일의 최신 버전을 저장합니다. Iceberg 테이블에 쓰기 작업을 하거나 트랜잭션을 수행할 때, 새로운 파일들을 생성 하고 카탈로그에 최신 버전을 알려줍니다. 만약 마지막 단계에서 오류가 발생하면 트랜잭션이 롤백됩니다. 이것이 Iceberg에 진정한 트랜잭션 보장을 제공하는 방식입니다. Iceberg 구현에는 이 외에도 여러 가지 기능이 있습니다. 예를 들어, 데이터를 삽입하다 보면 작은 파일들이 많이 생성되는 경우가 있습니다. 이럴 때 pg_lake는 10분마다 백그라운드 워커를 실행하여 이러한 파일들을 하나로 합칩니다. 이를 컴팩션이라고 합니다. 예를 들어, 이전에는 1MB 파일 몇 개가 있었는데, 이제는 하나의 20MB 파일로 통합될 수 있습니다. Iceberg에서는 파티셔닝과 같은 작업도 가능 하지만, pg_lake에서도 PostgreSQL의 모든 기능을 활용할 수 있습니다. Iceberg 테이블에서 시퀀스를 사용하고, 트리거와 제약 조건을 적용할 수 있습니다. 즉, 매우 심층적인 통합이 가능합니다. 기본적으로, pg_lake 테이블은 PostgreSQL 테이블처럼 작동한다고 할 수 있습니다. 힙 메모리를 사용하는 대신 Iceberg를 사용하여 테이블을 생성할 수 있습니다. PostgreSQL에서 테이블을 생성하는 것과 마찬가지로, Iceberg를 사용하면 동일한 방식으로 테이블을 생성할 수 있습니다. 그 외에는 이러한 테이블이 PostgreSQL 테이블과 동일하게 동작합니다. 데이터 삽입, 업데이트, 열 추가 및 삭제, 시퀀스 및 저장 프로시저와 같은 PostgreSQL에서 사용하려는 다른 기능들을 사용할 수 있으며, 쿼리 및 저장 프로시저 실행도 가능합니다. 가장 큰 장점은 이러한 테이블들이 저렴하고 압축된 스토리지 , 사실상 무제한의 저장 공간에 저장된다는 것입니다. 또한 쿼리가 위임되기 때문에 매우 빠른 분석이 가능하며, 다른 애플리케이션에서도 쉽게 접근할 수 있습니다. 다른 애플리케이션처럼 객체 스토리지에서 데이터를 직접 가져올 수 있기 때문에 PostgreSQL과 통신할 필요가 없습니다. 물론 몇 가지 제약 사항이 있습니다. 모든 것을 공짜로 얻을 수는 없죠. pg_lake의 Iceberg 테이블에는 인덱스, 외래 키, 행 수준 보안을 사용할 수 없다는 제약이 있습니다. 이러한 것들은 Iceberg의 일반적인 제약 사항입니다. 인덱스를 추가하자는 제안도 있으므로 향후에는 가능해질 수도 있습니다. 이러한 새로운 테이블 형식을 구현한 방식은 확장 API를 통해서입니다. PostgreSQL은 확장 기능 을 통해 서버로 들어오는 거의 모든 명령, 즉 SQL 명령, DDL 명령, DML 명령을 가로채서 PostgreSQL이 일반적으로 수행하는 작업과 다르거나 추가적인 작업을 수행할 수 있도록 합니다. 따라서 Iceberg 테이블에 대한 ALTER TABLE 명령이나 Iceberg 테이블에 대한 쿼리를 가로챌 수 있습니다 . 예를 들어, Iceberg 테이블만 포함하는 쿼리가 있을 때, 해당 쿼리를 DuckDB에 위임하여 처리 속도를 크게 향상시킬 수 있습니다. 하지만 실제로 PostgreSQL의 다양한 후크 기능을 조합하여 이러한 원활한 사용자 경험을 구현하고 있습니다. 내부적으로는 DuckDB를 통합하는 작업을 진행했는데 , DuckDB는 멀티스레드 벡터화 쿼리 엔진으로 분석 속도가 매우 빠릅니다 . 작년에 제가 발표한 강연에서 DuckDB가 PostgreSQL보다 분석 속도가 훨씬 빠른 이유를 설명한 바 있습니다. 하지만 DuckDB는 스레드 풀이 크기 때문에 메모리 사용량도 많습니다. 따라서 PostgreSQL에 연결할 때마다 새로운 프로세스가 생성되므로, 각 프로세스에 DuckDB 인스턴스를 실행할 수는 없었습니다 . 그렇게 하면 메모리 부족 현상이 매우 빠르게 발생하기 때문입니다. 그래서 PostgreSQL과 함께 실행되는 별도의 서버를 운영하고 , 모든 PostgreSQL 세션은 이 서버에 연결됩니다. 따라서 Iceberg 테이블에 대한 쿼리가 들어오면 pg_lake의 쿼리 최적화 프로그램은 이 쿼리의 어떤 부분을 pg_duckdb 서버로 위임할 수 있는지 확인합니다. 그러면 데이터가 그곳으로 전송됩니다. 저희는 실제로 Postgres 프로토콜을 구현했습니다. 기본적으로 Postgres끼리 통신하는 거죠. 그러면 DuckDB가 쿼리를 받아서 실행합니다. S3와 통신할 수 있는 자격 증명도 가지고 있어서 데이터 파일을 가져올 수 있습니다. 전체 데이터를 다운로드하지 않고 일부만 가져오는 경우도 많습니다. 또한 모든 파일을 저장하는 캐시도 있어서 대부분의 경우 객체 스토리지에 직접 접근하지 않아도 됩니다. Iceberg에 데이터가 있으면 빠른 분석 쿼리를 수행할 수 있고 다른 시스템에서도 쿼리할 수 있기 때문에 매우 유용합니다. 하지만 실제로 Iceberg에 데이터를 어떻게 가져올까요? 처음 개발했을 때는 "이거 정말 좋네, 사람들이 많이 사용할 거야"라고 생각했습니다. 그런데 뭔가 부족하다는 것을 깨달았습니다. Postgres 데이터를 Iceberg로, Iceberg 데이터를 Postgres로, 또는 데이터 레이크 데이터를 Postgres로 가져오는 데 도움이 되는 기능이 필요했습니다 . 그래서 pg_incremental이 탄생하게 된 것입니다. pg_incremental의 기본 아이디어는 들어오는 데이터를 다른 테이블로 이동하려는 경우 를 생각해 보는 것 입니다. 처음에는 기존 데이터를 모두 가져와서 이동하고, 그 후에는 주기적으로 새로운 데이터를 가져 와서 대상 테이블로 이동 해야 합니다. pg_incremental 은 다양한 유형의 소스 데이터에 대해 이러한 작업을 수행할 수 있는 패턴을 찾습니다. 예를 들어 소스 데이터가 시퀀스 번호가 있는 PostgreSQL 테이블이라고 가정해 보겠습니다. 이 경우 pg_incremental은 아직 처리되지 않은 모든 시퀀스 번호를 가져오는 쿼리를 실행하도록 도와줍니다 . 또는 특정 열을 기준으로 데이터를 기간별로 나누고 아직 처리되지 않은 기간의 데이터를 가져오는 쿼리를 실행할 수도 있습니다. 혹은 객체 스토리지를 살펴보고 어떤 파일이 있는지 확인한 다음, 처음에는 모든 파일을 가져오고, 새 파일이 추가될 때마다 해당 파일만 가져오는 방식을 사용할 수도 있습니다. pg_incremental의 가장 큰 장점은 각 입력 값을 한 번만 처리한다는 것입니다. 그래서 각 파일은 한 번씩 처리되거나 각 행은 한 번씩 처리됩니다. 예를 들어, PostgreSQL에 이벤트가 들어온다고 가정해 보겠습니다. 기기에서 PostgreSQL에 레코드를 지속적으로 삽입하는 것은 매우 흔한 패턴입니다 . 이런 경우 추가 전용 테이블이 사용됩니다. 애플리케이션 관점에서 응답 시간이 매우 빠릅니다. 일반적으로 파티셔닝을 사용하여 오래된 파티션을 빠르게 삭제하고 쿼리 속도를 높입니다. 또한 인덱스를 사용하여 최근 7일간의 데이터를 PostgreSQL에 보관하여 최근 10개의 이벤트를 빠르게 조회할 수 있도록 합니다. 그리고 7일 후에는 데이터를 삭제합니다. 하지만 모든 데이터를 더 압축된 형태로 보관하고 과거 데이터에 대한 빠른 분석을 수행하고 싶을 수도 있습니다. Iceberg는 이러한 경우에 매우 유용합니다. 이제 PostgreSQL에서 테이블을 생성한 다음 동일한 열을 가진 Iceberg 테이블을 생성할 수 있습니다. 그리고 나서 시퀀스 번호를 기준으로 모든 이벤트를 처리하는 pg_incremental 작업을 설정할 수 있습니다 . 처음 실행될 때는 테이블에 이미 있는 모든 시퀀스 번호를 가져오고, 그 후에 는 매분마다 다른 매개변수를 사용하여 다시 실행됩니다 . 따라서 $1과 $2는 쿼리가 실행될 때마다 계속 변경되며, 순차적으로 처리됩니다. 예를 들어, 처음에는 0부터 100까지 처리하고, 그다음에는 101부터 110까지, 그다음에는 111부터 120까지 처리하는 식입니다 . 이렇게 계속 진행됩니다. 또한 내부적으로는 특정 범위의 처리가 완료되기 전에는 해당 범위를 처리하지 않도록 하는 로직이 내장되어 있습니다. 즉, 이전 시퀀스 번호를 사용하는 진행 중인 트랜잭션이 있는 경우, 해당 트랜잭션이 완료될 때까지 기다립니다. 이처럼 간단한 3단계만으로 Iceberg에 자동 아카이빙이 가능하고, 빠른 분석 기능을 제공하며 , 다른 애플리케이션에서도 이 데이터를 쿼리할 수 있습니다. 비슷한 패턴이지만, 여러 면에서 여전히 상당히 다른 점은 제가 포스트그레스에서 큐로 사용하는 테이블이 있다는 것입니다. 그래서 간단하게 작업을 처리해야 할 때가 있습니다. 이벤트를 어딘가에 영구적으로 기록하는 방법이 필요하고, 꼭 PostgreSQL에 저장할 필요는 없습니다. 다른 시스템에서 쿼리할 수 있는 위치에만 있으면 됩니다. 그래서 PostgreSQL 테이블을 큐로 사용하고, Iceberg 테이블을 대상으로 사용합니다. 이 경우에는 pg_incremental을 사용할 필요 없이 일반 pg_cron 작업을 실행해도 됩니다. pg_cron은 10초마다 실행되는 주기적인 작업으로, 큐의 모든 데이터를 삭제하고 Iceberg 테이블에 일괄적으로 삽입합니다. Iceberg를 사용할 때는 일괄 처리가 매우 중요합니다. Iceberg 테이블에 단일 행을 직접 삽입하면 수백 밀리초의 응답 시간이 발생 하고 한 번에 하나씩만 삽입 될 수 있기 때문에 PostgreSQL보다 훨씬 비효율적입니다. 하지만 일괄 처리를 하면 이러한 문제가 해결됩니다. 대량 처리의 경우에도 여전히 수백 밀리초가 소요될 수 있는데, 이는 파일을 객체 스토리지에 기록하는 데 시간이 걸리기 때문입니다. 그리고 일반적으로 초기 오버헤드가 발생합니다. 또 다른 패턴은 반대 방향으로 데이터를 처리하는 경우입니다. 데이터가 PostgreSQL에 직접 기록되지 않고 객체 스토리지에 기록된 후, 이를 PostgreSQL로 가져오려는 경우입니다. 예를 들어 다른 애플리케이션의 로그를 압축된 JSON 파일로 저장한 후, 이를 PostgreSQL 테이블이나 Iceberg 테이블에 저장하려는 경우입니다. Iceberg를 사용할지 힙을 사용할지 선택하는 것만으로도 간편하게 처리할 수 있습니다 . pg_incremental을 사용하면 특정 URL 패턴을 따르는 모든 파일을 선택하여 명령어를 실행하는 파일 목록 파이프라인을 생성할 수 있습니다 . 이 파이프라인은 더 작은 배치로 작업을 수행하여 한 번에 100개 파일씩 처리합니다. 하지만 이렇게 하면 테이블에 삽입하고, 파일 이름이 이 100개 집합에 속하는 외부 테이블에서 선택합니다 . 그리고 이미 있는 모든 파일을 처리한 후에는 주기적으로 새 파일이 있는지 확인합니다. 새 파일이 있으면 INSERT SELECT 명령을 다시 실행합니다. 이렇게 단 세 개의 명령만으로 객체 스토리지에서 PostgreSQL 또는 Iceberg 테이블로 데이터를 가져오는 전체 ETL 파이프라인을 구축할 수 있습니다. PostgreSQL 테이블의 경우 인덱스 등을 추가할 수도 있습니다. 일반적으로 pg_lake와 같은 도구 없이 이러한 파이프라인을 구축하려면 상당히 많은 도구가 필요합니다 . PostgreSQL에서만 작업을 수행하는 것 외에도 이 패턴이 매우 유용한 또 다른 영역은 PostgreSQL을 데이터 웨어하우스와 연결하는 것입니다. 물론 데이터 웨어하우스라고 하면 Snowflake를 떠올리지 만 다른 데이터 웨어하우스도 포함될 수 있습니다. 요즘 흔히 볼 수 있는 현상 중 하나는 pg_lake가 운영 데이터베이스인 Postgres 와 분석 데이터베이스, 즉 Snowflake나 다른 시스템과 같은 데이터 웨어하우스를 연결하는 다리 역할을 한다는 것입니다. Iceberg는 이러한 연결을 매우 쉽게 만들어 줍니다. 한쪽에서 Iceberg 테이블에 데이터를 쓰면 표준 프로토콜을 사용하기 때문에 다른 쪽에서 직접 쿼리할 수 있습니다 . Snowflake Postgres 서비스에서는 pg_lake 통합을 최대한 원활하게 구현하려고 노력했습니다. Postgres 인스턴스를 생성하고 연결하면 pg_lake가 이미 연결되어 있습니다. 또한 Postgres 인스턴스에 연결된 객체 스토리지도 제공됩니다. Iceberg 테이블을 생성하면 기본적으로 이 객체 스토리지에 저장됩니다. 다른 위치에 저장할 수도 있지만, 기본적으로 관리형 객체 스토리지에 저장됩니다. 따라서 CREATE TABLE AS 또는 INSERT SELECT 문을 실행하여 Postgres 테이블에서 데이터를 가져올 수 있습니다 . 그리고 Snowflake 사용자라면 Snowflake에서 바로 Iceberg 테이블을 생성할 수 있습니다. 정확히 말하면 테이블을 생성하는 것이 아니라 참조하는 것입니다. 그런 다음 해당 데이터를 직접 쿼리하고 데이터 웨어하우스에서 할 수 있는 모든 작업을 수행할 수 있습니다 . 추가적인 파이프라인을 구축하거나 AI 작업을 수행할 수도 있습니다. 두 시스템의 모든 기능을 결합하여 사용할 수 있다는 점이 매우 좋습니다. 요약하자면, pg_lake는 Iceberg와 같은 형식, JSON과 같은 파일 형식을 사용하여 데이터 레이크와 통합하고, 더 나아가 다른 플랫폼과도 통합하는 데 중점을 둡니다. 외부 도구를 많이 실행할 필요 없이 익숙한 SQL을 통해 객체 스토리지의 데이터와 상호 작용할 수 있습니다 . 모든 것이 자체적으로 완벽하게 작동합니다. 특히 Iceberg는 트랜잭션 보장을 제공하며, pg_incremental과 같은 기능도 이를 기반으로 합니다. Iceberg 테이블에 데이터를 쓰는 트랜잭션 과 PostgreSQL 테이블에서 데이터를 쓰는 트랜잭션을 동시에 수행할 수 있습니다. 즉, 실제 처리와 동시에 처리 내역을 기록할 수 있다는 뜻입니다. 이는 매우 편리한 기능입니다. 또한 pgcron 및 pgincremental과 같은 주기적인 작업 스케줄러를 함께 사용하면 데이터베이스 내에서 증분 처리를 수행할 수 있습니다. 따라서 여러 외부 도구를 사용하는 것보다 훨씬 간편하고 효율적입니다. 네, 이 글을 통해 pg_lake가 무엇인지, 어떻게 활용할 수 있는지 조금이나마 이해하셨기를 바랍니다. 궁금한 점이 있으면 디스코드에서 저에게 문의해 주세요. 이메일로 연락 주셔도 좋습니다. 그럼 이만, 내년 POSETT에서 뵙기를 기대하며, 그때까지 기다려 주시면 감사하겠습니다.
