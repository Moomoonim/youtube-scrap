## 스크립트

CLI와 MCP 모두 AI 에이전트가 외부 세계와 상호 작용할 수 있도록 합니다. 이제 CLI 명령줄 인터페이스를 살펴보겠습니다. 이때 에이전트는 CLI를 사용하여 명령을 실행합니다 . 일반 터미널 명령어로 실행됩니다. 어떤 명령어를 말씀하시는 건가요? 음, LS 같은 명령어, 그러니까 cat처럼 쓰는 명령어도 또 다른 예죠 . 음, 몇 가지 더 생각해 보자. grep, 그리고 curl이라고 해보자. 그러니까, 이런 종류의 명령어를 실행할 수 있는데, 개발자가 명령 터미널에 입력하는 명령어와 완전히 똑같습니다. MCP는 전용 서버가 구조화된 도구를 제공하는 표준화된 프로토콜입니다. 자, 이것들은 예를 들어 파일 읽기 같은 도구들입니다. 또 다른 방법으로는 파일 검색이 있을 수 있습니다. 그리고 각 도구에는 '파일 읽기'와 같이 도구에 지정된 이름이 있습니다 . 해당 도구의 기능에 대한 설명이 영어로 적혀 있습니다. 그리고 JSON 스키마도 가지고 있는데, 이 스키마는 어떤 입력값을 기대하고 어떤 출력값을 반환하는지 정확하게 정의합니다. 현재 점점 더 많은 개발자들이 MCP는 불필요한 복잡성을 야기하며 CLI 도구가 더 저렴하게 동일한 작업을 수행할 수 있다고 주장하고 있으며, 이를 뒷받침하는 수치도 어느 정도 있습니다. 그러니까, 그 주장은 대략 이런 식입니다. AI 모델은 수백만 개의 CLI 예제를 기반으로 학습되었으며, 학습 데이터 세트에는 Stack Overflow 게시물 및 매뉴얼 페이지와 같은 소스의 예제가 포함되어 있습니다. 그래서 해당 모델은 이미 이러한 명령어들을 비롯한 훨씬 더 많은 명령어를 사용하는 방법을 알고 있습니다 . 그러니까, 우리는 계속해서 추가할 수 있다는 거죠. 예를 들어 Git이 있고 Docker가 있다고 가정해 봅시다. 계속해서 나열할 수도 있습니다 . 어떤 플래그를 전달해야 하는지 알려주는 스키마가 필요하지 않습니다 . 그러한 지식은 훈련 과정에서 자연스럽게 습득됩니다 . MCP를 사용하면 모든 도구의 스키마가 대화 시작 시 모델의 컨텍스트 창에 로드되며, 이러한 스키마 하나를 로드하는 데 수백 개의 토큰이 소모될 수 있습니다. 에이전트가 유용한 작업을 수행하기도 전에 컨텍스트 창을 채우고 있습니다 . 그렇다면 어느 쪽이 옳은 걸까요? MCP는 CLI에 비해 유용한 추상화 도구인가, 아니면 불필요하게 컨텍스트 창을 채우는 과도한 기능인가 ? 자, 제가 AI 코딩 에이전트를 이용해 수행한 두 가지 예시를 보여드리겠습니다. 동일한 작업을 CLI와 MCP를 사용하여 수행했을 때의 차이점을 설명해 드리기 위한 것이며, 여러분 도 원하는 AI 에이전트를 사용하여 동일한 연습을 직접 해보실 수 있습니다. 첫 번째 연습은 간단한 파일 작업입니다. 여기 마크다운 파일이 몇 개 있는 폴더가 있는데, 에이전트는 두 가지 작업을 수행해야 합니다. 먼저 notes.md라는 파일 하나를 읽어온 다음, 두 파일 모두를 검색하여 특정 단어를 찾아야 합니다. 이제 저는 AI 코딩 에이전트에 두 가지 요청을 각각 보냈습니다. 하나는 CLI를 사용하여 해당 작업을 수행하도록 요청하는 것이고, 다른 하나는 MCP를 사용하도록 요청하는 것입니다. CLI 방식의 경우, 에이전트가 결국 두 개의 bash 명령어를 사용하게 되었습니다. 그래서, 처음에 사용한 bash 명령어는 `cat notes.md`로 파일 내용을 표준 출력으로 내보낸 다음, `grep`을 사용하여 두 마크다운 파일 전체에서 'agent'라는 단어를 검색했습니다 . 자, CLI에 익숙하지 않은 분들을 위해 간단히 이러한 명령어에 대해 설명드리겠습니다. ` cat`은 `concatenate`의 줄임말로, 여기서는 단일 파일의 내용을 출력하는 데 사용됩니다. `grep`은 파일을 한 줄씩 스캔하여 패턴과 일치하는 모든 줄을 출력하고, ` -N` 플래그는 줄 번호를 추가합니다. 자, 이렇게 에이전트가 CLI를 처리했는데, 에이전트가 어떤 명령어와 플래그를 사용해야 할지 알아내기 위해 아무것도 찾아볼 필요가 없었다는 점을 강조할 만합니다. 이는 훈련 데이터에 내장되어 있었습니다. 이제 에이전트가 MCP 방식을 채택했을 때 , 파일 시스템 서버라고 불리는 특정 MCP 서버에서 두 번의 도구 호출을 사용하게 되었습니다 . 그래서 MCP 서버에서 사용한 두 가지 도구는 notes.md 파일을 읽는 파일 읽기 도구 와 검색하려는 단어 문자열(그중 하나가 바로 ' agent'였습니다)을 제공하는 파일 검색 도구였습니다. 두 접근 방식 모두 작업을 성공적으로 완료했고 동일한 정보를 반환했지만, CLI 명령은 좀 더 간결했고 모델은 grep에서 N을 뺀 것이 올바른 플래그 조합이라는 것을 알기 위해 어떤 스키마도 알 필요가 없었습니다 . 자, 파일 시스템 MCP 서버는 13가지 도구를 제공한다고 광고합니다. 그래서 실제로 사용한 건 두 개뿐이었어요. 사용되지 않은 도구가 11개 더 있으며, 각 도구에는 전체 JSON 스키마가 함께 제공됩니다. 에이전트가 그중 두 개를 사용하기 위해 수천 개의 도구 정의 토큰이 컨텍스트 창에 로드되었습니다 . 그래서 MCP가 불필요한 복잡성이라는 비판이 나오는 이유가 바로 그런 데 있다고 생각합니다 . 솔직히 말해서, 이렇게 간단한 게임이라면 둘 다 괜찮을 거예요. 규모가 커질수록 그 차이는 더욱 두드러집니다. 그럼 다른 걸 생각해 봅시다. 전 세계에서 가장 널리 사용되는 개발 도구 중 하나인 Git을 생각해 봅시다 . 이제 Bash를 사용하는 AI 에이전트는 다음과 같은 여러 Git 명령어를 실행할 수 있습니다. 예를 들어, 이 명령어를 실행하여 최근 10개의 커밋을 표시할 수 있고, `git status` 명령어를 실행하여 작업 트리를 확인할 수 있습니다. 즉, 모델은 Git 코드를 이해하고 있습니다. 깃발을 인식합니다. 학습 데이터를 통해 형식 문자열을 모두 알고 있습니다. 자, 이제 MCP 대안을 생각해 봅시다. 이 경우에는 GitHub MCP 서버입니다. 그건 공구 13개를 배송하는 게 아니에요. 이 패키지에는 80가지의 다양한 도구가 포함되어 있으며, 각 도구의 정의, 이름, 설명, 매개 변수 유형 및 설명이 포함된 전체 JSON 입력 스키마 등 모든 정보가 대화 시작 시 모델의 컨텍스트 창에 삽입됩니다. 따라서 80가지 도구 중 한두 가지만 필요하더라도 약 5만 5천 개의 토큰이 생성됩니다. API 가격 책정 방식에서는 해당 토큰이 실제 현금과 같습니다. 그것들은 실제 작업에 사용할 수 있는 컨텍스트 창 공간을 직접적으로 잠식합니다. 그리고 그 모델은 몇 가지 bash 명령어를 사용해서도 동일한 Git 작업을 수행할 수 있었을 것입니다. 그래서, 그것이 CLI 진영의 가장 강력한 주장입니다. 로컬 개발자 도구의 경우, MCP는 모델이 이미 보유하고 있는 지식에 대해 상당한 비용을 지불하고 있습니다. 그렇다면 MCP는 그저 쓸모없는 존재일까요? 자, 그럼 연습 문제를 하나 더 풀어볼까요? 이번 과제는 modelcontextprotocol.io에서 웹페이지를 가져와서 메인 제목과 처음 몇 단락의 요약을 알려주는 것입니다. 자, 먼저 MCP 접근 방식을 살펴보았고, 네, MCP를 사용하여 MCP에 대한 페이지, 즉 약간의 메타 정보를 가져오고 있습니다. 이제 에이전트는 MCP 서버에 단일 호출을 사용했으며, 사용된 서버는 fetcher라고 불렸습니다. 이것은 헤드리스 브라우저를 기반으로 구축된 MCP 서버이므로 JavaScript를 렌더링할 수 있으며, Fetcher에서 제공하는 도구 중 하나인 'URL 가져오기'라는 도구를 사용하여 단일 요청을 보냈고, 해당 요청에는 modelcontextprotocol.io 웹 페이지 링크가 포함되어 있었습니다 . 그래서 서버는 브라우저를 실행했습니다. 이 페이지를 불러오고, 렌더링이 완료될 때까지 기다린 다음, 결과를 읽기 쉬운 텍스트로 변환하여 콘텐츠를 반환했습니다. 이 작업에는 약 250개의 토큰이 사용되었고, 소요 시간은 단 몇 초였습니다. 자 , 이것으로 MCP에 대한 설명을 마치겠습니다. CLI 접근 방식은 curl로 시작되었습니다. 평범하지만 좋은 컬. 그리고 바로 이 부분에서 고통스러워집니다. 그래서 상담원이 처음 시도한 방법은 ` curl minus S URL head minus 200` 명령어를 사용하는 것이었습니다. 이 명령어는 원시 HTML을 가져와서 처음 200줄만 표시하는 것입니다. 하지만 반환된 내용은 거의 전부 자바스크립트와 번들 코드였습니다. modelcontextprotocol.io 는 Next.js 애플리케이션이고 서버는 완성된 HTML 페이지를 보내지 않기 때문입니다. curl은 실제로 자바스크립트를 실행하지 않고, 브라우저에서 페이지를 생성하는 자바스크립트 애플리케이션을 전송합니다. 결국 남는 건 뼈대와 프레임워크 코드 더미뿐입니다. 그래서 이때부터 요원은 즉흥적으로 대처하기 시작했습니다. 텍스트 처리 도구들을 연결하여 HTML 태그를 제거하고 자바스크립트만 걸러내려고 시도했습니다. 그 방법은 효과가 없었어요. 그래서 소스 코드 내에 JSON 형식으로 포함된 페이지 콘텐츠를 찾으려고 시도했습니다. 그 프로그램은 일부 조각은 찾았지만, 전체 페이지는 찾지 못했습니다. 그런 다음 Next.js가 브라우저로 콘텐츠를 스트리밍하는 데 사용하는 내부 데이터 형식을 역분석하기 위해 Python 스크립트를 작성했습니다 . 웹 페이지를 읽기 위해 자바스크립트 프레임워크 내부 구조를 역분석하는 것. 제가 이 코드를 실행했을 때 , 페이지를 요약하는 데 필요한 충분한 콘텐츠를 얻기까지 여러 번 시도가 필요했습니다. 그리고 그 과정은 몇 분이나 걸렸고, 2 천 개가 넘는 토큰이 사용되었으며, 게다가 제 노트북에서 추가적인 로컬 처리 작업까지 해야 했습니다. 모두 같은 결과를 얻기 위해서다. 그래서 계획이 뭐죠? 음, 명령어가 작업에 직접 매핑될 때 CLI가 우위를 점한다고 말할 수 있을 것 같습니다 . 그래서 저는 파일 작업, Git 사용, 텍스트 처리 및 스크립트 실행과 같은 작업을 생각하고 있습니다. 명령줄 도구가 수십 년 동안 문제를 해결해 왔고 모델이 이미 해당 도구를 잘 알고 있는 경우. 또한 CLI 도구는 자연스럽게 파이프와 함께 구성됩니다. 따라서 우리는 명령어를 한 줄로 연결할 수 있는데, 이는 각 도구 호출이 독립적이기 때문에 MCP에서는 불가능한 기능입니다. 하지만 MCP에 대해서도 찬성할 만한 근거가 있다고 생각합니다 . MCP는 기본 도구가 제공하는 것과 실제로 필요한 것 사이에 차이가 있을 때, 예를 들어 제 Next.js 웹 페이지 예시처럼, 유용할 때 승리합니다. 그리고 이는 다른 여러 가지 일에도 마찬가지로 적용됩니다 . 예를 들어 인증은 어떻습니까? 그러니까 슬랙이나 노션, 또는 데이터베이스의 인증 같은 거죠 . CLI를 사용하면 에이전트가 OAuth 토큰을 관리하고, 채널 ID를 조회하고, 토큰 갱신을 처리합니다. 기본적으로 이 모든 작업은 상당히 수작업으로 이루어집니다. 지금은 AI 에이전트가 그 작업을 수행하고 있지만, 여전히 수동으로 처리해야 하는 부분이 있습니다 . 반면에 MCP는 서버가 이 모든 것을 처리합니다. 그러니까, 이건 에이전트가 직접 처리하는 게 아니라 서버에서 관리하는 거라고 할 수 있겠죠. 에이전트는 자신이 원하는 바를 말할 뿐입니다. 그리고 조직 차원에서 살펴보면 몇 가지 차이점도 있다고 생각합니다. 그래서 MCP는 이 점에서 몇 가지 장점이 있습니다. 에이전트가 여러 직원을 대신하여 업무를 수행하는 경우 사용자별 접근 제어가 필요할 수 있습니다 . 그리고 공유 자격 증명을 사용하지 않아야 할 수도 있습니다. 우리는 실제로 어떤 일이 진행되고 있는지 추적하기 위해 감사 추적 기록이 필요할 수 있습니다 . 그런 기능들은 나중에 CLI에 추가하기가 어렵지만 , MCP는 프로토콜 자체에 모든 기능이 내장되어 있습니다. MCP 든 CLI든 , 아마 예상하셨겠지만 정답은 둘 다 사용하는 것입니다. 제가 테스트한 AI 에이전트는 결국 두 가지 모두를 사용합니다. 이 시스템은 서로 다른 작업을 위해 CLI와 MCP를 나란히 사용합니다 . CLI에서 명령어가 작업에 매핑될 때 . 추상화 또는 거버넌스가 정당화할 때 MCP를 적용합니다. 선택은 담당자와 그 담당자에게 지시를 내리는 사람에게 달려 있습니다 . 만약 에이전트가 웹 페이지를 제대로 읽기 위해 자바스크립트 프레임워크를 역분석하기 시작한다면 , 그건 에이전트가 잘못된 프레임워크를 선택했다는 좋은 징조입니다 .
