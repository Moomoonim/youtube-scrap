NVIDIA의 첫 번째 AI 및 데이터 과학 서밋에 참석해 주셔서 정말 감사합니다. 오늘은 데이터 준비 및 ETL 파이프라인 속도 향상부터 그래프 분석 확장, 머신 러닝 모델의 정확도 향상, 대규모 언어 모델 파이프라인에 벡터 검색 통합에 이르기까지 모든 것을 다루는 환상적인 기술 세션들을 준비했습니다. 하지만 기술적인 세부 사항에 들어가기 전에, 좀 더 높은 차원에서 가속 데이터 과학이란 무엇인지, 어떻게 우리가 매일 사용하는 도구와 구축하는 도구에 가속 데이터 과학을 통합할 수 있는지, 그리고 왜 이것이 데이터 과학 산업과 전반적인 실무의 미래 방향이라고 확신하는지에 대해 이야기해 보고 싶었습니다. 마지막 질문에 대한 답은 아마도 가장 쉬울 것 같습니다. 데이터 과학 모델과 데이터 준비에 필요한 데이터와 컴퓨팅에 대한 수요는 엄청난 속도로 증가하고 있습니다. 추천 시스템을 구축하는 팀과 같은 프로젝트를 보면, 수천만 명의 사용자와 수십만, 심지어 수백만 개의 콘텐츠가 있다고 말합니다. 두 그룹의 교차곱을 취하고 가능한 모든 상호 작용을 살펴보고 싶다면, 수조 개의 항목으로 이루어진 데이터 세트를 처리해야 하는 상황에 직면하게 될 것입니다. 이 경우 모든 데이터를 준비하고, 모델을 실행하고, 가능한 한 빨리 결과를 반환하여 사용자가 최신 경험을 얻을 수 있도록 해야 합니다. 또는 대규모 언어 모델을 생각해 보세요. 얼마 전까지만 해도 수십억 개의 매개변수를 가진 모델은 공상 과학 소설의 영역이라고 생각했지만, 오늘날 많은 사람들이 70억 개, 700억 개, 심지어 그보다 더 큰 매개변수를 가진 모델을 실제로 사용하고 있습니다. 이러한 모델은 새로운 토큰이나 문장을 생성하기 위해 엄청난 양의 컴퓨팅 작업을 수행해야 합니다. 데이터 과학의 전통적인 응용 분야인 예측을 생각해 보세요. 얼마 전까지만 해도 월별 재고 예측이 가능했지만, 이제는 주별, 일별로 바뀌었고, 이제는 시간별, 실시간 예측을 통해 물류상의 갑작스러운 수요 변화나 재고 부족 문제에 대응해야 합니다. 이러한 모델에 대한 요구 사항은 증가하고 있지만, 모델을 자주 실행해야 하는 요구는 훨씬 더 빠르게 증가하고 있습니다. 따라서 데이터는 데이터와 컴퓨팅 요구량은 계속해서 급증하고 있습니다. 사기 탐지, 매일 전국에서 발생하는 수십억 건의 신용카드 거래, 유전체 분석, 네트워크를 통과하는 모든 패킷에 정교한 모델을 적용해야 하는 사이버 보안 등 모든 분야에서 동일한 현상이 반복되고 있습니다. 컴퓨팅 및 데이터 요구량은 계속 증가하고 있지만, 안타깝게도 모의 법칙과 단일 스레드 CPU 성능은 이러한 성장을 따라가지 못하고 있습니다. 매년 데이터 센터 규모를 두 배로 늘려야 하는 상황에서 모델이 처리해야 하는 데이터 양을 따라잡을 수는 없습니다. 얼마 전까지만 해도 CPU 컴퓨팅 성능이 매년 매우 빠르게 성장했지만, 이제는 그 속도가 둔화되어 과거 50%에서 연간 10% 정도로 떨어졌습니다. 하지만 다행히도 가속 컴퓨팅은 지속적으로 발전하고 있으며, 매년 1.5배 이상의 증가를 보이고 있습니다. 특히 대규모 언어 모델 추론과 같은 주요 응용 분야에서는 이러한 증가세를 확인할 수 있습니다. 지난 10년간 대규모 언어 모델의 성능이 1,000배 증가했습니다. 이는 단순히 따라잡는 것을 넘어 모의 법칙이 약속했던 것을 뛰어넘는 수치입니다. 이러한 발전의 비결은 비밀이 아닙니다. 바로 특수 애플리케이션에 맞춰 하드웨어와 소프트웨어를 함께 발전시켜 나가는 데 있습니다. 30년 전에 결정된 고정된 명령어 세트를 사용하는 범용 플랫폼을 구축하는 대신, 새로운 하드웨어 기능을 빠르게 추가하고 명령어 세트를 변경하며 모든 것을 통합할 수 있도록 완벽한 소프트웨어 스택을 제공하는 것입니다. 이 모든 것은 AI, 데이터 과학, 데이터 처리와 같은 특수 애플리케이션을 목표로 삼아 최적의 플랫폼을 구축하는 데 중점을 두고 있습니다. 하지만 매년 새로운 하드웨어 기능이 빠르게 출시되는 상황에서 개발자들이 이러한 생태계에 참여하려면 완벽한 플랫폼이 필수적입니다. 바로 이러한 이유로 엔비디아는 항상 풀 스택 기업으로서의 정체성을 유지해 왔습니다. 최고 수준의 GPU, NCK, 인피니트 밴드 스위치, 엔비 링크, 그리고 그레이스 세대와 같은 CPU까지, 하드웨어 구성 요소를 구축하는 것부터 시작하지만, 이러한 구성 요소들을 소프트웨어와 결합하는 것이 무엇보다 중요합니다. 이러한 저수준 성능 라이브러리를 사용하면 엄청난 속도로 IO에 액세스 하거나 GPU 클러스터에서 오케스트레이션할 수 있습니다. 이 모든 것은 개발자가 자신에게 가장 적합한 수준에서 스택에 접근할 수 있도록 해야 합니다. 예를 들어 의료 영상용 Monai나 대규모 언어 모델용 Nemo와 같은 애플리케이션 프레임워크를 사용하는 경우, 전체 스택이 함께 구축되어 있으므로 대규모 애플리케이션에 배포하고 코드를 거의 작성하지 않을 수도 있습니다. 또는 가속 라이브러리 수준에서 접근하여 Rapids 데이터 과학 스택을 사용하여 이 플랫폼에서 Python 코드를 획기적으로 가속하거나 CUDA C++ 수준에서 더 낮은 수준으로 작업할 수도 있습니다. 개발자가 자신에게 가장 적합한 수준에서 스택에 참여할 수 있도록 하는 것이 바로 저희의 철학이며, 이것이 저희가 수년간 개발해 온 목표입니다. 특히 데이터 과학에 적용할 때, 저희는 보통 이 다이어그램과 같은 것을 떠올립니다. 저는 수년간 실무 데이터 과학자로 일했고, 그 후에는 데이터 과학자들을 관리했습니다. 그 기간 동안 제 삶은 왼쪽의 타이밍 다이어그램과 매우 비슷했습니다. 우리 모두 이런 기분을 잘 알죠. 멋진 아이디어가 떠올라서 새로운 데이터셋을 추가하고, 몇 가지 특징을 더해서 모델을 어제보다 더 좋게 만들겠다고 생각합니다. 코드를 작성하고 작업을 시작한 다음 기다리고, 커피 브레이크를 갖고, 문서를 읽고, 코드 리뷰를 하고... 시간은 계속 흘러가죠. 그러다 문득, 추가하고 싶었던 특징 하나를 빼먹었다는 걸 깨닫고, 몇 분 동안 코드를 다시 작성하고 작업을 재시작하고 또 기다립니다. 더 나은 모델을 만들기 위해 한 번 시도할 때마다 한 시간 이상 기다려야 하는 건 정말 답답하고 느린 반복 과정입니다. 그래서 결국에는 타협해서 데이터의 아주 작은 부분집합이나 일부만 사용해 보는데, 이는 대표성이 떨어지는 모델로 이어지고, 개선이 되는지 아닌지조차 불분명해지기 쉽습니다. 그래서 저희는 처음부터 데이터 과학을 위한 가장 빠른 플랫폼을 구축하는 것을 목표로 삼았습니다. 이것이 바로 저희 가속화된 데이터 과학 전략의 첫 번째 기둥이며, 이 다이어그램에 있는 모든 사람들을 한데 모으는 것이 핵심입니다. 오른쪽 다이어그램에서처럼 대기 시간을 몇 시간에서 몇 분으로 단축하면 훨씬 더 많은 다양한 특징 조합을 시도하고, 여러 모델을 구축하고, 동일한 모델의 100가지 변형을 실행하는 하이퍼파라미터 스윕을 수행할 수 있습니다. 오른쪽 다이어그램의 데이터 과학자는 하루 동안 수십 개 이상의 모델을 테스트할 수 있으므로, 매번 모델 반복마다 몇 시간씩 기다려야 하는 사람보다 훨씬 더 나은 결과를 얻을 수 있습니다. 이것이 바로 모든 데이터 과학자에게 매우 중요하다고 생각하는 환경이며, 세계에서 가장 빠른 데이터 과학 플랫폼을 구축하게 된 첫 번째 동기입니다. 하지만 이 모든 것은 엔드 투 엔드 플랫폼으로 구축해야만 가능합니다. 따라서 엔드 투 엔드 접근 방식은 가속 데이터 과학이라는 아이디어의 두 번째 핵심 요소입니다. 처음부터 Rapids CF와 같은 라이브러리를 사용할 수 있습니다. 이 라이브러리는 데이터 준비, ETL, 특징 추출, 병합, 조인 등 우리가 매일 데이터를 다루면서 수행하는 모든 핵심 작업을 가속화하는 데 매우 친숙한 파이썬 인터페이스를 제공합니다. 또는 동일한 라이브러리를 직접 사용할 수도 있습니다. 극도로 최적화된 코어를 사용하지만, Rapids Accelerator for Patchy Spark를 사용하면 Spark SQL 코드를 코드 변경 없이 그대로 가져와 GPU로 전환하여 엄청난 속도 향상을 경험할 수 있습니다. 이러한 모든 도구는 테이블 형식 데이터 처리, 텍스트 데이터 작업, Nemo 데이터 큐레이터 제품처럼 대규모 언어 모델을 위한 데이터 큐레이션 등 모든 작업에서 동일하게 작동합니다. 하지만 데이터 로딩 및 ETL 파이프라인에서 모델 학습에 이르기까지 엔드 투 엔드 프로세스를 고려해야 합니다. 즉, PyTorch, TensorFlow, Jacks 또는 기존 머신 러닝 모델과의 원활한 상호 작용이
