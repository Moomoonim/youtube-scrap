## 스크립트

데이터 엔지니어로서 제 업무는 BI 분석가가 업무를 수행할 수 있도록 올바른 데이터를 생성하는 적절한 파이프라인을 구축하는 것입니다. 이번 데모에서는 Amazon Q Developer를 사용하여 잘못된 데이터를 생성하는 파이프라인을 테스트하는 방법을 보여드리겠습니다. 먼저 BI 분석가가 발견한 버그를 재현하는 것부터 테스트 프로세스를 시작할 것입니다. OpenSearch에 저장된 문서 수를 세어보려고 하는데, 방법을 모르겠습니다. 이럴 때 Amazon Q를 활용하여 테스트 프로세스를 시작할 수 있습니다. OpenSearch 인덱스에 저장된 문서 수를 세는 방법을 알아보겠습니다. OpenSearch에서는 인덱스를 데이터라고 부르는데, 관계형 데이터베이스의 테이블과 같은 역할을 합니다. Amazon Q Developer를 사용하면 어떤 명령어를 사용할 수 있을까요? `get index name`, `SL stats`, 그리고 ` count` 명령어를 사용할 수 있겠네요. 자, 이 명령어를 복사해서 사용해 보겠습니다. 대시보드에서 이 명령을 실행할 수 있습니다. 개발 도구를 사용할 수 있기 때문입니다. 좋습니다. 명령을 입력하고 인덱스 이름을 ' movies'로 지정하겠습니다. 이 명령을 실행하여 문서 수를 확인해 보겠습니다. 현재 인덱싱된 문서는 4,971개입니다. BI 분석 도구에 따르면 5,000개의 문서가 저장되어야 하므로 이 과정에서 뭔가 문제가 발생하고 있는 것 같습니다. ID에서 원인을 찾아보겠습니다. 다시 ID로 돌아가서, 이 파이프라인을 위해 작성한 코드의 다른 버전을 실행하여 OpenSearch에 기록될 문서 수를 출력해 보겠습니다. 이를 위해 OpenSearch의 B API라는 기능을 활용할 것입니다. B API에서 인덱스와 통계를 추출하여 데이터베이스에 기록합니다. 이 로딩 프로세스의 동작을 다시 확인하기 위해 프로그램을 실행해 보겠습니다. 보시다시피 이 파일에서 5,000개의 문서가 로드되었습니다. 오픈 검색에서 문제가 발생한 건수는 4,971건으로, 콘솔 에서 확인했던 문제와 일치합니다. 이제 문제 해결 과정을 시작하여 원인을 파악해 보겠습니다. 오픈 검색에서 검색할 영화 목록이 담긴 파일을 조사해 보니, 일부 영화의 개봉일 필드 데이터 형식이 잘못된 것을 발견했습니다. 예를 들어, '구름 속 산책(A Walk in the Clouds)'이라는 영화는 개봉 연도가 누락되어 잘못된 데이터 형식을 사용하고 있습니다. 제 생각에는 오픈 검색이 잘못된 데이터 형식을 사용하는 영화들을 모두 저장하고 있는 것 같습니다. 하지만 오픈 검색 랩 환경에서 이 문제를 어떻게 해결해야 할지 모르겠습니다. 그래서 아마존 Q를 사용하여 문제의 원인과 해결 방법을 찾아보겠습니다. 아마존 Q에서 새 대화창을 열고 "오픈 검색에서 잘못된 날짜 및 시간 형식을 사용하는 문서를 건너뛰지 않도록 인덱스를 구성하는 방법"을 질문하겠습니다. 어떤 결과가 나올지 지켜보겠습니다. 일반적으로 권장 사항을 확인하려면 질문을 할 때 약간의 맥락을 제공해야 합니다. 그래서 저는 항상 OpenSearch나 DynToB를 사용하는 것처럼 맥락을 설정하는 방법을 설명합니다. 제공된 권장 사항을 검토해 보면 인덱스 매핑에서 'ignore mou format'이라는 매개변수를 사용할 수 있는 것 같습니다. 이제 인덱스 구성에 이 매개변수를 설정하여 문제가 해결되는지 확인해 보겠습니다. AWS 콘솔로 돌아가서 이 정보를 다시 확인해 보겠습니다. 새 매개 변수를 사용하려면 현재 매핑을 삭제해야 합니다. 전체 인덱스를 삭제하고 새 인덱스의 릴리스 날짜 필드에 해당 매개변수를 사용하겠습니다. 릴리스 날짜 필드는 여기입니다. 여기에 'ignore M format'을 입력하고 true로 설정합니다. 기본값은 false일 것으로 예상됩니다. 개발자가 OpenSearch 전문가가 아닌 이상 이러한 특수한 지식을 미리 알기는 어렵습니다. 저는 전문가가 아니므로 Amazon Q 개발자의 도움을 받을 수 있는 상황 중 하나입니다. 개발자들이 이런 삼중 공격 시나리오에서 작업할 때 지식과 경험의 격차가 있습니다. 그래서 새로운 매개변수를 사용하여 이 새로운 버전의 매핑을 삽입하고 IDE로 돌아가서 프로그램을 다시 실행해 보겠습니다. 방금 새로운 수정 사항을 적용했으니 GoLink 프로그램을 다시 실행해 보겠습니다. 콘솔을 지우고 메인 프로그램을 다시 실행하겠습니다. OpenSearch에서 5,000건의 읽기와 5,000건의 쓰기가 발생했습니다. AWS의 OpenSearch에서 실제로 저장된 숫자가 맞는지 다시 한번 확인해 보겠습니다. AWS 콘솔로 돌아가서 이전에 사용했던 통계 명령어를 다시 한번 사용하겠습니다. 이 명령어를 실행하면 인덱싱 측면에서 현재 OpenSearch에 5,000개의 문서가 저장되어 있습니다. Amazon Q의 도움으로 문제 해결에서 해결책으로 매우 빠르게 넘어갈 수 있습니다. 데이터 엔지니어로서 이러한 도구를 활용하는 것은 제 업무입니다. 생성형 AI를 활용하여 S 문제를 해결하는 능력을 향상시킬지는 모르겠지만, 데이터 엔지니어로서 제가 가진 지식의 부족한 부분을 채워줄 수 있는 완벽한 조합인 것 같습니다. 아마존 Q 개발자의 도움을 받아 이런 상황을 해결할 수 있을 것 같네요.
