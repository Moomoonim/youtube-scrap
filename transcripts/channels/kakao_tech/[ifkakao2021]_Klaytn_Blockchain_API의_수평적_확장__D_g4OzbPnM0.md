## 스크립트

안녕하세요. 그라운드 X에서 클레이트 블록체인을 개발하고 있는 에이단입니다.이 발표에서는 클레이튼 블록체인의 기능 중 API 서버로서의 기능을 수평적으로 확장시키기 위한 노력을 공유하려고 합니다. 최종적으로 만들어진 구조는 가벼운 기능을 수행하는 클레튼 노드들이 오토스케일되는 구조이고 저희는이를 클레튼 엔드 포인트 시스템이라 부르고 있습니다. 발표의 준서는 다음과 같습니다. 먼저 API 기능의 소평적 확장이 필요했던 배경을 공유해 드리고 개발 과정에 겪은 대표적인 어려움 세 가지와 극복한 방법을 이야기할 것입니다. 후반부에서는 현재까지의 개선 내용을 정리하고 앞으로 추가 개선해 나갈 발전 사항들을 말씀드리겠습니다. 그럼 클레턴 API 기능의 소적 확장이 필요한 배경부터 말씀드리겠습니다. 블록체인을 이용하는 서비스들은 클레이트 노드와의 연결이 필수적입니다. 클레이트 노드는 클레턴 P2P 네트워크에 속하여 다른 노드로부터 블록을 전달받고 그 안에 포함된 트랜잭션을 처리합니다. 트랜잭션을 처리하는 과정에 발생한 데이터는 블록과 함께 클레튼의 내부 데이터베이스에 저장됩니다. 블록체인 서비스들은 클레이트 노드의 API를 통해서 노드 내부에 저장된 데이터를 읽기도 하고 새로운 트랜잭션을 만들기도 합니다. 만약 한 블록체인 서비스에서 클레이트 API 사용이 계속 증가하고 있다면 어떤 준비를 해야 할까요? 클레이트 노드의 자원 사용이 지속적으로 과다하다면 스케일업을 고려해 볼 수 있고 좀 더 탄력적인 운영을 필요로 한다면 스케일하웃을 고려해 볼 것입니다.이 발표에서는 다음과 같이 스케일하웃이티 되는 상황에 대해서 이야기해 볼 것입니다.이 그림만 보면 단순히 클레이트 노드를 추가하면 될 것 같은데 생각보다 그 과정이 쉽지는 않습니다. 아직까지는 단일 서비스가 블록체인 API를 과도하게 사용하는 경우가 많지 않아서 클레이트와 같은 블록체인 노드를 수평적으로 확장하는 어려움은 그리 알려지지 않았습니다. 그런데 그라운드 X는 이런 고민을 조금 빨리 시작하게 되었습니다. 그 이유는 카스라고 불리우는 클레턴 API 서비스가 존재하기 때문입니다. 카스는 블록체인 개발을 쉽고 빠르게 할 수 있도록 도와주는 서비스입니다. 블록체인 서비스들이 직접 클레이트 노드를 운영하지 않더라도 카스를 통해서 클레턴 API를 사용할 수 있습니다. 블록체인 서비스가 카스를 향해서 클레이트 API를 요청하면 카스는 그라운드 X가 운영하는 클레튼 노드에게이 요청을 전달하여 처리합니다. 물론 카스는 클레이트 API 외에도 다양한 기능을 제공합니다. NFT나 FT를 위한 스마트 컨트랙트를 손쉽게 배포하거나 사용할 수 있는 API를 제공하기도 하고 개인 키의 생성이나 관리를 대신해 주기도 합니다. 블록체인 서비스 개발을 시작하시려는 분들은 클레튼api닷컴에 한번 접속해 보세요. 네. 이마 홍보고를 마치고 다시 수평적 확장 내용을 이어하겠습니다. 카스는 서비스 특성상 탄력적인 운영을 필요로 하고 내부 구속 요소들이 모두 오토스케일 가능한 구조입니다. 따라서 연결되어 있는 클레이트 노드도 사용량에 따른 탄력적인 운이 필요했습니다. 그러나이 과정에는 여러이 있었습니다. 클레턴 노드의 속평 확장에는 여러움 중 블록체인의 특성이 잘 드러나는 세 가지 이야기를 하려고 합니다. 첫 번째는 데이터베이스 복재의 어려움입니다. 클레이트 노드는 내부의 데이터베이스를 가지고 있습니다. 여기에는 블록 데이터뿐만 아니라 블록을 처리하는 과정에서 생기는 데이터도 포함하고 있기에 많은 스토리지 용량을 요구합니다. 만약 클레튼 사이프레스 메인넷의 노드를 가장 데이터가 많이 쌓이는 모드로 운영하면 현재 약 4.9바의 스토리지를 필요로 합니다. 따라서 클레이트 노드를 추가하기 위해서는 4.9T바의 데이터를 복재해야 하는데이 과정에 많은 시간이 소요되어 빠른 확장을 어렵게 합니다. 저희는 스토리지 복제 시간을 단축하거나 없애는 방법을 고민하였고 다음과 같은 아이디어를 적용하였습니다. 기본적인 개선 아이디어는 클레이트 노드에서 데이터베이스를 분리하는 것입니다. 그리고이 데이터베이스를 여러 노드들이 공유하게 되면 클레이트 노드가 추가되더라도 데이터베이스를 복제할 필요가 없습니다. 최근 대부분의 시스템은 데이터베이스가 분리되어 있는데 블록체인은 아직 로컬를 사용하는 경우가 많습니다. 블록체인의 철학상 각각의 노드들은 서로 다른 신뢰 주체가 운영한다고 가정하기에 데이터베이스를 공유하는 상황을 고래하지 않으며 작은 데이터를 빠르고 입고 쓰기에는 로컬 디비가 더 적합하기 때문입니다. 저희는 동일한 주체가 여러 노드를 효율적으로 운영해야 하는 상황이고 이에 적합한 리모트 DV를 도입하기로 했습니다. 클레턴의 경우 하나의 데이터가 평균 400바이츠의 크기를 가지며 수만 RPS 즉 초당 수만 건의 리드라이트 요청을 처리할 수 있는 성능을 필요로 했습니다. 또한 카스와 같은 서비스에 사용되기 위해서는 균일하고 낮은 레이턴시에 대한 요구 사항도 있었습니다. 균일한 레이터시 부분은 다음 장에서 추가 설명드리겠습니다. 오른쪽 그림은 클레이트의 기본 데이터베이스인 레벨의 내부 동작 방식입니다. 레벨 DB는 키밸류 스토리지이며 데이터를 디스크에 저장할 때 계층을 만들어 저장합니다. 새로운 데이터를 디스크에 저장할 때는 레벨 0에 저장하고 레벨 0에 설정된 용량이 가득 차게 되면 콤팩션 과정을 거치며 레벨 0에 저장된 데이터를 레벨 1로 내리게 됩니다.이 컴팩션 과정은 레벨이 증가해 가며 계속 이어지게 됩니다. 데이터를 읽을 때는 레벨에서 원하는 데이터를 찾고 없으면 다음 레벨을 탐색하게 됩니다. 만약 찾고자 하는 데이터가 레벨 3에 있다면 레벨 0부터 1, 2, 3까지의 모든 레벨을 대상으로 검색합니다. 이러한 방식은 데이터 쓰기를 빠르게 처리할 수는 있지만 중간중간 콤팩션 과정을 거치며 디스크 아이오를 많이 필요로 하고 데이터 읽기에는 균일하지 못한 레이턴시를 보입니다. 게다가 블록체인은 내부 데이터 구조의 특성상 병렬로 데이터를 읽기보다는 순차적으로 읽는 경우가 많아서 레이턴시가 누적되게 됩니다. 이러한 특성은 안정적인 서비스 레벨을 보장하기 어렵게 만들며 새로운 디비 탐색에 있어서 균일한 레이턴시도 중요한 요소로 생각되게 되었습니다. 저희는 클레이트의 성능 요구 사항을 만족할 수 있는 데이터베이스들을 찾기 위해 많은 검토를 진행했습니다. 키밸류 데이터베이스를 우선적으로 보았지만 내부 자료 구조 변경을 염두해 두고 관계형 데이터베이스를 검색해 보기도 했습니다. 그러나 하나의 데이터베이스만으로는 높은 RPS를 보장하면서도 읽기 요청에 대한 균일한 레이턴시를 만족하기가 쉽지 않았습니다. 그래서 저희는이 중 세 개의 데이터베이스를 함께 사용하는 방안을 뗐습니다. 가장 핵심적인 데이터베이스는 AWS의 다이나모디비입니다. 비교적 높은 RPS를 만족하면서도 균일한 일키 레이턴시를 가지고 있었습니다. 그러나 클레이트 노드가 최신 블록을 처리하는 작업에는 좀 더 빠른 응답 시간이 요구되었고 레디스를 캐시레이어로 사용하기로 했습니다. 그리고 다이나모 DB의 데이터 사이즈 제한으로 인해 S3를 추가적으로 사용합니다. 그 결과 다음과 같은 모습을 가지게 됩니다. 클레튼 노드들은 모두 동일한 데이터베이스를 공유하고이 데이터베이스는 세 종류로 나뉘어져 있습니다. 레디스는 데이터 중 가장 많이 사용되는 최신 상태 정보 데이터를 가지고 있습니다. 가장 빠른 성능을 가지고 있고 빈번하게 사용됩니다. 다이나모 DB는 클레이트 노드에서 사용하는 모든 데이터를 저장하고 있습니다. 그러나 400k바의 데이터 크기 제한이 있어 큰 데이터의 경우에는 S3에 추가적으로 저장하게 됩니다.이 경우는 자주 발생하지는 않고 주로 용량이 큰 블록을 저장하기 위해 사용됩니다. 이렇게 데이터베이스 복재의 어려움은 해결되었습니다. 그럼 다음 어려움으로 넘어가 보겠습니다. 다음은 채신 블록 동기화의 어려움입니다. 앞에 소개한 데이터베이스 공유 방안을 적용한 이유에 추가적으로 개선된 문제점입니다. 다음과 같이 두 개의 클레이트 노드가 하나의 데이터베이스를 공유하고 있는 상황입니다. 각 노드는 클레이트 네트워크에 속한 다른 노드들과 연결되어 있습니다. 각 노드는 P2P로 연결된 클레이트 네트워크 노드로부터 블록을 전달받아 처리하게 됩니다. 블록 처리는 데이터베이스에 새로운 데이터를 쓰는 과정을 포함하기에 두 개의 노드는 각각 블록 처리 연상과 데이터 쓰기를 수행하게 됩니다. 즉 불필요한 중복 작업을 하게 됩니다. 타이 각 노드가 저장하는 데이터는 완전히 동일하기에 여러 번 오버라이팅하더라도 인테그리티가 해손되지는 않습니다. 따라서 불필요한 중복 작업을 수행하기는 하지만 클레튼 API를 사용함에 있어서 오류가 발생하지는 않습니다. 그런데 사용성 측면에서 바라보면 클레턴 API 사용자가 혼란을 겪을 수밖에 없는 상황이 발생될 수 있습니다. 각 클레이트 노드는 현재 블록 번호를 내부적으로 관리하고 있으며 새로운 블록을 P2P 네트워크로 전파받고 문제 없이 처리한 이후에이 블록 번호를 갱신하게 됩니다. 이렇게 현재 블록 번호를 갱신하는 과정은 네트워크 지연이나 노드 내부의 캐시 상태 등에 따라 편차가 발생할 수 있습니다. 그래서 이로부터 동기와 문제를 유발하게 됩니다. 예를 들어 두 개의 노드를 함께 사용하고 있는 블록체인 서비스는 최신 데이터를 조회하는데 혼란을 겪을 수 있습니다. 최신 블록을 조회하는 API를 빠르게 연속적으로 호출하면 요청이 분배되는 방식에 따라 현재 블록 번호가 1이었다가 2가 된 이후에 다시 1이라 응답받을 수 있습니다. 많은 클레턴 API들이 현재 블록 보너를 기준으로 동작하는 방식을 제공하기 때문에 블록체인 서비스가이 방식을 사용하는데 많은 불편함을 초래할 수 있습니다. 이런 불필요한 중복 작업의 수행과 그리고 그로 인해 발생하는 동기와 문제를 해결하기 위해서 클레이트 노드의 역할을 분리하는 접근법을 택했습니다. 블록 프로세싱을 담당하는 노드를 패처라고 이름 붙였습니다. 패처는 API 서버의 기능은 수행하지 않고 블록을 처리하는 역할만 담당합니다. 블록을 처리하는 과정은 새로운 데이터를 쓰는 작업을 포함하기에 유일하게 데이터베이스에 대한 쓰기 권한을 부여받습니다.
