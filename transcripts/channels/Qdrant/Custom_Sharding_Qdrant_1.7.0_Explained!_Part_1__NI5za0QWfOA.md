## 스크립트

안녕하세요 여러분, 벡터 공간 토크로 돌아왔습니다! 오늘은 Quadrant에서 멋진 기능들이 가득한 1.7 버전을 출시해서 여러분과 함께 이야기 나눠보려고 합니다. 오늘은 이 기능들을 중심으로 세 가지 주요 특징을 살펴보겠습니다. 첫 번째는 커스텀 샤딩, 두 번째는 희소 벡터, 그리고 세 번째는 디스커버리 API입니다. 이번 영상에서는 Quadrant의 CTO인 Andre V와 함께 커스텀 샤딩에 대해 이야기 나눠보겠습니다. 그럼 바로 시작해 볼까요? 그리고 혹시 이 멋진 티셔츠를 원하시는 분들을 위해 알려드립니다. Quadrant에서 지금 엄청나게 많이 배포하고 있어요! Andre, 커스텀 샤딩이란 무엇이고 왜 중요한가요? 안녕하세요 여러분, Quadrant는 이미 오래전부터 샤딩 기능을 제공해 왔습니다. 이 기능을 통해 단일 노드를 넘어 원하는 만큼 머신을 생성하고 데이터를 자동으로 분산시킬 수 있습니다. 하지만 한 가지 제약 사항이 있었습니다. 샤드를 한 번 생성하면 컬렉션 내에서 추가 샤드를 만들거나 삭제할 수 없다는 것이었습니다. 샤드를 사용하면 단순히 이동하거나 복제본을 생성할 수 있습니다. 어느 정도 규모에서는 괜찮지만, 그 이상으로 확장하여 대규모 배포를 하려면 사용자 지정 샤딩이 필요합니다. 사용자 지정 샤딩은 데이터를 저장할 샤드를 지정하는 키를 사용할 수 있도록 해줍니다. 데이터를 업로드할 때 이 키를 지정하면 Quadrant가 자동으로 데이터가 저장될 머신을 인식합니다. 반대로 검색할 때도 마찬가지입니다. 하나 또는 여러 개의 샤드를 지정하면 Quadrant가 해당 데이터를 찾을 위치를 자동으로 파악하여 클러스터의 모든 머신에 결과를 요청하지 않고 오버헤드를 최소화 하고 성능을 극대화합니다. 네, 이게 기본적인 C 언어 설명입니다. 제가 제대로 이해했다면, 화면에 표시되는 ' 샤드 키'나 '내 샤드'와 같은 키를 통해 원하는 샤드를 정확하게 지정할 수 있다는 말씀이시죠? 그런데 이 기능의 확장성과 동적 확장성에 대해 궁금합니다. 예를 들어 갑자기 샤드 용량이 증가할 경우 어떻게 처리되는지 알고 싶습니다. 제가 너무 많은 정보를 쏟아냈네요. 뭔가 특별한 게 있는 것 같은데, 저희와 이야기하고 싶으신 것 같네요. 네, 맞습니다. 그래서 저희는 샤드 생성과 샤드 삭제를 위한 두 가지 새로운 API 엔드포인트를 도입했습니다. 컬렉션을 구성하여 사용자 지정 샤딩을 지원하도록 설정하면 재시작이나 다운타임 없이 동적으로 샤드를 생성하거나 삭제할 수 있습니다. 이를 통해 데이터에 3단계 격리 수준을 제공합니다. 기존에는 컬렉션 기반 격리와 멀티 테넌시 설정을 위한 리소스 기반 격리가 있었는데, 이제 리소스 기반 격리를 통해 단일 컬렉션을 사용하면서도 클러스터 내 샤드 배치를 더욱 정확하고 정밀하게 조작하고 사용자 지정하여 오버헤드를 최소화할 수 있습니다. 이 책에서는 특히 Cassandra를 사용해 본 적이 없거나 익숙하지 않은 분들을 위해 샤딩이 어떤 문제를 해결하는지 설명드리겠습니다. 몇 가지 시나리오가 있는데, 첫 번째는 지역 기반 데이터 배치입니다. 전 세계에 고객이 있다고 상상해 보세요. 어떤 고객은 미국 데이터를 조회하고 싶어하고, 또 다른 고객은 유럽 데이터를 조회하고 싶어합니다. 동일한 클러스터 내에서 이를 구현하려면 데이터 위치에 따라 샤드 키를 할당하면 됩니다. 유럽용 샤드, 아시아용 샤드, 미국용 샤드 등을 각각 할당하는 것이죠. 각 고객은 자신이 관심 있는 지역의 데이터만 조회할 수 있습니다. 이렇게 하면 대륙 간 데이터 전송으로 인한 비용 낭비를 줄일 수 있습니다. 동시에 모든 데이터를 한 곳에서, 하나의 컬렉션, 하나의 클러스터에서 관리할 수 있고, 심지어 여러 지역에 걸쳐 데이터 복제까지 가능합니다. 특히 의료 분야에서 일하는 분들 중에는 HIPOC 규정 준수 등의 이유로 캐나다의 의료 관련 데이터를 외부로 유출할 수 없는 경우가 있습니다. 아무리 글로벌 기업이라도 캐나다 데이터를 안전하게 보관해야 하죠. 이런 경우에 이 솔루션이 매우 유용할 것 같습니다. 그렇죠? 네, 바로 이런 이유 때문에 데이터 관리가 더욱 중요해지는 것입니다. 다른 지역에서도 접근 가능하지만 특정 머신에 위치한 특정 샤드에만 데이터를 보관하고 싶고, 해당 지역을 벗어나지 않도록 하고 싶습니다. 이것이 첫 번째 사용 사례였고, 두 번째 사용 사례는 시간 기반 데이터 배치입니다. 지역 설정과 유사하지만, 예를 들어 데이터 스트림이 있고 최신 업데이트에만 관심이 있다고 가정해 보겠습니다. 전체 기록을 인덱싱할 필요 없이 지난주 데이터만 필요한 경우, 날짜 별로 샤드를 구성하면 모든 최신 업데이트가 하나의 샤드에 저장됩니다. 그리고 다음 날이 되면 오래된 샤드를 사용 중지하면 지연 없이 즉시 삭제됩니다. 특정 시점을 지정하여 삭제할 필요 없이 전체 샤드를 한 번에 삭제할 수 있기 때문입니다. 특히 트래픽이 많은 소셜 미디어 플랫폼에 유용합니다. 이런 유형의 데이터를 다루는 회사들이 그렇죠. 네, 그럼 마지막으로 말씀드린 사용 사례, 또는 샤딩을 사용하는 또 다른 이유는 인덱싱을 더 효과적으로 제어할 수 있다는 점입니다. 정확히 말하자면, 검색과 인덱싱 시간을 분리하는 데 있어 핵심적인 요소입니다. 예를 들어, 인덱싱 작업을 많이 처리할 수 있는 고성능 CPU와 메모리를 가진 머신이 있다고 가정해 보겠습니다. 하지만 이런 머신은 비용이 많이 들고 항상 가동될 필요는 없습니다. 이럴 때 특정 머신을 위한 샤드를 생성하여, 이 고성능 머신에서 인덱스를 생성한 다음, 데이터를 처리하도록 설계된 다른 머신으로 샤드를 전송할 수 있습니다. 이 다른 머신은 높은 처리량을 가질 수 있지만 CPU 나 CPU 용량은 고성능 머신만큼 높지 않을 수 있습니다. 또한, 최근 버전에서 스냅샷 기반 샤프 전송 기능을 구현했기 때문에 이러한 방식이 가능해졌습니다. 즉, 사용자 지정 샤딩 때문이 아니라 최신 릴리스에서 도입된 기능입니다. 스냅샷 기반 샤딩이 정확히 뭔가요? 이전에는 클러스터 내의 머신 간에만 데이터를 전송했는데, 이제는 인덱스를 생성한 상태에서도 데이터를 전송할 수 있네요. 오, 좋네요. 데이터가 많은 경우에 딱 좋을 것 같아요. 기존의 일반 샤딩 방식과 비교했을 때, 어떤 규모에서 샤딩을 사용하는 게 좋을까요? 데이터가 단일 머신에 저장되지 않을 정도라면 샤딩이 매우 유용합니다. 샤딩을 사용하면 데이터를 정밀하게 제어할 수 있기 때문에 엄청난 규모의 배포 환경이 아니더라도 충분히 활용할 수 있습니다. 하지만 대규모 배포 환경에서는 데이터를 정밀하게 관리하기 위해 샤딩을 사용하는 것이 필수적이죠. 소규모 배포 환경에서도 충분히 유용합니다. 네, 이해가 되네요. 벡터 크기는 상관없나요? 아니요, 모든 벡터를 사용할 수 있습니다. 좋습니다. 네, 이 정도면 충분할 것 같네요. 사용자 지정 샤딩에 대해 더 자세히 설명해 주실 부분이 있을까요? 네, 이쯤에서 마무리하죠. 그럼 어떻게 시작하면 될까요? 샤딩 방식을 명시적으로 지정해서 컬렉션을 생성하면 됩니다. 네, 이제 사용 가능합니다. 물론 1.7 버전으로 업그레이드하는 것도 잊지 마세요. 당연히 그래야겠지만, 혹시 모르니 미리 말씀드리는 게 좋겠죠. 요즘 세상에 너무 자세히 설명하는 건 지나치지 않으니까요. 안드레, 시간 내서 새로운 기능에 대해 설명해주셔서 감사합니다. 정말 재밌을 것 같네요. 혹시 사용해 보시고 후기를 남겨주시는 분이 있다면 티셔츠를 보내드리겠습니다. 저희는 커뮤니티에서 어떤 활동을 하는지 듣는 걸 좋아하거든요. 그러니 언제든 연락 주셔서 어떻게 생각하시는지 알려주세요. 그리고 혹시 안드레가 밤에 할 일이 생길 수 있도록 PR을 제출해 주실 수도 있겠네요. 그럼 나중에 뵙겠습니다. 감사합니다.
