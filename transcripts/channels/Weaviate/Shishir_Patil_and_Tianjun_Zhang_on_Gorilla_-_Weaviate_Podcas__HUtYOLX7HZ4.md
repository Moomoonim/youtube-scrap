Gorilla의 탄생 배경에 대해 간략하게 말씀해주시겠어요? 네, 물론입니다. 작년 말, 아마 2022년 11월이나 12월쯤이었던 것 같습니다. 당시 Char가 큰 인기를 끌었고 많은 사람들이 Char를 사용하려고 시도하고 있었죠. 저희도 포함해서, 초기 사용자로서 곧 깨달은 것은 이러한 도구들, 특히 채팅 방식의 도구들은 LMS 기술의 가능성을 보여주는 데는 좋았지만, 미래의 LMS는 이런 모습이 아닐 거라고 생각했다는 점입니다. LMS는 강력한 도구이긴 하지만, 결국 도구일 뿐이죠. 이제는 더 많은 작업을 처리하기 위해 다른 도구들과 상호 작용해야 합니다. 컴퓨터 과학에서 도구들이 서로 상호 작용하는 방식은 API 호출을 통해서입니다. 바로 그 아이디어에서 ' 이 도구는 다른 API와 통신해야 한다'는 생각이 나왔습니다. 그렇게 코릴라가 시작되었죠. 네, 정말 멋지네요. 영상 데모에서 CLI를 사용하는 방법을 보여주셨는데, 자연어로 " S3 버킷에서 고릴라 데이터셋을 다운로드하고 싶다"라고 요청하는 예시가 있었죠. 이러한 모든 API 요청과 중간 조정 과정은 모두 코릴라가 처리합니다. 모델과 T, 그리고 우리가 버클리에서 만났을 때 당신 이 GitHub CLI를 보여주면서 GitHub CLI 요청을 어떻게 포맷하는지 알려줬던 게 기억나요. Gorilla를 사용해서 탐구하기 시작한 특정 API에 대해 좀 더 자세히 이야기해 줄 수 있을까요? 네, 저희는 박사 과정생이자 머신 러닝 연구원으로서 논문 작성을 위해 처음에는 Hugging Phase 모델, TensorFlow, TorchUp을 선택했습니다. 이러한 모델들은 머신러닝 분야에 특화되어 있고, 보통 이미지 분류에 사용하는 모델이 무엇인지는 알지만 정확히 어떤 모델을 원하는지는 모르는 경우가 많습니다. 특히 모델 크기에 대한 구체적인 요구 사항이 있을 수 있습니다. 예를 들어, 1천만 개 미만의 파라미터를 가진 작은 모델을 원한다거나, 특정 최신 패밀리를 원한다거나 하는 식이죠. 이러한 제약 조건도 논문 작성에 도움이 됩니다. 그리고 나서 저희는 일반 사람들이 어떤 API를 사용해야 할지 잘 모르는 상황을 고려하여 API를 개발하는 방향으로 나아가고 있습니다. 시시르와도 잠깐 이야기를 나눴던 게 기억나네요. 특히 GitHub 관련해서요. 지난 금요일에 프로젝트 베이스를 확인하고 싶을 때, 대략적인 명령어는 알지만 정확한 명령어는 모르는 경우가 있잖아요. Kubernetes나 AWS 같은 것도 마찬가지고요. 그래서 두 번째 개발 단계에서는 특히 Gorilla SI를 활용해서 Linux 명령 줄, GitHub, AWS Ager에 집중하고 있습니다. GCP 관련 지원도 받고 있고요. 정말 마음에 들어요. 예전에는 팟캐스트 썸네일 이미지를 만들어서 웹사이트에 투표 요청을 보내곤 했는데, 새 브랜치를 만들고 거기에 넣는 과정이 꽤 번거로웠거든요. 그런데 Gorilla 모델을 사용하면 이런 과정이 훨씬 간소화될 것 같아요. 앞으로 Gorilla SI를 더 자세히 활용해 보고 싶습니다. Gorilla는 we8 API를 지원하지만, 좀 더 자세히 살펴보고 싶습니다. Gorilla 문서에서 언급하신 것처럼 Torch Hub, TensorHub, Hugging Face 같은 도구들을 사용하면 원하는 모델을 지정하고 제약 조건을 설정할 수 있습니다. 예를 들어, ImageNet 정확도가 85% 이상인 ResNet을 사용해야 하지만 파라미터 수는 2천만 개 미만이어야 한다는 식이죠. 그래야 서비스 비용 부담을 줄일 수 있으니까요. 그리고 GitHub, Kubernetes 같은 API도 있는데, Kubernetes, GitHub 클라우드 스토리지, 다운로드 등에 대한 API는 어떻게 사용하는지 설명해 주시겠어요? 모델 추론, 특히 Hugging Face 같은 도구에서 적절한 모델을 선택하는 과정은 복잡하고 여러모로 비슷합니다. 예를 들어, Gorilla를 통해 제공하는 머신러닝 API들을 살펴보면, 하나의 작업에 대해 거의 동일한 기능을 수행하는 다양한 모델들이 존재하는데, 각 모델마다 약간의 차이가 있습니다. 자, 그러니까 예를 들어, 제가 광학 감지 모델을 가지고 있는데, 하나는 동물용이고 다른 하나는 식물용일 수 있다고 가정해 볼게요. 아니면, 거의 똑같은 모델이라도 하나는 Res 18 백본을 쓰고 다른 하나는 Res 50 백본을 쓰는 식으로요. 이렇게 유사한 API들을 구분해내는 게 꽤 흥미로운 점이죠. 왜냐하면, Stripe 결제 API 와 GCP API를 구분해 보라고 하면 어떤 면에서는 쉬울 수도 있어요. 도메인도 다르고, 기능도 다르고, 방식도 다르니까요. 하지만 이렇게 매우 유사한 두 API를 구분하고 제가 제시하는 제약 조건을 만족시킬 수 있냐고 묻는 건 꽤 까다롭고 어려운 일이죠. 그래서 저희가 만든 초기 API 벤치마크가 꽤 까다로운 거예요. 현재 존재하는 다양한 API들 사이의 차이점을 찾아내야 하니까요. 앞서 언급했듯이, 그건 쉬운 일이 아니에요. 매일같이 "텍스트 음성 변환은 어떻게 하죠?"라고 묻는 건 아니지만, 연구자나 일반 사용자들은 T가 언급한 API들을 자주 사용하는 경향이 있죠. 그래서 시나리오에 따라 사용 사례가 매우 다릅니다. 어떤 경우는 더 실용적이고 유용하죠. 이번 경우는 일상적인 개발자나 일반 사용자 관점에서 접근했습니다. 다행히 저희는 Discord 커뮤니티를 통해 많은 피드백을 받고 있고, 많은 사용자들이 이 서비스를 이용하고 있습니다. 새롭게 알게 된 사실은 사람들이 Salesforce, ServiceNow, 그리고 오픈 API 사양 같은 API에 관심이 많다는 것입니다. 그래서 저희는 이러한 새로운 API들을 활용해 모델을 학습시키고 Gorilla 생태계에 통합하려고 노력하고 있습니다. API Zoo, 그리고 제가 본 바로는 Gorilla에 대한 반응이 꽤 많더군요. 이런 API 앱이 정말 좋은 것 같습니다. LLM용 스토어는 사람들이 정말 좋아하는 헤드라인 같은 거죠. 네, 그래서 사람들이 모델 API부터 시작해서, 특정 요청이 올바르게 포맷되었는지 평가하는 추상 구문 트리 같은 흥미로운 것들을 많이 하신 것 같아요. 하지만 청취자들이 궁금해할 만한 점이 있다면, API Zoo를 통해 Kubernetes나 GitHub CLI 같은 다양한 API 의 빅데이터 세트를 구축하고 계신데, 이런 API Zoo가 어떻게 발전해 나갈 거라고 생각하시는지 궁금합니다. 또 다른 흥미로운 점은 논문은 특정 시점의 스냅샷인 반면, 오픈 소스 프로젝트는 거의 매일 진화한다는 거죠. 그래서 저희도 처음 시작할 때부터 이 점을 염두에 두고 있었어요. 하지만 동시에 벤치마킹할 수 있는 기준이 되는 확고한 무언가가 필요하죠. 계속 변하는 목표물이 있다면, 어떻게 성과를 내고 있는지 알 수 없으니까요. 이런 생각을 하면서 프로젝트를 진행하신 것 같아요. 논문의 일부로 공개된 API 벤치마크는 다양한 모델들을 평가하는 기준이 될 수 있습니다. 그래서 최대한 쉽게 사용할 수 있도록 평가 스크립트를 제공하고, 학습 및 평가 분할 과정을 깔끔하게 정리해 두었습니다. 이를 통해 사람들은 다양한 모델 벤치마크 및 시장 분석 등을 시도해 볼 수 있습니다. 물론 이러한 방식은 천천히 발전해 나갈 것입니다. 한편, 우리가 알게 된 것은 우리 세 명이나 심지어 소수의 사람들만이 할 수 있는 것보다 훨씬 더 많은 API가 존재한다는 사실입니다. 따라서 사람들이 자신의 API를 공유하고, 이를 기반으로 모델을 학습시켜 더 많은 사람들에게 서비스를 제공할 수 있도록 하는 것이 목표입니다. 중요한 점은, 기존 API처럼 데이터 스크래핑, LLM(Learning Modeling Model) 이 데이터를 학습 하고 제공하는 것에 대한 법적 문제가 제기되는 것과는 달리, API는 분산되어야 한다는 것입니다. 특정 API를 사용하는 사람이 많을수록 더 많은 영향력을 행사할 수 있습니다. API Zoo는 API를 사용하는 사람들을 위한 플랫폼입니다. 즉, API를 사용하는 사람들을 위한 플랫폼이라는 점에서 인센티브 구조가 매우 잘 맞춰져 있다고 볼 수 있습니다. 실제로 많은 사람들이 API Zoo에 API를 등록하고, 다른 사람들이 이를 활용하여 API를 사용하고 그 위에 새로운 기능을 구축할 수 있도록 Swagger 문서와 튜토리얼을 제공하고 있습니다. 이것이 API Zoo의 기본 아이디어였고, API Zoo에 API를 등록하여 모델을 학습시키고, 다른 많은 사람들이 이 모델을 사용하여 빠르게 적응하고 작업을 완료할 수 있도록 하는 데 많은 관심이 있었습니다. 또한, 사람들은 매일 새로운 API를 개발하고, 기존 API 버전을 변경하기도 합니다. 하지만 API Zoo는 고정된 데이터 세트가 아니라, 사용자가 새로운 API를 개발하거나 기존 API 버전을 업데이트하고, API 사용 방식을 변경할 수 있도록 설계된 동적인 플랫폼입니다. 또 다른 흥미로운 질문은 API Zoo를 통해 사람들이 자유롭게 업데이트할 수 있게 되면서 언어 모델이 API 의 이러한 동적 변화를 가장 잘 지원할 수 있는 방법을 연구하는 것입니다. 네, 정말 흥미로운 주제라고 생각합니다. LLM 학습에 대해 더 자세히 알아보기 전에, Gorilla LMS 와 Open AI Funks의 차이점을 간단히 살펴보겠습니다. Open AI Funks는 JSON 형식의 인수를 JSON 딕셔너리 형태로 제공하는 방식인데, 이는 제로 샷 방식과 세밀한 조정 방식의 차이입니다. Open AI Funks 방식의 한계는 API에 특화된 LLM 학습 방식과 비교했을 때 어떤 점이 다를까요? 네, 좋은 질문입니다.
