MCP에는 서버가 클라이언트에게 완료를 요청할 수 있도록 하는 샘플링이라는 숨겨진 기능 또는 기본 요소가 있습니다. 이것은 무슨 뜻인가요? 즉, 서버는 SDK를 직접 제공할 필요 없이 클라이언트에게 어떤 모델이 구성되어 있는지 묻고 클라이언트가 서버에 완성된 모델을 제공하는 방식으로 독립적으로 모델을 사용할 수 있다는 의미입니다. 그럼 이건 무슨 역할을 하나요? 두 가지 기능을 합니다. 무엇보다도 , 이를 통해 고객은 보안, 개인정보 보호 및 비용을 완벽하게 제어할 수 있습니다. 따라서 추가 API 키를 제공하는 대신, 클라이언트가 이미 보유하고 있는 구독을 활용할 수 있습니다. 하지만 이것은 또한 두 번째 장점을 제공하는데, 여러 개의 MCP 서버를 흥미로운 방식으로 연결하면 전체 패턴이 매우 재귀적으로 변한다는 것입니다. 그게 무슨 뜻일까요? 좀 추상적이네요. 도구를 노출하는 MCP 서버를 사용할 수 있지만, 도구 실행 중에 하위 MCP 서버를 추가로 사용해야 할 수도 있습니다. 그리고 이와 유사한 시스템의 하류 어딘가에 , 아시아 트래커 서버가 있어서 완료 처리를 하려고 할 수도 있습니다. 하지만 샘플링을 사용하면 요청을 순차적으로 전달하여 클라이언트가 원하는 구독 요금제를 항상 완벽하게 제어할 수 있습니다 . 이 시스템은 상호 작용 비용에 대한 개인 정보 보호를 완벽하게 제어하며, 기본적으로 MCP 서버가 모델과 수행하고자 하는 모든 상호 작용을 관리합니다. 그리고 그것은 매우 강력한 연결 기능을 가능하게 하고, 이미 존재하는 MCP 에이전트를 구축하는 방식과 유사한 더욱 복잡한 패턴을 가능하게 합니다. 하지만 그건 샘플링이죠. 샘플링은 현재로서는 가장 흥미로운 기능 중 하나이지만, 안타깝게도 클라이언트 측 에서 가장 지원이 부족한 기능 중 하나라고 생각합니다 . 저희 첫 번째 파티 프로젝트 제품들을 위해서요 . 저희는 올해 어딘가에서 샘플링 행사를 진행할 예정입니다. 음, 그러면 여러분은 더욱 흥미로운 MCP 서버를 구축하기 시작할 수 있을 겁니다. 그리고 마지막으로 좀 더 흥미로운 기본 요소에 대해 이야기하고 싶습니다. 돌이켜보면 프로토콜을 구축한 사람 중 한 명으로서, 솔직히 말해서 이름을 정말 못 지었을지도 모르겠습니다. 저는 작명에 그다지 능숙하지 않거든요. 아마 발표 내내 그런 모습을 보게 되실 겁니다. 바로 ' 루트(roots)'라는 개념입니다. 루트는 흥미로운 부분인데, 예를 들어 오늘 제가 Git 명령어를 처리하는 MCP 서버를 구축한다고 가정해 보겠습니다. 저는 Git 자체를 직접 다루고 싶지는 않습니다. 저는 소스 코드 관리 명령어를 사용하고 싶지 않습니다. 저는 그 일들을 전혀 기억하지 못해요.
