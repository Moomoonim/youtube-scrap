# 대화 → 사양(PRD) → 코드 패턴 비교 브리핑

> Salesforce TDX 2026의 **Engine 사례**(Slack 대화를 PRD로 종합해 프런트엔드까지 자동 생성)와 같은 패턴을 다룬 코퍼스 내 영상 5편을 비교한다.
> 각 항목은 해당 영상의 발화에 근거하며, 수치·주장은 발표자 발화 그대로다. 한국어 자동번역 자막의 훼손 가능성은 인용 시 원 영상 확인이 필요하다.

---

## 0. 기준 사례 — Engine (Salesforce TDX 2026)

**출처**: 「Build the Future with Salesforce Headless 360 | TDX 2026 Keynote Replay」 — https://www.youtube.com/watch?v=aKsZdyyzcfU

패턴을 다섯 단계로 분해하면 다음과 같다. 이 문서의 비교축이 된다.

| 단계 | Engine의 구현 |
|---|---|
| ① 맥락 수집 | Slack 프로젝트 채널의 논의·API 계약·데이터 모델 |
| ② 사양 생성 | Slackbot이 종합해 **PRD** 작성 |
| ③ 조직 접지 | **Metadata Catalog MCP**가 기존 메타데이터를 의미론적으로 검색해 에이전트에 제공 |
| ④ 산출물 생성 | Agent for Vibe 2.0이 **React 앱**을 플랫폼 네이티브로 생성(GraphQL·신뢰 계층 상속) |
| ⑤ 운영 | 스모크 테스트 → Slack 배포 → 피드백 채널에서 세션 추적 ID로 관찰·개선 |

## 1. 가장 유사 — 「The Complete AI Transformation Blueprint」 (Cole Medin)

- **링크**: https://www.youtube.com/watch?v=OcTMwjqje5Q · 2026-07-21 · 약 26,329단어 (코퍼스 내 PRD 언급 최다 51회)

**벤더 플랫폼 없이 같은 흐름을 구현한 일반화 버전**이다. Engine이 Salesforce 스택 안에서 한 일을 Claude Code + Jira MCP로 재현한다.

- **② 사양 생성 단계가 동일하다.** "첫 번째 커맨드는 코딩 에이전트를 **비정형 대화에서 구조화된 PRD로** 이끄는 프로세스입니다. 탐색에서 구조로 가는 거죠." PRD를 "그린필드 개발이면 초기 작업 범위, 스프린트 계획이면 처리해야 할 티켓 전부"로 정의한다.
- **Engine보다 한 단계 더 나간다.** PRD를 Claude Code가 파싱해 개별 작업 단위(phase)로 쪼개고, **Jira MCP 서버로 티켓을 자동 생성**한다. "그러면 개발자들이 그냥 집어 들고 작업하면 된다"는 구조이며, 티켓을 집으면 담당자가 자동 배정되게 만들 수도 있다고 말한다. 결과적으로 **여러 개발자가 병렬로** 움직인다.
- **재사용·표준화 원칙**이 명시적이다: "같은 프롬프트를 **세 번 넘게** 쓰고 있다면 커맨드나 스킬로 만들어야 합니다. 재사용 가능한 워크플로로 만들어 **팀 전체의 표준**으로 삼는 것이죠." 이는 TDX Ep.3(에이전트 안전 배포)에서 나온 "스킬 공유로 개인 역량을 조직 자산화" 논지와 같은 계열이다.
- **AI 레이어**라는 개념으로 ①③에 해당하는 기반을 규정한다 — 글로벌 규칙(코딩 스타일·테스트 전략·로깅 전략), 커맨드, 스킬. "기존 코드베이스에 이 레이어가 없다면 **앞단에 시간을 많이 투자해 구축하라**"고 권한다.
- **바이브 코딩과 선을 긋는다**: "우리는 바이브 코딩을 하는 게 아닙니다. 계획과 검증을 통해 **우리 자신을 운전석에** 두기 때문입니다."

**Engine과의 차이**: Engine의 ③(조직 메타데이터 접지)에 해당하는 장치가 약하다. 대신 ⑤를 티켓·담당자 관리라는 조직 운영 쪽으로 확장했다.

## 2. 개념 정립 — IBM Technology 「Spec-Driven Development」

- **링크**: https://www.youtube.com/watch?v=mViFYTwWvcM · 약 1,103단어

이 패턴에 **이름을 붙이고 계보를 세우는** 짧은 해설 영상이다.

- 핵심 명제: "이전에는 코드를 작성하고 검토하는 것이 가장 어려웠는데, 이제는 **LLM에게 무엇을 이루고 싶은지 효과적으로 전달하는 방법**을 아는 것이 중요합니다. 이것이 사양 기반 개발입니다."
- **계보 정리**: 전통 개발은 코드 → 문서 순이었고, 테스트 주도 개발(TDD)은 테스트로 동작을 먼저 정의했다. 사양 주도 개발은 **그 순서를 완전히 뒤집어** 사양 → 설계 문서·요구사항 → 구현 → 코드로 간다. "TDD와 BDD를 훨씬 더 강화한 방식."
- **바이브 코딩과의 대조 예시**(사용자 인증 기능): 바이브 코딩은 "인증 페이지가 필요해"라고 말하는 것인데, 모델이 **30가지 방법 중 무엇을 고를지 알 수 없어** 여러 번 주고받다 보면 직접 짜는 것보다 오래 걸릴 수 있다. 사양 주도는 같은 LLM으로 먼저 요구사항을 만든다 — `/login` 엔드포인트, POST, 사용자명·비밀번호 두 변수, 실패 코드, 누락 시 처리, 그리고 **테스트 케이스("유효한 자격 증명 → 200")** 까지.
- 결론: "코딩 에이전트의 **모호성이 줄어들고**", 사양이 "구현·테스트 등 모든 후속 작업을 이끄는 **주요 산출물**"이 된다.

**용도**: Engine 사례가 왜 PRD부터 출발했는지에 대한 이론적 근거로 인용할 수 있다.

## 3. 개인 실천 — Google Developers 「The evolved developer」 (Muhammad Farooq)

- **링크**: https://www.youtube.com/watch?v=bvfTtLzWVPw · 약 6,308단어

조직이 아니라 **한 개발자의 작업 방식**에서 같은 패턴이 나타난 사례다.

- 방법: "저는 소프트웨어를 개발할 때 **먼저 사양서를 만들어 원하는 기능을 정리**하고, 그다음 세분화합니다."
- 근거: 사양 없이 맡기면 "시스템이 **원하지 않는 기능을 마음대로 추가**해 버릴 수도 있다"는 것. 스택이 자기 목적에 최적화돼 있지 않을 수 있으므로 "시스템에 무엇을 입력해야 하는지 정확히 알려줘야" 하며, 바로 여기서 **기술적 전문성이 중요해진다**고 본다.
- 역할 변화: 1차 버전은 크로스 플랫폼 버그 수정에 매달렸지만, "**두 번째 버전부터는 기술 관리자 역할**을 더 많이 하게 됐다. 정확한 디자인 사양을 먼저 생각해내고 Gemini·Cursor 등 여러 도구를 조합해 연구·구현·테스트했다." 노력은 더 들었지만 훨씬 빨랐고 기능도 나아졌다고 말한다.

**Engine과의 연결**: TDX 기조연설의 "나는 더 이상 한 명의 엔지니어가 아니라 엔지니어링 매니저"라는 발언이 개인 차원에서 어떻게 실현되는지 보여준다.

## 4. 역할론 — Cursor 「The New PM」 (Claire Vo)

- **링크**: https://www.youtube.com/watch?v=4CAFK-rc26A · 약 3,551단어

PRD라는 산출물 자체를 **역사적 조건의 산물로 재해석**한다.

- "PRD 같은 거요. **버튼 작동 방식까지 설명해야 하는** 복잡한 문서 말이에요. 이게 바로 **10년 전 엔지니어링이 얼마나 희소했는지**를 보여주는 예입니다. 그들은 버튼이 어떻게 작동하는지 스스로 알아낼 수 없었어요."
- 대비되는 현재: "**필요할 때마다 무한한 엔지니어링 지능**을 발휘할 수 있다고 상상해 보세요." 백로그도 범위 축소도 사양하고 "전부 배송하고 싶다"는 태도가 가능해졌다는 것.

**비판적 독해의 축**: 1번(Cole Medin)과 2번(IBM)이 "사양을 더 정교하게 쓰라"고 말하는 반면, 이 영상은 **사양 문서가 존재했던 이유 자체가 사라지는 중**일 수 있다고 시사한다. Engine 사례를 평가할 때 "PRD 자동생성은 과도기적 형태인가"라는 질문을 던질 수 있다.

## 5. 반례·경고 — Replit 「Agent 3 Livestream」

- **링크**: https://www.youtube.com/watch?v=WI-mA0SEnRk · 약 7,490단어

**이 패턴이 실패하는 조건**을 짚는 유일한 자료다.

- "사람들이 GPT나 Claude 채팅방에 가서 **엄청나게 큰 PRD 문서를 생성해 달라고 하는데, 그 문서의 모든 정보가 유용하거나 관련 있는 것은 아닙니다.** 그러면 **잘못된 맥락이 모델에 입력되는** 겁니다."
- 판단 기준으로 제시하는 질문: "이것이 유용한가, 간결한가, 그리고 **이 지침을 신입 개발자에게 주면 그가 실행할 수 있는가?**"
- 같은 영상에 **Slack을 인터페이스로 삼은 개인 비서 에이전트**(Alfred) 구축 사례가 나온다 — 노션 DB 접근, 해커뉴스 맞춤 도구, "모든 건 Slack을 통해 이루어진다". Engine이 Slack을 관문으로 쓴 것과 같은 발상이다.

**Engine과의 대조점**: Engine은 PRD를 **실제 API 계약·데이터 모델에서** 뽑아냈고 Metadata Catalog로 조직에 접지했다. 이 영상은 **접지 없는 대용량 PRD 자동생성이 오히려 해롭다**고 말한다. 즉 이 패턴의 성패는 문서의 분량이 아니라 **맥락의 정확성**에 달렸다는 반증 자료다.

## 종합 — 다섯 자료가 채우는 자리

| 자료 | 다루는 단계 | 이 패턴에 대한 입장 |
|---|---|---|
| Engine (TDX 2026) | ①~⑤ 전부 | 벤더 플랫폼으로 완결 |
| Cole Medin 워크숍 | ①②④⑤ + 티켓 분해 | 도구 무관하게 재현 가능, 커맨드·스킬로 팀 표준화 |
| IBM Spec-Driven | ② 개념 | 사양이 주 산출물, TDD를 뒤집은 계보 |
| Google 진화한 개발자 | ② 개인 실천 | 사양 없으면 원치 않는 기능이 붙음, 역할은 기술 관리자로 |
| Cursor The New PM | 역할론 | 사양 문서는 엔지니어링 희소성의 산물 — 조건이 바뀌는 중 |
| Replit Agent 3 | ②의 실패 조건 | 접지 없는 대용량 PRD는 잘못된 맥락 주입 |

**공통 명제**: 코드 생성이 쉬워질수록 병목은 **"무엇을 만들지 정확히 전달하는 일"** 로 이동한다(IBM). 그래서 조직은 대화·티켓·메타데이터 같은 기존 맥락을 사양으로 변환하는 경로를 만든다(Engine·Cole Medin).

**갈리는 지점**: 그 사양을 **더 정교하게 쓸 것인가**(IBM·Google·Cole Medin) 아니면 **사양 자체가 과도기적 형식인가**(Cursor). 그리고 사양의 품질은 분량이 아니라 접지에서 나온다는 경고(Replit)가 양쪽 모두에 적용된다.
