Port Key는 LLM을 더 쉽게 사용하고, 프로덕션 환경에서 LLM 서비스를 제공하고, 다양한 LLM으로 라우팅하여 비용을 절감하는 등 여러 가지 흥미로운 기능을 제공하는 혁신적인 회사입니다. 지금부터 이러한 기능들에 대해 자세히 알아보겠습니다. 먼저 Rohit, 팟캐스트에 참여해주셔서 정말 감사합니다. 저도 기쁩니다. Connor, 앞으로의 대화가 기대됩니다. 좋습니다. Port Key의 설립 비전, 그리고 해결하고자 했던 문제에 대해 이야기해 주시겠어요? 네, 좋습니다. 저는 지난 3년 동안 여러 회사에서 LLM 애플리케이션을 개발해 왔습니다. 애플리케이션을 개발하면서 깨달은 점은, 첫 번째 버전을 만드는 것은 매우 쉽다는 것입니다. 해커톤의 일환으로 시간 만에 가치 있는 무언가를 만들었다는 사실에 매우 흥분하게 되죠. LLM과 Vector DBS는 정말 강력한 도구이기 때문에, 우리는 그것을 세상에 보여주고 싶어 안달이 납니다. 그리고 그 순간, 실제로 작업을 시작하거나 프로덕션 환경에 배포하다 보면, 기존 엔지니어링 분야에서 해결되었던 많은 엔지니어링 과제들이 LLM 엔지니어링 분야에서는 해결되지 않았다는 것을 깨닫게 됩니다. 예를 들어, 로깅을 위해 DataDoG를 사용하는 데 익숙하지만, 이렇게 큰 문자열 덩어리를 DataDoG에 어떻게 저장할까요? DataDoG는 제대로 작동하지 않습니다. 마찬가지로 벡터 데이터베이스는 일반 데이터베이스와는 동작 방식이 다릅니다. 따라서 벡터 데이터베이스를 어떻게 모니터링하고, 앱의 안정성, 보안, 규정 준수를 어떻게 보장할까요? 이러한 많은 부분을 고려해야 합니다. 저는 DevOps의 핵심 레이어가 LLM 환경에 맞춰 구축되지 않았다고 생각합니다. 제가 자주 예로 드는 것은, 다른 모든 API는 성공 또는 오류라는 확정적인 결과를 반환하지만, LLM이나 벡터 데이터베이스는 모든 결과가 0에서 1 사이의 확률이라는 매우 예측 불가능한 특성을 가지고 있다는 것입니다. 따라서 모든 시스템은 확정적인 결과가 아닌 확률이라는 새로운 현실에 적응해야 합니다. 이러한 배경에서 저희는 LLM MOPS(Management of Operations and Practices) 회사가 필요하다고 생각했고, 과거에 일종의 선언문을 작성했습니다. 12월과 1월에 이것이 어떤 모습일지 논의했지만, 3월 초에 실제로 구축을 시작했습니다. 네, 정말 흥미로운 점들이 많습니다. 데이터 모니터링은 핵심 주제인데, LLM 운영과 ML 운영을 좀 더 명확하게 구분할 수 있을까요? 물론이죠. 매우 흥미로운 주제라고 생각합니다. 어느 정도는 서로 밀접하게 연결되어 있다고 생각합니다. LLM 운영이 ML 운영의 하위 개념이라고 말하는 사람들을 본 적이 있는데, 저는 조금 동의하지 않습니다. 핵심적인 차이점은 ML 운영이 서버에 더 집중하는 반면, LLM 운영은 서비스에 더 집중한다는 것입니다. ML 운영에서는 드리프트, 정확도 등의 지표가 있었지만, LLM 분야에서는 이러한 용어를 거의 들어본 적이 없을 겁니다. 자체적으로 핵심 기반 모델을 구축하는 경우가 아니라면 드리프트 등에 대해 걱정할 필요가 없습니다. 99%의 경우, 사전 학습되어 바로 사용할 수 있는 LLM 모델을 배포해서 사용하기 때문에, 모델 활용 자체에 더 신경을 쓰게 됩니다. API의 지연 시간은 얼마나 되는지, 정확도는 어느 정도인지, 즉 평가, 출력 유효성 검사, 재시도 지표 등 모든 것이 중요한 요소입니다. MLOPs 지표와는 달리, 이 두 지표는 많은 부분에서 차이가 있으며, 어떤 경우에는 매우 큰 차이를 보일 수 있습니다. LLM의 경우 테스트 데이터와 학습 데이터의 개념을 생각해 보세요. 대부분의 회사는 테스트나 학습을 전혀 하지 않고 그냥 API를 선택해서 데이터를 추가하기 시작합니다. 이것이 바로 MLOPs와 LLM, UPS의 가장 큰 차이점이라고 생각합니다. LLM 과 머신 러닝에 대한 좀 더 학술적인 주제로 넘어가기 전에, 저는 시장 현황에 대해 정말 궁금합니다. 어제 Eric이 WE8의 Latu를 살펴보고 있었는데, Replica를 사용해서 제공하는 방법도 봤고, Brev도 있고, Modal Banana처럼 서버 목록을 감싸서 사용하는 방법도 알고 있습니다. 다양한 모델을 실행할 수 있는 옵션이 너무 많아요. 모델 추론 API 시장의 현황은 어떤가요? 정말 놀랍다고 생각해요. 불과 1년 전이나 2년 전까지만 해도 모든 걸 직접 배포해야 했죠. 그래서 사람들은 SAG 메이커 같은 환경을 구축해서 직접 모델을 배포하고 테스트하는 데 매달렸어요. 할 일이 너무 많아서 모두가 6~8개월 동안 바쁘게 지내다가 뭔가 결과물이 나오면 거기서부터 시작하는 식이었죠. 하지만 추론 API 엔드포인트가 등장하면서 상황이 완전히 바뀌었어요. 이제 대부분의 기업은 배포만 하거나 다른 사람이 배포를 관리하도록 맡기는 것에 만족하고 있어요. GPU 속도를 어떻게 최적화하고 머신의 모든 코드를 어떻게 효율적으로 활용할지는 내 전문 분야가 아니니까 시간을 투자할 필요가 없다고 생각하는 거죠. 대신 이런 API를 활용해서 비즈니스 문제를 해결할 수 있어요. 그리고 바로 그런 점에서 모자이크( Mosaic)나 데이터 브릭스(Data Bricks)에서 아주 흥미로운 통계를 발표했던 것 같은데, 맞나요? 통계에 따르면 LLM(로컬 라이프사이클)은 지금까지 그 어떤 분야보다도 가장 빠르게 성장하고 가장 빠르게 도입되고 있는 부문일 가능성이 높습니다. 이는 이전에는 비즈니스 로직을 도입하기 전에 데이터 과학 및 머신 러닝 학습 및 테스트가 많이 필요했지만, 이제는 비즈니스 로직을 처음부터 도입하고 정확도, 지연 시간 또는 비용을 고려할 때 나중에 테스트 및 학습을 진행하는 방식으로 바뀌었기 때문일 것입니다. 질문에서 조금 벗어난 것 같지만, 추론 API 엔드포인트 덕분에 더 많은 기업이 Transformer 기술을 쉽게 활용할 수 있게 된 것은 분명합니다. 그 결과, 더 이상 기본적인 모델을 배포하는 데 그치는 것이 아니라, 다음 단계의 미세 조정이나 데이터 개인 정보 보호 또는 규정 준수 지표가 필요하게 되었습니다. 이러한 경우, 매우 저렴한 가격으로 이러한 서비스를 제공하는 다양한 기업들이 있습니다. 저희는 Banana Model과 같은 업체와 협력한 적이 있는데, 그들과의 협업은 매우 수월했으며, 그들은 이미 배포 전 단계의 모델을 보유하고 있다고 말했습니다. GPU가 정말 빠르게 보편화되면서 제가 직접 모든 GPU를 관리할 필요가 없어졌습니다. 사실, 저는 기업들이 거의 세 가지 계층으로 발전하고 있다고 봅니다. 첫 번째는 베어메탈 GPU를 제공하는 회사들입니다. 모델을 배포하고 학습시키는 방식이죠. 하지만 이건 초보자에게는 적합하지 않습니다. 머신러닝 전문가와 데이터 과학자가 이미 있고, " 좋아, 내가 직접 해보자"라고 생각하는 사람들을 위한 것입니다. 두 번째는 정보 회사들입니다. 모든 오픈 소스 모델을 배포하거나, 원하는 작업이나 미세 조정을 알려주시면 저희가 직접 처리해 드립니다. 일종의 관리형 모델 서비스라고 할 수 있죠. DeVix가 MPT 등을 통해 어느 정도 이런 서비스를 제공하고 있습니다. 그리고 세 번째는 오픈 소스 기반의 기업들입니다. 엔드 투 엔드 작업을 하는 경우, API 키만 관리하면 나머지는 모두 알아서 처리해 줍니다. 따라서 얼마나 깊이 있게 접근하느냐에 따라 거의 세 가지 계층으로 나눌 수 있다고 생각합니다. AI 회사로서 어떤 방향으로 나아가고 싶은지, 혹은 얼마나 성숙한지를 묻는다면, 회사마다 선택하는 기준이 다를 것 같아요. 네, 팟캐스트 후반부에서, 엔드 투 엔드 방식으로 모델을 구축하는 것과 언어 모델을 미세 조정하는 것 중 어떤 것을 더 선호하는지, 그리고 그에 대한 여러분의 생각을 좀 들어보고 싶습니다. 하지만 저는 우선 PortKey 제품에 대해 이야기하고 싶습니다. 정말 좋은 투어였습니다. 베어메탈부터 오픈소스 모델 실행, 또는 직접 미세 조정한 모델 실행까지 세 가지 레벨로 구성되어 있다는 점이 마음에 들었습니다. 배포는 제가 알아서 처리해 드리니 걱정할 필요가 없다는 점이 정말 흥미롭습니다. 이 시장에서 이런 방식이 등장했다는 게 정말 놀랍습니다. PortKey 투어에서 특히 인상 깊었던 점은, GBT 4, Anthropics Command Nightly, 그리고 클라우드를 사용하고 있는데 OpenAI 때문에 사용량 제한에 걸리고 있다는 것입니다. 그래서 여러 개의 LLM을 관리하는 방법에 대해 어떻게 생각하시는지 궁금합니다. 앱에서는 절대적으로 그렇습니다. 거의 이렇게 생각하시면 됩니다. 저는 기존 DevOps 세계에서 많은 유사점을 찾게 되는데, 기존 DevOps 세계에는 API 게이트웨이와 로드 밸런서라는 개념이 있습니다. 이제 우리는 이와 유사한 기능을 구현했습니다. AI 게이트웨이나 LLM 게이트웨이를 생각해 보세요. 이러한 게이트웨이는 연결되어 있으며, OpenCard의 여러 키 또는 여러 계정 간에, 또는 OpenCard와 Anthropic Games Store 간에도 로드 밸런싱을 수행합니다. 로드 밸런싱, 폴백, 재시도, 심지어 카나리 테스트까지 가능합니다. PortKey는 이 모든 것을 가능하게 합니다. 결국 우리는 폐쇄형 소스, 오픈 소스, Banana 등 모든 다양한 공급업체와 연결됩니다. 사용자는 하나의 엔드포인트에 호출하고, 이 호출이 어떻게 처리되기를 원하는지 구성을 정의하기만 하면 됩니다.
