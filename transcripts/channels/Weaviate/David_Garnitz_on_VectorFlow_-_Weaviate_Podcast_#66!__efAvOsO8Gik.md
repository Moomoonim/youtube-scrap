안녕하세요 여러분, VectorFlow 개발자 David Garnet과 함께한 Weave 팟캐스트 67번째 에피소드를 시청해 주셔서 정말 감사합니다. 본론 으로 들어가기 전에, David에게 팟캐스트에 참여해 주셔서 감사드리고, GitHub에서 VectorFlow에 많은 관심 부탁드립니다. 별점도 남겨주시면 감사하겠습니다. 오픈 소스는 언제나 환영받는 문화이며, 이 분야 에는 정말 흥미로운 아이디어들이 많습니다. 예를 들어 텍스트를 생각해 보세요. 텍스트에는 텍스트를 어떻게 청크할 것인가(메타데이터 추출 포함)과 같은 다양한 요소가 있습니다. 임베딩, 모델 추론, 그리고 Weave를 통해 Spark 커넥터나 gRPC API 등을 활용하여 벡터를 벡터 데이터베이스에 저장하는 방법 등 여러 가지가 있습니다. 이번 대화는 정말 즐거웠고, 여러분도 팟캐스트를 즐겁게 들어주셨으면 좋겠습니다. 그리고 이 영상 설명란에 있는 D Garnet의 오픈 소스 GitHub 저장소도 확인해 주세요. 위 비어 팟캐스트에 오신 것을 환영합니다! 벡터플로우(Vector Flow)의 창립자 데이비드 가넷을 모시게 되어 정말 기쁩니다. 벡터플로우는 데이터를 벡터 데이터베이스에 입력하는 방식을 혁신하고자 하는 매우 흥미로운 신생 기업입니다. 데이터 가져오기 및 수집과 관련된 모든 것을 혁신하고 있죠. 정말 다양한 주제를 다룰 예정이며, 엔드 투 엔드 스택을 제공합니다. 먼저 데이비드, 팟캐스트에 참여해 주셔서 감사합니다. 저도 초대해 주셔서 기쁩니다. 그럼 먼저 벡터플로우를 만들게 된 계기와 이 분야의 문제점을 어떻게 보고 계신지 여쭤보겠습니다. 좋은 질문입니다. 제 배경을 간략히 말씀드리자면, 대학원에서는 머신러닝 연구원이었고, SpaceX 와 Afirm 같은 회사에서 개발자 도구 및 인프라 구축 업무를 했습니다. 이후 FileRead라는 초기 단계 AI 회사에서 일하게 되었는데, 그곳에서는 엄청난 양의 데이터를 처리해야 했기 때문에 대규모 병렬화된 벡터 임베딩 파이프라인을 구축해야 했습니다. 그때 저는 팀원들과 함께 이 문제점을 직접 목격했습니다. 시장에 마땅한 솔루션이 없다는 걸 깨닫고 직접 만들기로 했죠. 정말 멋지네요. 아까 부하 테스트 같은 거 얘기했던 거 기억나요. 저희 Weave에서도 그런 사례를 많이 봐요. 엄청나게 많은 벡터를 입력하는 사람들이 있거든요. 수십억 개의 벡터 같은 거요. 이런 벡터 데이터베이스를 수십억 개씩 사용하는 것에 대해 좀 더 자세히 말씀해 주시겠어요? 이런 기회에 대해 어떻게 생각하시는지 궁금합니다. 두 가지 측면이 있다고 생각해요. 개인 메모 앱을 해킹하는 경우처럼 10만 개 정도의 벡터를 사용하는 경우도 있지만, 기업처럼 엄청난 양의 데이터를 다루는 경우도 있죠. 네, 맞아요. 저희 VectorFlow에서는 이런 데이터 검색 시스템이 보편화될 거라고 생각해요. 모든 대기업은 엄청난 양의 데이터를 보유하고 있으니까요. 외부 고객 대상 제품뿐만 아니라 내부 제품에서도 비용을 절감하고 속도를 높이기 위해 활용할 수 있습니다. 하지만 이 분야는 아직 초기 단계 이고 많은 기술이 성숙해야 하므로 대규모 데이터를 수집하고 스토어에 넣는 것뿐만 아니라 어떤 데이터가 관련 있는지 파악하는 데 큰 어려움이 있습니다. 특히 대기업의 경우 내부적으로 오래되고 쓸모없는 데이터가 많습니다. 따라서 데이터를 가져오는 것뿐만 아니라 어떤 데이터를 가져와야 하는지 파악하는 것도 어려운 과제입니다. 네, 확실히 그렇습니다. 아마도 이런 오래되고 쓸모없는 데이터를 처리할 수 있다면 좋을 것 같습니다. 벡터 데이터베이스로 데이터를 가져오는 것과 같은 논의가 있는데, 저는 LLM(로컬 라이브러리 관리자)이 어떤 클래스에 데이터를 넣어야 하는지 알 수 있다면 좋겠다고 생각합니다. 이 팟캐스트를 듣는 분들은 이미 알고 계시겠지만, Wevia는 클래스 추상화를 사용하여 특정 유형의 데이터를 분리합니다. 클래스별로 하나의 벡터 인덱스를 사용하는 식이죠. 따라서 LLM이 여러 소스에서 데이터를 가져올 때 어떤 클래스에 데이터를 넣어야 하는지 알 수 있다면 좋을 것 같습니다. 사람들이 흔히 구축하는 것은... 예를 들어 GitHub, YouTube, Slack 등에서 문서를 가져와 채팅하는 것처럼요. 그리고 이러한 문서들을 다른 클래스로 라우팅할 수도 있겠죠. 저는 이것을 하나의 부분으로 보고 있습니다. 또한 오래된 데이터 처리, 즉 문서 업데이트 처리도 또 다른 부분으로 생각합니다. 음, 그래서 우리 팟캐스트에서 이 모든 것을 처음부터 끝까지, 그리고 데이터 가져오기가 어떤 모습인지에 대해 합의점을 찾으면 좋을 것 같습니다. 소스에 연결하는 것은 PDF, Notion 리더, Google Drive 리더와 같은 것들이 있고, 텍스트 청킹 전략도 있습니다. 단순한 텍스트 분할기, 예를 들어 롤링 윈도우 청킹 같은 것들이 있고, 언어 모델이 텍스트 청크를 분석하고 의미적 공백이 있는 부분을 분할해 달라고 요청하는 LLM(Language Level Model)을 사용하는 방법도 있습니다. 메타데이터 추출 같은 것도 있는데, 일종의 레이어라고 할 수 있죠. 그리고 청크를 추출한 다음, 이 청크들을 모델 추론에 전달해서 벡터로 변환하는 거죠. 확실히 많은 혁신이 눈에 띄네요. 마지막으로, 이 벡터들을 Eva에 연결하는 게 모델 추론의 마지막 단계인 것 같아요. 이렇게 처음부터 끝까지 데이터를 벡터 데이터베이스로 가져오는 과정을 잘 설명한 것 같네요. 네, 좋은 개요라고 생각합니다. 저희도 연구와 여러 사람들과의 논의를 통해 알게 된 것 중 하나이자, VectorFlow에 적극적으로 반영하려고 하는 기능 중 하나가 바로 데이터를 벡터로 변환하기 전에 사전 처리하는 거예요. 단순히 메타데이터만 처리하는 게 아니라요. 메타데이터는 하이브리드 검색에 유용하긴 하지만, 업로드 속도가 느려지거나 다른 방법을 사용해야 하는 등의 단점도 있죠. 검색 알고리즘에 대해 말씀드리자면, 일부 사람들은 관련 정보를 청크에 넣기 위해 데이터를 전처리 하거나, 메타데이터를 추가하기 전에 벡터 데이터베이스에 업로드하는 등의 방법을 사용한다고 들었습니다. 이는 새롭게 떠오르는 단계라고 생각하지만 아직은 미성숙한 단계입니다. Weviate 측에서는 메타데이터 사용이나 전처리 등과 관련하여 어떤 경험을 하고 있는지 궁금합니다. 메타데이터를 추출하여 청크에 넣는 방식은 매우 흥미로운 주제이며, 이를 더욱 발전시킬 수 있을 것 같습니다. 예를 들어 법률 계약서를 분석할 때, 조항 S3001이 있다면 해당 헤더를 가져와 텍스트 청크에 "이것은 이 조항의 일부입니다"라고 표시하는 것과 같습니다. 이렇게 하면 벡터 임베딩 성능이 향상되고 BM25 점수에도 더 유리할 것으로 예상됩니다. 그러면 "s3001 같은 번호는 기억이 안 나네요"라고 말할 때, 일종의 벡터 검색을 위해 메타데이터를 청크에 추가하는 방식이 있는데, 이 문제를 바라보는 다른 관점도 몇 가지 있습니다. 제가 아주 좋아하고 과소 평가되고 있다고 생각하는 또 다른 아이디어는, 예를 들어 NBA 농구 선수들의 위키피디아 페이지를 분석한다고 가정해 보겠습니다. 그러다가 나이 정보를 발견한다고 해봅시다. LLM은 설정에 따라 본질적으로 확률적이기 때문에 항상 동일한 결과를 얻을 수 있는 것은 아닙니다. 따라서 의미 있는 테스트 결과를 얻으려면 LLM을 여러 번 실행해야 한다고 생각합니다. 이 아이디어에 대해 어떻게 생각하시는지 궁금합니다. 저희가 다른 사람들과 이야기해 본 것 중 하나는, 데이터에 대해 잘 알고 있다면 L1을 사용해서 질문을 만드는 대신, 직접 질문을 만들고 예/아니오로 답할 수 있도록 할 수 있다는 것입니다. 그런 다음 LLM을 사용해서 채점하거나 다른 방식으로 처리할 수 있습니다. 직접 채점하고 파이프라인을 만들어서 여러 번 실행함으로써 확률적 변동성을 커버하는 거죠. 예를 들어 20개의 문제가 있고 정답인지 오답인지를 표시할 수 있는데, 20점 만점으로 점수를 매기거나 100점으로 환산할 수 있어요. 이런 과정을 10번 또는 원하는 만큼 반복해서 평균과 분산을 계산할 수 있죠. 각 테스트마다 변수 하나만 바꾸면 되니까, 데이터에 맞춰 상위 K개 결과만 조정하거나, 임베딩 모델을 바꾸거나, 메타데이터 필터링 메커니즘을 변경하는 등 어떤 방법이 효과적인지 정확하게 파악할 수 있어요. 저희는 이런 방식으로 접근했는데, 여러분은 이 분야에 워낙 정통하시니까 다른 접근 방식을 가지고 계실지도 궁금하네요. 네, 전적으로 동감해요. 대규모 언어 모델이 등장하면서 추출형 질문 답변 방식의 인기가 시들해진 건 사실이죠. 검색된 컨텍스트에서 답변을 분류하는 모델이 있어서 그런 설정에서는 환각이 발생할 가능성이 전혀 없어요. 아니면 검색 경로가 자주 묻는 질문으로 연결되도록 하고, 새 질문과 자주 묻는 질문의 임베딩 유사성을 비교하는 거죠. 네바가 질문 간 임베딩 유사성이 질문과 답변의 임베딩 유사성보다 훨씬 쉽다는 내용의 멋진 블로그 글을 올렸는데, 저는 그 스타일이 마음에 들고, 그런 구성 요소에는 흥미로운 것들이 많다고 생각해요. 검색 상자의 모양 같은 부분에서 정말 많은 혁신이 일어나고 있죠. 이 팟캐스트를 게시할 때쯤이면, 제가 이걸 말해도 될지 모르겠지만, 그냥 말하지 않을게요. 저희 Alleviate에서 UI 구성 요소를 구축하는 프로젝트를 개발 중입니다. 사이트 소스를 보여주는 검색 상자 와 UI 관련해서는 Versel이나 Replit 같은 회사들과 협업이 많이 진행되고 있어요. 저는 개인적으로 참여하고 있지는 않지만, 사람들이 프런트엔드 컴포넌트를 쉽게 연결할 수 있도록 만드는 과정을 지켜보고 있습니다. 추출형 QA를 사용하든, 대규모 언어 모델을 사용하든, 사용자 인터페이스를 어떻게 디자인하는지는 정말 중요한 기회입니다. VectorFlow처럼 데이터 수집이 새로운 시장 카테고리로 떠오르고 있는 상황에서, 이러한 프런트엔드 컴포넌트를 개발하는 것도 좋은 방법이죠. React 컴포넌트 라이브러리 같은 것도 꽤 유용할 거예요. 모든 게 계속 발전하고 있으니까요. 제가 말씀드리려고 했던 것 중 하나는, 저희도 VectorFlow를 사용할 때 시스템의 진입점이 무엇인지 파악하려고 노력하고 있다는 점입니다. 예를 들어, 저희는 처음에 API를 시스템의 진입점으로 삼았습니다. 왜냐하면... Vectorflow는 기술에 구애받지 않는 플랫폼이죠. 클라우드 환경에도 구애받지 않도록 설계되었고요. 하지만 빠른 테스트와 반복 작업을 위해서는 사용자 인터페이스가 필수적이라는 점도 고려해야 합니다. 이러한 변화는 해당 분야가 성숙해지고 있다는 신호라고 생각합니다. 처음에는 연구원, 데이터 과학자, 전통적인 소프트웨어 엔지니어들이 주로 사용했지만, 이제는 주류로 진입하면서 일반 사용자도 쉽게 이해하고 활용할 수 있도록 사용성과 접근성을 고려해야 합니다. Vectorflow는 빠른 테스트 주기를 실행하는 데 매우 유용하며, 업계 전체적으로도 결과의 이해도를 높이는 데 많은 노력이 필요하다고 생각합니다. 왜 그런 결과가 나오는지, 그리고 소프트웨어 엔지니어링에서 말하는 '트레이서 불릿'처럼 어떤 경로를 통해 답을 찾았는지, 어떻게 반복할 수 있는지 등을 파악하는 것이 중요합니다. 네, 전적으로 동의합니다. 제로샷 모델이 소프트웨어 엔지니어들에게 딥러닝 도구를 활용한 개발을 전파하는 능력은 Wevia의 가장 큰 특징 중 하나라고 생각합니다. 오픈 AI 임베딩을 사용하면 임베딩 모델을 미세 조정하는 방법을 전혀 몰라도 의미 검색 애플리케이션을 구축할 수 있다는 점이 특히 그렇습니다. 임베딩 모델을 미세 조정하는 것은 상당히 어려운 작업이라고 생각합니다. 그래서 저는 메타데이터 추출과 L을 사용한 청킹 작업으로 거슬러 올라가는 장기적인 참조를 하고 있는 셈입니다. 특히 벡터 데이터베이스로 데이터를 가져오는 것과 같은 작업을 하고 싶습니다. 흥미로운 점은 제로샷 모델을 이러한 워크플로에 통합할 수 있는 기회가 더 많다는 것입니다. 특히, 제로샷으로 훈련된 LLM에 대해 어떻게 생각하시는지 궁금합니다. 예를 들어 GPT4는 지미 버틀러에 대한 위키피디아 구절을 입력받아 어떤 기호적 의미를 도출할지 결정하는 작업을 수행할 수 있을 것입니다. 이 문단에는 추출하고 싶은 메타데이터 속성이 포함되어 있을 수 있습니다. 예를 들어, " 28살"이라는 나이 부분을 빼야겠다고 생각할 수도 있습니다. 또는, 뒤죽박죽인 텍스트 덩어리를 주고 " 어디에서 이 텍스트를 분할해야 할까?"라고 생각할 수도 있습니다. LLM(Learning Language Manager)이 할 수 있는 또 다른 방법은, 150억 개 정도의 매개변수만 처리할 수 있도록 LLM을 세밀하게 조정하거나 특화하는 것입니다. 현재 텍스트-SQL 변환 기술은 거의 불가능에 가깝기 때문에, LMS를 세밀하게 조정하여 데이터 가져오기 스택에 통합하는 것이 중요합니다. 따라서 검색 결과에 도움이 될 만한 텍스트 덩어리의 유형을 생각해 보면, 관련 정보가 포함된 덩어리, 키워드가 포함된 덩어리, 문장이나 단락과 같은 간단한 덩어리, 그리고 더 복잡한 덩어리 등 다양한 유형이 있습니다. 예를 들어, 요약 청킹에 대한 이야기를 들어보셨을 텐데, 요약을 할 때 어떤 내용을 요약할지, 단락을 요약할지, 페이지를 요약할지, 아니면 문서를 요약할지 고민하게 됩니다. 예를 들어, "이건 2장이에요", " 4부예요"와 같이 내용을 명확하게 구분해야 할 수도 있죠. 요약하려는 페이지나 단락의 수를 고려해야 하는데, 특히 컨텍스트 크기가 큰 LLM(Long Level Model)이 이런 부분에서 매우 유용할 수 있습니다. 핵심은 GPT, 특히 GPT4와 같은 데이터셋은 API 사용에 비용이 많이 들 수 있다는 점입니다. API가 다운되는 경우도 있고요. 따라서 요약을 위해 특별히 설계된 모델이 있다면, 이를 워크플로에 활용하는 것이 매우 효과적일 수 있습니다. 마찬가지로 추출 기능도 특정 목적에 맞게 학습된 모델을 사용하여 키워드나 주제를 추출할 수 있습니다. 저희도 이러한 부분을 연구하고 있습니다. 흥미로운 점은, 더 빠르고 저렴한 전통적인 방식으로 딥러닝 모델의 성능에 근접할 수 있을까 하는 것입니다. 예를 들어, XGBoost를 사용하여 감정 분류를 하고 그 감정들을 메타데이터에 저장한다면, 훨씬 빠르고 저렴할 수 있지 않을까요? 물론 LLM만큼 성능이 높지는 않겠지만, 다른 이점들을 통해 그 정도의 단점을 상쇄할 수 있을 것입니다. 저는 요약 청킹과 같은 두 가지 방식을 생각해 봤는데, 이 부분은 나중에 다시 논의해 보겠습니다. 저는 감정 분류에 XGBoost를 사용하는 것에 집중하고 싶습니다.
