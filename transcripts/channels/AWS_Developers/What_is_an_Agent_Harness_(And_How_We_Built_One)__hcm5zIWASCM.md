## 스크립트

문서를 업데이트하고 제대로 작동하는지 확인하는 것은 엔지니어의 업무 중 가장 재미있는 부분은 아닙니다 . 최근에 저와 한 엔지니어는 Agent Core용 새 CLI와 연동되도록 문서를 업데이트해야 했는데, 에이전트를 사용해서 이 작업을 훨씬 빠르게 진행할 수 있었습니다. 우리는 에이전트가 AWS 계정에 액세스하고, 작성된 CLI 명령을 실행하고, 오류를 보고할 수 있도록 에이전트를 중심으로 하는 시스템을 구축했습니다. 에이전트 하네스는 모델과 현실 세계 사이의 제어 계층을 정의하는데, 그렇다면 에이전트 하네스란 정확히 무엇일까요? 이는 엔지니어들이 모델을 감싸는 인프라 환경으로, 단순한 챗봇 이상의 기능을 수행할 수 있도록 해줍니다. Cloud Code, Curie CLI, Codex와 같은 코드 에이전트는 자체 하네스를 사용하여 사용자의 프롬프트를 받아 모델에 전달한 다음, 모델에 작업을 실행하는 데 필요한 도구를 제공합니다 . 그래서 코딩 에이전트에게 이 함수에 대한 테스트 작성을 요청하면 단순히 복사 붙여넣기만 할 코드를 생성해 주지 않는 것입니다 . 대신, 샌드박스 환경에서 bash에 접근하여 저장소에 테스트 파일을 생성하고 , 생성된 출력을 붙여넣은 다음 실행하여 제대로 작동하는지 확인합니다. 올해 개발자들이 직면한 과제는 새롭고 개선된 모델이 출시될 경우에도 시간이 지나도 안정적으로 작동할 수 있는 에이전트 시스템을 구축하는 것입니다. 모델이 두뇌 역할을 하는 반면, 하네스는 에이전트가 실제 작업을 수행할 수 있도록 손, 인프라 및 메모리를 제공합니다 . 모델이 더욱 똑똑해질수록, 우리의 안전벨트는 더욱 단순해져야 합니다. 지나치게 견고한 안전 난간을 설치하면 시스템이 제대로 작동하지 못하고 모형에 소음이 발생할 수 있습니다. 메모리를 파일 시스템으로 오프로드하고 MCP와 같은 표준화된 인터페이스를 사용함으로써 모델이 최대한 스마트하고 유능해질 수 있도록 합니다. 그것이 바로 트랜스 에이전트의 철학입니다. 이는 모델 기반 아키텍처를 바탕으로 구축한 오픈 소스 프레임워크로, 순서를 하드코딩할 필요가 전혀 없습니다. 도구를 정의하고 프롬프트를 작성하면 모델이 언제 무엇을 호출해야 하는지 알아냅니다 . Trans를 이용해 하네스를 제작하는 과정을 단계별로 설명해 드리겠습니다. 이는 Trans 엔지니어링 팀에게 있어 실제 활용 사례입니다 . Trans TypeScript로 구축된 에이전트는 OpenAI의 변경 로그를 모니터링하고 API 업데이트가 SDK에 중요한지 판단하며, 중요한 경우 GitHub에 이슈를 제출합니다. Trans는 기본적으로 Amazon Bedrock과 호환되지만, 공급업체에 구애받지 않습니다. 지원되는 모델 제공업체를 한 줄로 간편하게 변경할 수 있습니다. 첫 번째 단계는 도구를 사용하는 것입니다. 해당 메서드는 이름, 설명, 입력 스키마 및 콜백 함수를 가져야 합니다. 설명은 모델이 언제 사용할지 결정하기 위해 읽는 내용입니다. 스키마는 모델이 전달할 수 있는 입력값을 정의합니다 . 콜백은 모델이 호출할 때 실행되는 코드입니다. 우리는 해당 도구를 에이전트에 전달하고 실행합니다. 모델은 프롬프트를 읽고 변경 로그를 가져와야 한다고 판단한 후 콜백을 호출하고 그 결과를 사용하여 응답합니다. 그건 도구 사용이에요. 생각하고, 행동하고, 반응하는, 하나의 순환 과정 . 이제 담당자는 결정을 내려야 합니다. 두 가지 도구를 더 추가할 예정입니다. 하나는 변경 로그 항목을 분류하고, 다른 하나는 GitHub에서 중복 항목을 검색합니다. 저희는 세 가지 도구를 하나의 에이전트에 모두 담았습니다. 이 모델은 변경 로그를 가져와 각 항목을 분류하고, 저장소 변경이 필요하다고 표시된 항목만 GitHub에서 검색합니다. 우리가 구축해야 할 라우팅 로직은 없습니다. 모델은 설명을 읽고 스스로 호출 순서를 정합니다. 설명은 담당 에이전트를 이끌어가는 방법입니다. 설명을 모호하게 작성하면 예측할 수 없는 결과가 나타날 것입니다. 정확한 설명은 신뢰할 수 있는 도구 선택으로 이어집니다 . 안전장치를 확인하고 입력 내용을 분류하세요. 새로운 모델 슬러그만 추가하면 저장소 변경은 필요하지 않습니다. 그건 우리가 쉬운 영어로 쓴 제약 조건이에요. 모델은 이를 읽고 런타임에 존중합니다. 미들웨어가 필요 없습니다. 또한 각 도구 호출 전후에 두 개의 라이프사이클 후크를 추가할 예정입니다. 모델이 내리는 모든 결정은 기록됩니다. 이렇게 하면 모델이 변경 로그를 가져와 각 항목을 분류한 다음 플래그가 지정된 항목만 GitHub에서 검색하는 것을 볼 수 있습니다 . 안전장치를 적용했기 때문에 모델 출시 단계를 건너뛰었습니다. 분류가 잘못되었다면 설명을 더 자세히 작성하세요. 디버깅은 단순히 문자열을 편집하는 것입니다 . 이제 요원이 행동할 수 있습니다. 또 다른 도구는 구조화된 템플릿을 사용하여 GitHub 이슈를 생성하는 것입니다 . 최종 결과물은 다음과 같습니다. 변경 로그에서 문제를 발견했고, 제목은 관례를 따랐으며, 본문에는 요약, 사용 예시 및 참조가 포함되어 있습니다. 템플릿이 있습니다. 가드레일은 설명에 나와 있습니다 . 먼저 분류하고, 중복을 제거한 다음 생성합니다. 템플릿은 입력 스키마를 통해 적용됩니다. 모델은 모든 필드를 제공해야 합니다. 그 구조는 우리가 방금 살펴본 문제를 그대로 반영합니다 . 네 가지 도구 모두 동일한 에이전트에서 실행됩니다. 이 모델은 설명과 시스템 프롬프트를 기반으로 문제를 검색하고, 분류하고, 중요하지 않은 것을 건너뛰고, 중복을 제거하고, 문제를 보고합니다 . 자, 이렇게 Trans 에이전트가 Trans를 개선하는 방법을 보여드렸습니다. 그것이 바로 모델 기반 프레임워크가 제공하는 것입니다. 특정 음악 모델의 장점에 얽매일 필요가 없습니다. 언제든지 간편하게 하네스를 조절할 수 있습니다. 최고의 에이전트를 만드는 데 최고의 모델이 필요한 것은 아닙니다 . 모델이 발전할 때마다 함께 발전하는 모델 기반 하네스가 필요합니다 .
