## 스크립트

안녕하세요, Rep의 Mt입니다. 오늘은 Reels에서 영구 저장소에 대해 이야기해 보겠습니다. 영구 저장소가 무엇인지, 왜 중요한지, 그리고 Reels에서 데이터를 저장하는 다양한 옵션에 대해 알아보겠습니다. 바로 시작해 볼까요? 먼저, 왜 데이터를 영구 저장해야 할까요? 다른 플랫폼이나 Reels에서 앱을 개발해 보신 분들은 아시겠지만, Reels에 이러한 옵션이 있다는 것을 몰랐을 수도 있습니다. 데이터를 저장하는 것이 생각보다 어렵다는 것을 느끼셨을 겁니다. Reels 에이전트, 특히 최근 출시된 에이전트가 강력한 이유 중 하나는 세션 간에 데이터를 영구적으로 저장할 수 있는 옵션을 제공하기 때문입니다. 할 일 목록을 만들었는데 페이지를 새로고침하면 모든 할 일이 사라진다면, 그런 목록은 더 이상 유용하지 않겠죠? 따라서 백엔드에서 데이터를 저장하고, 사용자 세션과 사용자 정보를 저장할 수 있는 기능이 필요합니다. Reels 웹사이트를 만들거나 제품을 개발할 때, 영구 저장소가 필수적입니다. 사용자 데이터를 저장하려면 사용자에 대한 정보와 사용자의 모든 활동을 저장하고, 이를 화면에 표시하여 사용자가 만족스러운 경험을 할 수 있도록 해야 합니다. 사용자는 앱을 종료했다가 다시 방문할 수도 있습니다. 기본적으로 릴(repple)이나 워크 스페이스에 들어가면 보이는 파일 트리는 영구적으로 저장되지 않습니다. 릴이 재시작되면 기존 파일로 롤백됩니다. 릴을 스냅샷이라고 생각하면 됩니다. 릴 배포는 릴 의 스냅샷입니다. 배포 버튼을 클릭하면 기존 파일 구조를 가져와 배포합니다. 사용자가 해당 릴에서 수행하는 작업은 저장되지 않습니다. 따라서 사용자 데이터를 저장하려면 영구 저장소를 사용해야 합니다. 이를 위한 세 가지 옵션이 있으며, 저장소 유형에도 여러 종류가 있습니다. 저는 데이터 엔지니어였기 때문에 각 유형에 대해 설명하겠지만, 누구나 이해할 수 있도록 아주 간단하게 설명하겠습니다. 저보다 더 잘 아시는 분도 계시다면 좋습니다. 이 설명이 대부분 유익할 것이고, 그렇지 않더라도 도움이 되기를 바랍니다. Repet에서 선택할 수 있는 스토리지 유형에 대해 설명해 드리겠습니다. 첫 번째 스토리지 유형은 PostgreSQL 데이터베이스입니다. PostgreSQL은 관계형 데이터베이스로, 데이터를 테이블에 저장합니다. 데이터베이스에 대해 잘 모르시는 분들을 위해 설명드리자면, Google 스프레드시트 여러 개가 ID와 기본 키를 통해 서로 연결된 구조라고 생각하시면 됩니다. 관계형 데이터베이스에 대해 더 자세히 알고 싶으시다면 온라인에서 관련 자료를 찾아보실 수 있으니 자세한 설명은 생략하겠습니다. Repet에는 PostgreSQL이 내장되어 있어 클릭 한 번으로 PostgreSQL 데이터베이스를 구축하고 데이터를 쉽게 읽고 쓸 수 있습니다. Repet 에이전트를 사용 중이시라면 PostgreSQL 데이터베이스를 인식하고 연동하여 애플리케이션을 구축할 수 있어 매우 편리합니다. 따라서 프로덕션 애플리케이션을 구축하는 대부분의 개발자분들께서는 Repet PostgreSQL을 사용해 보시기를 추천합니다. PostgreSQL 데이터베이스에 대한 몇 가지 정보를 알려드리자면, 서버리스 방식으로 항상 실행되며 Neon이라는 회사에서 서비스를 지원하고 있습니다. Replit은 정말 훌륭한 데이터베이스를 만들 수 있게 해줍니다. 어디서든 접근할 수 있다는 점이 특히 중요한데, Replit에서 '새 데이터베이스'를 클릭하면 연결 문자열과 자격 증명을 받게 됩니다. 이 정보를 바탕으로 노트북이나 데이터베이스 클라이언트, 또는 다른 프로그램들을 만들어 해당 데이터베이스를 참조하도록 할 수 있습니다. 말 그대로 어디서든 접근 가능한 데이터베이스를 갖게 되는 것입니다. 많은 사람들이 데이터베이스가 Replit 환경에만 국한된다고 생각하기 쉽지만, 그렇지 않다는 점을 강조하고 싶습니다. 연결 문자열만 있으면 어디서든 읽고 쓸 수 있습니다. 물론 연결 문자열은 민감한 정보이므로 다른 사람에게 함부로 알려주지 마세요. 데이터베이스는 어디서든 접근 가능하다는 점을 다시 한번 강조하고 싶습니다. 두 번째로, 데이터는 영구적으로 저장됩니다. 제가 앞서 설명드린 것처럼, 사용자가 다른 페이지로 이동하더라도 데이터베이스에는 데이터가 그대로 남아 있습니다. Replit을 원하는 만큼 재시작하더라도 데이터베이스를 계속 사용한다면 데이터를 영구적으로 저장하여 훌륭한 사용자 경험을 제공할 수 있습니다. 각 Replit은 고유한 데이터베이스를 가지며, 앞서 언급했듯이 여러 Replit의 데이터베이스에도 접근할 수 있습니다. 해당 연결 문자열을 사용하지만 기본적으로 Repple 내에서 '새 데이터베이스'를 클릭하면 새 데이터베이스가 생성됩니다. 계정 수준이 아닌 Repple 수준에서 데이터베이스가 생성되는 것입니다. 동일한 데이터베이스를 여러 Repple에서 사용하려면 올바른 정보를 입력하고 비밀번호를 업데이트하기만 하면 됩니다. 단 한 번의 클릭으로 시작할 수 있으며, Repple은 훌륭한 데이터베이스 제품을 만드는 Neon의 지원을 받습니다. 이 데이터베이스는 프로덕션 데이터에 적합하며 각 데이터베이스에는 10GB의 저장 공간이 제공되므로 시작하는 데 충분합니다. Repple에서 사용할 수 있는 다음 유형의 저장 장치는 키-값 데이터베이스입니다. 이 또한 약간 다른 유형의 데이터베이스입니다. 키-값 데이터베이스는 개념적으로 사전처럼 생각하면 가장 이해하기 쉽습니다. 사전이란 파이썬이나 JSON 객체와 같은 것을 의미합니다. 키와 값이 있습니다. 따라서 이 데이터베이스를 호출할 때는 키만 제공하면 데이터베이스가 값을 반환합니다. 따라서 매우 간단한 작업이나 단순한 작업에 훨씬 적합합니다. 음, 아시다시피, 특정 정보를 저장하기 위한 고유 키를 만들고, 그 키에 연결된 값을 저장하는 아키텍처가 있습니다. 필요할 때 데이터베이스에 ping만 하면 즉시 사용할 수 있죠. 이 방식이 얼마나 간단한지 정말 놀라운 점은 파이썬에서 딕셔너리를 사용하는 것처럼 구현할 수 있다는 것입니다. 즉, 영구 데이터를 얻기 위해 추가적인 단계를 거치지 않아도 되는 것처럼 느껴지게 해줍니다. 이는 간단한 애플리케이션에 매우 유용한 기능입니다. 키-값 데이터베이스는 리플별로 관리되기 때문에 리플 간에 접근할 수 없다는 점에서 약간 다릅니다. 또한 약 50MB의 저장 용량을 제공하는데, 이는 PostgreSQL 데이터베이스보다 적습니다. 따라서 다른 유형의 솔루션이라고 할 수 있습니다. 키-값 데이터베이스를 시작하는 것도 마찬가지로, 단 한 번의 클릭으로 생성할 수 있습니다. 파이썬과 Node.js용 SDK를 제공하며, 다른 프레임워크를 사용하여 접근할 수 있는 방법도 있습니다. 이러한 데이터베이스는 Repetition에서 지원되므로 저희 서버에 저장되어 장애 걱정 없이 안심하고 사용할 수 있습니다. 또한 프로덕션 데이터 관리에도 매우 적합합니다. 앞서 말씀드린 것처럼 50MB의 저장 공간이 제공되므로 키- 값 데이터베이스는 데이터를 저장하고 액세스하는 데 훨씬 더 간편하고 효율적인 접근 방식입니다. 마지막으로 객체 스토리지가 있습니다. 객체 스토리지는 AWS나 Google Cloud와 유사합니다. 실제로 저희 객체 스토리지는 Google Cloud를 기반으로 하며, 여러분이 작성하는 코드는 프록시 계층을 통해 Google Cloud Storage로 연결됩니다. 객체 스토리지가 생소하신 분들을 위해 설명드리자면, 컴퓨터의 디렉토리와 같지만 클라우드에 있는 디렉토리라고 생각하시면 됩니다. 문서, 사진, 비디오 등을 업로드할 수 있고, 사실상 무제한으로 데이터를 업로드할 수 있습니다. Google Cloud에서 제공하는 요금 또는 조정된 요금으로 객체 스토리지를 통해 구축되기 때문입니다. 이러한 점에서 객체 스토리지는 매우 유연하며 거의 디렉토리처럼 작동합니다. 사용자가 PDF나 문서를 업로드하고 액세스할 수 있도록 하는 애플리케이션이 있다고 가정해 보겠습니다. 예를 들어 GIF를 업로드하고 액세스할 수 있는 변환 도구를 구축하는 경우를 생각해 볼 수 있습니다. GIF 파일을 변환할 수는 있지만, 나중에 다시 액세스하거나 임시로 어딘가에 저장하고 싶을 때가 있습니다. 이런 경우 객체 스토리지를 사용하면 완벽한 해결책이 될 수 있습니다. 객체 스토리지는 저장소별로 새로운 가상 파일 시스템, 즉 버킷을 생성하는 방식입니다. 따라서 저장소 간에 직접 액세스할 수 없습니다. 시작하는 것도 매우 간단합니다. 클릭 한 번으로 생성할 수 있으며, Google Cloud에서 지원합니다. JavaScript 및 Python SDK도 제공하며, 이론적으로는 무제한 저장 공간을 확보하여 원하는 만큼 데이터를 업로드할 수 있습니다. 다만, 1TB 이상의 데이터를 객체 스토리지에 저장하면 비용이 발생할 수 있다는 점에 유의해야 합니다. 객체 스토리지에 대해 한 가지 더 알아둘 점이 있습니다. 최근에 알게 된 사실인데, Google Cloud 기반의 객체 스토리지를 사용하기 때문에 Python 및 JavaScript SDK로는 처리할 수 없는 작업, 예를 들어 연속 업로드나 청크 파일 업로드와 같은 고급 기능을 Google Cloud SDK를 통해 직접 구현할 수 있습니다. 저희 코드를 사용하고 싶지 않으시다면, Google Cloud 문서에 있는 코드를 사용하셔도 됩니다. 정상적으로 작동할 것입니다. 객체 스토리지 패널과 저희 문서 모두에 Google Cloud 인증 방법에 대한 안내가 있습니다. 기본적으로 Repet을 우회하고 Repet을 사용하여 해당 버킷에 대해 Google Cloud에 직접 인증하는 방식입니다. 이는 다소 고급 기능이므로, 제가 무슨 말을 하는지 이해가 안 되신다면, Repet SD를 사용하고 싶지 않다면 더 고급 기능을 제공하는 Google Cloud SDK를 직접 사용할 수 있다는 점을 알려드리고자 합니다. 지금까지 Repet의 세 가지 영구 스토리지 유형에 대해 설명드렸습니다. PostgreSQL 데이터베이스는 프로덕션 애플리케이션이나 관계형 데이터를 저장하는 데 적합하며, 키-값 데이터베이스는 ADL 또는 ABIABLOB과 유사한 간단한 데이터 구조를 가집니다. 마지막으로 객체 스토리지는 압축 데이터, CSV 파일, 파일 형식 파일 등 다양한 유형의 파일을 업로드하는 데 적합하며, 오디오, 이미지, 비디오, PDF 파일 등도 저장할 수 있습니다. 네, 이러한 옵션들을 통해 이제 이해하셨기를 바랍니다. Repet 플랫폼 내에서 필요한 모든 유형의 데이터 스토리지를 이용할 수 있습니다. 추가 웹사이트에 접속하거나 새 계정을 만들 필요도 없고, 리소스를 구축하고 다른 공급업체에 저장된 데이터를 관리할 필요도 없습니다. 모든 것이 Repet에 준비되어 있습니다. 저희 목표는 구축, 배포, 복제를 최대한 원활하게 진행할 수 있도록 지원하는 것이며, 바로 이러한 이유로 다양한 서비스를 제공하고 있습니다. 저는 Repet 개발자 관계 담당 Matt입니다. 지금까지 Repet에서 사용할 수 있는 다양한 스토리지 유형에 대한 소개였습니다. 다음에 또 뵙겠습니다.
