Welcome to this Yocto Project tutorial, where we introduce a widely-used and flexible toolset for embedded Linux development. The Yocto Project is an open-source initiative that provides a comprehensive set of templates, tools, and methods for building custom Linux-based systems tailored for embedded products. Yocto Project enables you to build efficient, scalable, and production-ready systems from the ground up. It supports all major hardware architectures, giving developers the freedom to target a wide range of embedded platforms. It’s important to note that Yocto Project is not an embedded Linux distribution - instead, it helps you create one that fits your specific requirements. Yocto Project brings together several essential components to streamline embedded Linux development. At its core is the OpenEmbedded build system, co-maintained with the OpenEmbedded Project. This includes OpenEmbedded-Core, which provides fundamental build metadata, and BitBake, the engine that drives the build process. Another key component is Poky, a reference embedded Linux configuration used for testing. Poky serves as a practical example of how to build a small embedded OS. To ensure reliability, the Yocto Project features an extensive testing infrastructure, powered by a Buildbot-based autobuilder. Developers also benefit from a suite of integrated tools, including automated build and testing utilities, processes and standards for board support definitions and interchange, tools for security analysis, license compliance, and software manifests (SBoM) support in SPDX format. The build system, downloaded with Poky, includes recipes and layers—flexible components that can be modified, extended, or used as is to create a custom embedded Linux system tailored to specific needs. With these tools, the Yocto Project provides a robust framework for building and maintaining embedded Linux solutions across diverse hardware platforms. BitBake is a highly efficient task execution system that automates the process of creating a working Linux OS. The workflow begins with configuring four key areas. Local user information in which details such as footprint size and machine architecture are configured. Software configuration is done via source recipe files, which specify the package location, license, checksum, and specialized instructions for building. Layers define the hardware and software configuration, including user-interface definitions, board-specific configurations, recipes, and image definitions. Distribution configuration specifies the resulting custom distribution items, such as the init system, device manager, and C library. Once configured, BitBake knows what it needs, where to locate it, and what actions to perform. The source code can come from external or local project source code management (SCM) systems or source mirrors. Patches are then applied based on your customized instructions. The shared state mechanism identifies only altered packages for faster compilation. The build result can be packaged into any of the most commonly used package formats. A sanity check is performed on each package to ensure there are no build errors and that it meets the configuration requirements. A directory of all compiled binary packages is created. From this package feed, a bootable Linux system is generated. This system can take several forms, from a raw disk image to a “live” image that can be booted from a USB memory stick. Additionally, an application developer SDK is created, which includes a cross-architecture compiler, analytical tools, and an Eclipse plug-in. Learning Yocto Project can be overwhelming for beginners due to its numerous technical terms. Understanding some fundamental terms is crucial as they are referenced repeatedly in the development flowYocto Project development consists of several key components: BitBake, metadata, configuration files, Poky, and layers. The Yocto Project Reference Manual offers an extensive list of terms and definitions, but in this video, we’ll focus on the ones most essential for getting started. The Yocto Project build tool automates the process of creating a working Linux operating system. BitBake is the core task scheduler and build tool used in the Yocto Project and OpenEmbedded build system. It is often compared to traditional tools like make, but it provides far greater flexibility and power, particularly for cross-compilation in embedded Linux environments. BitBake fetches required source code, resolves dependencies, builds the components, and packages the final image. BitBake is a build tool that interprets .bb recipe files to fetch, configure, build, and package software components. It automatically manages dependencies by constructing a build-order tree. BitBake schedules and executes tasks like fetching source code, configuring, compiling, and packaging. It uses global configuration files and supports hierarchical layering for flexible build environments. Additionally, BitBake enables both native and cross-compilation, allowing builds for target architectures different from the host system. BitBake is made up of several essential components. Recipes in the form of .bb files are used to define the necessary steps required to build software components. Configuration files, like local.conf and bblayers.conf, are used to control the build environment. Classes contained within .bbclass files contain reusable build logic that can be implemented across multiple recipes. Finally, tasks are pre-defined steps in the build process that include fetching source code, configuring the build, compiling, and packaging. Together, these components make up the core functionality of BitBake, providing the necessary tools for efficient and accurate software builds. Metadata in Yocto Project refers to the set of input files that define how software is built, configured, and packaged. These metadata files are primarily written in BitBake syntax and help Yocto Project determine how to fetch, compile, and install software. Metadata is structured in layers, which can be combined to obtain various components. Layers are collections of configuration files, recipes, and classes designed for a specific purpose. For example, the meta-xilinx-bsp layer is used for AMD evaluation board support. Yocto Project metadata is categorized into several types, each serving a specific purpose in the build process. Configuration files define build settings, machine types, and policies. Key examples include local.conf, which sets user-specific configurations like target machine and parallel builds, and bblayers.conf, which specifies available layers and their locations. Recipes (.bb files) outline how a package is built, detailing tasks such as fetching, unpacking, compiling, and installing. Class files (.bbclass) act as reusable templates to eliminate redundancy by defining shared tasks and functions. Append files (.bbappend) modify existing recipes from another layer, enabling extensions or overrides without altering the original files. Lastly, layer configuration (conf/layer.conf) defines the rules specific to a given layer, ensuring proper integration within the Yocto Project build system. Yocto Project’s metadata-driven approach allows developers to customize the build system efficiently while maintaining modularity and reusability. Configuration files allow developers to customize their Linux-based systems for specific hardware requirements. Several configuration files are in in Yocto Project, each with its own purpose. The&nbsp;conf/&nbsp;directory contains the configuration files that control Poky and BitBake. There are two mandatory build-specific configuration files:&nbsp;local.conf and bblayers.conf. One of the most important configuration files is the local.conf file. This file is located in the build directory and controls the build environment, including things like build settings, image settings, and package settings. It can be used to set variables, such as architecture, target system, and distribution version, among others. When we initialize a build environment, a file called&nbsp;build/conf/local.conf is created. This powerful configuration file allows you to control almost every aspect of the build process. The settings in local.conf directly influence how BitBake compiles your custom Linux embedded OS stack. You can modify these settings or introduce new variables to override defaults from other configuration files. Configuration file variables apply globally to every recipe and are collectively referred to as configuration metadata. The main configuration files are processed in the following order: build/conf/local.conf conf/machines/.conf conf/distro/.conf Within local.conf, comments provide helpful documentation, offering insights into available variables and their default values. Another important configuration file is bblayers.conf, which is also located in the build directory. This file sets up the build layers and defines the location of the required metadata. It controls which layers the BitBake build engine uses for building the entire image. This configuration file is crucial as it defines the layers that BitBake should include in the build process. In&nbsp;bblayers.conf, the&nbsp;BBLAYERS&nbsp;variable lists the directories of the layers to be included in the build. The&nbsp;?=&nbsp;operator means that&nbsp;BBLAYERS&nbsp;will be assigned this value only if it hasn't been set already. The backslash at the end of each line allows the string to continue onto the next line for better readability. The&nbsp;${TOPDIR}&nbsp;variable typically points to the top directory of the build environment. The paths listed, such as&nbsp;../meta,&nbsp;../meta-poky,&nbsp;../meta-yocto-bsp, and&nbsp;../meta-custom, are relative to this top directory and specify the locations of different layers. Understanding and correctly configuring&nbsp;bblayers.conf&nbsp;is essential for ensuring that the appropriate layers are included in your Yocto Project build process. Here are the other configuration files. site.conf is an optional system-wide configuration file that optimizes builds or specifies cache locations, making it useful for teams sharing a build environment. The layer.conf file is layer specific and defines how BitBake interacts with a given layer, primarily managing build dependencies within that layer. distro.conf defines policies for a specific Linux distribution, allowing customization of elements such as the toolchain, package manager, and security settings. machine.conf is hardware specific, setting kernel options, bootloader configurations, and other machine-related parameters. Finally, bitbake.conf provides core build settings used across all recipes. This file should not be modified directly—instead, settings can be overridden in local.conf. Together, these configuration files offer flexibility and control over the Yocto build process. Poky is the reference distribution of Yocto Project. It provides a ready-to-use build system based on BitBake and OpenEmbedded, helping developers create custom Linux distributions for embedded devices. It is not a full Linux distribution but a framework to build custom embedded Linux systems. Poky includes example configurations, recipes, and tools for testing. Poky consists of several key components that play a crucial role in the software building process. One of the most essential components is BitBake, the build engine that processes important metadata, such as .bb, .bbclass, and .bbappend files. BitBake’s responsibilities include handling task execution, such as do_fetch and do_compile, among others. OpenEmbedded Core is another important component of Poky, providing core metadata such as recipes, classes, and configuration. It also includes fundamental Linux packages. Poky-specific metadata can be found in meta-poky, which contains Poky’s own custom policies and configurations. Finally, board support packages (BSPs) can be found in meta-yocto-bsp and are key to testing. These BSPs include elements for testing on QEMU, such as qemux86-64 bit and qemuarm, as well as for generic x86-64 bit. Together, these four components provide the necessary tools and functionality for building efficient and customizable software packages in Poky. Yocto Project introduces a structured approach to organizing metadata through the layer model—an improvement over the classic Open Embedded project. This model enhances collaboration and customization by classifying metadata into distinct layers. In Yocto Project, each layer is independent yet reusable, allowing a modular way to organize metadata, making it easy to customize and extend builds. Each layer contains recipes, configuration files, and patches that define how software is built for an embedded Linux system. Yocto Project layers are categorized based on their functionality and role in the build system. Core layers include meta, which provides essential metadata from OpenEmbedded Core (OE-Core), meta-poky for Poky-specific configurations, and meta-yocto-bsp, which includes reference board support packages for platforms like qemux86-64 and qemuarm. BSP layers contain hardware-specific configurations, such as kernel settings, bootloaders, and device drivers, with examples like meta-xilinx layer for AMD development boards. Middleware/software layers provide additional software stacks, including networking, graphics, and security features. Notable examples are meta-openembedded, which offers a collection of useful packages, and meta-virtualization, which adds support for Docker, Xen, and other virtualization technologies. Distribution layers define policies for specific Linux distributions, such as meta-poky for the Poky reference distribution and meta-debian for Debian-based Yocto Project builds. Lastly, application layers contain custom applications and their dependencies, often tailored for specific projects or products, such as meta-myapp for a particular software solution. These layers help structure and modularize Yocto Project-based development, ensuring flexibility and maintainability. In the Yocto Project, recipes are essential files that define how a particular piece of software is built and packaged. These recipes provide detailed instructions for fetching, configuring, compiling, and installing software, ensuring a streamlined and consistent build process. Each recipe is identified by the&nbsp;.bb&nbsp;file extension, which stands for BitBake recipe. This extension signifies that the file contains the necessary steps and metadata for building the software within the Yocto Project framework. First, we have the&nbsp;header, which contains metadata about the recipe, such as the description and license. Next is the&nbsp;source&nbsp;section, which provides information on where to fetch the source code. The&nbsp;build instructions&nbsp;outline the steps to configure, compile, and install the software. Key variables in recipes include&nbsp;SRC_URI, which specifies the location of the source code, and&nbsp;S, the directory where the source code is unpacked. DEPENDS&nbsp;lists the build-time dependencies, while&nbsp;RDEPENDS&nbsp;lists the runtime dependencies. The&nbsp;inherit&nbsp;keyword allows the recipe to inherit common functionality from classes. The Yocto Project has a structured directory layout to manage embedded Linux system builds. The build/ directory contains configurations, sources, cache, and temporary files. AMD modifies and/or adds to this structure by adding a sources directory. poky/ is the main repository, while bitbake/ holds the build engine. meta/ includes core metadata, and meta-poky/ contains Poky-specific configurations. meta-yocto-bsp/ offers reference BSPs, and meta-openembedded/ adds extra software packages. meta-amd-adaptive-socs and meta-amd-edf layers adds support for AMD adaptive SoCs and AMD Embedded Development Framework (EDF). meta-virtualization/ supports virtualization tools like Docker and Xen. Custom layers go in meta-custom/, and scripts/ provides helper tools for setup and debugging. This modular structure ensures flexibility for various embedded systems. Now let’s look at your typical Yocto Project build flow for building custom embedded Linux for AMD adaptive SoC and FPGA platforms. At the start of the flow, this is done by setting up the Yocto Project environment using the Repo tool, which is a tool chosen by AMD for EDF flows to manage multiple Git repositories. It is not a requirement from Yocto Project. Repo is used by EDF flows to manage multiple Git repositories via a manifest. After Repo is added to the system PATH and Git is configured, it can fetch and organize all sources with a single command, avoiding per-repository clones. The EDF yocto-manifests define and pin the required layers for each release, ensuring the correct projects and revisions are synced. Before starting, make sure you are using a supported operating system for Yocto Project and configure Git with your username and email. Then, initialize Repo using the provided manifest link to set up all the required repositories. After initialization, run repo sync to pull in the sources. If needed, you can also start a new branch using repo start. Once the repositories are synced, source the setup script to prepare your build environment. Here is an example of the SD card boot flow showing the steps to build an AMD EDF Linux image. In this flow, you focus on building and packaging the boot image, followed by booting the board. Begin by building the required targets. The first target is the boot image as boot.bin, using supported recipes such as xilinx-bootbin, depending on the machine. By setting the MACHINE variable to the board-specific name and running BitBake, the recipe automatically generates boot.bin. For example, on the ZCU104 board, this produces the correct boot firmware. Next, build the common EDF Linux disk image using the edf-linux-disk-image recipe, which contains the EDF Linux OS. Here, the MACHINE variable is set to the appropriate common disk image definition, such as amd-cortexa53-mali-common for the Zynq MPSoC ZCU104 board. When both the boot.bin and EDF Linux disk image are built, verify the generated files in the deploy directory with the following command. After verification, copy the boot.bin into the WIC file using the wic cp command, ensuring the boot firmware and root filesystem are packaged together. Finally, we flash the WIC image to an SD card, insert it into the board, and power on to boot the system with the image we just built. Now let’s look at the multistage boot flow, where the process begins by building the OSPI boot firmware image. This is done by setting the MACHINE variable to the board-specific configuration and running BitBake with the edf-ospi recipe. For example, on the Versal VEK385, this generates the required boot firmware. Next, the common EDF Linux disk image is built using the edf-linux-disk-image recipe. This step produces the WIC image containing the Linux operating system. Here, the MACHINE variable is set to the correct common disk image definition, such as amd-cortexa78-mali-common for the VEK385. Once both the OSPI firmware and Linux disk image are built, the generated outputs can be verified in the deploy directory. Finally, flash the OSPI image to the board and boot the board using the EDF Linux image from the SD card, completing the multistage boot process.
