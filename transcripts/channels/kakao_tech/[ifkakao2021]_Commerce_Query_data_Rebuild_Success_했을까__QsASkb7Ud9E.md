## 스크립트

안녕하세요. 커머스 쿼리 데이터 리빌드 성공했을까라는 제목으로 발표하게 된 카카오 커머스 주문 플랫폼의 노아입니다. 저희는 많은 트래픽이 발생할 수 있는 서비스에서 겪을 수 있는 데이터 문제를 CQRS 방식으로 해결한 내용을 공유드리려 합니다. 공유해 드릴 내용의 순서는 문제였던 상황, 해결책, 시행 착고 추가 고민거리 마지막으로 좋아진 점 순입니다. 문제였던 상황에 대해서 설명드리겠습니다. 저희 데이터에는 총 세 가지의 문제가 있었습니다. 첫 번째는 DB용량, 두 번째는 성능, 세 번째는 MSA 환경에서의 도메인 경계 문제였습니다. 첫 번째로 DB 용량 문제입니다. 카카오 커머스에 선물하기는 10년이 넘은 서비스이고 폭발적인 성상체로 인해 디스크 사용량이 급증하고 있었습니다. 그에 따라 데이터베이스의 디스크 사이즈도 계속 확장하면서 진행하고 있었는데요. 현재는 더 큰 사이즈의 디스크 증가는 어려운 상황이었습니다. 주문 도메인의 데이터베이스 사용량은 61% 정도 사용되고 하루의 평균 0.1%의 1%의 증가량을 보이고 있었습니다.이 증가량을 계산해 보면 2022년 2월에는 위험 수치인 80%에 도달하는 상황이었습니다. 저희는 데이터베이스의 용량 문제를 해결하기 위해서 많은 고민을 했습니다. 가장 먼저 쉽게 떠오른 생각은 샤딩이었습니다. 샤딩은 하나의 데이터베이스에 있는 데이터를 다수의 데이터베이스에 분산시켜 저장하는 방법입니다. 주문 플랫폼은 10 개의 데이터베이스로 샤딩하는 프로젝트를 진행했습니다. 저희는 구매자 아이디 기준으로 데이터를 분사시켜 저장하기로 하고 샤딩하였습니다. 그런데 샤딩된 데이터베이스 클러스터를 사용하려 했으나 사용할 수 없는 상황을 만나게 되었는데요. 사용할 수 없었던 곳은 바로 카카오톡 선물하기에 받은 선물함에서 사용할 수가 없었습니다. 카카오톡 선물하기는 다른 커머스와 달리 수신자라는 개념이 있습니다. 선물하기의 선물함은 사용자께서 받은 선물을 확인하는 매우 중요한 서비스입니다. 선물함은 받은 유저 즉 수신자 기준으로 데이터를 조회해야 하는데요. 구매자 기준으로 샤딩된 데이터베이스에 수신자 기준으로 선물함을 조재하게 되면 브로드캐스트 커리로 실행되는 상황이라 성능명에서 좋지 못하다는 결론을 얻었습니다. 두 번째 문제로는 성능 문제가 있었습니다. 선물함을 조회하는 쿼리인데요. 인덱스 조인, 스칼라 커리를 이용한 정렬 등으로 성능이 좋지 않았습니다. 선물한 쿼리의 성능을 올리려면 인덱스 설계를 다시 해야 하는 상황인데요. 데이터는 14억권, 사이즈는 200GB, 사용되는 인덱스는 두 개로 각각 30GB를 사용하고 있었습니다. 데이터 사이즈가 커서 인덱스를 수정 또는 추가하기가 어려운 상황이었습니다. 안타깝게도 많은 선물을 받으신 유저의 경우 의도치 않게 커리 타임아웃으로 받은 선물함을 바로 조회하지 못하는 상황이었습니다. 세 번째 문제는 도맨 경계 문제가 있었습니다. 선물함에서 사용 가능 탭에 나타난 선물은 교환권의 유효 기간 만료가 최근 순으로 정렬되어야 하는데요. 그래서 데이터 정렬을 위해 교환권의 유효 기간 데이터가 꼭 필요한 상황이었습니다. 카카오 커머스 시스템은 MSA 환경에서 운영 중입니다. 각 도메인별로 데이터베이스 서버를 별도로 운영 중인 환경에서 선물함 정료를 위해 교환권 도메인의 교환권 테이블을 주문 데이터베이스에 듀얼라이트하고 있는 상황이었습니다. 앞에 말씀드린 문제를 해결하기 위해 여러 가지 방안을 고민했습니다. 그래서 선택한 결론은 CQRS를 이용해 문제를 해결하기로 결정했습니다. CQRS는 데이터 저장소에 대한 읽기인 커리와 데이터 생성 변경을 의미하는 커맨드의 역할을 분리하여 처리하는 것을 의미합니다. CQR라S를 구현하면 성능과 확장성을 최대할 수 있습니다. 선물함 데이터 조회를 위해 데이터를 수신자 기준으로 최적화대에 설계한 선물함 전용 스토리지를 구성하고 전체 데이터를 마이그레션과 실시간 싱크를 맞춰 선물함 데이터를 제공하기로 결정하였습니다. 선물한 커리용 스토리지를 선택해야 했습니다. 저희가 선택한 스토리지는 몽고디입니다. 몽고디비는 여러 가지 장점이 있는데요. 유연한 데이터 구조, 안정성, 확장의 용암, 인덱스 지원 등이 있습니다. 몽고디 DV를 데이터 이전하기 위해 준비해야 할 것들이 있는데요. 총 세 가지로 스키마 디자인, 실시간 데이터 싱크를 위한 CDC, 그리고 전체 데이터 마이그레이션을 위한 ETL이 있습니다. 첫 번째로 스키마 디자인을 설명드리겠습니다. 스키마 디자인을 위해선 신규로 사용될 스토리지의 사용처를 먼저 조사하는게 좋은데요. 저희는 17개의 API에서 사용되고 검색을 위한 필드는 12개, 정렬을 위한 필드는 두 개로 조사되었습니다. 데이터 조회를 위한 필드와 기타 정보를 확인하기 위한 필드 등을 포함하여 총 28개인 필드로 설계하였습니다. 두 번째로 해야 할 일은 도큐먼트 디자인입니다. 몽고 DV는 도큐먼트 베이스 DB인데요. RDBMS처럼 데이터를 정규화하여 조인하는 방식은 권장되지 않습니다. 저희는 주문 도메인 데이터와 교환권 도메인 데이터를 하나의 도큐먼트에 임비딩하는 방식으로 디자인하였습니다. 그다음으로 해야 할 일은 인덱스 설계인데요. 몽고 DV는 인덱스를 지원하는 노 SQL DB기 때문에 인덱스를 잘 설계하는게 매우 중요합니다. 몽고 DV의 인덱스 설계에 사용되는 보편적 설계 지침에 대한 약자로 ESR 룰이 있습니다. ESR룰은 E는 이퀄리티, S는 소트, R은 레인지를 뜻하는데요. 인덱스 구성할 필드를 이퀄리티, 소트, 레인지 필드 순으로 생성하라는 뜻입니다. 인덱스를 설계했다면 검증을 해야 하는데요. 몽고 DBN 익스플레인 기능이 있어서 커리의 퍼포먼스가 어떻게 나올지 확인할 수 있습니다. 저희는 사용될 커리를 전부 조사해 플랜을 확인하였고 온고 DBA 분들과 논의하여 설계를 완료했습니다. 스키마 디자인이 끝났다면 실시간 데이터 싱크를 위한 CDC를 준비하여야 합니다. CDC는 인프라 레이어에서 하는 방법과 어플리케이션 레이어에서 하는 방법이 있습니다. 인프라 레이어에서의 CDC는 MySQL의 경우 바이너리 로고하는 빈로그를 조회하여서 연결된 데이터를 캡처하는 방법이 있습니다. 대표적인 오픈 소스로는 디베지움이 있는데요. 디베지움은 MySQL 등 여러 데이터베이스를 지원하는 오픈소스로 많이 사용되고 있습니다. 어플리케이션 레이어의 CDC는 데이터의 변경, 추가 등이 일어나면 어플리케이션에서 이벤트를 발송하는 방법입니다. 하이버, 네이트 등의 ORM을 사용하면 NTT 변경 리슨을 통해서 쉽게 구현이 가능합니다. 저희는 어플리케이션 레이어의 CDC를 사용하였는데요. 만약 어플리케이션 레이어의 CDC가 힘든 환경이라면 인프라 레이어에서 하는 CDC를 추천드립니다.
