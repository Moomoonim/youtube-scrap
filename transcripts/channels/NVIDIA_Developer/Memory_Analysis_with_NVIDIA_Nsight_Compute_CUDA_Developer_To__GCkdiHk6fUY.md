## 스크립트

Welcome to this chapter of our&nbsp; CUDA Developer Tools series on&nbsp;&nbsp; Nsight Compute. Today we will take a&nbsp; look at the memory workload analysis.&nbsp; My name is Maximilian and I am a&nbsp; Developer Technology Engineer at&nbsp;&nbsp; NVIDIA and focus on CUDA performance optimization&nbsp; in professional visualization applications.&nbsp; GPU workloads often suffer from being heavily&nbsp; memory bound with ever increasing compute,&nbsp;&nbsp; especially in content creation where video frames&nbsp; are being streamed through memory with sometimes&nbsp;&nbsp; little processing like a color adjustment filter. The memory workload analysis section of Nsight&nbsp;&nbsp; Compute helps to guide us to achieve the full&nbsp; memory bandwidth of our GPU and optimize data&nbsp;&nbsp; access patterns to increase the cache hit&nbsp; rate. If you have not seen the introduction&nbsp;&nbsp; to Nsight Compute featuring the SOL section&nbsp; you might want to think about starting with&nbsp;&nbsp; Bob’s this video first which is linked&nbsp; in the video description. Besides that,&nbsp;&nbsp; I highly recommend watching the linked GTC&nbsp; presentation about the memory hierarchy and memory&nbsp;&nbsp; transactions on a NVIDIA GPU, in more detail than&nbsp; I will in this video. It is crucial to understand&nbsp;&nbsp; the way memory is requested and what cache&nbsp; lines and sectors are in the context of CUDA. We will start with a theoretical walkthrough of&nbsp; the memory analysis chart where we get an overview&nbsp;&nbsp; of hardware memory locality and memory type. The green elements denote logical units in&nbsp;&nbsp; software e.g. texture data with different&nbsp; ordering or simple global/local memory that&nbsp;&nbsp; refers to raw memory. All physical units&nbsp; in hardware are colored blue. Arrow links&nbsp;&nbsp; between physical units denote the amount of&nbsp; read or written bytes across this connection.&nbsp; The color of the arrow provides some insight&nbsp; into how far we are from the peak throughput&nbsp;&nbsp; of this interconnect. Via the dropdown menu&nbsp; we can also switch between the total bytes or&nbsp;&nbsp; the peak throughput percentage labeling of a&nbsp; connection. Upon a memory request inside our&nbsp;&nbsp; kernel depicted on the left we check if the&nbsp; requested sector behind an address is already&nbsp;&nbsp; present in L1. If not we fall through to L2 and&nbsp; check for the existence there. If none of the&nbsp;&nbsp; above contain the sector it is fetched from device&nbsp; memory. Our L2 cache is the point of truth for all&nbsp;&nbsp; streaming multiprocessors (SM). What I mean by&nbsp; that is that all memory traffic has to go through&nbsp;&nbsp; L2 - including PCI copies or device memory writes.&nbsp; Only if a sector to read is already present in L1&nbsp;&nbsp; the L2 cache is not used. The L2 cache ensures&nbsp; that no SM reads invalid data from device memory&nbsp;&nbsp; that has not been written back as it is shared&nbsp; across the whole GPU while L1 memory is local&nbsp;&nbsp; to one streaming multiprocessor. We can reduce&nbsp; traffic between L2 and device memory by increasing&nbsp;&nbsp; L2 hit rate and we can reduce traffic between&nbsp; L1 and L2 with a higher L1 hit rate. Of course,&nbsp;&nbsp; traffic can also be reduced by changing the&nbsp; algorithm to simply require less data to be&nbsp;&nbsp; transferred. Those hitrates are important to&nbsp; ensure low latency of memory request as fetches&nbsp;&nbsp; from device memory take many cycles. To understand&nbsp; more about the communication between the different&nbsp;&nbsp; types of memory and about how the hit rate is&nbsp; calculated it is important to understand at what&nbsp;&nbsp; granularity the different units communicate. Cache lines are 128 bytes long in L1 and L2,&nbsp;&nbsp; but any communication on the GPU is done in&nbsp; sectors whose size is only 32 byte. While&nbsp;&nbsp; on newer hardware more than 1 sector can be&nbsp; communicated at once a single sector is still&nbsp;&nbsp; the smallest communication possible in the memory&nbsp; system. The concept of cache lines is important as&nbsp;&nbsp; we can not allocate single sectors in cache but&nbsp; always allocate full cache lines into which when&nbsp;&nbsp; then read contiguous cache sectors. As a practical&nbsp; example why cache line allocation is important we&nbsp;&nbsp; will assume a cache of only 2 cache lines. If we&nbsp; now read a picture in which each row is over 128&nbsp;&nbsp; bytes long we see the following: Reading the first&nbsp; entry of the first row and the first of the second&nbsp;&nbsp; row we would each allocate a cache line. If we&nbsp; now read the third row, we have to invalidate&nbsp;&nbsp; a cache line to read the next. We would not be&nbsp; able to reuse any cache lines. This essentially&nbsp;&nbsp; lowers our possible cache storage to 25%. If we&nbsp; read the same memory in rows rather than columns,&nbsp;&nbsp; we read the full cache line then the next and so&nbsp; on. After reading both full cache lines we again&nbsp;&nbsp; have to invalidate but we were able to hold on&nbsp; to much more sectors and therefore more values&nbsp;&nbsp; much longer. Especially with wider prefetches that&nbsp; transfer 2 sectors at a time we also increase our&nbsp;&nbsp; latency. The previous explanation does hold for&nbsp; L2 and L1 cache. If we would read 32 consecutive&nbsp;&nbsp; bytes in one SM we would have a hit rate of 97%&nbsp; in L1. This would result in 0% in L2 because we&nbsp;&nbsp; send only one request to L2 and after that&nbsp; has been executed all data is present in L1&nbsp;&nbsp; and will be a cache hit on further requests. If&nbsp; we, on the other hand, have a kernel that reads&nbsp;&nbsp; values with a stride of 32 byte meaning only the&nbsp; first value within one sector we get 0% L1 cache&nbsp;&nbsp; hitrate. L2 will only have to reallocate a new&nbsp; cache line for every 4th value when reading with&nbsp;&nbsp; a 32 byte stride, but has to request data from&nbsp; device memory on each request if we assume no&nbsp;&nbsp; prefetch is happening in this case. The earlier&nbsp; we have a hit, the lower the memory latency is,&nbsp;&nbsp; with device memory clearly being the worst&nbsp; case, because this memory is not on chip. We&nbsp;&nbsp; have not talked about shared memory yet and&nbsp; especially the improvements that it got with&nbsp;&nbsp; Ampere. Shared memory is per SM memory and is&nbsp; effectively L1 memory, with the difference that&nbsp;&nbsp; this memory is not written back to device memory&nbsp; and is meant as a workspace memory. By requesting&nbsp;&nbsp; shared memory one reduces the available L1 memory. This way data can be shared across all threads in&nbsp;&nbsp; a block running on the same SM (CTA) without&nbsp; going through L2. This is also an effective&nbsp;&nbsp; measure to manage the L1 cache manually if the&nbsp; desired caching is not achieved automatically.&nbsp;&nbsp; With Ampere the _Load Global Store Shared_&nbsp; instruction was introduced which allows to&nbsp;&nbsp; directly read data to shared memory without&nbsp; going through unmanaged L1 memory first.&nbsp; Just as a brief outlook: Preloading data to&nbsp; shared memory is a commonly used pattern for&nbsp;&nbsp; sliding window operators like a convolution. All threads in the CTA, also SM, are used to&nbsp;&nbsp; preload data to shared memory. After that the&nbsp; data is accessed by all the other threads and the&nbsp;&nbsp; weights are persistent in L1 cache, for example. This already brings us to the load and store&nbsp;&nbsp; address spaces used in our kernel, here&nbsp; shown as green boxes. The most basic&nbsp;&nbsp; loads are global and local loads that will&nbsp; load raw byte data.For surface and texture&nbsp;&nbsp; loads we can possibly see different indexing&nbsp; schemes for example for Z ordered textures.&nbsp; Furthermore we see the shared load&nbsp; operation for ampere and later GPUs,&nbsp;&nbsp; that we talked about before. It is important to understand the&nbsp;&nbsp; difference between local and global load/stores.&nbsp; Any local load and store is usually something we&nbsp;&nbsp; want to get rid of! The origin of these local&nbsp; operations is often due to register spilling&nbsp;&nbsp; for which I’ll have a link in the video&nbsp; description. This means the kernel is not&nbsp;&nbsp; able to keep its working data in the physical&nbsp; register file and has to write back to memory.&nbsp;&nbsp; This has very strong performance implications! Finding the origin of those local operations&nbsp;&nbsp; can be done using this address space column&nbsp; of the memory chart or by using the source&nbsp;&nbsp; page of Nsight Compute and looking&nbsp; for `LDL` and `STL` instructions.&nbsp; The usage of this source page will be covered in&nbsp; a separate tutorial. Looking at it can be very&nbsp;&nbsp; helpful to identify the exact line of code&nbsp; that is responsible for this local access.&nbsp; All absolute values that we see in the memory&nbsp; workload analysis chart are shown in the table&nbsp;&nbsp; below which I will not go into detail&nbsp; about right now, but rather want to give&nbsp;&nbsp; some example usage on how to use this section. The code for the following sample can be found on&nbsp;&nbsp; github and is linked in the video description. We&nbsp; will profile this very simple program to convert&nbsp;&nbsp; an 8bit png from RGBA to grayscale. What we do in our kernel is: we load&nbsp;&nbsp; 4 consecutive pixel values which are our RGBA&nbsp; values, apply a multiplier to each and add them&nbsp;&nbsp; up to a single grayscale float value, then we&nbsp; downcast and save it back to our output buffer.&nbsp; For now I collapsed the optimized versions,&nbsp; please explore the code for those on github.&nbsp; First let's make sure we have our theoretical&nbsp; values set - we are reading a 4 channel `uint8_t`&nbsp;&nbsp; picture of size 3840x2160 and write at the&nbsp; same size but only one channel `uint8_t`.&nbsp; So we expect a load of&nbsp; ~33.2MB and a store of ~8.3MB.&nbsp; While Nsight can give us a good measurement&nbsp; of how far we are from the CUDA device&nbsp;&nbsp; hardware limits, it can not tell us if&nbsp; our processing approach is suboptimal,&nbsp;&nbsp; This is something we should always keep in mind. I will use Nsight Compute’s capability to remotely&nbsp;&nbsp; profile using an SSH connection.&nbsp; We will start with creating a&nbsp;&nbsp; new project and establishing the connection. I usually name my project with a %i in the name,&nbsp;&nbsp; that way Nsight Compute will simply enumerate the&nbsp; profiles I take without overwriting an old file&nbsp;&nbsp; or me needing to remove an old file. To get the memory chart analysis,&nbsp;&nbsp; we have to either select the detailed&nbsp; profile or the full profile. I recommend&nbsp;&nbsp; simply going with the full profile. Furthermore, I also like to import the&nbsp;&nbsp; source in the others tab as it will allow&nbsp; me to track my source changes across my&nbsp;&nbsp; profiles in case I do not version them correctly. Now we can simply hit the launch button, on the&nbsp;&nbsp; first launch it will upload only the binaries,&nbsp; which can actually take some time. For me, I’ve&nbsp;&nbsp; done that already, so our baseline will pop up. Before we dive into our memory workload analysis&nbsp;&nbsp; we can already see in the speed of light&nbsp; section that our memory speed of light is&nbsp;&nbsp; already at 80%. This usually indicates a very&nbsp; well performing kernel. But our compute speed&nbsp;&nbsp; of light is very low - to me, it seems lower than&nbsp; expected. Looking at the memory workload analysis&nbsp;&nbsp; section we see that the link to device memory is&nbsp; at very low peak throughput judging by its color.&nbsp; But the link between L2 and L1&nbsp; shows much more data flow than we&nbsp;&nbsp; would expect given our point wise operation. The cache hit ratio for L2 also seems superb,&nbsp;&nbsp; but things are sometimes not as good as&nbsp; they look, which is why it is important&nbsp;&nbsp; to understand why we calculated the&nbsp; previously mentioned theoretical numbers.&nbsp; We want to know if we are really limited by&nbsp; hardware, or if our algorithm is suboptimal.&nbsp;&nbsp; Nsight Compute can only show correct speed&nbsp; of light measurements if the used algorithm&nbsp;&nbsp; is limited by hardware. It can not tell us if we&nbsp; are doing suboptimal or superfluous processing.&nbsp; What is happening here is that as we read&nbsp; 256 pixels vertically in one block that each&nbsp;&nbsp; thread requests data for one pixel. Assuming an&nbsp; uninitialized cache this leads to allocating a&nbsp;&nbsp; cache line in L2 and L1 then loading the sector&nbsp; of that line from global memory in which the&nbsp;&nbsp; pixel data is. As we are processing vertically&nbsp; we request 256 cache lines and 256 sectors but&nbsp;&nbsp; we only read 256*4 bytes from those sectors.&nbsp; Although, for each of those 256 sectors, we&nbsp;&nbsp; have to transmit 32 bytes. Even worse is that the&nbsp; same is happening for storing the grayscale data,&nbsp;&nbsp; to store data we request 256 sectors, store one&nbsp; byte and write the complete sector back. We are&nbsp;&nbsp; actually lucky with our problem to not generate&nbsp; even more device memory requests from L2 due to&nbsp;&nbsp; having that little data that fits in our L2 cache. In this case Nsight compute even provides warnings&nbsp;&nbsp; that indicate that our algorithm is not doing&nbsp; what it should do. They tell us very clearly&nbsp;&nbsp; that we read little data of our requested&nbsp; sectors and that we should try using more&nbsp;&nbsp; sectors. This kernel only accesses on average one&nbsp; sector out of the possible four sectors per cache&nbsp;&nbsp; line - this is exactly what we just talked about. To compare results more easily we will set the&nbsp;&nbsp; current unaligned report as our baseline. Changing the access from columns to rows is&nbsp;&nbsp; possible for this processing by simply changing&nbsp; the block dimension in the kernel launch. I&nbsp;&nbsp; predefined this as another optimization&nbsp; level so let’s just launch with another&nbsp;&nbsp; command line argument, which takes care of this. Now looking at the aligned reads we immediately&nbsp;&nbsp; see that we are about 8 times faster. The speed&nbsp; of light section also indicates higher throughput&nbsp;&nbsp; with less gap between compute and memory. In the memory chart our link between device&nbsp;&nbsp; memory and L2 is very close to peak performance.&nbsp; We load the expected amount of data from L2 to L1&nbsp;&nbsp; and thinking about our cache hit rate we&nbsp; also see what we expect: 75% L1 hit rate&nbsp;&nbsp; which is due to requesting all bytes of the&nbsp; neighboring pixels. What else can we learn ?&nbsp; Given the report we know that the kernel&nbsp; is heavily memory latency bound as we&nbsp;&nbsp; have to wait for device memory on each&nbsp; pixel. In such cases it can be beneficial&nbsp;&nbsp; to process multiple values in one thread. Let’s check what we gain if we process 4 values.&nbsp; After reprofiling we see we did not gain much -&nbsp; if anything. Nonetheless, let’s investigate the&nbsp;&nbsp; memory chart closer. We see that the requests&nbsp; to global memory did not decrease, nor did the&nbsp;&nbsp; L2 to L1 which we also did not expect, but our&nbsp; L1 store to L2 increased! And it's not matching&nbsp;&nbsp; the expected 8 megabytes. Why is that the case ? We are processing 4 pixels per thread now. But&nbsp;&nbsp; after every pixel we write one byte to our&nbsp; image. This needs to be flushed to L2 which&nbsp;&nbsp; artificially increases the throughput from L1&nbsp; to L2 as we write with an unit8 so little data&nbsp;&nbsp; at the same time. Threads that write to the&nbsp; same sector at the same time can be grouped&nbsp;&nbsp; together in one single write operation,&nbsp; but the wait period for this is very short.&nbsp; This brings us to vectorized loads which is the&nbsp; last iteration on this kernel. We can use one&nbsp;&nbsp; uchar4 to load all values for one pixel but we&nbsp; would still have to write back a single uint8.&nbsp;&nbsp; Going even wider operations ends up at reading&nbsp; one uint4, which can then process 4 pixels in&nbsp;&nbsp; one thread and write back as one uchar4 - this&nbsp; resembles basically exactly the same as we’ve&nbsp;&nbsp; been doing in the multiple value kernel before. With both these optimizations we have to make&nbsp;&nbsp; sure that we have enough work available to&nbsp; not reduce the number of blocks in our grid&nbsp;&nbsp; so much that we are no longer able to saturate&nbsp; the GPU. After reprofiling and taking another&nbsp;&nbsp; look at the memory chart we see that our&nbsp; write to L2 is back to the expected 8MB.&nbsp; In addition we have no pressure anymore on&nbsp; the Load Store Unit (LSU) and did cut our&nbsp;&nbsp; requests by over 90%! This can also be seen when&nbsp; comparing the Compute speed of light section of&nbsp;&nbsp; our aligned report and the vectorized load&nbsp; as we have to do less indexing math on the&nbsp;&nbsp; pointers. Nonetheless the kernel did not get&nbsp; much faster as we were already limited by&nbsp;&nbsp; device memory in the previous versions. Assuming our initial case of reading in&nbsp;&nbsp; columns is the way we must process our&nbsp; data, this approach can also be very&nbsp;&nbsp; helpful to make each load a little less costly. In conclusion we can say that the best use of&nbsp;&nbsp; the memory workload section is to ensure&nbsp; that you load only as much memory as you&nbsp;&nbsp; really need and aligning read accesses with&nbsp; sector or even cache line boundaries is very&nbsp;&nbsp; beneficial. For alignment issues there will also&nbsp; be hints in the Source section, this will help&nbsp;&nbsp; identifying memory stalls together with source&nbsp; correlation.
