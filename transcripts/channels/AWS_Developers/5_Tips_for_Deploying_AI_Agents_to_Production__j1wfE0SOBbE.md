Cognito 인증자가 포함된 API 게이트웨이가 인증을 처리합니다. 저희는 두 가지 이유로 AWS WAF를 앞에 연결합니다. 하나는 SQL 인젝션 및 크로스 사이트 스크립팅과 같은 일반적인 웹 공격을 차단하는 관리형 규칙 이고, 다른 하나는 IP별 요청 수를 제한하는 속도 기반 규칙입니다. 그런 다음 API 게이트웨이와 에이전트 사이에 Lambda 함수가 위치하여 인증을 연결합니다. 프런트엔드에서 에이전트 런타임을 직접 호출할 수 있도록 OAuth를 사용하여 에이전트 런타임을 구성하고 싶을 수도 있지만, 게이트웨이와 에이전트가 동일한 ID 공급자로부터 동일한 토큰을 허용하는 경우 , 에이전트 엔드포인트를 찾은 사용자는 게이트웨이를 완전히 건너뛸 수 있습니다. 모든 속도 제한 및 필터링이 무시됩니다. 더 나은 방법은 에이전트 코어의 기본값인 IAM 인증을 그대로 사용하는 것입니다. 그런 다음 게이트웨이와 에이전트 사이에 Lambda 함수를 배치하십시오 . Lambda는 에이전트를 호출할 수 있는 권한이 있는 IAM 역할을 가지고 있습니다 . 사용자는 OAuth를 사용하여 게이트웨이에서 인증합니다 . Lambda는 JWT를 사용하여 사용자의 ID를 추출하고 IAM 자격 증명을 사용하여 에이전트를 호출합니다. 이제 에이전트 엔드포인트는 올바른 IAM 역할을 가진 AWS 서비스에서만 호출할 수 있습니다. 사용자는 URL을 찾더라도 직접 접속할 수 없습니다. 여기 페이로드에 사용자 ID가 포함되어 있는 것을 확인할 수 있습니다. 컨테이너는 이를 수신하고 에이전트가 실행되기 전에 서버 측에서 호출 상태로 매핑합니다 . 모델은 그것을 직접 보지 못합니다. 이는 1절에서 설정했던 것과 동일한 격리 방식이며, 단지 서비스 경계를 ​​넘어선 것뿐입니다. Agent Core 대신 ECS 또는 Lambda에서 에이전트를 실행하는 경우에도 동일한 패턴이 적용됩니다. 게이트웨이를 앞에 두고 내부 호출 시 서비스 자격 증명을 사용하십시오. 프런트엔드 측에서는 TypeScript 앱이 URL만 바꾸면 됩니다. 에이전트를 직접 호출하는 대신, 사용자의 코그니토 토큰을 사용하여 API 게이트웨이를 호출합니다. 섹션 1과 동일한 페치, 동일한 SSE 파싱이 적용됩니다. 프런트엔드는 자신과 상담원 사이에 세 가지 서비스가 존재한다는 사실을 알지도 못하고 신경도 쓰지 않습니다. 현재 저희 도구는 하드코딩된 데이터를 반환합니다. 우리에게는 제대로 된 데이터베이스가 필요하며, 바로 이 부분에서 흔히 볼 수 있는 안티패턴을 발견했습니다. Nova Micro는 Converse API를 통한 툴 호출을 지원하므로 이전 섹션에서 설정한 것과 동일한 유형의 툴과 호환됩니다 . Nova Micro와 같은 경량 모델과 Sonnet 간의 격차는 상당히 커서, 트래픽의 일부만 라우팅하더라도 대규모로 사용할 경우 상당한 비용 절감 효과를 볼 수 있습니다. 마지막으로, 요청 처리 시간이 8초나 걸린다면 , 그것이 모델 자체의 문제인지, 도구가 느린 것인지, 아니면 추론 과정이 너무 많았던 것인지 알아야 합니다. 프롬프트를 수정하거나, 도구를 최적화하거나, 주기 예산을 추가하는지에 따라 그 차이점은 달라집니다. 다행인 점은 스트랜드를 사용하면 에이전트가 요청을 완료할 때마다 자동으로 메트릭을 받을 수 있다는 것입니다. 별도의 수집기나 설정이 필요하지 않습니다. 사이클 카운트는 에이전트가 거친 추론 루프 횟수를 알려줍니다. 총 소요 시간은 전체 작업에 걸린 시간을 알려줍니다. 토큰 사용량을 통해 입력 및 출력 토큰을 얻을 수 있으므로 요청당 비용을 추적할 수 있습니다 . 도구별 통계를 보면 어떤 도구가 호출되었는지, 몇 번 호출되었는지, 각 도구에 얼마나 시간이 걸렸는지 알 수 있습니다. 1절에서 설명한 스트리밍 설정에서 이러한 정보는 스트림이 끝날 때 에이전트 결과 이벤트에 나타납니다 . 이미 완료 이벤트와 함께 프런트엔드로 전송했으므로 채팅 UI에서 응답 시간과 토큰 사용량을 바로 표시할 수 있습니다 . 그러니까, 이런 내용을 서버 측에 기록하고 싶다는 거죠 . 도구 호출 횟수가 높고 반복적인 작업이 수행되는 것은 에이전트가 무한 루프에 빠졌음을 의미합니다 . 한 주기 동안 지속 시간이 길다는 것은 모델이 느리다는 것을 의미합니다. 이제 어디를 봐야 할지 아시겠죠. 프로덕션 환경에서 완벽한 분산 추적을 위해서는 모든 추적 도구를 개방형 원격 측정 범위로 설정하십시오. 콘솔에서 어떻게 보이는지 보여드리겠습니다. 추적 콘솔을 1로 설정하고 요청을 보내면 터미널에서 모든 스팬을 볼 수 있습니다. 에이전트 호출, 모델 호출, 도구 실행 등 모든 과정이 중첩되어 있으며 시간 제약이 있습니다. 실제 운영 환경에서는 콘솔에 로그를 기록하는 대신 이러한 추적 정보가 OTLP 엔드포인트로 전송됩니다. CloudWatch는 이제 OTLP 직접 수집을 지원하며, LangFuse, Datadog 등 OTLP를 지원하는 다른 서비스로 연결할 수도 있습니다 . 표준 개방형 원격 측정 방식이기 때문에 특정 방식에 종속되지 않습니다. 이것이 바로 다섯 가지 모범 사례입니다. 툴 호출 이벤트를 사용하여 스트리밍하면 UI가 항상 반응성을 유지합니다. 인증 계층을 분리하세요. 하나는 공개 인증이고, 다른 하나는 내부 인증입니다. 테넌트 격리 기능을 갖춘 계약 기반 데이터베이스 서비스를 사용하고 , 에이전트가 통제 불능 상태가 되지 않도록 안전장치와 예산을 설정하며, 내장된 메트릭 및 추적 기능을 활용하여 모든 요청에서 에이전트가 수행한 작업을 정확하게 파악하십시오 . 이 모든 것은 에이전트의 핵심 로직을 변경할 필요가 없습니다. 동일한 TypeScript, 동일한 Strands SDK, 동일한 도구를 사용합니다. 우리는 그 주변에 프로덕션 레이어를 계속 추가해 나갔습니다. 혹시 이 내용들 중 더 자세히 알고 싶은 부분이 있다면 댓글로 알려주시고, 더 많은 콘텐츠를 원하시면 구독해주세요 .
