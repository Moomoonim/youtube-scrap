## 스크립트

안녕하세요, Repet의 Matt입니다. 애플리케이션 배포를 고려하고 계신다면 잘 찾아오셨습니다. 오늘은 Repet에서 제공하는 네 가지 배포 유형에 대해 자세히 알아보겠습니다. 각 유형에 어떤 애플리케이션이 가장 적합한지 살펴보고, 특히 Reserve VMS 배포와 Autos Skill 배포 중 어느 것을 선택해야 할지 고민되는 경우 각 방식 의 장단점을 논의해 보겠습니다. 어떤 경우에는 특정 방식으로 애플리케이션을 배포할 수도 있지만, 상황에 따라 적합하지 않을 수도 있습니다. 그럼 이 모든 것을 살펴보겠습니다. 먼저 네 가지 배포 유형을 설명하고, 아래 댓글과 링크에서 확인할 수 있는 의사결정 트리를 보여드리겠습니다. 이 트리는 제가 애플리케이션을 배포할 때 사용하는 것과 동일한 논리입니다. 이 영상을 통해 여러분이 개발 중인 모든 프로젝트를 배포하는 방법에 대해 자신감을 갖게 되기를 바랍니다. 좀 더 복잡한 배포에 도움이 될 만한 다른 튜토리얼 링크도 있지만, 바로 본론으로 들어가 보겠습니다. 첫 번째 배포 유형은 정적 배포입니다. 이름에서 알 수 있듯이 정적 배포는 정적 파일 집합으로 컴파일되기 때문에 정적이라고 합니다. 이러한 파일은 주로 HTML 또는 JavaScript 파일입니다. 여기서 ' 정적'이라는 것은 클라이언트, 즉 브라우저에서 실행된다는 의미입니다. 브라우저는 일반적으로 HTML 파일을 제공하고 JavaScript 파일을 실행합니다. 예를 들어 Streamlet을 실행하는 것은 정적 파일의 예가 아닙니다. Streamlet과 같은 Python 애플리케이션을 실행하려면 Streamlet main.py를 실행해야 하기 때문입니다. 즉, 브라우저에서 실시간으로 실행되는 것이 아니라 Python에 대한 명령을 실행하는 것입니다. 브라우저가 클라이언트 측 JavaScript 실행을 지원하기 때문에 브라우저에서 실행할 수 있는 다양한 종류의 작업에 놀라실 겁니다. 예를 들어, 제가 이전에 공유했던 3js 데모나 Transformers JS 라이브러리의 멋진 새 프로젝트처럼 클라이언트 측에서 JavaScript를 실행하는 것이 점점 더 가능해지고 있습니다. 정적 배포를 클라이언트 구성 요소가 없다고 해서 폄하하려는 건 아니지만, 정적 배포란 미리 컴파일된 정적 ​​파일들의 집합입니다. 정적 배포의 장점은 배포 속도가 매우 빠르다는 것입니다. 말 그대로 몇 초 만에 반복적으로 배포할 수 있습니다. 혹시 정적 배포가 무엇인지 아직 잘 모르시는 분들을 위해 비유하자면, GitHub Pages를 생각해 보세요. GitHub Pages에 배포할 수 있는 것처럼 정적 배포도 반복적으로 사용할 수 있습니다. 정적 배포에 필요한 것은 공개 디렉터리와 빌드 명령입니다. 공개 디렉터리는 빌드 명령의 출력이 저장되는 곳입니다. V와 같은 프레임워크에서는 '공개'가 될 수도 있고, 다른 프레임워크에서는 ' 빌드'가 될 수도 있습니다. 간단히 말해서, ` mpm run build`와 같이 실행했을 때 정적 파일들이 출력될 디렉터리를 지정하는 것입니다. 그리고 빌드 명령은 그 디렉터리에 빌드하려면 `npm run build`와 같이 입력하면 됩니다. 매우 간단하죠. 정적 배포는 정말 유용합니다. 제 블로그도 정적 배포 방식으로 운영되고 있습니다. 서버가 있고 프레임워크가 활발하게 실행 중인 경우라면 제한된 배포 유형만 사용할 수 있습니다. 이 배포 유형은 적합하지 않습니다. 이제 다음 배포 유형인 예약 배포에 대해 알아보겠습니다. 예약 배포는 이름에서 알 수 있듯이 정해진 시간 에 실행되는 스크립트입니다. 데이터 가져오기, 스크래핑, 업데이트 등 실행해야 하는 다양한 작업에 유용하며, 슬랙 채널에 메시지를 보내 거나 특정 주기로 작업을 수행하는 데에도 사용할 수 있습니다. 예약 배포의 가장 큰 장점은 한 번 실행된 후에는 종료된다는 것입니다. 따라서 컴퓨팅 자원을 지속적으로 실행하는 경우보다 사용량이 훨씬 적습니다. 예약 배포는 실행 후 종료되므로 사용자에게 UI를 제공하지 않습니다. 따라서 더 큰 애플리케이션의 일부로 예약된 작업이 필요한 경우 여러 개의 예약 배포를 사용 하거나 해당 예약 작업을 다른 유형의 배포에 통합하는 것을 고려해 볼 수 있습니다. 익숙한 분이라면 다음과 같이 생각할 수 있습니다. 크론 작업과 같은 예약 배포를 정의할 때 KRON 구문을 사용합니다. 익숙하지 않더라도 걱정하지 마세요. 자연어를 해당 구문으로 컴파일해 주기 때문에 실행 빈도를 정확하게 정의하거나 KRON 구문을 정의하는 것이 매우 쉽습니다. 예약 배포의 요구 사항으로는 빌드 명령(선택 사항)과 실행 명령이 있습니다. 예를 들어, 데이터를 가져오는 Python 스크립트를 작성하고 해당 스크립트가 Main.py 파일에 있다면 실행 명령은 ` python main.py`가 됩니다. 또한 타임아웃을 설정할 수 있습니다. 예를 들어, 매번 제대로 작동하지 않거나 특정 시간(분 또는 초) 후에 종료되도록 하려는 스크립트의 경우 선택적으로 타임아웃을 지정할 수 있습니다. 하지만 기본적으로 필요한 것은 실행 명령뿐이며, 스크립트를 실행하는 간단한 작업입니다. 이제 좀 더 복잡한 두 가지 유형의 배포에 대해 알아보겠습니다. 이들을 복잡하다고 부르는 이유는 혼동하기 쉽기 때문입니다. 첫 번째는 예약된 VM 배포입니다. 예약된 VM은 예약된 가상 머신을 의미합니다. 이름에서 알 수 있듯이, 앱을 배포하는 데 사용되는 항상 켜져 있는 백그라운드 실행 머신입니다. 예를 들어, Python 코드 main.py를 지속적으로 실행하고 싶다면 예약된 VM에 배포합니다. 그러면 main.py가 실행되고, 제가 종료하도록 지시할 때까지 해당 명령이 계속 실행됩니다. 예약된 VM은 항상 켜져 있기 때문에, 배포 시 크기를 정의할 수 있고, 항상 켜져 있는 상태로 유지되므로 고정 비용이 발생합니다. 매달 특정 금액을 지불하게 되며, 이 비용은 변동되지 않습니다. 하지만 단점도 있습니다. 특정 리소스 용량을 정의했는데 앱에 오류가 발생하거나, API를 개발 및 배포했는데 API에 오류가 발생하거나, 또는 매우 복잡한 작업을 처리해야 하는데 충분한 리소스를 정의하지 않았다면, 사용자는 성능 저하를 경험할 수 있습니다. 따라서 리소스 용량을 신중하게 고려해야 합니다. 리소스를 할당할 때는 예비 VM이 원하는 작업을 실행하는 데 필요한 리소스를 충분히 확보하고 있는지 확인해야 합니다. 예비 VM의 요구 사항은 선택적 빌드 유형, 실행 명령(필수), 앱 유형( 웹 서버 또는 백그라운드 워커)입니다. 앱 유형은 앱에 사용자 인터페이스(UI)가 노출되어 있는지 여부를 결정합니다. 예를 들어 Discord 봇이나 Slack 봇을 배포하려면 UI가 없는 백그라운드 워커를 사용해야 합니다. 이러한 봇은 대부분 지속적으로 명령을 수신해야 하므로 예비 VM에 매우 적합합니다. 사용자가 Slack 이나 Discord에 명령어를 입력하면 해당 명령어가 서버에 ping을 보내고 서버는 응답합니다. 이러한 서버는 항상 켜져 있어야 하고 명령을 수신해야 하므로 예비 VM이 매우 유용합니다. 봇을 위해 수행하는 계산이나 작업이 그다지 집약적이지 않다면, 슬랙봇이 사용자에게 응답하지 않고 매일 20분마다 메시지만 보내는 경우라면 예약 배포를 사용하는 것도 가능하며, 이 방식이 더 저렴할 수 있습니다. 하지만 항상 켜져 있어야 하는 경우에는 예약 VM을 사용하는 것이 좋습니다. 마지막으로 포트 구성은 대부분 선택 사항입니다. 앱이 반복적으로 실행되는 경우 포트가 자동으로 구성되므로, 앱 배포에 문제가 있거나 앱을 실행하지 않았 거나 포트를 구성하지 않은 경우가 아니라면 신경 쓸 필요가 없습니다. 모든 것을 제대로 설정했다면 포트 구성은 필요하지 않을 것입니다. 이제 마지막 배포 유형인 자동 확장 배포에 대해 설명하겠습니다. 자동 확장 배포는 서버 크기를 조정하여 애플리케이션 트래픽 변화에 맞춰 확장 또는 축소할 수 있습니다. 예를 들어 트위터에 게시물을 올리거나 앱을 개발하여 테스트하는 경우를 생각해 보세요. 트래픽이 얼마나 증가할지 예측하기 어려울 수 있습니다. 누구나 사용할 수 있고, 그냥 X 플랫폼( 예전에는 트위터로 알려졌던 곳)에 올리면 입소문을 타고 수백만 명이 방문할 수도 있습니다. 자동 확장 배포를 제대로 구성하면 사용자가 사이트에 접속할 때 자동으로 머신 수를 늘릴 수 있습니다. 적절한 머신 리소스를 선택하면 앱의 기능에 따라 시행착오를 거쳐 최적화할 수 있지만, 리소스를 제대로 구성하면 사용자가 많아져도 중단 없이 앱을 사용할 수 있습니다. 여러 인스턴스를 생성하고 앱을 확장하여 모든 사용자를 수용할 수 있기 때문입니다. 따라서 자동 확장 배포는 매우 강력한 기능입니다. 하지만 반대로, 아무도 앱을 사용하지 않는다면 문제가 될 수 있습니다. 솔직히 말해서, 제가 X에 게시하는 대부분의 콘텐츠가 그렇습니다. 입소문이 날까 걱정할 필요가 없다면, 콘텐츠를 게시하고 빌드하는 데 집중해야 합니다. 아무도 보지 않기 때문이죠. 마치 예약된 VM을 여러 개 생성해 놓으면 항상 실행되고 있는 것처럼 말입니다. 항상 실행되지만, 자동 확장 배포의 경우 아무도 애플리케이션을 보지 않으면 실행 규모가 0으로 줄어듭니다. 즉, 마치 노트북이 절전 모드로 들어가는 것처럼 완전히 꺼지는 것입니다. 배포도 절전 모드로 전환됩니다. 아무도 애플리케이션을 보지 않다가 누군가 접속하면 잠시 깨어나는 시간이 있을 수 있습니다. 마치 컴퓨터가 깨어나는 것과 비슷하지만, 보통 1 ~2초 정도로 거의 느껴지지 않습니다. 그 후에는 다른 사용자들이 애플리케이션을 사용하는 동안에도 실행 상태가 유지됩니다. 이는 애플리케이션이 절전 모드일 때 빌드가 발생하지 않기 때문에 비용 절감에 매우 효과적입니다. 물론 장단점이 있는데, 이에 대해서는 영상 후반부에서 자세히 설명하겠습니다. 자동 확장 배포를 사용하려면 선택적으로 빌드 명령과 실행 명령이 필요하며, 포트 구성도 필요합니다. 포트 구성은 대부분 이미 설정되어 있을 것입니다. 또한, 자동 확장 배포에는 더 많은 구성 옵션이 있습니다. 자동 확장을 통해 배포할 때 머신 유형을 선택하는 것이
