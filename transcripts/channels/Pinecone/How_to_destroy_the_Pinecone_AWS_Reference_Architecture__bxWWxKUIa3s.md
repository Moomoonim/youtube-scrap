## 스크립트

안녕하세요, 저는 Pine Cone의 Zach입니다. 지금부터 Palumi를 사용하여 배포된 AWS 참조 아키텍처를 삭제하는 방법을 안내해 드리겠습니다. 왼쪽에는 방금 전체 참조 아키텍처를 배포한 모습이 보이고, 오른쪽에는 점프 HST를 통해 중앙 RDS PostgreSQL 인스턴스에 연결된 모습이 보입니다. 익숙하지 않으신 분들을 위해 설명드리자면, 저장소에 오셔서 참조 아키텍처의 구성도를 보시면 프런트엔드 UI와 ECS 마이크로서비스는 VPC의 퍼블릭 서브넷에 의도적으로 배포되어 있습니다. 나머지 두 마이크로서비스와 PostgreSQL 데이터베이스 자체는 프라이빗 서브넷에 있습니다. 이는 인터넷을 통한 PostgreSQL 데이터베이스에 대한 직접 접근을 차단하기 위한 의도적인 설계입니다. PostgreSQL 데이터베이스에 직접 접근할 수 있는 것은 백엔드에서 실행되는 두 마이크로서비스인 Pelican과 Emu뿐입니다. 프런트엔드도 보안 그룹 설정 덕분에 직접 접근할 수 있지만, 클라이언트 컴퓨터에서는 프라이빗 서브넷에 있는 PostgreSQL에 직접 연결할 수 없습니다. 이는 많은 아키텍처에서 흔히 볼 수 있는 패턴이며, 저희 아키텍처에서도 마찬가지입니다. 저희는 데이터베이스 영구 저장 계층을 안전하게 보호하기 위해 의도적으로 이러한 분리를 만들었습니다. 따라서 해당 계층에 직접 액세스하려면 여기 저장소에 있는 지침을 따라야 하며, 일반적인 작업에 대한 목차에서 링크를 찾을 수 있습니다. 그러면 점프 호스트 사용 방법, 실행 방법, 점프 호스트 작동 방식에 대한 설명이 나오는 섹션이 나옵니다. 중요한 점은 제가 지금 하는 것처럼 PostgreSQL 과 직접 상호 작용하기 위해 점프 호스트를 실행하는 경우(예: 이슈 카운트, ARB, 임의 SQL 쿼리 등) 해당 점프 호스트에는 Palumi가 프로비저닝되지 않았다는 것입니다. 이는 AWS에서 ClickOps, AWS CLI 또는 API를 통해 몇 가지 설정을 되돌려야 한다는 것을 의미합니다. 그래야 Palumi destroy 명령을 실행하여 Palumi가 아키텍처를 깔끔하게 해체하는 데 필요한 모든 API 호출과 종속성을 처리할 수 있는 참조 아키텍처 상태로 만들 수 있습니다. 이제 보안 그룹 변경 사항을 되돌리는 작업을 시작하겠습니다. 우리는 AWS 콘솔에서 설정을 완료했고, 이제 Palumi Disclose 명령어를 사용하여 참조 아키텍처를 삭제할 것입니다. 먼저 이해해야 할 것은 데이터베이스에 자체 보안 그룹(RDS 보안 그룹)이 있다는 것입니다. Palumi 코드에 명시된 대로 이 보안 그룹은 기본적으로 두 가지 보안 그룹에만 접근 권한을 부여합니다. 하나는 프런트엔드 보안 그룹으로, 사용자에게 표시되는 프런트엔드 UI에 시맨틱 검색 테이블을 제공하는 그룹입니다. 다른 하나는 Pelican 보안 그룹으로, Pelican 마이크로서비스가 PostgreSQL에 직접 연결하여 변경된 레코드를 수신하는 데 사용됩니다. 이 비디오의 이전 섹션에서 점프 호스트를 설정하는 과정에서 배포 후 수동으로 인바운드 규칙을 추가했습니다. 이 규칙은 EC2 점프 호스트를 프로비저닝하는 데 사용된 Launch Wizard 2라는 보안 그룹도 이 RDS 인스턴스에 접근할 수 있도록 허용하는 것입니다. 이 규칙 덕분에 개발자 컴퓨터에서 SSH를 통해 점프 호스트로, 그리고 점프 호스트에서 RDS 인스턴스로 쿼리를 전송할 수 있습니다. 그리고 결과가 다시 제게 스트리밍되고, 이 모든 과정은 여기에서 다시 설명되어 있습니다. 단계별로 따라가면서 이해하고 싶으시다면, 다이어그램과 문서도 참고하시면 됩니다. 수동 설정 방법도 설명되어 있으니, 이제 역순으로 진행해 보겠습니다. 먼저 RDS 보안 그룹에 대한 인바운드 규칙을 다시 편집하고, 점프 포스트에 액세스 권한을 부여하기 위해 수동으로 추가했던 규칙을 삭제하겠습니다. 이제 세션을 종료한 후 점프 포스트에서 RDS에 직접 다시 연결하려고 하면, 필요한 네트워크 연결이 더 이상 없기 때문에 명령이 영원히 멈추는 것을 확인할 수 있습니다. 또한, 앞서 언급했듯이 전체 아키텍처가 배포되었고, 세 개의 마이크로서비스와 각각의 ECS 클러스터가 실행 중인 것을 확인할 수 있습니다. 시스템이 현재 부하 상태이고 레코드를 처리 중이므로 스케일아웃 동작이 나타나는 것을 볼 수 있습니다. 따라서 가장 먼저 RDS 보안 그룹 변경 사항을 되돌렸습니다. 배포된 사용자 지정 VPC가 종속성 문제로 인해 영원히 멈추는 것을 방지하기 위해 수동으로 해야 할 작업이 하나 더 있습니다. 여기에서 이전에 시작한 점프 호스트 또는 배스천 호스트를 찾아서 종료해야 합니다. 종료 확인을 클릭하고 완전히 삭제될 때 까지 기다려야 합니다. 이 EC2 인스턴스 또는 점프 호스트는 탄력적 네트워킹 인터페이스를 사용하기 때문입니다. 먼저 이 인스턴스를 제거하지 않고 Palumi를 통해 ` palumi destroy` 명령을 실행하면 Palumi가 VPC를 제거하기 위해 호출하는 API가 종속성 문제로 인해 10~20분 동안 멈출 수 있습니다. 따라서 Palumi는 배스천 호스트를 인식하지 못하므로 수동으로 배스천 호스트를 삭제하는 것이 훨씬 효율적입니다. Palumi는 인프라스트럭처 코드 외부에서 배스천 호스트를 실행했기 때문입니다. 이제 이 인스턴스가 사라진 것을 확인할 수 있습니다. 환경 변수를 모두 설정한 동일한 세션의 터미널로 돌아가서 ` palumi destroy` 명령을 실행해 보겠습니다. 이 명령이 어떤 작업을 수행하는지 살펴보면 참조 아키텍처의 일부로 정의된 스택의 모든 리소스( 출력 등)가 모두 삭제되는 것을 확인할 수 있습니다. 따라서 ' 예'를 선택할 수 있습니다. 일반적으로 Palumi를 통해 배포된 참조 아키텍처의 해제 프로세스는 매우 원활하지만, 간혹 일부 리소스가 멈춰서 수동으로 삭제해야 하는 경우가 있습니다. 이제 해제 과정이 진행되는 것을 지켜보겠습니다. 제 경험상 이 시스템을 배포하고 해제하는 과정에서 가장 흔하게 문제가 발생하는 리소스는 방금 언급한 문제와 같은 이유로 사용자 지정 VPC입니다. 예를 들어 RDS 보안 그룹 업데이트를 해제하는 것을 잊었거나, 백엔드 리소스에 직접 액세스하기 위해 프로비저닝한 Bastion 또는 JumpPost 서버를 수동으로 종료하는 것을 잊은 경우 사용자 지정 VPC 해제에 시간이 더 오래 걸릴 수 있습니다. VPC가 완전히 해제되려면... 탄력적 네트워크 인터페이스를 포함한 모든 종속성을 완전히 제거해야 합니다. ECS 서비스, 점프 호스트, RDS 등이 사용하는 모든 종속성, 즉 보안 그룹도 모두 제거해야 합니다. 다시 한번 강조하지만, 여기서 핵심은 인프라스트럭처 코드(IAC), Palumi 외의 부분, 즉 index.ts 타입스크립트 파일에 정의되지 않은 모든 작업은 원래대로 되돌려야 한다는 것입니다. AWS CLI 또는 UI를 사용하여 변경 사항을 되돌릴 수 있습니다. 계정에 index.ts 파일에 등록된 리소스만 배포된 상태가 되면 Palumi destroy 명령을 실행하고 기다리면 됩니다. 또한 다양한 리소스가 중단되지 않도록 주의해야 합니다. 예를 들어 프런트엔드 서비스인 Pelican 서비스, Emu 서비스의 경우, 방금 배포한 참조 아키텍처에서 보았듯이 테스트 중이라 부하가 걸린 상태였기 때문에 레코드가 많이 처리되고 있었습니다. Palumi destroy 명령은 기본적으로 ECS API에 다음과 같이 지시합니다. 해당 서비스를 강제로 삭제하고 실행 중인 ECS 컨테이너도 모두 삭제하여 작업이 원활하게 진행되도록 합니다. RDS 데이터베이스가 삭제되면 RDS 보안 그룹으로 이동하여 실제 서비스들을 삭제하기 시작합니다. Emu 서비스는 여전히 삭제해야 하고, 애플리케이션 로드 밸런서와 마이크로서비스용 보안 그룹도 삭제해야 합니다. 이제 삭제해야 할 사용자 지정 VPC의 종속성들을 삭제하는 단계로 넘어갑니다. 역순으로 진행하면서 먼저 경로, 라우팅 테이블 연결, NATA 게이트웨이를 삭제한 다음 VPC 자체를 삭제합니다. NATA 게이트웨이 삭제는 RDS 인스턴스 삭제와 마찬가지로 각각 몇 분 정도 소요됩니다. 게이트웨이 삭제가 완료되면 서브넷을 삭제하고, SQS를 삭제하고, 임대했던 탄력적 IP 주소를 해제하여 사용자 지정 VPC에 필요한 모든 종속성을 제거합니다. 이제 종속성 삭제가 완료되었으므로 사용자 지정 VPC 자체를 삭제합니다. 바로 이 부분에서 작업이 중단될 수 있습니다. 오랫동안 또는 조용히 멈춰있는 상태로 남아 있을 수 있습니다. 만약 Palumi Band에서 변경했던 점프 호스트 변경 사항을 되돌리지 않았다면 말이죠. 따라서 참조 아키텍처를 삭제하려면 먼저 이 작업을 수행해야 합니다. 그래야 비교적 원활하게 해제할 수 있습니다. Palumi가 이미 VPC를 삭제하려고 시도하는 경우, 저는 가끔 참을성이 없을 때 VPC를 직접 찾아서 수동으로 삭제합니다. 여러 가지 이유로 이 방법이 조금 더 빠를 수 있습니다. Palumi는 삭제가 완료되면 비교적 빠르게 변경 사항을 인식합니다. 따라서 종속성이 정리되어 더 이상 남아 있지 않다면 이 방법으로 좀 더 빠르게 작업을 완료할 수 있습니다. 그러면 참조 아키텍처를 처음 적용했을 때 생성했던 것과 동일한 수의 리소스가 삭제됩니다. 소요 시간은 참조 아키텍처를 배포하는 데 일반적으로 걸리는 시간보다 정확히 1분 정도 빠릅니다. 즉, 환경 변수를 필요한 대로 설정한 후 약 17분 30초 정도 소요됩니다. 참조 아크의 반복이며 삭제하는 데 걸리는 시간과 거의 비슷합니다. 물론 특별한 문제가 발생하지 않는다는 가정하에 말이죠. 자, 이것이 바로 플루미를 사용하여 참조 아크를 삭제하는 방법입니다.
