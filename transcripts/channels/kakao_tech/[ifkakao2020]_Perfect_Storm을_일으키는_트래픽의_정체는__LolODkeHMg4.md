## 스크립트

안녕하세요. 카카오 커머스에서 선물하기를 맡고 있는 이즈입니다. 카카오 커머스에서는 올해 이프 카카오의 세션 두 개를 준비했습니다. 둘 다 대량의 트래픽 대응에 관한 주제인데요. 이번 세션에서는 미시적 관점에서 트래픽을 JBM 특성과 함께 분석해 본 결과로 퍼펙트 스톰을 일으키는 트래픽의 정체는이라는 제목을 붙여 봤습니다. 두 번째 세션에서는 거시적 관점에서 대량의 트래픽에 대응하기 위해 고민하다 개발한 페이스 메이커에 대해서 설명드릴 예정입니다. 퍼펙트 스톰이란 무엇일까요? 개발 분야에서는 다소 생소할 수 있는 용어인데요. 작은 태풍이 우연치 않게 다른 자연 현상과 만나 초대형 태풍으로 지나는 것을 말합니다. 경제 분야에서는 여러 악제가 겹쳐서 일어나는 절체 절명의 경제 위기를 뜻하죠. IT 서비스인 선물하기에서는 어떤 퍼펙트 스톰이 발생할 수 있을까요? 먼저 본 세션을 준비하는 계기가 된 간헐적으로 출렁이는 트래픽 상황을 설명드리고 해당 문제의 원인을 파악하는 과정에서 알게 된 주연 지시의 특징. 이런 특징이 리모트 API 호출이 많은 MS 환경에서 발생시킬 수 있는 문제들. 그리고 갑작스러운 대량의 트래픽이 어떻게 문제를 증폭시켜 퍼펙트 스톤과 같은 장애 상황을 유발할 수 있는지 말씀드리도록 하겠습니다. 간헐적으로 출렁이는 트래픽 상황에 대해서 말씀드리도록 하겠습니다. 선물하기는 매년 거래액 50% 이상 빠르게 성장하고 있는 서비스입니다. 늘어나는 트래픽에 대응하기 위해서 전체 시스템의 확장성 개선을 위해 다양한 프로젝트가 진행 중입니다. 모리틱한 서비스 구조를 그림처럼 도메인별 서비스로 분리하여 MS 하는 구조와 개선도 그 중 하나입니다. 그런데 언제부터인지 외브 트래픽은 변화가 없는데 내부 API 서버군에서 간헐적으로 쓰레쉬 홀드를 넘는 알람이 발생하였습니다. 문제 서버는 노란 서버인데요. 노란 서버로 유입되는 트래픽이 그래프처럼 출렁이는 패턴을 보이고 있었습니다. 산내 APM 툴로 각 서버근의 CPU, 메모리, 네트워크 사용량 등의 리소스 상태를 확인해 봐도 별 이상이 없는 겁니다. 노란 물음표 서버군에서 지연 지시의 액티비티가 비교적 활발하긴 했지만 100m세 수준의 퍼스트 타임이라 무시할 만한 수치로 보였습니다. 자바 기반의 서비스를 오랜 기간 운영하신 분들이면 비슷하게 느끼실 텐데요. JDK8에서 지연지가 안정화된 후부터는 JBM GC에 별로 신경을 쓰지 않아도 별 이슈가 없었습니다. 지연 지시 설정으로 오랜 기간 안정적으로 서비스를 운영해 왔었는데 100m세 수준의 퍼스트 타임이라 조금 더 알아보시죠. 운영하면서 별다른 문제가 없어서인지 G 지원시의 동작 방식에 대해서 자세히 모르고 있었던 거 같습니다. 이번 기회에 GGC 이전의 GC들의 문제점과 GGC에서는 이런 문제점을 어떻게 해결했는지 알아보도록 하겠습니다. 먼저 가장 오래 전에 사용된 패럴 올드 GC에 대해서 알아보겠습니다. 패럴 올드 GC의 메모리 레이아웃을 보면 화면과 같습니다. 0올드 영역으로 구분되어 있고 에덴 영역에서 생성된 객체가 마이너지 GC마다 나이를 먹어서 올드로 프로모션 되는 방식입니다. 패널 올드 GC에서는 메이저 GC 발생 콤팩션을 하기 때문에 힙 사이즈를 1기가 이상 할당할 경우 퍼스트 타임이 2에서 3초로 길어지는 이슈가 있었습니다. 그래서 힙 사이즈를 1기하로 주고 재비엄 인스턴스를 여러 개 띄우는 운영 노하우가 필요했습니다. 하드웨어는 계속 발전하여 사용할 수 있는 메모리량은 커져 갔지만 자바가 제대로 하드웨어 리소스를 활용하지 못하는 느낌이었죠. 이후 대용량 메모리를 사용할 수 있는 CMS가 도입되었는데요. CMS에 대해서는 메이저 GCC의 퍼스트 타임이 마이너지 GC 정도로 짧다고 대부분 알고 계실 겁니다. 더 큰 메모리를 할당 가능한데 퍼스트 타임이 짧았던 이유는 올드 영역 GC 때 콤팩션을 하지 않아서였습니다. 그래서 오랜 기간 운영하다 보면 결국 메모리가 단편화되고 프로모션 실패를 겪게 됩니다. 그러면 콤팩션을 동반한 풀 GC가 실리 GC 방식으로 동작하기 때문에 퍼스트 타임이 훨씬 길어지고 시스템 안정성에 문제가 생깁니다. CMS의 초기 메모리 레이아웃은 제네레이션널 개념으로 구분된 건 패널러 올드 지시와 동일하지만 앞에서 언급된 프로모션 실패를 억제하기 위해서인지 올드 영역을 최대한 크게 할당하였습니다. 에덴 영역이 작아져서 올드 영역으로 불필요하게 프로모션 되는 문제를 줄이기 위해 테니어링 쓰레시홀드를 4로 유지하는 방식으로 0 영역에서의 시간을 확보했습니다. 지연 지시의 경우는 기존의 메모리 레이아웃인 제레이션 개념을 탈피했습니다. 물리적인 메모리 영역의 구분을 없애고 바둑판 모양의 동일한 크기를 가지는 리즌을 통해서 논리적으로 존재하도록 설계되었는데요. GC에서 카피 콤팩션 등의 비싼 작업을 위진 단위에 작은 작업으로 쪼겠다고 이해하시면 됩니다. 이렇게 나눠져 있기 때문에 목표 정지 시간에 설정이 가능하고 최대한 이에 부합하게 동작합니다. 지연 지시까지의 개선 방향을 보면 대형량 메모리 지형과 풀지로 인한 긴 퍼스트 타임의 개선에 포커싱되어 있습니다. 지연 지시의 경우 디폴트로 0 영역을 전체 힙해서 60% 정도로 활당합니다. 마이너지 C는 0 영역의 리즌들이 가득찰 때 실행되어 대부분의 리즌은 가비지로 회수됩니다. 살아 있는 객제들은 서바이벌 영역으로 카피되고 콤팩션 됩니다. 목표 전기 시간이 기본 200mm으로 설정되어 있고 실제 서버에서 모니터링해 봐도 평상시 트래픽에서는 100에서 200mm 수준으로 동작하는 걸 확인할 수 있습니다.이 시점에서 많은 분들이 오해하고 계신 내용인데 마이너지c 스타더 월드입니다. 패럴 GC, CMS 등에서는 마이너 GCC의 퍼스트 타임 자체가 아주 작은 값이라서 신경 쓸 필요가 없어서 그렇지 스톱더 월드로 동작합니다. 앞으로의 얘기는 지원 G시에서 마이너 지c시로 인한 100에서 200m세의 스타더 월드가 서비스에 미치않는 영향에 대한 이야기입니다. 스타터 월드가 서비스에 미치는 영향은 그림처럼 단순하게 표현할 수 있습니다. 쓰레드펄 리퀘스트 모델을 가정하고 설명드리겠습니다. 오른쪽 그림처럼 응답 시간이 지시로 인한 퍼스트만큼 증가한 걸 볼 수 있는데요. 지연 지시를 사용하고 있어 100ms의 퍼스트 타임이 생겼고이 정도의 지연은 별 이슈가 아닐 것 같습니다. 그럼 외부 API를 호출한 경우는 어떤 영향이 있을까요? 앞에서와 동일한 요청인데 이번에는 요청 중간에 외부 API를 호출하여 100m세만에 응답을 받아 총 응답 시간은 150m을 상황을 가정해 봅시다. 외부 API 노출 중에 지시가 발생한다면 어떻게 될까요? 앞서 본 것처럼 GC 실행 시간 100m을 더해 응답 시간이 250mm이 될까요? 아니요. 그렇지는 않습니다. 외부 API를 호출한 점선 구간은 실제적으로는 대부분 응답을 기다리고 있는 구간입니다. 응답을 기다린 상태인데 다시 스타트 월드가 된 거죠. 그림의 빨간 화살표 구간은 구체적으로 어떤 상황일까요?이 이 부분을 이해하기 위해서는 GC가 스타더 월드를 구현하는 방식을 알아야 합니다. JBM은 GC가 실행될 때 어떻게든 쓰레드를 멈추게 할 수 있을까요? 세이프 포인트라는 방식을 사용하는데요. 세이프 포인트는 말 그대로 안전한 지역으로 해석할 수 있습니다. JBM이 스택과 힙을 안전하게 조작할 수 있도록 스레드를 유지할 수 있는 영역을 말합니다. 쓰레드가 락 대기 상태이거나 웨이팅 상태일 때 세이프 포인트 영역에 있다고 볼 수 있습니다. 제인하이 코드로 진입하는 구간도 세이프 포인트입니다. 세이프 포인트 영역은 컴파일 타임에 그림처럼 바이트 코드에 마킹됩니다. 스톱 월드에서는 JBM이 각 쓰레드를 직접 제어하는게 아니라 쓰레드들이 세이프 포인트 영역에서 실행될 때 플래그를 주기적으로 확인해서 스톱더 월드 상태일 경우 멈추는 방식으로 동작합니다. 이해하시기 편하게 RMI 관련 쓰레드 덤프를 가지고 왔습니다. 참고로 지시로 인한 스타트 월드뿐만 아니라 쓰레드 덤프나 힙 덤프를 뜨게 될 때도 동일한 세이프 포인트 방식이 적용됩니다. 자바코드 영역을 실행하던 쓰레드는 세이프 포인트 영역이 아니라서 스톱더 월드인 상황이라도 계속 실행되게 됩니다. 이런 호출의 흐름은 결국 소켓 인풋 스트림 클래스의 소켓 리드 메소드에서 JNI를 통해 네이티브 코드 영역으로 진입합니다. 앞에서 말씀드린 것처럼 JNI는 세이프 포인트 영역입니다. 세이프 포인트 영역에서 지시로 인한 스톱 더 월드가 발생한다고 해서 반드시 해당 쓰레드가 바로 블락되는 것은 아닙니다. 당장은 아니지만 언젠가는 블락될 것이 확실합니다.이 경우에도 JNI를 통해 네이티브 코드 영역으로 진입한 쓰레드는 GCS 스타더 월드에 영향을 받지 않고 계속 실행되게 됩니다.이 이 상태에서 외브 API의 응답이 도착해서 다시 자바코드 영역으로 진입하는 순간 세이프 포인트 영역을 벗어나기 전 스톱더 월드 상황을 확인하고 블락되어 GC가 끝나길 기다리게 됩니다.
