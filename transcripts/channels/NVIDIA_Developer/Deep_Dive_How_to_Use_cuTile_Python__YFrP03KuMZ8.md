cuTile is an array oriented programming&nbsp; model for NVIDIA GPUs that automates block&nbsp;&nbsp; level parallelism, memory movement, and tensor&nbsp; core utilization. We've built it to simplify&nbsp;&nbsp; GPU programming and to improve portability for&nbsp; hardware features like tensor cores and tensor&nbsp;&nbsp; memory accelerators. cuTile is simpler and higher&nbsp; productivity than traditional simpy programming.&nbsp;&nbsp; You should be able to get good performance faster&nbsp; with it. However, you do have less control than&nbsp;&nbsp; with simpy. With cuTile, you don't have to decide&nbsp; how data is loaded, mapped to threads, and stored&nbsp;&nbsp; locally. The system does that for you. You just&nbsp; express your computation as array operations. It's also not portable.&nbsp;&nbsp; The code you'd write would change from GPU&nbsp; architecture to GPU architecture. With cuTile,&nbsp;&nbsp; we can write the simple code on the right&nbsp; and get good and portable performance. cuTile will be exposed first in Python, but&nbsp; a C++ dialect is also coming, which will be&nbsp;&nbsp; intentionally similar to what you've seen today,&nbsp; but will use modern C++ idioms and best practices. cuTile is built on top of tile IR a novel&nbsp; low-level compiler stack an intermediate&nbsp;&nbsp; representation for tile programs that we've&nbsp; developed cuTile Python kernels are JIT&nbsp;&nbsp; compiled to tile IR using an execution model&nbsp; that allows the code to be executed without&nbsp;&nbsp; the need for a Python interpreter similar&nbsp; to Numba's no Python compilation mode this&nbsp;&nbsp; model has some semantic compromises All objects&nbsp; have either value or pointer semantics. There's&nbsp;&nbsp; no reference counting and you can't do some&nbsp; Pythonic things like dynamically modify types. In traditional simpy, the unit of execution is a&nbsp; thread. You write functions that are executed by&nbsp;&nbsp; many threads at once organized into a hierarchical&nbsp; grid. We call these functions kernels. In coup&nbsp;&nbsp; tile, the unit of execution is a block. A block&nbsp; is a group of threads or execution resources that&nbsp;&nbsp; has a single thread of control. You can write tile&nbsp; kernels that are executed by many blocks at once,&nbsp;&nbsp; but each block only executes the kernel once&nbsp; on the control thread. In simple elements,&nbsp;&nbsp; you write scalar operations on elements&nbsp; that each thread performs. If you want&nbsp;&nbsp; each thread to apply an operation to multiple&nbsp; elements, then you'd write a for loop. There&nbsp;&nbsp; are no native array operations in CUDA&nbsp; simpy. On the other hand, in cuTile,&nbsp;&nbsp; everything is an array. You express&nbsp; blockwide operations on entire arrays.&nbsp;&nbsp; Let's look at an example. When running a simp&nbsp; kernel, each thread within a block will execute&nbsp;&nbsp; the kernel. But a tile kernel is run by just a&nbsp; single thread per block. Within a tile kernel,&nbsp;&nbsp; we create tiles which are a special type of local&nbsp; array that you can perform array operations on.&nbsp;&nbsp; Those array operations are sequential with&nbsp; respect to the control thread, but they may&nbsp;&nbsp; be paralyzed under the hood by the system using&nbsp; the blocks threads and other execution resources. If you know how to use numpy, then you know how&nbsp; to use catile python. Here's an example of softmax&nbsp;&nbsp; written in the left in straight numpy and in the&nbsp; right in cuTile. Cut tile is array based and there&nbsp;&nbsp; are two kinds of arrays in coup tile. Global&nbsp; arrays are typical numpy like mutable arrays&nbsp;&nbsp; that are accessible by all tile blocks. If you&nbsp; modify their contents any other references to&nbsp;&nbsp; the underlying data will see the changes. They&nbsp; are passed in as kernel parameters or globals.&nbsp;&nbsp; You can only perform a limited set of operations&nbsp; on global arrays in tile code. Most importantly,&nbsp;&nbsp; loading from them to create tile arrays or storing&nbsp; tile arrays to them. Tile arrays are immutable&nbsp;&nbsp; numpy like arrays that are local to a block.&nbsp; Operations on tile arrays always return a copy,&nbsp;&nbsp; not a view, and are paralyzed across the block.&nbsp; Most of the operations that you can perform on&nbsp;&nbsp; numpy arrays will be supported on tiles. These&nbsp; array operations will be parallelized using the&nbsp;&nbsp; blocks execution resources. But from the&nbsp; perspective of the block's single thread&nbsp;&nbsp; of control, these operations are performed&nbsp; sequentially. All of CUDA's underlying launch&nbsp;&nbsp; APIs support both Simpy and Tile kernels. Users&nbsp; don't have to care how a kernel was written, be&nbsp;&nbsp; it simpy or tile to use it. That means you can use&nbsp; and integrate tile kernels anywhere that you can&nbsp;&nbsp; use simp kernels in kupi, kudf, PyTorch, jacks,&nbsp; etc. Array parameters to kernel launches can be&nbsp;&nbsp; anything that satisfies DLPAC. So numpy arrays,&nbsp; coup arrays, PyTorch arrays, jacks arrays, etc. Tile arrays have value semantics which simplifies&nbsp; compiler analysis by eliminating problems such&nbsp;&nbsp; as aliasing. Tile arrays are immutable&nbsp; and all tile operations return copies&nbsp;&nbsp; not views. Some numpy array operations such as&nbsp; indexing, reshaping, and transposing typically&nbsp;&nbsp; return views not copies when possible. The tile&nbsp; equivalence will always return copies, not views. Assignment to the elements of a tile is&nbsp; ill-formed. They're cheap to copy and&nbsp;&nbsp; won't be materialized unnecessarily. Imagine an&nbsp; architecture where all the instructions are array&nbsp;&nbsp; operations and all the operons and registers are&nbsp; arrays. That's the tile programming model. If a parameter to a kernel is&nbsp;&nbsp; annotated with cuda.tileconstant, then it will be&nbsp; constant embedded and can be used as a tile shape.&nbsp;&nbsp; All uses of the parameter will behave&nbsp; as if they were replaced by the literal&nbsp;&nbsp; value of the parameter. In tile programming, the system decides&nbsp; where the tile will be stored.
