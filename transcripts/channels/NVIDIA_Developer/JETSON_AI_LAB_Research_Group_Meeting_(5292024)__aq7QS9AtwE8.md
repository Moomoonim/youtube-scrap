" 오늘 날씨 어때?" "피츠버그." 네, 모델이 물어봤죠. 시스템 프롬프트에 이미 피츠버그라고 나와 있으니 당연히 알고 있어야 했지만요. 물론 이미 알고 있다는 걸 다시 알려줄 수도 있지만, 어쨌든 제가 알려준 내용을 인수로 전달하고 호출해서 응답을 보냈습니다. 이 방식의 또 다른 장점은 함수에서 응답을 따로 다듬을 필요가 없다는 겁니다. REST API 등에서 가져온 전체 JSON 데이터를 그대로 반환하기 때문에 모델이 바로 활용할 수 있습니다. 예를 들어, 홈 어시스턴트에서 응답을 받았을 때도 마찬가지였죠. 이걸 필터링하는 건 정말 간단해요. 제가 이 모든 정보를 입력했는데도 켜져 있는지 꺼져 있는지 구분할 수 있더라고요. 날씨 설명도 마찬가지예요. 데이터를 많이 입력할수록 더 잘 작동하는 것 같아요. " 내일 날씨는 어때?"라고 물었더니 샌프란시스코라고 답하더군요. 이 경우에는 위치를 다시 물어봤는데, 아마 제가 입력값을 입력하는 방식 때문인 것 같아요. 이 기능을 제대로 이해하려면 문서가 정말 잘 작성되어야 할 것 같아요. 예를 들어, 위치를 입력하지 않으면 채팅에서 이미 알고 있는 이전 위치를 사용한다거나 하는 식으로요. 그러면 항상 " 어떤 위치의 날씨를 원하세요?"라고 묻지 않아도 되잖아요. 처음 테스트했을 때는 인수를 잘 제공해 주는 기능이 있어서 좋았는데, 이 경우에는 현재 날씨 함수와 예보 함수를 구분해서 호출할 수 있어요. 내일, 금요일, 다음 주말 등 원하는 기간에 따라 다음 5일간의 예보 데이터를 모두 반환해 줘요. 며칠 후 여기로 돌아와서 데이터를 추출하고 그에 대한 질문에 답할 수 있습니다. 날씨 봇 같은 걸 만드는 건 아니지만, 이 로봇이 가진 능력과 입력할 수 있는 인자, 호출 기능 등을 실험해 보기에 좋은 예시입니다. 꽤 유망해 보입니다. 아직 완벽하진 않지만, 더 다듬을 수 있는 부분이 있습니다. 다음에는 비전 시스템과 통합해서 더 많은 기능을 만들어 볼 생각입니다. 다양한 응답과 도구, 호출 기능 등을 갖춘 지금이 훨씬 에이전트처럼 느껴집니다. 흥미롭게도 Noose에는 Gen Struct라는 모델이 있는데, 이 모델은 사용자가 만든 에이전트 프로필을 기반으로 에이전트용 합성 학습 데이터 세트를 생성합니다. 이 모델이 학습에 사용할 데이터 세트를 만드는 것 같습니다. 이 부분을 살펴보고 더 세밀하게 조정할 수 있을 것 같습니다. 그리고 채팅 데이터도 수집하기 시작하고 싶습니다. 음, 그래서 시간이 지남에 따라 학습할 수 있도록 하는 거죠. 예를 들어, 잘못 입력하거나 이미 위치를 알고 있는데 잊어버리는 경우, 그냥 알려주면 " 아, 죄송합니다"라고 하고 요청한 대로 처리합니다. 그리고 채팅 기록을 녹음하고 수집해서 미세 조정을 하면, 시간이 지남에 따라 원하는 동작을 추출할 수 있을 겁니다. 그래서 음성으로 대화하는 게 훨씬 쉽죠. 하루 종일 타이핑하는 건 싫지만, ASR(자동 음성 인식) 기능 등을 이용해서 정보를 수집하는 건 좋습니다. 아, 채팅 중에 Carri라는 사람이 있었는데, 에이전트라는 용어가 언제, 언제 에이전트로 간주되는지 정확히 정의할 수 있을까요? 좋은 질문입니다. 제 생각에는 여러 모델이 관여하거나, rag 나 함수 호출 같은 작업을 수행하거나, 여러 번의 대화가 오가는 경우를 에이전트라고 생각합니다. 예를 들어, 화면을 다시 한번 보여드리겠습니다. 이 모든 게 잘 작동하도록 하려면, 에이전트라는 업계 용어는 없지만, 제 생각에는... 단순한 주고받기 채팅보다 훨씬 더 복잡합니다. 기본적으로 훨씬 더 비 구조적인 채팅이 진행되고 있었죠. 그래서 지난 한 달 정도 동안 채팅 기록에 채팅 상태가 저장되는 방식을 다시 검토해 봤습니다. 이제 각 채팅 메시지마다 별도의 클래스가 있습니다. 이러한 방식 덕분에 단순히 사용자끼리 주고받는 일반적인 채팅, 즉 한 사람이 봇과 대화하고 다시 사람이 봇과 대화하는 방식이 아니라, 사람이 봇에게 전화를 걸고, 봇이 다시 사람에게 전화를 거는 식의 개방형 채팅이 가능해졌습니다. 소스 코드보다는 문서를 참조하는 게 더 나을 것 같네요. 이러한 개방형 채팅 메시지 형식은 텍스트, 이미지, 오디오 등 다양한 모달리티를 지원할 수 있기 때문에 멀티모달 환경에도 매우 적합합니다. 또한, 이 데모에서 보여드린 것처럼 사용자, 봇, 도구 응답 등 다양한 역할을 지정할 수 있습니다. 이 채팅 템플릿은 별도의 파일에 정의되어 있는데, 이 기능을 위한 특별한 템플릿이 있어서 모든 것이 제대로 작동하게 되었습니다. 그리고 이 템플릿은 KV 캐싱 및 채팅 관리와 같은 모든 기능과 통합되었습니다. 한 가지 알아차리실 점은 이러한 채팅이 간단한 대화만으로도 많은 토큰을 소모하기 시작했다는 것입니다. 시스템 프롬프트가 너무 길어서 거의 2,200개의 토큰을 사용했습니다. 하지만 LLM 추론 및 KB 캐싱 등을 최적화하기 위해 기울인 모든 노력 덕분에 이제는 괜찮습니다. 그리고 제 생각에는 이 채팅을 한 번에 1~2분 이상 사용하는 경우는 거의 없을 것이기 때문에 이 정도가 적절하다고 생각합니다. 다음에 다시 접속하면 해당 채팅을 저장한 후 새 채팅이 시작됩니다. 네, H&amp;R 및 R 플러그인은 동시에 실행될 수 있습니다. 예를 들어 날씨와 같은 봇 기능 플러그인을 통해서 말이죠. 이 모든 것을 동시에 실행할 예정이며, 다음 단계는 비전 언어 모델(VLM)과 통합하는 것입니다. 이를 통해 사용자가 질문을 하거나, VLM에서 지난 X분 동안 비디오 카메라의 캡션 정보를 표 형식으로 받아올 수 있도록 할 것입니다. 그런 다음, 이 정보를 요약하여 "몇 시에 사람이 화면에 나타났습니다."와 같은 정보를 제공할 수 있습니다. 또한, 쿼리를 변경하여 이미지에 몇 명이 있는지 확인할 수도 있습니다. 예를 들어, " 사람 찾기"와 같이 사용자가 요청하는 정보를 제공하고, 이미지에 몇 명이 있는지 계산해 줍니다. 이것이 제가 다음에 하고 싶은 작업이며, 이번 데모는 이러한 고급 기능을 실제로 구현할 수 있는지 확인하기 위한 것이었습니다. 지난 회의 이후로 저는 AWQ 기반 양자화 작업에도 더 집중해 왔습니다. 이번 데모에서는 AWQ 기반 TinyChat 백엔드를 사용했는데, NanoLM에서도 다시 작동하도록 만들었습니다. 지난 주말에는 Hugging Tra Hugging Face Transformers API와 AWQ API를 모두 다시 작동시켰습니다.
