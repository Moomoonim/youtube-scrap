Leta는 기본적으로 모든 상태 정보( 메모리 및 외부 데이터 소스 포함)를 활용하여 가장 중요한 정보를 설정된 토큰 예산 내에 압축하는 방식으로 관리합니다. 메시지 버퍼와 컨텍스트 메모리에 각각 일부를 할당하는 구조화된 컨텍스트 윈도우를 사용하고, 외부 데이터에 대한 재귀적 요약 및 통계 정보도 관리합니다. 이를 통해 LLM은 언제 외부 데이터를 쿼리해야 하는지 알 수 있습니다. 즉, 이러한 구조화된 컨텍스트 윈도우 관리가 컨텍스트 컴파일이라고 하며, 이를 통해 더 작은 컨텍스트 윈도우를 사용하면서도 효율적인 에이전트를 구축할 수 있습니다. 일반화 가능하다니 놀랍네요. 그러고 보니 어제 버클리에서 이 주제에 대한 논문이 나왔던 것 같은데, 어... 추론을 이용한 컨텍스트 윈도우 구조화에 관한 거였죠. 아, 죄송해요. 갑자기 이런 생각들이 떠오르네요. 팟캐스트에서 찰스와 처음 나눴던 대화가 생각났는데, 컨텍스트 윈도우를 여러 부분으로 나누는 것에 대한 거였어요. 예를 들어, 여기는 검색 컨텍스트, 여기는 내부 작업 메모리 같은 부분들이죠. 정말 흥미로운 아이디어네요. 음, 컨텍스트 윈도우 구조화에 대해 좀 더 자세히 알아볼 수 있을까요? 어느 정도의 구조를 말하는 건가요? 검색 컨텍스트, 작업 메모리 같은 부분만 있는 건가요? 아니면 그보다 더 복잡한 구조가 있는 건가요? 음, 제 생각에는 일반적인 애플리케이션에서 사용하는 것보다 몇 가지 추가적인 구성 요소가 더 있는 것 같아요. 대부분의 에이전트 애플리케이션에서는 처음에 시스템 프롬프트가 있고, 도구 정의도 있고, 그 외에도 다른 도구들을 사용하고 있을 거예요. 일종의 래그 기반 메모리 형태를 띠고 있어서 잠재적으로 관련 있는 메시지 5개 정도를 검색할 수 있고, 나머지는 컨텍스트 내 메시지로 표시됩니다. 이것이 오늘날 대부분의 에이전트 컨텍스트 윈도우가 보이는 방식이라고 생각합니다. Lea에서는 추가 구성 요소가 있습니다. 예를 들어 컨텍스트 내 메모리의 경우 개발자가 이러한 구성 요소에 할당되는 공간을 사용자 지정할 수 있습니다. 컨텍스트 내 메모리의 크기에 문자 제한을 설정할 수 있습니다. 컨텍스트 내 메모리는 여러 섹션으로 나뉘어 있는데, 일반적으로 사람용 섹션과 페르소나용 섹션이 있지만 개발자가 사용자 지정할 수 있습니다. 또한 재귀적 요약 기능도 있습니다. 메시지가 삭제되면 요약을 업데이트하여 LLM이 전체 메시지 기록을 지속적으로 관리할 수 있도록 합니다. 그리고 에이전트 래그는 사용하지 않지만, LM이 명시적으로 결정한 경우에만 과거 메시지를 검색합니다. 이 도구에 대해 말씀드리자면, 정말 놀랍고 흥미로운 아이디어가 너무 많아요. 다음 질문을 좀 더 신중하게 고르려고 하는데, 일종의 자기 편집 프롬프트 같은 걸로 시작해 보는 것도 재밌을 것 같아요. 음, 조금은요. 저는 인류 모델 컨텍스트 프로토콜(AMCP)을 좀 다뤄봤는데, 클라우드 데스크톱을 we8 같은 곳에 연결하면 데이터베이스에 메모리를 저장하는 기능이 정말 멋지더라고요. 챗봇을 사용하거나 작업을 수행할 때, "메모리를 저장해" 같은 프롬프트가 뜨면 어떤 결과가 나오는지, 어떤 종류의 메모리가 저장되는지 궁금합니다. 아마 이 질문은 답이 정해져 있지 않아서 어떤 것이든 될 수 있을 것 같아요. 네, 음, mgpt와 Noweta의 독특한 점 중 하나는 메모리 관리 책임을 LLM(로컬 메모리 관리자)에 맡긴다는 점입니다. 이 방식은 범용적인 접근 방식이라는 장점이 있고, LLM이 발전할수록 메모리 관리도 향상된다는 장점이 있습니다. 하지만 동시에... 약간 예측 불가능하다는 위험이 있다고 생각하는데, 그게 오히려 더 자연스럽다고도 할 수 있겠죠. 마치 인간이 기억하는 방식처럼요. 인간이 기억하는 것도 약간 예측 불가능하잖아요. 음, 기본적으로 LLM(로봇 메모리)이 어떤 정보를 컨텍스트 메모리에 저장할지 결정하는 건 LLM의 몫입니다.
