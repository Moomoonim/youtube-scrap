## 스크립트

Uploading a large amount of data, Quadrant doesn't just store vectors. It's handling payloads, indexes, and much more in the background. Because of this, there's no single configuration that works for all workflows. So, we're going to go through a bunch of different options and best practices that you can try. But before we get started, we need to understand the difference between dense and sparse vectors when indexing. Dense vectors typically use HNSW, while sparse vectors use a completely different indexing. Because they're different, they create different memory and performance considerations when during bulk uploads. First option is going to be storing dense vectors on disk. For large uploads, the raw vector data itself can consume a lot of RAM. Now, this can reduce your RAM usage as your collection starts to grow. The trade-off is that search may rely on more disk access, potentially increasing in latency. The second option is creating a payload before you upload. If you already know which fields you've been filtering on, such as categories, tenant IDs, sources, you can create those indexes first. This avoids creating indexes later when you've already uploaded everything. The trade-off is that only index fields you can actually plan to filter on. The final option for dense vectors is using quantization. Quantization allows you to have your original vectors on disk while being able to have a smaller compressed representation for search. Now, this is great cuz you can significantly reduce your memory while keeping your search performance practical. Trade-off is that compression may affect your search quality, so test it on your own data. Now, we just went through all three options for dense vectors. But now, let's talk about sparse vectors. For sparse vectors, we can actually put our index on disk. Now, this can be useful when large sparse indexes start to consume too much memory. Now, this is great because it starts to reduce your RAM usage as your index starts to grow. The trade-off is that sparse searches may become more dependent on disk performance. So far, we've been able to go over the best options for dense and sparse vectors. But let's cover some best practices for both. The first best practice is batching your uploads. Uploading points one at a time creates unnecessary network and processing overhead. A batch size starting from 64 to 256 is a good starting point. The trade-off is that large batches use more memory and more expensive to retry if they fail. The second best practice is using multiple upload workers. This allows several batches to be able to be sent at the same time instead of relying on one upload stream. But, start with a small number of workers and then slowly start to increase. The trade-off is that too much parallelism can overwhelm the CPU, memory, disk, and network resources. And finally, for larger uploads, consider the idea of multiple shards. Each shard has its own write path, allowing more ingestion to work in parallel. Now, this can work really well when you have it at the same time as upload workers. The trade-off is that every shard adds overhead. So, more shards are not always better. At the end of this, the right combination only can depend on your workload. Maybe you're prioritizing memory usage, ingestion speed, or search performance, or maybe a balance between them all. If you want to dive a little deeper, check out our article into bulk uploads.
