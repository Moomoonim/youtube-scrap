## 스크립트

이 비디오에서는 카오스 엔지니어링의 정의와 이유에 대해 알아보고, 카오스 엔지니어링을 수행하는 데 사용할 수 있는 도구인 AWS 장애 주입 시뮬레이터를 살펴본 후 데모를 통해 알아보겠습니다. 카오스 엔지니어링이란 무엇일까요? 카오스 엔지니어링은 애플리케이션에 장애나 오류를 인위적으로 도입하고 그 결과를 관찰한 후, 관찰 내용을 바탕으로 수정하는 것입니다. 왜 카오스 엔지니어링을 수행해야 할까요? 문제가 발생했을 때를 대비하기 위해서입니다. 장애는 불가피하며, "문제가 발생하는 순간이 우리를 선택한다"는 말을 항상 듣습니다. 따라서 문제가 발생했을 때 준비되어 있어야 합니다. 카오스 엔지니어링은 과학 실험과 같은 실험이므로 여러 단계를 거칩니다. 카오스 엔지니어링에는 어떤 단계가 있을까요? 첫 번째 단계는 정상 상태 단계입니다. 이 단계에서는 시스템이 계획대로 작동할 때의 정상적인 상태를 정의합니다. 즉, 모든 것이 계획대로 작동할 때의 시스템을 정의하는 것입니다. 정상 상태를 정의한 후에는 가설을 정의합니다. 가설을 세우고 무엇이 잘못될 수 있는지, 현금 흐름에 문제가 생기면 어떻게 될까, 로드 밸런서에 문제가 생기면 어떻게 될까와 같은 질문들을 스스로에게 던지게 됩니다. 가설을 정의한 후에는 실험을 시작하고 실행합니다. 실험을 실행할 때는 애플리케이션의 작은 부분부터 시작하여 학습한 내용을 바탕으로 반복적으로 개선해 나갑니다. 실행 후에는 결과를 검증하고 오류를 수정합니다. 오류를 수정하고 학습한 내용을 기반으로 애플리케이션을 개선하는 것입니다. AWS FIS는 애플리케이션에 오류를 주입하는 데 사용하는 AWS 관리 도구 또는 관리 서비스입니다. 이를 통해 학습하고, 학습한 내용을 바탕으로 애플리케이션을 반복적으로 개선할 수 있습니다. AWS FIS의 사용 사례는 무엇일까요? 예를 들어 경기 당일 시뮬레이션을 생각해 볼 수 있습니다. 과거에 경험했던 시즌별 트래픽 급증이나 애플리케이션의 취약점을 시뮬레이션할 수 있습니다. 또한 배포 파이프라인에 통합하는 것이 좋습니다. 프로덕션 환경 배포는 이미 자동화되어 있으므로 파이프라인에 통합하는 것이 효율적입니다. 또 다른 사용 사례로는 CPU 스트레스 테스트를 생각해 볼 수 있습니다. 인스턴스가 있고 데모를 보면 어떻게 보이는지 알 수 있습니다. 이미 이 실험에 사용할 E2 인스턴스가 있습니다. 몇 가지 속성을 자세히 살펴보겠습니다. VPC를 보세요. 나중에 중요합니다. 태그도 살펴보겠습니다. 이것도 나중에 중요합니다. 첫 번째 실험은 AWS 콘솔 또는 AWS CLI에서 생성할 수 있습니다. 콘솔에서 생성하는 방법을 살펴보고 거기서 실험을 시작해 보겠습니다. 이제 AWS 결함 주입 시뮬레이터로 이동하여 실험 템플릿을 생성해 보겠습니다. 템플릿에 설명을 입력합니다. 저는 간단하게 '간단히 중지할 수 있는 실험 1'이라고 입력했습니다. 이름과 설명은 원하는 대로 지정할 수 있습니다. 그런 다음 액션을 추가합니다. 액션은 이 실험에서 실제로 수행할 작업을 지정합니다. 액션 이름과 설명도 원하는 대로 지정할 수 있습니다. 이제 액션 유형에 대해 이야기해 보겠습니다. 앞서 말씀드렸듯이 이러한 실험을 수행할 수 있는 유형이 있습니다. 8 시간짜리 서비스 두 개 정도를 선택할 수 있는데, 이게 전부입니다. EC2 작업 유형을 선택했으니 인스턴스를 중지, 종료 또는 재부팅할 수 있습니다. 저는 EC2 인스턴스를 중지하도록 선택했습니다. 다음 옵션은 ' 시작 후'입니다. 여기서는 다른 작업이 완료된 후에 이 작업을 실행하도록 지정할 수 있지만, 저는 비워 두겠습니다. 또 다른 옵션으로 특정 시간 후에 인스턴스를 시작하도록 설정할 수 있는데, 저는 1분 후에 시작하도록 설정했습니다. 작업을 저장하는 것을 잊지 마세요. 이제 대상을 정의해 보겠습니다. 앞서 태그를 살펴봤는데, 대상 방법으로 리소스 태그를 선택했습니다. 태그 이름에 주목했는데, 이제 여기에서 정의합니다. 이전에 봤던 키 이름을 입력하고 값은 이전에 살펴본 myc2 FIS 실험입니다. 따라서 해당 태그가 있는 모든 인스턴스가 이 실험의 대상이 됩니다. 저는 '모두'를 선택했지만, 개수나 백분율을 선택할 수도 있습니다. 나머지는 모두 비워 두겠습니다. 이 실험에는 이미 기존 IM 역할이 있으며, 이 역할에는 액세스 권한이 있어야 합니다. 이러한 대상에 대해 실험을 수행하기 위해 나머지는 모두 비워 두겠습니다. Amazon S3 버킷으로 로그를 보내지도 않고, 이 실험에 대한 중지 조건도 정의하지 않습니다. 태그는 이미 살펴봤고, 이제 실험 템플릿을 생성해 보겠습니다. ' 생성'을 입력하라는 메시지가 표시되면 '생성'을 입력하고 ' 실험 템플릿 생성'을 누릅니다. 이제 실험 템플릿이 생성되었고, 여기에서 실험을 시작할 수 있습니다. 저는 실험 템플릿 콘솔에서 시작하도록 선택하고 '실험 시작'을 누릅니다. 다시 메시지가 표시되면 '시작'을 입력하고 실험을 시작합니다. 이제 실험이 실행 중입니다. 실행 중인 동안 E2 인스턴스에 어떤 변화가 있는지 확인해 보겠습니다. 인스턴스가 이미 중지 상태(대기 중)로 전환된 것을 볼 수 있습니다. 즉, 1분 후에 다시 시작하도록 설정했으므로 곧 다시 시작될 것입니다. 이제 실험을 확인해 보면 완료되었음을 알 수 있습니다. 이제 AWS CLI를 사용하여 실험을 생성하는 방법을 살펴보겠습니다. 중지 조건에 특히 주의하세요. 이것은 CLI를 통해 생성할 템플릿의 이름입니다. 보시다시피 리소스 이름은 이전에 살펴본 대로 실행 중 상태이며, 해당 VPC에 있습니다. 중지 조건은 CloudWatch 알람을 통해 설정할 수 있으므로, 이를 정의하고 `create template` 명령을 실행하면 템플릿이 생성됩니다. 이제 콘솔에서 확인할 수 있습니다. 마지막으로 콘솔에서 실험을 시작해 보겠습니다. 여기서 중요한 점은 AW CLI에서 이 템플릿을 생성했더라도 콘솔에서 시작해야 한다는 것입니다. 실험을 시작해 보면 실행 중입니다. 이제 EC2 콘솔로 돌아가서 인스턴스의 상태를 확인해 보겠습니다. 중지되고 있습니다. 중지가 완료되었습니다. 다시 실험 콘솔로 돌아가서 확인해 보면 실행 중이었는데 완료되었습니다. EC2 콘솔로 돌아가면 잠시 후 다시 시작하도록 설정했기 때문에 대기 중입니다. 이제 다시 실행 중입니다. 이 영상을 시청해 주셔서 감사합니다. 마음에 드셨다면 좋아요를 눌러주시고, 채널 구독도 고려해 주세요. 다음 영상에서 뵙겠습니다.
