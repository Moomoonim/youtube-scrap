## 스크립트

롭, 트린, 오늘 여기에서 당신을 만났습니다. 발표하고 싶은 자료가 있는 것 같은데, 몇 가지 질문도 드리고 싶습니다. 제가 정말 아끼는 주제이자 최근 들어 많이 언급되고 있는 LLM을 평가 기준으로 활용하는 것에 대해 이야기해 보려고 합니다. 요즘 정말 뜨거운 주제라서 어떤 사람들은 2024년의 핵심 주제라고까지 말하더군요. 그럼 바로 시작해 볼까요? LLM을 평가 기준으로 사용할 때 중요한 주제는 무엇이고, 어떤 핵심 지표를 사용하시나요? 어떻게 작동하는지 자세히 설명해 주시겠어요? 네, 우선 초대해 주셔서 정말 감사합니다. 혹시라도 기술적인 문제가 생기더라도 괜찮습니다. 기술적인 문제 없이 진행되는 데모나 발표는 본 적이 없으니까요. 이런 일이 생기기 마련이죠. 정말 기대됩니다. LLM 평가에 대해 이야기할 수 있어서 기쁩니다. 말씀하신 대로 정말 어려운 주제죠. 맞습니다. 맞아요, 그러니까 LLMS, Chad JPD, JPD 4 등등이 진행해 온 방식을 보면, 사람들이 프로토타입을 만들기 시작했는데, 평가 방식이 그냥 눈으로 보고 직감에 따라 판단하는 거 였어요. 그러니까, 스타트업 방식대로 제품을 배포하고 문제가 생기면 고쳐가는 식이었죠. 하지만 사람들이 깨달은 건, 이런 방식은 확장성이 없다는 거예요. 당연한 거죠. 평가는 매우 주관적이에요. 개발자, 즉 사람이 모든 반응을 살펴보는데, 어떤 날은 이게 마음에 들고 어떤 날은 저게 마음에 들 수도 있죠. 10개 이상의 반응을 일일이 읽어보는 건 불가능하잖아요. 그런데 실제 사용 사례의 특징은 지속적인 개선이 필요하다는 거예요. 프롬프트, 검색, 임베딩 모델, 검색 메커니즘 등을 계속해서 개선해야 하죠. 그래서 문제가 생기는 거예요. 확장성이 뛰어난 기술을 사용해야 하는 경우, LLMS를 판정 도구로 사용하는 것이 좋습니다. LLMS는 확장성이 뛰어나기 때문입니다. API 호출을 통해 결과를 얻을 수 있고, 좋은 품질의 결과를 제공한다면, 사람이 하는 작업을 모방하거나 보완하여 진정한 보조자 역할을 할 수 있습니다. LLMS를 판정 도구로 사용하는 것에 대해 생각하고 더 깊이 파고들수록, 언제 API 호출을 사용해야 하는지에 대한 질문이 떠오릅니다. 출력을 필요로 하는 순간에 바로 사용하는 것이 아니라, 출력이 실제인지 확인하기 위해 사용하고, 사용자에게 보여주기 전에 사용자로부터 피드백을 받은 후 일괄적으로 사용하는 것이 일반적입니다. 따라서 특정 사용 사례는 자동으로 제외됩니다. 예를 들어, 환각을 완화하거나 더 나은 평가를 위해 LLMS를 판정 도구로 사용하려는 경우, 이는 즉시 적용할 수 있는 방법이 아닙니다. 제가 제대로 이해했다면, 좀 더 자세히 설명해 주시겠어요? 실제로 어떻게 적용되는지 말씀해 주시면 좋겠습니다. 네, 네, 좋은 질문입니다. 제가 보기에는 세 가지 경우가 있는 것 같습니다. 첫 번째는 말씀하신 것처럼 사용자에게 응답을 보여주기 직전에 응답이 적절한지 확인하는 경우입니다. 대부분의 경우, 확인에는 추가 시간이 소요되고 지연 시간이 발생하기 때문에 그렇게 할 수 없습니다. 하지만 보안과 관련된 경우, 예를 들어 사용자가 LLM을 탈옥하려는지 여부를 확인해야 하는 경우가 있습니다. 이런 경우에는 응답 생성과 병렬로 평가를 진행할 수 있습니다. 사용자 쿼리만으로 탈옥 의도인지, 아니면 제품을 특정 모델 목적에 맞게 사용하려는 의도인지 확인할 수 있기 때문입니다. 관련성, 환각, 품질 등 다른 평가는 대부분 사용자에게 응답을 보여준 후에 수행해야 합니다. 두 가지 방법이 있습니다. 하나는 직접 실험하는 것이고, 다른 하나는 프로덕션 환경에서 모니터링을 실행하여 오류 사례를 찾아내는 것입니다. 일반적으로 개발자들은 이 두 가지 방법을 조합하여 오류 사례를 찾아내고 실험한 후 시스템을 개선합니다. 그런데 병렬로 작업을 진행하면 마치 프롬프트를 두 개 보내는 것처럼 느껴질 수 있습니다. 또 하나 생각해 본 것은 이렇게 하면 시스템 에 상당한 비용이 추가되지 않을까 하는 점입니다. 사실상 비용이 두 배로 늘어나는 셈이니까요. 하지만 나중에는 평가 방식과 응답을 LLM에 보내는 방식을 개선하는 여러 가지 방법을 고안해낼 수 있을 거라고 생각합니다. 예를 들어 토큰을 줄이거나 응답을 연결하는 등의 방법을 사용할 수 있겠죠. 제가 모르는 다양한 팁들을 알고 계시다면 알려주시면 좋겠습니다. 저한테는 그 부분에 대해 말씀드렸지만, 어떤 비용이 발생할까요? 얼마나 증가할 것으로 예상하시나요? 네, 제 생각에는 그게 평가의 매우 타당한 한계점인 것 같습니다. 그래서 예를 들어, 저희가 믿는 바는 GP4 같은 비싼 모델을 평가에 사용하지 않는 것입니다. 비용이 누적되고 효율적이지 않기 때문입니다. 응답 평가 에 더 많은 비용을 지출한다면 차라리 다른 일을 하는 게 낫습니다. 예를 들어 사람이 직접 응답을 생성하는 것처럼요. 그래서 저희는 더 작고 저렴한 모델에 의존합니다. 두 번째로, 저희가 채택한 방법론은 모든 데이터 포인트에 대해 모든 것을 평가할 필요가 없다는 것입니다. 예를 들어 탈옥 여부나 최종 응답 품질과 같은 상위 수준 검사를 수행하고, 품질이 낮은 경우 해당 실패 사례에 대해 일련의 검사를 실행하여 파이프라인의 어느 부분에서 정확히 실패하는지 파악합니다. 이것이 바로 저희의 방식입니다. 우리가 근본 원인 분석이라고 부르는 것인데, 프로덕션 환경에서 발생하는 모든 실패 사례(예: 10% 또는 20%)를 모아서 일련의 검사를 실행하는 것입니다. 이 검사는 철저할 수도 있고, 5~10가지 정도일 수도 있습니다. 이러한 검사를 바탕으로 오류의 원인을 파악할 수 있습니다. 검색 문제인지, 인용 문제인지, 활용 문제인지, 잘못된 쿼리인지, 사용자가 질문한 내용이 불분명한지, 임베딩 모델이 적절하지 않은지 등을 알아낼 수 있습니다. 이렇게 하면 두 가지 장점을 모두 활용하고 동시에 비용을 절감할 수 있습니다. LLM을 테스트처럼 사용한다는 말도 들어봤는데, LLM이 테스트 작성을 돕는다는 뜻은 아니고, LLM이 존재하고 LLM 의 일부라는 의미입니다. 네, 제가 보기에 핵심은 객관적으로 활용해야 한다는 점입니다. LLM 평가를 하려는 많은 사람들이 LLM에게 "이게 제 답변인데, 관련성이 있는지 없는지 판단해 주시겠어요?"라고 묻거나, 더 나아가 "매우 관련성 높음", " 어느 정도 관련성 있음", "매우 관련성 없음"과 같이 등급을 매기는 방식을 사용합니다. 하지만 이렇게 하면 매우 주관적이게 되고, 관련성 여부를 LLM이 판단하게 됩니다. 객관적인 기준으로 바꿔야 합니다. 답변을 개별적인 사실들로 분석하고, 각 사실이 질문과 관련이 있는지 없는지 살펴본 다음, 비율을 계산하여 최종 점수를 매겨야 합니다. 이렇게 하면 LLM이 자신의 결과물을 선호하는 자기중심적 편향과 같은 여러 편견을 상당 부분 줄일 수 있습니다. 저는 이것이 LLM 평가를 효과적으로 만드는 핵심이라고 생각합니다. 평가가 효과적인 이유는 LLM 애플리케이션과 유사하기 때문입니다. LLM 평가도 마찬가지로, 제대로 작동하고 인간의 기대에 부합하는 점수를 얻으려면 많은 노력을 기울여야 합니다. LLM이 인간을 너무 잘 모방해서 자기 목소리까지 좋아하는 게 참 재밌네요. 네, 그럼 실제 적용 사례에 대해 좀 더 자세히 설명해 주시겠어요? 다양한 기법을 사용할 수 있고, 사용 사례에 따라 평가 방식이 매우 다르다는 것도 알고 있습니다. 예를 들어 코드 생성 사용 사례의 경우, 코드가 실행되었는지 여부를 확인하는 것으로 충분하고, 해당 코드가 실제로 더 가치 있는지, 아니면 단순히 편법인지 등을 자세히 분석할 수 있습니다. 하지만 더 민감한 사용 사례와 덜 민감한 사용 사례가 있는데, 이러한 유형의 사용 사례는 어떻게 접근해야 할까요? 평가에 대한 접근 방식은 모든 상황에 맞는 단 하나의 해결책이 있는 것이 아니라는 점을 고려해야 합니다. 다양한 사용 사례에 따라 고려해야 할 사항이 다릅니다. 예를 들어 환각을 분석하는 경우에도 사용 사례나 비즈니스에 따라 평가 관점이 다를 수 있습니다. 어떤 사람은 정확성의 특정 측면에 중점을 두는 반면, 다른 사람은 그 측면보다는 다른 측면에 더 중점을 둘 수 있습니다. 따라서 우리는 사용 사례별로 다른 기준을 정의합니다. Q&amp;A 봇의 경우 답변의 질과 맥락의 질을 살펴봅니다. 대화형 에이전트의 경우 대화 전체의 질과 사용자의 만족도를 살펴봅니다. 장문의 콘텐츠를 작성하는 경우 콘텐츠의 일관성, 창의성 또는 흥미도를 살펴봅니다. AI 에이전트의 경우 계획 능력, 특정 작업을 실행하는 능력, 목표 달성을 위한 단계 수 등을 살펴봅니다. 이처럼 다양한 평가 기준이 있으며, 각각 의 기준은 다음과 같습니다. 다양한 사용 사례에 더 적합하고, 좋은 도구라면 개발자가 비즈니스에 더 적합하도록 도구를 변형하고 수정할 수 있는 특정 맞춤 설정 기능을 제공해야 한다고 생각합니다. 특히 더 널리 사용되는 기능이 있다고 생각하시나요? 제가 지금 부업으로 개발을 하면서 생각해보니, 어디서부터 시작해야 할지 고민이 되는데, 어떤 걸 추천하시나요? 네, 확실히 LLM의 가장 큰 사용 사례 중 하나는 RAG 애플리케이션이라고 생각합니다.
