React를 사용하면 이 두 가지를 병렬로 작성할 수 있으며, 프로세스들은 Repple 내에서 서로 통신합니다. 두 번째 방법은 서비스를 서로 다른 프로세스에 배포하는 것입니다. Python Repple을 배포하고, 이 Python Repple이 React Repple이나 npm을 실행하는 NP Repple과 통신하도록 구성하는 것입니다. 이 두 가지 방법 모두 장단점이 있으며, 지금부터 이에 대해 논의하겠습니다. 두 방법 모두 유효한 솔루션입니다. 첫 번째 방법인 단일 Repple 배포는 배포 흐름이 좀 더 간단합니다. 실제로 하나의 Repple만 사용하기 때문입니다. 여러 배포를 관리할 필요 없이 왔다 갔다 할 필요도 없고, 여러 배포에 대해 걱정할 필요도 없습니다. 결과적으로 비교적 간단합니다. 하나의 배포에서 많은 작업이 이루어지지만 파일 관리는 매우 간단합니다. 여러 탭이나 다른 배포 사이를 왔다 갔다 할 필요도 없고, 설정을 개별적으로 구성하는 방법을 걱정할 필요도 없습니다. 단점은 관리해야 할 배포가 하나뿐이기 때문에 유연성이 떨어진다는 것입니다. API를 사용하는 경우, 기본적으로 예약된 가상 머신을 반복적으로 배포해야 합니다. API를 지원하는 두 가지 배포 유형은 예약된 가상 머신과 자동 확장 배포이기 때문입니다. 자동 확장 배포를 API에 사용하는 경우, 자동 확장 배포는 절전 모드로 전환되기 때문에 하루 중 언제든 API를 호출하려고 하면 다시 시작될 때까지 지연이 발생할 수 있습니다. 즉, 콜드 스타트 ​​문제가 발생합니다. 또한 프런트엔드를 열면 전체 애플리케이션이 다시 시작되어야 합니다. 자동 확장 배포는 이러한 단점을 극복합니다. 간단한 앱에는 정말 좋습니다. 그런 앱은 다운타임을 허용할 수 있지만, API가 포함된 앱에는 그다지 좋지 않습니다. API를 사용하는 앱에는 적합하지 않기 때문입니다. 사실상 두 서비스를 모두 관리하는 예비 VM을 배포해야 하는데, 이는 예비 VM이 항상 실행 중이라는 의미입니다. 따라서 이러한 최적화를 고려한다면 비용 문제가 발생할 수 있습니다. 둘째, 작업 공간이 상당히 어수선해질 수 있습니다. 데모에서 보시다시피 MPM 프로젝트와 Python 프로젝트가 있을 것입니다. 즉, Python 파일, Poetry 파일, JavaScript 파일이 여기저기 흩어져 있다는 뜻입니다. 폴더를 정리하는 방법을 잘 활용하면 어느 정도 해결할 수 있지만, 보기에 좋지 않을 수 있습니다. 기술적으로는 충분히 가능하고, 데모 에서는 실제로 구현해 볼 것입니다. 하지만 일부 사용자에게는 미관상 좋지 않을 수 있습니다. 자, 두 번째는 멀티릴 아키텍처입니다. 장점은 어수선함을 줄여준다는 것입니다. 방금 언급한 문제를 걱정할 필요가 없습니다. 모든 파일을 한 곳에 모아둘 수 있습니다. 파이썬 파일은 하나의 리플에, 모든 MPM 파일은 다른 리플에 저장할 수 있습니다. 완전히 분리되어 있죠. 만약 저처럼 정리정돈을 잘하는 편이고, 컨 마리 방식을 사용하고, 컨테이너 스토어를 자주 이용한다면, 멀티 리플 아키텍처가 적합할 겁니다. 리플을 컨테이너처럼 생각하면 되는데, 꽤 좋은 비유죠? 파이썬 파일과 자바스크립트 파일을 분리해서 관리할 수 있고, 완전히 격리된 환경을 만들 수 있습니다. 꼭 필요한 건 아니지만, 이렇게 하면 편리할 수 있죠. 하지만 가장 큰 장점은 배포 유연성입니다. 예를 들어, 저희 아키텍처에서는 백엔드 API를 예약된 가상 머신으로 배포할 겁니다. 즉, 항상 실행 중이고 언제든 사용 가능하다는 뜻이죠. 프런트엔드 앱은 정적 배포 방식으로 배포할 겁니다. 정적 배포의 장점은 HTML 파일 묶음으로 구성되어 있어 배포 비용이 매우 저렴하다는 점입니다. 사실상 거의 무료나 다름없어요. 그리고 정적 배포 방식이 바로 모든 사용자가 접속하게 될 곳이죠. 정적 파일들은 브라우저에서 실행되니까, 모든 부하가 사용자의 브라우저로 옮겨가게 되는 거예요. 그러니까 크롬 같은 브라우저가 프런트엔드에서 필요한 작업을 수행하는 거죠. 가상 머신을 예약해서 비용을 발생시키는 방식이 아니라요. 프런트엔드는 간단하고 직관적인, 그리고 비용도 저렴한 API와 통신만 하면 되니까요. 덕분에 상태 관리 방식에 있어서 유연성이 훨씬 높아요. 제가 앞에서 말했던 게 바로 이 부분이죠. 특정 유형의 데이터를 영구 저장하고 싶다면 백엔드에서 관리하거나 데이터베이스에 저장할 수 있어요. 프런트엔드는 백엔드와만 통신하고 상태 변수 관리 같은 건 신경 쓸 필요가 없죠. 이 방식의 단점은 컨텍스트 전환이 잦다는 거예요. 예를 들어 백엔드 작업을 하다가 새 탭을 열어서 프런트엔드로 이동해야 하는 거죠. 백엔드에 있는 이 부분을 잊어버리셨군요. 이제 코드를 검색해야 하는데, 다른 리플(repple)로 다시 탭 키를 눌러 이동해야 합니다. 단일 리플 아키텍처를 사용하는 경우 코드 검색을 하면 하나의 리플에 있는 모든 코드를 찾을 수 있고, 찾기 및 바꾸기를 하면 모든 리플에 걸쳐 변경 사항이 적용됩니다. 하지만 다중 리플 아키텍처를 사용하는 경우에는 다른 리플로 돌아가서 작업하는 동안 변경 사항을 기억해야 한다는 점을 잊지 마세요. 두 개의 배포 환경이 있기 때문에 첫째로 복잡성이 증가합니다. 여러 가지 작업을 수행해야 하기 때문입니다. 둘째로, 두 개의 배포 환경에서 직접 설정을 하지 않으면 비용이 더 많이 발생할 수 있습니다. 예를 들어, 하나의 Reserve VM 대신 두 개의 Reserve VM을 배포하면 Reserve VM이 항상 실행되기 때문에 비용이 두 배로 증가합니다. 이는 양날의 검과 같습니다. 현명하게 구성한다면 비용을 절감할 수 있습니다. 신중하게 생각하고 배포 방식을 올바르게 선택하면 비용을 절감할 수 있습니다. 제 생각에는 프런트엔드와 백엔드를 모두 실행하는 단일 예약 VM을 항상 실행하는 것 보다 백엔드로 별도의 예약 VM을 배포 하고 프런트엔드로 정적 사이트를 배포하는 것이 비용이 더 많이 들 것 같습니다. 비용이 같지 않더라도 제대로 된 방식으로 배포하면 비용을 절감할 수 있을 거라고 생각합니다. 하지만 복잡성이 더 크고 설정 작업이 더 많이 필요하기 때문에 좀 더 세세한 부분까지 이해해야 합니다. 이제 두 가지 방식 모두 살펴보고 실습으로 넘어가겠습니다. 먼저 템플릿을 하나 공유하겠습니다. 여기에서 템플릿을 열고 두 가지 아키텍처를 모두 포함하는 단일 Repple 배포를 구축해 보겠습니다. 백엔드 API를 호출하는 간단한 카운터 앱을 만들 건데, 먼저 하나의 Repple을 사용하여 어떻게 하는지 살펴보겠습니다. 그럼 이제 분리해서 두 개의 별도 Repple을 만들고 배포해서 서로 통신하게 해 보겠습니다. 바로 시작해 보죠. 새 Repple을 만들겠습니다. 파이썬 Repple을 만들고 이름을 ' Matt's new front stack full stack repple'이라고 하겠습니다. 목표는 이 파이썬 Repple에 Node.js를 설치하고 백엔드를 가리키는 프런트엔드를 구성하는 것입니다.
