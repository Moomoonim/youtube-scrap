## 스크립트

안녕하세요, 저는 사이버텍(Cybertec)의 시니어 개발자/컨설턴트인 파블로 골루브(Pavlo Golub)입니다. 오늘은 DBA, 개발자, DevOps 엔지니어, 그리고 관리자들이 SQL 및 PL/pgSQL 코드의 코드 커버리지를 측정하고 테스트 중에 실제로 실행되는 코드 부분을 파악하는 데 도움을 주는 새로운 도구인 pgcov를 소개하고자 합니다. pgcov와 함께 PostgreSQL 코드에 진정한 테스트 커버리지를 적용해 봅시다. 먼저 저희 회사 사이버텍에 대해 간략히 소개하겠습니다. 사이버텍은 커뮤니티의 일원이며, 커뮤니티에 매우 중요한 역할을 하고 있습니다. 저희가 하는 모든 일은 사람들을 위한 것이며, 대부분의 도구는 오픈 소스입니다. 이 pgcov 또한 오픈 소스입니다. 또한, 저희는 다양한 서비스를 제공하고 있습니다. 웹사이트에서 자세한 내용을 확인하실 수 있으며, 제가 직접 관리하고 있는 여러 도구와 제품도 있으니 살펴보시기 바랍니다. 자, 그럼 이제 어떤 문제가 있는지 살펴보겠습니다. 이건 모든 프로그래밍 언어에서 흔히 볼 수 있는 그림이죠 . Go, Rust, C, C++ 등등, 어떤 언어든 테스트 커버리지를 측정할 수 있습니다. 하지만 사각지대가 있습니다. PostgreSQL 코드에 대해서는 아직 커버리지 가시성이 없습니다. 데이터베이스 로직을 테스트 하고, 테스트가 통과하고, CI도 정상 작동 하지만, SQL이나 PL/pgSQL 코드의 어떤 부분이 실제로 실행되었는지 확실히 알 수 없죠 . 솔직히 말해서, 알 수 없습니다. 그렇다면 PostgreSQL은 왜 다른 프로그래밍 언어와 다를까요? SQL은 진짜 코드이고, 더 나아가 튜링 완전 언어이기 때문입니다. 즉 , 함수, 프로시저, 트리거, 조건문, 반복문 등 모든 종류의 요소가 존재합니다 . PL/pgSQL도 마찬가지로 진짜 프로그래밍 언어입니다. 문제는 우리가 이를 다르게 취급한다는 점 입니다. 그렇다면 PostgreSQL에서 커버리지를 측정하기 어려운 이유는 무엇일까요? 첫째, 코드가 데이터베이스 엔진 내부에서 실행되지만 , 우리는 거기에 직접 접근할 수 없기 때문입니다. 그리고 실행은 상태를 유지하고 트랜잭션을 사용합니다. PostgreSQL 자체는 코드 커버리지 훅 이나 계측 지원을 제공하지 않습니다. SQL 레벨에서 작동하는 전용 도구도 없습니다. 따라서 불가능하다는 것이 아니라, 단지 공백이 있다는 것입니다. 이 공백을 채워야 합니다. 현재 대부분의 SQL 코드는 회귀 테스트를 통해 테스트됩니다. SQL 코드를 작성하고, 테스트를 실행한 다음 예상 출력과 실제 출력을 비교합니다. 이렇게 하면 정확성을 테스트할 수 있습니다. 하지만 어떤 분기문, 조건문 또는 반복문의 어느 부분이 실행되었는지 알 수 없습니다 . 테스트는 통과했지만 코드 커버리지에 대한 정보는 전혀 없습니다. 또 다른 방법은 PL/pgSQL 검사라는 PL/pgSQL용 정적 분석 도구를 사용하는 것입니다. 이 도구는 타입 검사, 린팅, 사용되지 않는 코드 찾기 등에 도움을 줄 수 있습니다. 하지만 문제는 pgTAP이 런타임 중에 실행되지 않기 때문에 테스트에 대한 정보를 알 수 없고, 따라서 코드 커버리지 지표를 생성할 수 없다는 것입니다. 또 다른 강력한 솔루션으로는 pgTAP이 있습니다. pgTAP 은 뛰어난 프레임워크이자 어설션 및 표현력 있는 테스트를 위한 훌륭한 도구입니다. 하지만 pgTAP 역시 어떤 분기 에서 어떤 코드 부분이 실행되었는지 알려주지 않습니다 . 따라서 pgTAP은 동작 테스트와 결과 테스트에는 유용 하지만, 실행 경로에 대해서는 아무것도 알 수 없습니다. 비교표를 만들어 보겠습니다 . Go, Rust, Python 등 유명하고 잘 알려진 프로그래밍 언어에는 코드 커버리지 도구가 있지만, SQL과 PL/SQL에는 없습니다. 왜 이것이 중요할까요? 우선 이러한 문제의 영향을 가장 많이 받는 사람들은 개발자입니다. 개발자는 코드의 어떤 부분이 테스트에서 완전히 제외되었는지, 어떤 부분이 테스트되지 않았는지 알고 싶어 합니다 . DBA와 DevOps 담당자 또한 마찬가지입니다. 그리고 저는 지원 관리자 나 상위 관리자들이 테스트를 통해 완벽하게 커버된 코드에 관심이 없다고 말하려는 것은 아닙니다 . 그렇다면 Postgres에서 코드 커버리지란 무엇을 의미할까요? 개발자로서 저는 제 함수가 테스트 중에 실행되는지 알고 싶었습니다. 함수 내부의 어떤 분기가 실행되었는지, 즉 테스트 범위가 얼마나 커버되었는지 알고 싶었죠. 그리고 테스트에서 어떤 오류가 발생했는지도 알고 싶었습니다 . 성능이나 정확성 문제가 아니라, 코드의 양, 즉 테스트로 얼마나 많은 부분이 커버되었는지 알고 싶었습니다. 그래서 저는 새로운 도구를 만들어야겠다고 생각했고, 몇 가지 제약을 두었습니다. 우선, 이 도구는 모든 PostgreSQL 버전에서 작동해야 합니다. 클라우드 버전, 기본 PostgreSQL, TimescaleDB 등 어떤 버전이든 상관없습니다. 확장 기능에 의존해서는 안 됩니다 . 최소한의 PostgreSQL 버전만 지원해야 합니다. 엔진을 수정해서는 안 됩니다 . 그렇지 않으면 제가 직접 PostgreSQL 포크를 만들어야 하기 때문입니다. 또한 , 이 도구는 CI/CD 환경에 적합해야 합니다. GitHub나 GitLab 저장소를 사용하는 사람들 이 이 도구를 쉽게 통합할 수 있도록 말입니다. 제 도구는, 음, 저장소에 이미 있는 다른 테스트들과 호환 되도록 만들고 싶습니다 . 예를 들어, 회귀 테스트나 pgTAP 테스트를 사용하고 있다면 아무런 변경 없이 그대로 작동해야 합니다. 그리고 모든 테스트는 완전히 격리된 상태로 실행 되어야 합니다. 즉, 한 테스트의 결과가 다른 테스트의 결과에 영향을 미치지 않아야 합니다. 이것이 제가 생각하는 핵심 아이디어입니다. SQL을 소스 코드로 간주하고, 계측 작업을 수행한 다음, 격리된 테스트를 실행하고, 실행 과정을 관찰한 후, 마지막으로 사람이 읽 거나 기계가 볼 수 있는 코드 커버리지 보고서를 생성하는 것입니다. 이는 전 세계 모든 코드 커버리지 도구가 작동하는 방식과 유사 하지만, 우리는 이를 생소한 분야에 적용했습니다. 자, pgcov를 소개합니다. pgcov 는 PG Coverage의 약자로 , SQL 및 PL/pgSQL에 테스트 커버리지 분석 기능을 제공합니다. 독립 실행형 CLI이며, 단일 바이너리로 구성되어 있고, psql에 대한 종속성 이나 확장 프로그램이 필요하지 않습니다. 이 도구는 CI/CD 파이프라인과 잘 통합되며, pgTAP 및 회귀 테스트와 함께 사용할 수 있습니다. 아주 간단하죠. 자, 이제 pgcov가 어떻게 작동하는지 살펴보겠습니다. 우선, 테스트 본문을 계측해야 합니다. 계측이란 무엇일까요? 코드의 모든 실행 가능한 문장 앞에 특수한 구문을 삽입 하는 것을 의미합니다 . 여기 예시에서 계측된 원본 코드와 계측된 코드를 비교해 볼 수 있습니다. pg_notify 호출을 삽입하는데, 첫 번째 매개변수는 채널 이름인 pgcov 이고, 페이로드의 두 번째 매개변수 는 테스트할 함수가 있는 파일 이름, 시작 위치에서의 바이트 오프셋, 그리고 명령어의 바이트 길이입니다. 확장자나 변경 사항 없이, 순수 SQL만 사용합니다. 소스 코드에는 아무런 변경도 가하지 않습니다. 실행 중에 파일에서 읽어와 계측하고 임시 데이터베이스에서 실행합니다. 따라서 모든 테스트는 자체적인 PostgreSQL 데이터베이스를 사용합니다. 이 데이터베이스는 pgcov_test라는 이름과 날짜, 그리고 임의의 숫자로 구성됩니다. 그다음 계측된 소스 파일을 배포합니다. 그러면 pgcov가 전용 연결을 통해 모든 시그널을 수신하기 시작합니다. 그런 다음 테스트 SQL 파일을 하나씩 실행 하고 발생한 시그널을 수집합니다. 작업이 완료되면 임시 데이터베이스를 삭제하고 작업을 마무리합니다. 따라서 클러스터는 깨끗해지고 아무것도 남지 않습니다. pgcov 내부에서는 수신 기능을 사용하여 이러한 시그널을 수집합니다. 그리고 모든 페이로드를 수집하여 실행된 문장의 맵을 생성합니다. 네, 이게 전부입니다. 그럼 pgcov가 기존 도구 목록에서 어떤 위치를 차지하는지 비교해 보겠습니다. 회귀 테스트는 코드 커버리지 정보를 제공하지 않습니다 . PL/pgSQL의 정적 분석 도구인 plpgsql_check도 마찬가지입니다. pgTAP도 코드 커버리지 정보를 제공하지 않지만, pgcov는 코드 커버리지 정보만 제공합니다. 이것이 pgcov의 기본 개념입니다. 그렇다면 pgcov는 소스 코드와 테스트 코드를 어떻게 구분할까요? Go 언어와 동일한 규칙을 사용합니다. 따라서 확장자가 .sql인 모든 파일은 소스 파일로 간주됩니다. 하지만 테스트 파일을 지정하려면 항상 파일 이름 뒤에 "postfix_test"를 붙입니다. 이렇게 하면 pgcov는 접미사가 붙은 파일을 테스트 파일로 , 다른 SQL 파일은 소스 파일로 인식합니다. 간단한 예시를 통해 살펴보겠습니다. 최소한의 제품 재고 관리 시스템이 있다고 가정해 보겠습니다. 제품에는 ID, 이름, 가격, 재고 수량, 카테고리가 있습니다. 그리고 미리 정의된 PL/pgSQL 함수들이 있다고 가정해 보겠습니다. add_product() 함수는 유효성 검사를 거쳐 새 제품을 추가하고, get_stock_status() 함수 는 재고 수준 정보를 제공합니다 . 또한 apply_pricing_policy() 함수는 등급별 할인을 적용할 수 있도록 합니다 . 예를 들어 get_stock_status 함수의 일부를 살펴보면 여러 가지 다른 경로가 있습니다. 첫 번째는 제품이 존재하지 않는지 확인하는 오류 검사입니다. 두 번째는 빈 선반인지, 즉 제품이 아예 없는지 확인하는 것입니다. 세 번째는 제품 수량이 10개 미만이면 해당 제품의 재고가 부족하다는 의미이고, 그렇지 않으면 재고가 충분하다는 의미입니다. 제 예시를 따라해 보시려면 제 GitHub 저장소( cybertech-postgresql/pgcov) 에서 소스 코드를 찾으실 수 있습니다 . 그곳에 예제 및 데모 폴더가 있습니다. 여기에는 01_schema라는 테이블 파일, 02_functions라는 로직 파일, 그리고 demo_test.sql이라는 테스트 파일이 있습니다. 자, 이제 pgcov를 실행해서 코드 커버리지를 확인해 보겠습니다. pgcov를 실행하려면 "pgcov run" 명령어를 입력하고 첫 번째 매개변수 "-c"를 지정합니다 . "-c"는 연결을 의미합니다. 데이터베이스 연결 문자열을 지정하고, 마지막 매개변수로 SQL 파일이 있는 폴더를 지정합니다. 그러면 출력을 볼 수 있습니다. 테스트 1개, 통과한 테스트 1개, 총 1개 , 코드 커버리지 50%, 총 소요 시간 592밀리초라고 표시됩니다. 기억하시겠지만, 여기에는 demo_test.sql 파일이 하나만 있습니다. 즉, 테스트가 하나만 있다는 뜻입니다. 그래서 총 1개가 나오는 것입니다. 모든 테스트가 통과했고 코드 커버리지도 50%입니다. 그렇다면 뭔가 테스트되지 않은 부분이 있는 것 같습니다. 정확히 무엇이 누락되었는지 어떻게 확인할 수 있을까요? 우선, 사람이 보기 편한 HTML 보고서를 생성해 보겠습니다. "pgcov report" 명령어를 추가하고 형식을 HTML로 지정합니다 . "-o" 옵션은 부분 HTML 보고서를 의미합니다. 이제 HTML 보고서를 브라우저에서 열어보면 다음과 같은 이미지를 볼 수 있습니다. Go 언어를 사용해 보신 분들이라면 비슷한 점을 발견하실 수 있을 겁니다. 여기에는 세 가지 색상이 있습니다. 회색은 소스 코드에서 추적되지 않는 부분을 의미합니다. 주석이나 정의 라인 등 이 여기에 해당합니다. 빨간색은 테스트에서 다루어지지 않은 구문을 나타냅니다. 그리고 초록색은 테스트에서 다룬 부분을 나타냅니다. 상단의 드롭다운 메뉴를 선택하면 테스트 중에 사용 가능한 소스 파일을 볼 수 있습니다. 지금은 02_functions 파일을 열었 지만, 01_schema 파일을 선택하면 스키마 파일은 항상 실행되므로 모두 초록색으로 표시됩니다. 이제 1, 2, 3, 3개의 분기가 누락된 것을 확인할 수 있습니다. 즉, 출력 결과가 제한적입니다. 하나의 함수만 살펴보았지만, 전체 결과는 총 4개의 분기가 누락되었음을 보여줍니다. get_stock_status 함수에서 2개, apply_pricing_policy 함수에서 2개의 분기가 누락되었습니다. 이것도 또 다른 기능입니다. demo_test.sql 파일에는 주석 처리된 두 번째 DO 블록이 있습니다. 주석을 해제하면 어떤 부분이 바뀌었는지 확인할 수 있습니다. 주석을 해제하면 누락된 분기를 실행해 볼 수 있고, 주석 처리된 코드에는 추가 값을 사용하여 add_product 함수를 더 많이 호출하는 내용이 포함되어 있습니다 . 자, 여기 있는 각 어설션은 이전 보고서에서 빨간색으로 표시된 줄을 직접적으로 대상으로 합니다 . 그렇죠 ? 이제 업데이트된 테스트로 pgcov를 다시 실행하면 테스트 수는 여전히 동일합니다. 총 1개, 통과한 테스트는 1개뿐이지만 커버리지는 증가했습니다. 이제 50%에서 70%로 올라갔죠? HTML 보고서를 다시 생성해서 무엇이 바뀌었는지 확인해 보겠습니다. 변경된 내용을 보면, get_stock_status 함수의 3개 분기 중 2개를 테스트했습니다. 이제 "IF NOT FOUND" 문을 제외한 거의 모든 부분을 테스트했습니다 . 이 부분은 별도로 테스트해야 합니다. 이렇게 해서 커버리지를 높이는 겁니다. 미리 정의된 임계값이 없는 한, 커버리지를 단계적으로 높이기 위해 테스트를 수정하는 거죠 . 보통 80% 정도면 괜찮다고 생각하지만, 이는 제품과 저장소에 따라 다릅니다. 자 , 여기서는 커버리지가 50%였는데, 테스트를 개선해서 70%대로 올라갔습니다 . 어떤 명령어를 사용했을까요? 명령어는 단 두 개뿐이며 사용법도 매우 간단합니다. 첫 번째는 "run" 명령어로, 데이터베이스 클러스터 연결 문자열을 지정할 수 있습니다. 두 번째는 타임아웃 시간 설정입니다. 테스트가 무한정 실행되는 것을 원하지 않는다면 타임아웃 시간을 설정하여 실행 시간을 제한할 수 있습니다. 두 번째 는 병렬로 실행할 테스트 개수를 지정하는 것입니다. 출력 파일 형식도 지정할 수 있는데 , 기본값은 .pgcov/coverage.json입니다. 마지막은 "verbose" 명령어로, 도구가 테스트를 실행하는 과정을 실시간으로 확인할 수 있습니다 . 세 번째는 "pgcov report" 명령어로, JSON 출력을 LCOV와 같은 다양한 형식으로 변환할 수 있습니다. LCOV 는 Codecov를 비롯한 여러 제공업체와 원활하게 연동됩니다 . JSON 형식은 기계 학습에 적합하여 AI 에이전트와 함께 사용하기에 좋습니다. HTML 형식은 사람이 읽기에 적합합니다. CI/CD 환경에서 실행하는 것도 매우 간편합니다. GitHub Actions에서 실행한 다음 보고서를 생성하고 , 생성된 보고서를 Coveralls와 같은 공급업체에 보내면 됩니다. 자, 그럼 pgcov가 무엇이 아닌지 설명해 드리겠습니다. pgcov는 마이그레이션 도구가 아닙니다. pgTAP이나 회귀 테스트를 대체하는 도구도 아닙니다. 즉, pgcov를 사용하려면 테스트가 필요합니다. 프로파일러도 아니고 쿼리 분석기도 아닙니다. 계측된 코드를 실행하는 데 일반 회귀 테스트를 실행하는 것보다 시간이 더 오래 걸릴 수 있습니다 . pgcov는 특정 ORM 프레임워크나 언어에 종속되지 않으므로 원하는 모든 환경에서 쉽게 사용할 수 있습니다. 또한 pgcov는 매우 엄격하고 특정 목적에 특화된 도구입니다. 실행 가시성 확보에만 초점을 맞추고 있으며, 실행하려는 내용만 측정합니다. 몇 가지 제한 사항이 있습니다. 우선 C, Python, Perl 및 기타 저장 프로시저 코드는 계측할 수 없습니다. 분기별 속성 정보는 계측하지 않습니다. PostgreSQL 13 이상 버전에서만 작동합니다. 이전 버전에서도 사용 가능할 수도 있지만, 확실하게 장담할 수는 없습니다. PostgreSQL을 업그레이드하는 것이 좋습니다. 향후에는 "병합" 명령어를 추가하거나, 코드 커버리지가 낮을 경우 오류를 발생시키는 "fail-under" 옵션을 추가할 수도 있습니다 . 저희는 모든 코드의 커버리지를 측정하고 있으며, pgcov는 PL/pgSQL 코드와 일반 SQL 코드 모두에 대해 커버리지를 측정할 수 있도록 도와주는 도구입니다 . 이를 통해 모든 코드를 완벽하게 테스트했다고 자신 있게 말할 수 있습니다. 궁금한 점이 있으면 이메일 이나 다른 소셜 채널을 통해 직접 문의해 주세요 . 여러분의 의견을 기다리겠습니다. 감사합니다.
