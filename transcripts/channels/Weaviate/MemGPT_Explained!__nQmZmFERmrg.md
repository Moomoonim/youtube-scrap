## 스크립트

안녕하세요 여러분, MGPT 유료 영상을 시청해 주셔서 정말 감사합니다. MGPT는 운영 체제 개념과 대규모 언어 모델 응용 프로그램을 연결하는 매우 흥미로운 새로운 연구 논문입니다. 아마도 이 논문 의 가장 흥미로운 점은 검색, 증강 생성, 그리고 LLM 도구 사용에 대한 관점을 재구성한다는 것입니다. 즉, LLM을 운영 체제의 커널, 즉 페이지 교체와 유사하게 자체 메모리를 처리하는 프로세서로 생각하는 것입니다. 하지만 MGPT의 세부 사항을 자세히 살펴보기 전에 간단히 설명하자면, 대규모 언어 모델은 입력 으로 처리할 수 있는 텍스트 양에 한계가 있습니다. 예를 들어, 이러한 대규모 언어 모델과 채팅을 한다고 가정해 보겠습니다. 일반적으로 상당히 많은 양의 메시지를 주고받을 수 있습니다. 최대 입력이 8,000개의 토큰인 GBT4의 경우, 챗봇이 과거 대화를 더 이상 추론할 수 없게 되기 전까지 약 50개의 토큰으로 140개의 메시지를 주고받을 수 있습니다. 즉, GBT 채팅에서 메시지를 보냈다고 가정해 보겠습니다. 2개월 전에 챗봇에게 생일이 10월 11일이라고 알려줬는데, 2 개월 후에는 생일을 기억하지 못한다고 가정해 봅시다. 이는 챗봇의 관점에서 볼 때, 인기 있는 대규모 언어 모델과 얼마나 많은 대화를 주고받을 수 있는지에 대한 문제입니다. 문서와의 채팅을 생각해 보면, 컨텍스트 창에 특정 정보를 입력해야 하므로 토큰이 소모되고, 컨텍스트 창을 통해 이전 메시지를 참조하기 전에 얼마나 많은 메시지를 주고받을 수 있는지에 대한 문제가 발생합니다. 이러한 문제를 해결하기 위해 검색 증강 생성(RAG)이 등장했습니다. 이는 벡터 에딩과 검색 쿼리를 사용하여 입력에 관련 정보만 채우는 매우 인기 있는 기술입니다. 예를 들어, RAG를 사용하지 않고 " RTOC는 무엇인가요?"라고 물으면 챗봇은 그것이 무엇인지 모릅니다. 하지만 " 다음 정보를 바탕으로 답변해 주세요."라고 말한 다음 "refc는 무엇인가요?"라고 물으면 챗봇은 답할 수 있습니다. 즉, 사용자가 " refc는 무엇인가요?"라고 묻는 것만으로도 충분한 답변을 얻을 수 있습니다. 우리는 컨텍스트 창에서 사용할 정보를 검색하고 질문에 답할 수 있는 비교적 간단한 RAG 설정으로 문제를 해결할 수 있습니다. 예를 들어 이 특정 예시에서는 200~300개의 토큰만 필요하다고 가정해 보겠습니다. 하지만 사용자가 특정 애플리케이션에서 참조(refc)를 사용하는 방법에 대해 반복적으로 질문하는 긴 대화를 상상해 보세요. 이 경우 대화 기록의 메모리 관리 와 검색 데이터베이스에서의 조회를 균형 있게 관리해야 합니다. MGBT의 핵심 아이디어는 매우 흥미로운데, 대규모 언어 모델이 자체 입력 창의 한계를 인지하고 그에 따라 조치를 취한다면 어떨까요? 즉, 검색 결과를 추가해야 할 시점이나 대화에서 학습한 내용을 작업 메모리에 저장해야 할 시점을 파악하여 대규모 언어 모델을 도구 사용으로 확장하는 것입니다. 이제 MGBT의 전체 아키텍처를 살펴보겠습니다. MGBT는 RAG 애플리케이션을 위한 운영 체제로, 메모리와 도구 사용을 연결하고 특히 메인 컨텍스트 메모리 관리에 중점을 둡니다. 운영 체제의 중심에는 대규모 언어 모델 프로세서가 있고, 그 다음에는 가상 컨텍스트가 있습니다. 메인 컨텍스트는 현재 사용되는 것입니다. 대규모 언어 모델이 예측을 수행하기 위한 입력에서 외부 컨텍스트는 예를 들어 벡터 데이터베이스 또는 데이터 저장소라고 할 수 있습니다. 이 저장소는 페이지 교체 및 운영 체제와 같은 주요 컨텍스트와 교체하여 특정 작업을 완료하는 데 필요한 관련 컨텍스트를 얻을 수 있습니다. 이것이 메모리 부분입니다. 메모리는 함수와 도구 사용을 통해 관리됩니다. 도구 사용은 매우 흥미로운 개념으로, 언어 모델을 계산기나 날씨 API와 같은 서비스에 연결할 수 있습니다. 예를 들어 "지금 보스턴 의 날씨는 어떻습니까?"라고 묻고 싶다면, 모델은 매개변수에 저장된 정보에 의존하는 대신 외부 요청을 보내야 합니다. 특히 날씨 API의 경우, 벡터 데이터베이스에 해당 정보를 최신 상태로 유지하기는 어려울 것입니다. 따라서 이러한 외부 서비스도 이 그림에 포함될 수 있습니다. 하지만 더 흥미로운 것은 메모리 읽기 및 쓰기와 관련된 함수입니다. 메모리 읽기는 벡터 데이터베이스에서 데이터를 읽거나 검색 쿼리를 수행하는 것을 말합니다. MGPC 논문에는 페이지네이션 및 쿼리 재작성과 관련된 개념도 있지만, 이는 나중에 자세히 다루겠습니다. 하지만 이것은 운영 체제 기능을 사용하여 작업 컨텍스트에 펜을 꽂는 것처럼 메모리를 읽어 메인 컨텍스트에 추가하는 개념입니다. 이 부분은 나중에 자세히 다루겠습니다. 또한 흥미롭게도 메모리 쓰기 기능도 있습니다. 예를 들어 제가 채팅 GBT와 오랫동안 대화하는 동안 MGBT는 이러한 기능을 사용하여 Connor가 10월 11일이 생일이라고 알려주면 이를 제 저장소에 추가합니다. 또한 인터럽트와 이벤트라는 개념도 있습니다. 이벤트는 MGBT가 처리를 시작하도록 트리거하는 역할을 합니다. 예를 들어 제가 Chad GBT에게 "rtoc가 뭐야?"라고 물어보면 이 모든 처리를 시작하는 이벤트가 트리거될 수도 있고, 문서를 업로드하거나 " 컨텍스트 창이 3,500토큰에 도달했습니다. 이제 줄이기 시작합시다."와 같은 시스템 메시지가 표시될 수도 있습니다. 또는 5분마다 토큰을 줄이는 타이머처럼 작동할 수도 있습니다. 이처럼 운영 체제의 인터럽트 기능을 통해 다양한 작업을 수행할 수 있습니다. 아마도 대규모 언어 모델처럼 비동기 처리가 필요할 수도 있겠죠. 예를 들어 SelfRag가 어떻게 작동하는지 연구해 보세요. SelfRag는 MGBC와 비슷한 시기에 나온 논문입니다. 채팅을 계속하면서 비동기적으로 연구를 진행하다가 갑자기 " 연구 보고서를 다 끝냈는데, 대화에 포함시킬까요? 아니면 어떻게 할까요?"라는 메시지가 뜬다고 가정해 봅시다. 이것이 MGBT의 작동 방식에 대한 일반적인 개요입니다. 이 인용문은 논문에서 가져온 것인지 확실하지는 않지만, 참고로 말씀드리자면 논문 외부에서 가져온 것입니다. 조셉 곤잘레스 교수와 함께 진행한 Amazing Run LLM 팟캐스트에서 찰스 패커가 한 말입니다. 그는 MGBT를 메모리 관리 도구를 사용하는 방법을 아는 에이전트라고 설명했는데, 정말 완벽한 표현이라고 생각합니다. 검색 증강 생성 분야 전체에 있어 매우 흥미로운 방향은 대규모 언어 모델에 데이터베이스에 쓰기, 또는 이 경우에는 특정 메인 컨텍스트에 쓰기(WR) 기능을 부여하는 것입니다. 기존에는 저장 벡터 데이터베이스에서 읽는다는 개념이 있었지만, 이제는 다른 방식으로 접근할 수 있게 된 거죠. 그냥 아무 생각 없이 메인 컨텍스트에 넣는 것과는 달리, 이제 중간 레이어에 검색 결과가 있고, 그 검색 결과 중에서 무엇을 메인 컨텍스트에 넣고 대화를 이어갈지 결정하는 과정이 생깁니다. 이 인용구는 메모리 관리 도구를 사용하는 방법을 아는 에이전트라는 점에서 매우 강력하다고 생각합니다. 여기서 핵심 아이디어는 대규모 언어 모델을 위한 운영 체제를 구축하는 것입니다. 청중 여러분께 질문 하나 드리고 싶은데요, Lang Chain이나 Llama Index 같은 프레임워크를 이런 식으로, 즉 언어 모델과 도구, 벡터 데이터베이스, 메모리 간의 연결을 조율하는 대규모 언어 모델을 위한 운영 체제로 생각하는 것에 대해 어떻게 생각하시나요? 좀 더 자세히 살펴보자면, Andre Karpathy 도 이러한 LLM과 운영 체제에 대한 흥미로운 트윗을 올렸습니다. LLM과 데이터베이스뿐 아니라 이러한 모든 것을 조율하는 전체 운영 체제를 갖는다는 생각은 매우 흥미로운 발상이라고 생각합니다. Andre Karpathy는 최근 여러 퍼즐 조각을 공개하며 보다 완전한 개념을 제시했습니다. LLM이 챗봇이 아니라 새로운 운영체제의 커널 프로세스라는 그림이 그려지고 있습니다. MGBT에서 볼 수 있듯이 LLM은 메모리를 변경해야 한다거나, 특정 도구를 사용해야 한다거나, 특정 이벤트에 응답해야 한다고 지시하는 커널 프로세스입니다. 즉, 커널과 운영체제는 메모리 관리 및 도구 사용 방식을 조율하는 역할을 합니다. 예를 들어, 현재 LLM은 텍스트, 오디오, 비전, 코드 인터프리터, 프로그램 작성 및 실행 기능, 브라우저, 인터넷 접속, 파일 및 내부 메모리 저장 및 검색을 위한 임베디드 데이터베이스 등 다양한 모달리티에 걸쳐 입력 과 출력을 조율합니다. 이처럼 LLM은 다양한 기능을 수행할 수 있으며, 많은 컴퓨팅 개념이 적용됩니다. 현재 초당 10Hz 토큰 속도로 실행되는 단일 스레드 실행을 볼 수 있으며, 어셈블리 수준 실행 추적 스트림을 확인할 수 있습니다. 컴퓨터 보안 개념은 공격, 방어 및 새로운 취약점과 관련하여 그대로 이어집니다. 이처럼 짧은 텍스트 안에도 탐구할 만한 흥미로운 정보가 너무나 많습니다. 단일 스레드 방식에서는 LLM 프로세스가 하나만 실행됩니다. 제가 아는 한, 적어도 저는 터미널에 LLM 로그를 기록하고 진행 상황을 지켜보는 방식으로 사용하고 있습니다. 토큰 비용을 지불하고 있기 때문이죠. 하지만 이런 방식은 SE(엔터프라이즈 엔지니어링)에도 적용될 수 있습니다. 예를 들어 Lang Smith 의 Lang Chain은 복잡한 프롬프트 체인을 시각화하여 실행 추적을 이해하는 데 도움을 줍니다. 저는 이런 병렬 처리, 즉 동시성과 LLM 작업을 생각해 봤습니다. 예를 들어 Rag를 검색하면 백그라운드에서 조사가 진행되고 완료되었다는 메시지가 표시됩니다. 이런 방식에는 많은 가능성이 있다고 생각합니다. 저는 운영 체제를 예로 들어 설명하는 것도 좋아합니다. 업계가 비슷한 형태로 발전하고 있기 때문입니다. Windows, OS X, Linux, GPT, Palm Cloud, Llama 같은 운영 체제는 기본 앱과 앱 스토어를 제공합니다. Chat, GBT Marketplace, 그리고 코드 인터프리터가 CoH에 통합된 Coral처럼 말이죠. 네, 우리는 이런 유형의 앱을 확실히 보고 있습니다. 언어 모델을 중심으로 저장하면 대부분의 앱을 여러 플랫폼에 맞게 조정할 수 있습니다. 예를 들어 API wv8 generate 모듈은 앱 스토어에서 모델을 꺼내 사용하는 방법도 보여줍니다. 요약하자면, LLM을 챗봇으로 보는 것은 초기 컴퓨터를 계산기로 보는 것과 같습니다. 우리는 완전히 새로운 컴퓨팅 패러다임의 출현을 목격하고 있으며, 아직 초기 단계입니다. 따라서 LLM과 운영 체제라는 전체적인 맥락에서 이 트윗은 매우 흥미롭습니다. 좀 더 자세히 살펴보겠습니다. 특히 MGBT와 운영 체제를 대규모 언어 모델 도구로 만드는 요소, 즉 이러한 종류의 메모리 관리에 대해 알아보겠습니다. MGBT에 추가된 기능은 작업 컨텍스트, 추가, 교체와 같은 함수입니다. 예를 들어 " 안녕하세요, 채드. 환영합니다. 컴퓨터 과학 박사로서 당신과 함께 이 여정을 시작하게 되어 기쁩니다."라고 말하고, 사용자가 " 제 생일은 10월 11일이고, 제가 가장 좋아하는 케이크는 초콜릿 라바 케이크입니다."라고 말한다고 가정해 보겠습니다. 이것은 대화 기록을 Shashir Patel은 이 논문의 저자 중 한 명인데, 이 논문은 Gorilla LLM을 개발한 연구실에서 나왔습니다. 그래서 Gorilla LLM과의 연관성이 있는지 궁금해서 관심을 갖게 되었습니다. 여기서 핵심은 Gorilla에서 가능한 한 적은 토큰을 할당하는 것입니다. MGBT와 Gorilla를 생각해 보면, 가능한 한 적은 토큰으로 도구를 설명하는 것이 핵심입니다. 메모리 할당과 마찬가지로 토큰 할당을 효율적으로 해야 하기 때문입니다. 예를 들어 WE8 Gorilla의 경우 벡터 데이터베이스 API에 접근할 수 있고, BM25 벡터 검색이나 하이브리드 검색과 같은 다양한 검색을 수행할 수 있으며, 재순위 지정 등을 추가할 수 있습니다. 필터를 추가하여 간결한 자연어 설명만 입력하면, 검색을 실행하기 위한 자연어 명령을 수행할 수 있습니다. 단순히 음악 검색이 아닌, 더욱 정교한 검색도 가능합니다.
