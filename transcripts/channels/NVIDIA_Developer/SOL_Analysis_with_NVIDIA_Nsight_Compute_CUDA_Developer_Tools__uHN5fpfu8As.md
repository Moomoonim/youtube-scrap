Welcome to this chapter of our CUDA Developer&nbsp; Tools video series. My name is Bob Crovella,&nbsp;&nbsp; and I’m on the solution architecture team&nbsp; at NVIDIA. In this video, I’ll be going over&nbsp;&nbsp; the SOL section in Nsight Compute, our primary&nbsp; profiler for GPU CUDA kernel analysis. The SOL&nbsp;&nbsp; section is the first section of profiler data&nbsp; that will be included in standard or default&nbsp;&nbsp; Nsight Compute output. SOL stands for Speed Of&nbsp; Light, and that refers to one of the key ideas&nbsp;&nbsp; that this section tries to communicate: “how&nbsp; is the code performing (or what is the device&nbsp;&nbsp; utilization) compared to relevant maximums?”&nbsp; The reason this section is presented first (by&nbsp;&nbsp; default) is that these comparisons to relevant&nbsp; maximums can be a good starting point for&nbsp;&nbsp; selecting directions to investigate, when trying&nbsp; to understand or improve the performance of your&nbsp;&nbsp; code. A typical question to ask is: “what is&nbsp; the current limiter to code performance?”,&nbsp;&nbsp; which is usually one of the cyclical questions&nbsp; asked during an analysis-driven optimization&nbsp;&nbsp; exercise. The SOL section can help begin&nbsp; to answer that question, at a high level. The SOL section is also easy to capture&nbsp; or generate, because it is part of default&nbsp;&nbsp; Nsight Compute reporting. If you profile your&nbsp; code with the ncu command line or CLI tool,&nbsp;&nbsp; and no options, the SOL section will be part of&nbsp; the default output of the CLI tool. Likewise,&nbsp;&nbsp; when processing a profiler report using the&nbsp; GUI tool, the SOL section will be included&nbsp;&nbsp; by default in the report. Like other profiler&nbsp; reports and sections, the SOL section will be&nbsp;&nbsp; created separately for each different kernel&nbsp; invocation that you profile. The SOL report&nbsp;&nbsp; presented by the CLI tool is by default less&nbsp; detailed than the report presented by the GUI tool&nbsp;&nbsp; but you can get additional information using the&nbsp; -print-details all profiler command line switch. During this video we will be profiling this code.&nbsp; The kernel is very simple, basically computing a&nbsp;&nbsp; normcdf math function provided by the CUDA math&nbsp; library, for an array of vector type. Note there&nbsp;&nbsp; are two variants, one using double type, and one&nbsp; using float type. We will compare these. If we&nbsp;&nbsp; profile the double variant code using the nsight&nbsp; compute CLI profiler on a GTX 1660Ti on CUDA 12.0,&nbsp;&nbsp; we get output like this. Similar information is&nbsp; available in the GUI version of the profiler.&nbsp;&nbsp; One method to use the GUI version is to&nbsp; generate a profiler report using the -o&nbsp;&nbsp; switch for the ncu CLI tool, and then copy the&nbsp; report file to a machine that has the profiler&nbsp;&nbsp; installed in a graphical desktop environment,&nbsp; and import the file there. If we use the GUI,&nbsp;&nbsp; we see the following for the speed-of-light&nbsp; report section. Note that these listed metrics and&nbsp;&nbsp; measurements correspond to the CLI output. In the&nbsp; GUI version, there is more information available&nbsp;&nbsp; for this report section. We can expand the section&nbsp; by clicking on the triangle button to the left of&nbsp;&nbsp; the section title to reveal additional information&nbsp; available in the report section. In addition, we&nbsp;&nbsp; can get additional information about a measurement&nbsp; or metric by hovering the mouse over the metric,&nbsp;&nbsp; as we see here. In this case, we can see that the&nbsp; DRAM Throughput metric refers to measuring traffic&nbsp;&nbsp; between the GPU itself and the DRAM attached&nbsp; to the GPU, and the measurement is expressed&nbsp;&nbsp; as a percentage of peak achievable. Now let's&nbsp; revisit the previous report section view, and talk&nbsp;&nbsp; about the various components. The measurements&nbsp; and metrics at the top are the same as those&nbsp;&nbsp; reported in the CLI report section. The Compute&nbsp; (SM) Throughput measurement gives an indication&nbsp;&nbsp; of SM activity level, as a percentage of peak&nbsp; achievable. A high number here is both a good&nbsp;&nbsp; thing to attain, as well as a general indicator&nbsp; of where to focus to make improvement. We’ll&nbsp;&nbsp; see an example shortly. The Memory throughput&nbsp; measurement indicates the level of activity in&nbsp;&nbsp; the GPU memory pipeline as a percentage of peak&nbsp; achievable. The L1/Tex cache throughput presents&nbsp;&nbsp; a similar measurement for traffic to the L1/TEX&nbsp; unit, and the L2 Cache throughput measurement&nbsp;&nbsp; indicates the level of traffic flowing to the&nbsp; L2 Cache (as a percentage of peak), and the&nbsp;&nbsp; DRAM throughput indicates the level of traffic to&nbsp; the GPU off chip DRAM array, as already mentioned. Moving to the column of measurements on the&nbsp; right in the top area of this report section,&nbsp;&nbsp; the Duration is the measurement of the elapsed&nbsp; time that the kernel consumed, measured in&nbsp;&nbsp; milliseconds. The elapsed cycles line is a similar&nbsp; measurement, expressing the kernel duration in&nbsp;&nbsp; terms of elapsed GPU core clock cycles, rather&nbsp; than milliseconds. These two numbers are related&nbsp;&nbsp; to each other by the SM Frequency indication, such&nbsp; that the elapsed time in nanoseconds multiplied by&nbsp;&nbsp; the SM Frequency in cycles/nanosecond should&nbsp; be approximately equal to the Elapsed cycles.&nbsp;&nbsp; The DRAM Frequency indicates the DRAM clock speed&nbsp; expressed as clock cycles per nanosecond. This is&nbsp;&nbsp; an indication of transfers per second frequency,&nbsp; not the base clock frequency of the DRAM,&nbsp;&nbsp; so the “pumped” characteristic (transfers/clock)&nbsp; characteristic of modern DRAM increases this&nbsp;&nbsp; number. Finally, the SM Active Cycles indication&nbsp; represents the number of elapsed cycles during&nbsp;&nbsp; which at least one warp was active. This is&nbsp; upper-bounded by the Elapsed Cycles indication. If we study the measurements discussed so far,&nbsp; we can see that for this particular kernel,&nbsp;&nbsp; the SMs are quite busy, but the&nbsp; memory traffic is relatively low,&nbsp;&nbsp; expressed as a percentage of peak achievable.&nbsp; The memory subsystems are not very busy,&nbsp;&nbsp; over the kernel duration. Therefore the kernel&nbsp; duration is primarily driven by compute traffic,&nbsp;&nbsp; not memory activity. If we want to improve the&nbsp; performance of such a kernel (i.e. shorten its&nbsp;&nbsp; duration) we will need to seek ways to reduce&nbsp; the compute load. Reducing memory traffic&nbsp;&nbsp; or improving memory utilization efficiency is&nbsp; not likely to yield much benefit in this case. Let’s cover the remaining information&nbsp; presented. The next item in this report&nbsp;&nbsp; section is an indication of “High Throughput”.&nbsp; This particular part of the report section is&nbsp;&nbsp; an output of a “Rule” in Nsight Compute. Rules in&nbsp; Nsight Compute can be used to process metric data&nbsp;&nbsp; and measurements and give text that includes&nbsp; analysis or assessment. Nsight Compute has a&nbsp;&nbsp; number of available Rules, and this particular&nbsp; one is telling us that we have one subsystem&nbsp;&nbsp; (in our case SM/Compute) that is above 80%,&nbsp; indicating it is highly utilized. If we are&nbsp;&nbsp; going to improve our kernel performance,&nbsp; we will probably have to address this by&nbsp;&nbsp; shifting some of that load. So this rule output&nbsp; has confirmed what we had already conjectured,&nbsp;&nbsp; based on study of the individual&nbsp; metrics and measurements. Furthermore,&nbsp;&nbsp; the rule text is pointing us to a different&nbsp; report section that may have information&nbsp;&nbsp; useful for next steps. The Rules output is&nbsp; extremely valuable, especially for beginners,&nbsp;&nbsp; because it analyzes data based on expertise&nbsp; provided by the Nsight Compute development team,&nbsp;&nbsp; effectively a kind of expert system. Pay&nbsp; attention to rules outputs, which can range&nbsp;&nbsp; from information such as this one, to warnings&nbsp; which indicate more important performance issues. Moving on, the next part of this report&nbsp; section depicts bar charts showing the&nbsp;&nbsp; relative utilization of compute&nbsp; throughput and memory throughput,&nbsp;&nbsp; for this kernel. These are basically&nbsp; the same numbers as the Compute SM&nbsp;&nbsp; Throughput and Memory Throughput numbers&nbsp; already covered, expressed graphically. Moving on, the remaining section area has detailed&nbsp; metrics organized into two columns or categories.&nbsp;&nbsp; Up to this point, the characterization provided&nbsp; in this section has largely been to indicate&nbsp;&nbsp; a comparison between compute throughput or&nbsp; utilization and memory throughput or utilization.&nbsp;&nbsp; The remaining columns of metrics further subdivide&nbsp; and characterize each of these two categories. Taking a look at the column on the left, called&nbsp; Compute Throughput Breakdown, we see that the word&nbsp;&nbsp; “pipe” appears frequently. The characterization&nbsp; of the Compute throughput is now broken out by&nbsp;&nbsp; individual “pipes”. You can think of a pipe as&nbsp; a functional unit inside a GPU or GPU SM that&nbsp;&nbsp; processes certain types of instructions or&nbsp; operations. For arithmetic work, for example,&nbsp;&nbsp; we might have different pipes or functional&nbsp; units that process integer operations vs.&nbsp;&nbsp; floating point operations. In fact, the individual&nbsp; pipes represented include 64-bit floating point,&nbsp;&nbsp; 32-bit floating point, integer operations, and&nbsp; tensor core operations, as well as other types.&nbsp;&nbsp; Again you can get individual descriptions by&nbsp; hovering the mouse over the measurement title&nbsp;&nbsp; of interest.. For this code, we see that FP64&nbsp; ie. 64-bit floating point operations are the&nbsp;&nbsp; most significant consumer of compute throughput.&nbsp; So the takeaway previously was that we wanted to&nbsp;&nbsp; consider whether we could shift the compute load&nbsp; elsewhere, and in this area we now know that&nbsp;&nbsp; the compute load that we want to shift is 64-bit&nbsp; floating point compute. Our code makes substantial&nbsp;&nbsp; use of 64-bit floating point operations in&nbsp; calculating the normcdf function, and furthermore&nbsp;&nbsp; the GTX1660Ti device has only a relatively small&nbsp; number of 64-bit floating point compute units to&nbsp;&nbsp; handle this type of work. The combination of&nbsp; these factors results in this characteristic&nbsp;&nbsp; of our code being the “long pole”, the thing&nbsp; that we might focus on to improve performance. Taking a look at the column on the right,&nbsp; called Memory Throughput Breakdown,&nbsp;&nbsp; we see that similarly, memory subsystem&nbsp; utilization is now further characterized&nbsp;&nbsp; into specific types of activity, spanning various&nbsp; aspects of the memory subsystem including DRAM,&nbsp;&nbsp; L2 cache, L1/Tex unit, the Load/Store unit&nbsp; (LSU), and other mechanisms. Our previous&nbsp;&nbsp; high level characterization from this report&nbsp; section indicated that overall, memory subsystem&nbsp;&nbsp; utilization was low for this code, and we see&nbsp; this reflected again in these detailed metrics. So is there anything we can do with this code&nbsp; to change its behavior? We’ve already discussed&nbsp;&nbsp; some possible clues. The profiler has indicated&nbsp; that compute utilization is the “long pole” or&nbsp;&nbsp; the bottleneck. Furthermore the profiler&nbsp; has indicated the specific compute “pipe”&nbsp;&nbsp; of interest that is the bottleneck is the&nbsp; 64-bit floating point “pipe”. We also know&nbsp;&nbsp; that the GeForce GTX1660Ti has relatively limited&nbsp; 64-bit floating point throughput or capability. A simple change we could make to the code to see&nbsp; how behavior and performance would be affected,&nbsp;&nbsp; would be to switch from using 64-bit&nbsp; floating point to 32-bit floating&nbsp;&nbsp; point. This means we will be using float&nbsp; quantities instead of double quantities,&nbsp;&nbsp; and that we will use the 32-bit floating&nbsp; point version of our normcdf function,&nbsp;&nbsp; called normcdff. The code is already set up&nbsp; to make that switch by compiling without the&nbsp;&nbsp; USE_DOUBLE define. When we do that and reprofile&nbsp; the code, we see a report that looks like this.&nbsp;&nbsp; We can make a number of observations about&nbsp; this. Before we do that, let’s use one of&nbsp;&nbsp; the basic features of the UI reporting called&nbsp; “baselines”. Setting a baseline in a report&nbsp;&nbsp; tab causes that report tab data to be used as&nbsp; a reference point when we are looking at other&nbsp;&nbsp; report tabs. Here we see that I have a report&nbsp; tab for the previous report we were looking at,&nbsp;&nbsp; and a report tab for the new version of the&nbsp; code that uses float instead of double. If&nbsp;&nbsp; we go to the previous report tab, click the&nbsp; “Add Baseline” button at the top, and then&nbsp;&nbsp; switch back to this report tab, we see output&nbsp; that looks like this (8). Now we effectively&nbsp;&nbsp; have our “old” and “new” data presented in&nbsp; comparative fashion, in a single report view.&nbsp;&nbsp; This makes it easy to see where the biggest&nbsp; changes were, from the profiler’s perspective. So what has changed? First of all we see that the&nbsp; kernel duration has gotten dramatically shorter,&nbsp;&nbsp; going from about 2.71 milliseconds in the double&nbsp; case to about 63 microseconds in the float case,&nbsp;&nbsp; a reduction of over 97%. The profiler is also&nbsp; telling us that our code is “balanced” meaning&nbsp;&nbsp; that both compute and memory utilization are&nbsp; taking place in roughly equal relative amounts,&nbsp;&nbsp; when compared to the peak theoretical offering&nbsp; on this device. Previously we had an “unbalanced”&nbsp;&nbsp; code where the 64-bit floating point was&nbsp; the limiter to performance, and the memory&nbsp;&nbsp; utilization was relatively low. We see this&nbsp; in the bar chart summarizing this, where the&nbsp;&nbsp; green bars correspond to the previous report, now&nbsp; used as a baseline, and the blue bars represent&nbsp;&nbsp; the current report. Our rule output is telling us&nbsp; the same thing, that we have balanced throughput. Looking at the detailed metrics,&nbsp; we again see confirmation of this.&nbsp;&nbsp; Switching from double to float has changed&nbsp; the computation, and therefore the pipe used,&nbsp;&nbsp; from 64-bit to 32-bit floating point. We&nbsp; see now in the Compute Throughput Breakdown,&nbsp;&nbsp; that the FP64 pipe is no longer utilized,&nbsp; but the Pipe referred to as “FMA” is now&nbsp;&nbsp; the most active. The FMA pipe is the one that&nbsp; handles 32-bit floating point calculations. We&nbsp;&nbsp; can make the observation at this point&nbsp; that the ordering of pipe activity in&nbsp;&nbsp; this report section is not fixed, but is&nbsp; arranged in pareto order. Therefore the&nbsp;&nbsp; ordering in the report changes depending&nbsp; on which pipes are most heavily utilized. This change in the kernel has had several&nbsp; impacts. First of all we know that 32-floating&nbsp;&nbsp; point quantities take up half the space of 64-bit&nbsp; floating point quantities, so this variant of the&nbsp;&nbsp; kernel is loading and storing half as much data.&nbsp; However, the kernel is also dramatically shorter&nbsp;&nbsp; in duration, due primarily to the change in&nbsp; compute pipe utilization. Comparatively speaking,&nbsp;&nbsp; our GTX1660Ti device has much more capability&nbsp; when processing 32-bit floating point quantities&nbsp;&nbsp; compared to 64-bit floating point quantities.&nbsp; So the huge reduction in duration of the kernel&nbsp;&nbsp; means that even though we are loading and storing&nbsp; only half as much data, the overall time period&nbsp;&nbsp; during which the load and store activity is&nbsp; taking place is much shorter. The result is&nbsp;&nbsp; that our memory utilization (actual traffic vs&nbsp; peak theoretical) has increased substantially,&nbsp;&nbsp; from a number in the 3-4 percent range,&nbsp; to a number that is over 70%. Since both&nbsp;&nbsp; compute utilization and memory utilization are&nbsp; relatively high, this kernel is “balanced”. This is just one report section that is available&nbsp; in Nsight Compute.
