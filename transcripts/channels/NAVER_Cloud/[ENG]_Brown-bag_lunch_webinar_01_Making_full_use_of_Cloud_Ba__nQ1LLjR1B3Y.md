## 스크립트

안녕하세요, 저는 네이버 클라우드 플랫폼의 낙수장입니다. 2023년을 시작하는 첫 번째 브라운백 세션에 오신 것을 환영합니다. 오늘 브라운백 세션에서는 다양한 사고 발생 시 중요한 데이터를 보호하는 백업에 대해 이야기해 보겠습니다. 최근 NIDC 화재 사고와 같은 사례를 참고하여 이번 세션의 주제를 "비상시 데이터 복구를 위한 백업"으로 정했습니다. 그럼 어떤 내용을 다룰지 살펴보겠습니다. 먼저 백업이란 무엇이며 왜 필요한지 알아보겠습니다. 백업은 단순히 파일을 복사하거나 압축하여 저장하는 것이 아니라, 복구를 목적으로 한다는 것을 알고 계실 겁니다. 따라서 단순히 파일을 복사하는 것보다 파일을 사용하여 얼마나 빠르게 복구할 수 있는지가 매우 중요합니다. 백업에는 RPO( 복구 시점 목표)와 RDO( 복구 시간 목표)와 같은 중요한 전략이 있습니다. 즉, 데이터 손실이나 사고 발생 시 서비스를 얼마나 빠르게 복구하고 서비스 연속성을 유지할 수 있는지가 매우 중요합니다. 따라서 단순히 데이터를 저장하는 것뿐만 아니라 목표 시간 내에 데이터를 신속하게 복구할 수 있는 방법을 찾는 것이 중요합니다. 몇 가지 예시를 준비했습니다. 최근 IDC에서 화재 사고가 발생했습니다. 사실 IDC 사고는 매우 드문 사례입니다. IDC에서 화재나 사고와 같은 문제가 발생하는 것은 매우 이례적이지만, 전혀 발생하지 않는다고는 할 수 없습니다. 아주 드물게 발생하며, IDC에 문제가 생기면 그 영향은 막대합니다. 해킹으로 인해 데이터가 손실될 수도 있습니다. 해커가 랜섬웨어와 같은 악성 프로그램을 사용하여 데이터를 암호화하고 복호화를 위해 금전을 요구하는 경우가 있습니다. BitLocker의 원래 목적은 외부 해커로부터 데이터를 안전하게 보호하는 것이지만, 해커들이 이를 악용하여 데이터를 암호화하고 복호화를 요구하는 경우도 있습니다. 다행히 백업된 데이터가 있다면 랜섬웨어 또는 해커가 BitLocker를 사용하여 암호화한 데이터를 삭제 하고 최신 데이터로 복원할 수 있습니다. 시스템 충돌 또한 자주 발생하는 문제입니다. 운영 체제에 문제가 생기거나 블루스크린이 나타나면 데이터가 손실될 수 있으며, 심각한 경우에는 시스템을 부팅하여 데이터를 복구할 수 없을 수도 있습니다. 다양한 원인이 있지만, 가장 흔한 원인은 사용자의 잘못된 조작으로 인한 인적 오류입니다. 데이터 손실이나 시스템 오류가 발생할 수 있으므로, 중요한 데이터를 복원하려면 백업이 필수적입니다. 백업은 자동차 보험과 유사합니다. 저는 최근 자동차 보험을 갱신했는데, 갱신할 때마다 보험료가 아까운 것 같습니다. 사고를 낸 적도 없고 앞으로도 사고가 날 것 같지 않지만, 만일의 사태에 대비해 보험에 가입합니다. 만약 사고가 발생한다면 보험의 도움 없이 막대한 비용을 부담해야 하기 때문입니다. 자동차를 소유하고 있다면 자동차 보험에 가입하는 것처럼 백업도 마찬가지입니다. 백업에는 비용이 발생할 수 있지만, 이러한 비용은 나중에 발생할 수 있는 문제 와 해결 비용에 비하면 매우 적습니다. 또한 많은 분들이 백업 과 아카이빙을 혼동하시는데, 일반적으로 데이터를 리눅스 서버나 윈도우 서버의 특정 디렉터리에 복사합니다. 사진의 경우 여러 하드 디스크에도 복사하는데, 이는 나중에 필요할 때 데이터를 안전하게 보관하기 위함입니다. 디스크에 오류가 발생하더라도 다른 디스크의 데이터를 사용할 수 있습니다. 엄밀히 말하면 이것은 아카이빙입니다. 데이터를 복사해 두면 언제든지 가져와 사용할 수 있습니다. 데이터를 저장하거나 가져와서 기존 저장소처럼 사용할 수 있습니다. 이것이 아카이빙입니다. 백업은 데이터가 손상되었을 경우 복구하기 위해 데이터를 저장하는 것입니다. 백업 데이터는 손상되지 않는 한 복구할 수 없습니다. 과거에는 테이프에 백업을 저장했고, 때로는 오프사이트에 저장하기도 했기 때문에 백업의 특성이 다릅니다. 일반 데이터처럼 백업 데이터에 접근해서 사용할 수 없습니다. 이것이 백업과 아카이빙의 차이점입니다. 이러한 차이점을 구분하는 것이 중요합니다. 오늘 우리는 백업에 대해 이야기할 것입니다. 백업은 데이터가 손상되거나 손실되었을 때 복원하기 위해 데이터를 저장하는 것을 의미합니다. 백업 유형을 살펴보면 전체 백업이 가장 잘 알려져 있습니다. 증분 백업과 차등 백업도 있는데, 이는 나중에 설명하겠습니다. 사실 이 세 가지에서 파생된 백업 유형은 매우 많지만, 오늘은 전체 백업, 증분 백업, 차등 백업에 대해서만 설명하겠습니다. 저희는 저장 장치가 있는데, 첫날에는 10테라바이트의 데이터가 있었습니다. 다음 날에는 데이터가 1테라바이트 증가하여 11테라바이트가 되었고, 셋째 날에는 다시 1테라바이트 증가하여 12 테라바이트가 되었으며, 넷째 날에도 마찬가지로 13 테라바이트가 되었습니다. 매일 전체 백업을 수행하면 테라바이트, 11테라바이트, 12테라바이트, 13테라바이트의 데이터가 개별적으로 백업됩니다. 이렇게 4일 동안의 백업이 저장되는 백업 저장 장치의 용량은 총 46테라바이트가 됩니다. 전체 백업의 장점은 백업이 생성된 시점을 기준으로 복원할 수 있다는 것입니다. 따라서 셋째 날의 데이터는 셋째 날 백업을 사용하여 즉시 복원할 수 있습니다. 빠르고 편리한 복구라는 장점이 있지만, 보시다시피 총 46테라바이트라는 매우 큰 용량이 필요합니다. 다음으로 증분 백업에 대해 설명드리겠습니다. 증분 백업의 경우, 만약 10테라바이트의 데이터가 있다면, 첫째 날에 테라바이트 단위의 데이터를 백업하고, 둘째 날, 셋째 날, 넷째 날에는 각각 증가된 용량만큼만 백업하는 방식입니다. 따라서 첫째 날에 전체 백업을 하고, 둘째 날, 셋째 날, 넷째 날에 각각 1테라바이트씩 백업하면 총 13테라바이트의 용량만 필요합니다. 이 방식의 장점은 백업 공간을 크게 절약할 수 있다는 것입니다. 하지만 단점도 있습니다. 셋째 날 데이터를 복원하려면 먼저 첫째 날의 전체 백업과 둘째 날의 증분 백업이 필요하고, 그 후에 셋째 날의 증분 백업을 복원해야 합니다. 즉, 복구 작업을 세 번 수행해야 합니다. 원하는 데이터는 순차적으로 복원해야만 얻을 수 있으므로 복원 시간이 약간 늘어납니다. 다음으로 차등 백업이 있습니다. 첫째 날에 10테라바이트의 데이터가 있고 둘째 날에 1테라바이트가 증가하면, 증가된 1테라바이트는 둘째 날에 백업됩니다. 셋째 날에 다시 1테라바이트가 증가하면 둘째 날 데이터는 무시되고 전체 백업과의 차이만 백업됩니다. 전체 백업이 4일차에 동일한 방식으로 수행되는 경우, 전체 백업을 기준으로 변경된 데이터만 백업되므로 총 용량은 3테라바이트가 되고, 따라서 전체 백업 용량은 16테라바이트가 되어 증분 백업보다 약간 더 커집니다. 전체 백업만큼 빠르지는 않지만, 전체 백업을 복원한 후 4일차 백업만 필요하므로 원하는 시점으로 복원하는 것이 훨씬 쉽고 빠릅니다. 대부분의 백업 방법은 이와 같은 전체 백업을 기반으로 하며, 이후 증분 백업, 차등 백업 또는 기타 파생 백업 방법을 사용합니다. 최근 몇 년 동안 이러한 백업은 크게 두 가지 방향으로 발전해 왔습니다. 첫 번째는 데이터 보안 관점에서 데이터를 효과적으로 보호하는 방법에 중점을 두는 것으로, 이 분야에서 많은 진전이 이루어지고 있습니다. 두 번째는 용량 감소에 중점을 두는 것으로, 다양한 효율적인 압축 알고리즘을 사용하여 데이터를 단순화하고 중복을 제거하는 것을 목표로 하며, 각 증분 백업을 그대로 저장하는 대신 중복을 제거합니다. 전체 백업, 증분 백업, 차등 백업 등 다양한 백업 유형을 다룹니다. 이번 세미나는 간단한 강연 형식으로 진행되므로 네이버 클라우드 플랫폼 제품뿐 아니라 이러한 백업의 기본 개념과 네이버 클라우드 플랫폼 및 서비스에서 백업하는 방법에 대해서도 알아보겠습니다. 먼저 Windows에서 백업하는 방법을 살펴보겠습니다. Windows 서버는 기본적으로 백업 기능을 제공하지 않습니다. Windows Server 2003부터는 역할 및 기능을 통해 기능을 확장할 수 있습니다. 특정 기능을 선택하려면 ' Windows Server Backup'이라는 기능을 활성화해야 합니다. 추가 설치가 진행되면 Windows 관리자 권한으로 백업을 수행할 수 있습니다. 오른쪽 메뉴에서 ' 백업 일정', '일회성 백업', ' 복구'를 확인할 수 있습니다. ' 백업 일정'은 예약된 시간에 백업을 수행하는 기능이며, '일회성 백업'은 한 번만 수행하는 백업입니다. ' 복구'를 사용하면 백업된 데이터를 복원할 수 있습니다. Windows에서의 백업은 어렵지 않습니다. ' Windows Server Backup' 기능을 추가로 설치하고 Windows 백업 관리자에서 백업 일정을 예약하기만 하면 됩니다. Linux 서버에서는 오픈 소스 백업 도구가 있지만, tar 와 cront tab이 가장 일반적으로 사용됩니다. tar는 백업 관리자 역할을 하는 프로그램입니다. 데이터를 압축하고 결합하는 데에는 CrontTab이라는 프로그램이 있습니다. CrontTab은 작업을 스케줄에 추가하고 정해진 시간에 실행해 줍니다. 먼저 tar 명령어를 사용하여 파일을 압축하고 결합할 것입니다. 이때 G 옵션은 반드시 필요합니다. 먼저 G 옵션을 사용하여 파일 목록을 생성해야 합니다. 그러면 추가적인 tar 압축이 수행될 때 변경되거나 추가된 파일만 압축 파일에 추가됩니다. CrontTab을 사용하면 주기적인 백업을 수행할 수 있도록 스케줄러를 설정할 수 있습니다. Linux에서는 tar와 CrontTab을 사용하여 백업할 수 있습니다. Windows나 Linux에서 서버에서 백업을 수행할 때는 주의해야 할 사항이 있습니다. 백업 데이터를 저장할 드라이브는 별도의 파티션으로 구성해야 합니다. 일반 파일과 백업 파일을 분리하여 관리하지 않으면 디스크가 손상되었을 때 백업 데이터를 복구하기가 매우 어려워집니다. Linux에서도 마찬가지로 백업 데이터를 추가 저장 장치에 저장하는 경우 클라우드의 디스크 기능인 '연결 해제' 기능을 사용하여 다른 서버에 쉽게 연결하고 복원 시간을 단축할 수 있습니다. 그렇지 않으면 백업 데이터를 추출하는 데 너무 많은 비용이 발생할 것입니다. 지금까지 파일 백업에 대해 살펴보았지만, 데이터베이스 백업도 중요한 부분입니다. 데이터베이스 백업은 일반 파일 백업처럼 할 수 없습니다. 그렇게 백업하면 제대로 백업되지 않을 가능성이 매우 높습니다. 데이터베이스는 데이터를 끊임없이 읽고 쓰기 때문입니다. 읽기에는 문제가 없지만 쓰기에 문제가 있습니다. 어떤 종류의 데이터가 지속적으로 입력되는데, 데이터가 입력되는 순간에 백업이 진행되면 백업은 필연적으로 실패합니다. 이는 DBMS가 적절한 잠금을 설정하기 때문입니다. 적절한 잠금이 걸린 파일에 접근하려고 하면 정상적으로 접근할 수 없습니다. 따라서 일반적으로 열려 있는 파일의 경우, 빨간색 오류가 발생하는 이유는 무언가가 잠겨 있기 때문입니다. 일반적으로 DBMS에서 제공하는 백업 프로그램을 사용해야 합니다.
