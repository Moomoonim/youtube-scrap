## 스크립트

안녕하세요 여러분, 제 이름은 아부 바크르이고 그 라디오의 핵심 관리자 중 한 명입니다. 보시다시피 저희는 최근 그 라디오 5를 출시했습니다. 그라디오 5의 주요 목표 중 하나는 파이썬 개발자들이 아름답고 잘 작동할 뿐만 아니라 웹 보안 모범 사례를 따르는 안전한 머신 러닝 웹 애플리케이션을 쉽게 만들 수 있도록 하는 것이었습니다. 이를 위해 저희는 트레일 오브 비츠(Trail of Bits)와 협력하여 그 라디오에 대한 독립적인 보안 감사를 의뢰했습니다. 그들은 그라디오의 전체 코드베이스를 검토했고, 매우 신속하게 문제를 파악하여 가능한 모든 보안 취약점을 찾아냈습니다. 그 결과, 그라디오에서 여러 가지 보안 취약점을 발견했습니다. 그래서 저희는 그 라디오 5를 출시하기 전에 이러한 취약점들을 하나씩 해결하고, 문제를 완화하고, 재발 방지 조치를 취했습니다. 이를 통해 그 라디오 사용자 여러분께 그라디오 5를 안전하게 사용할 수 있다는 확신을 드릴 수 있었습니다. Gradio 5를 사용하면 기본적으로 안전한 애플리케이션을 구축할 수 있습니다. 이 비디오에서는 Trail of Bits에서 발견된 주요 보안 취약점 몇 가지를 살펴보려고 합니다. 투명성을 위해 해당 보고서를 공개했으며, 이 비디오 설명란에서 링크를 찾을 수 있습니다. 또한, Gradio 사용자이거나 Gradio 또는 다른 프레임워크를 사용하여 웹 애플리케이션을 개발하는 개발자에게 이러한 개념이 영향을 미칠 수 있으므로 주요 발견 사항 몇 가지를 설명하는 것이 유용할 것이라고 생각합니다. 그럼 이러한 문제에 대해 이야기해 보겠습니다. 시작하기 전에 보안 위협이 발생하는 네 가지 일반적인 시나리오가 있습니다. 첫 번째 시나리오는 Gradio 앱을 로컬에서 실행하는 경우입니다. 컴퓨터에서 Gradio 앱을 로컬로 실행하는 경우에도 특정 보안 고려 사항이 있습니다. 두 번째 시나리오는... 보안 위협은 Gradio 애플리케이션을 서버에 배포할 때 발생할 수 있습니다. 첫 번째 시나리오는 Facebook Spaces와 같은 무료 호스팅 플랫폼(Facebook Spaces는 Gradio 애플리케이션을 호스팅할 수 있는 무료 공간입니다)에 배포하는 경우입니다. 두 번째 시나리오는 Gradio 애플리케이션을 공유 링크를 통해 공유하는 경우입니다. Gradio에는 내장된 공유 메커니즘이 있어, 앱을 실행할 때 ` launch` 메서드에서 `share`를 `true`로 설정하면 다른 사람들이 Gradio 애플리케이션에 액세스하고 실행할 수 있는 간단한 공개 URL인 공유 링크가 생성됩니다. 이는 매우 간단 하지만 두 번째 시나리오와 유사한 보안 문제를 가지고 있으며, 특히 고려해야 할 몇 가지 고유한 보안 사항이 있습니다. 마지막으로 네 번째 시나리오는 Gradio CI(지속적 통합) 파이프라인입니다. Gradio CI 파이프라인은 기여자 의 커밋을 포함하여 Gradio 코드베이스에 대한 모든 커밋에 대해 특정 작업을 수행합니다. 이러한 작업이 Gradio에 어떤 취약점을 노출하는지 살펴봐야 합니다. 공급망 취약점에 대해 이야기해 보겠습니다. Gradio를 가져와서 사용하고 있다면, 제가 언급할 이러한 취약점들은 Gradio뿐만 아니라 많은 오픈 소스 프로젝트에도 영향을 미칩니다. 이 영상을 공유하는 목적 중 하나는 오픈 소스 프로젝트 관리자나 개발자 여러분이 자신의 코드를 살펴보고 이러한 취약점의 영향을 받고 있는지 확인하는 것입니다. 그럼 바로 시작하겠습니다. 먼저 로컬에서 실행해 보겠습니다. 참고로 이 영상은 Gradio에 대한 기본적인 지식을 전제로 합니다. Gradio를 사용해 본 적이 없다면 Gradio 웹사이트(gradio.doapp.g.ao)를 방문해 보세요 . 앱 관련해서 빠른 시작 튜토리얼을 확인해 보세요. 이 튜토리얼을 통해 이러한 문제들을 훨씬 더 쉽게 이해할 수 있을 겁니다. 문제들을 이해하는 데 필요한 맥락을 제공해 드릴 거예요. 자, 그럼 Gradio 앱을 로컬에서 실행한다고 가정해 봅시다. 어떤 문제가 발생할 수 있을까요? 가장 큰 문제는 코어, 즉 크로스 오리진 요청입니다. 코어란 무엇일까요? 코어 설정은 어떤 웹사이트가 다른 웹사이트나 로컬 호스트 에서 실행 중인 모든 것에 요청을 보낼 수 있는지 제한하는 데 사용됩니다. 예를 들어, 로컬 호스트(7860번 포트)에서 Gradio 앱을 실행하면 타사 웹사이트의 요청을 차단하는 코어 설정이 적용됩니다. 왜 이것이 중요할까요? Gradio 앱이 로컬에서 실행 중이라고 가정해 보겠습니다. 기본적으로 7860번 포트에서 실행되고 있죠. 이제 다른 웹사이트를 방문했는데, 그 웹사이트가 Gradio 튜토리얼처럼 보이지만 실제로는 로컬 호스트 786번으로 요청을 보낼 수 있는 악성 웹사이트일 수 있습니다. 7860이나 Gradio 앱이 실행되는 방식에 따라, 예를 들어 파일을 업로드하려고 시도할 수 있습니다. Gradio는 사용자가 어떤 앱을 실행하고 있는지 추측할 수 있습니다. 예를 들어 인기 있는 라디오 앱을 로컬에서 실행하고 있다면, 해당 앱은 요청을 보내 컴퓨터에서 작업을 실행하고, 예측 결과를 얻고, 웹사이트로 데이터를 전송하려고 시도할 수 있습니다. 따라서 타사 웹사이트에서 요청을 보내는 것을 방지하는 것이 매우 중요합니다. Gradio 4에서는 코어의 요청을 차단하는 설정이 있었지만, 쿠키가 포함된 요청이나 ' null origin'에서 시작된 요청의 경우 이러한 설정을 우회하는 방법이 있었습니다. 이는 매우 특수한 경우이지만, 타사 웹사이트가 실행될 때 일반적으로 요청의 출처를 확인할 수 있지만, 출처를 'null'로 설정할 수 있습니다. 예를 들어 웹사이트가 iframe 등에서 실행될 때 이러한 설정이 발생하며, 이 경우 코어의 미들웨어를 거치게 되어 Gradio는 해당 요청을 차단하지 않습니다. 우리가 바라는 것은 이제 이러한 요청을 허용해야 하는 몇 가지 합법적인 이유가 있다는 것입니다. 만약 이를 막고 싶지 않다면, 예를 들어 로컬 파일 시스템의 특정 파일에 웹 컴포넌트를 사용하여 Gradio를 임베드하는 경우와 같이 특정 상황에서는 ` strict cores`라는 매개변수를 전달하고 값을 `false`로 설정할 수 있습니다. 하지만 기본적으로 Gradio는 보안상의 이유로 이러한 모든 유형의 요청을 차단합니다. Gradio 5에서는 이 문제가 해결되었습니다. 자, 이제 두 번째 시나리오로 넘어가겠습니다. 다시 한번 말씀드리지만, 이 영상은 짧은 영상이며 모든 내용을 다루지는 않습니다. 하지만 전체 보고서는 공개되어 있으니 확인해 보실 수 있습니다. 이제 Gradio 애플리케이션을 Hugging Face 또는 자체 서버에 배포했다고 가정해 보겠습니다. 어떤 점을 고려해야 할까요? 한 가지 문제는 Gradio 애플리케이션 사용자가 특정 디렉터리, 즉 Gradio 앱의 작업 디렉터리 외부에 있는 파일에 접근하는 것을 막으려고 한다는 것입니다. 하지만 특정 방식으로 우회할 수 있다는 점이 문제입니다. 간단한 문제는 아니지만 우회할 수 있습니다. 그래서 5학년 과정에서 우리가 해결하는 것 중 하나는 사람들이 이 우회를 하지 못하도록 막는 것입니다. 또 다른 문제는 이러한 서버, 즉 Hugging Faces 공간이나 자신의 서버에 스팸을 보낼 수 있다는 것입니다. 특정 방식으로 스팸을 보내면 Gradio 애플리케이션의 다른 사용자 트래픽이 리디렉션될 수 있습니다. 이는 매우 교묘한 버그이며, 발견된 단서들을 통해 해결되었습니다. 현재는 패치가 완료되었지만, 또 다른 문제가 있습니다. 바로 XSS( 크로스 사이트 스크립팅)입니다. 기본적으로 이것은 보안 문제는 아니지만, 사회적 요소와도 연관되어 있다는 점에서 흥미로운 문제입니다. 예를 들어 Hugging Faces에 앱을 배포했다고 가정해 보겠습니다. Gradio는 파일을 업로드할 수 있도록 해줍니다. 예를 들어, 이미지를 잘 받아들입니다. 이제 이미지를 업로드할 수 있습니다. SVG 파일도 업로드할 수 있고, 업로드한 SVG 파일의 링크를 가져올 수 있습니다. 링크는 '허깅 페이스' 도메인이나 ' 허깅 페이스' 도메인처럼 공간 이름 과 같은 형식일 것입니다. 이제 SVG 파일을 얻었고, 다른 사람에게 보낼 수 있습니다. 상대방은 '허깅 페이스' 도메인을 보고 '이 파일은 믿을 만하네. 허깅 페이스에서 온 거잖아'라고 생각할 수 있지만, 실제로는 제3자가 업로드한 파일입니다. 상대방이 링크를 클릭하면 SVG 파일이 브라우저에서 열립니다. 그런데 SVG 파일 에는 자바스크립트, 즉 악의적인 스크립트를 포함할 수 있습니다. 따라서 특정 유형의 파일은 브라우저에서 열리지 않도록 하고 다운로드하도록 하는 것이 좋습니다. 다운로드 후에는 파일을 검사할 수 있기 때문입니다. 이것이 바로 크로스 사이트 스크립팅(XSS)을 방지하는 표준적인 방법입니다. 5단계에서도 마찬가지로 SSRF(슬래시 사이트 루프)를 다룹니다. SSRF는 완전히 해결하기 매우 어려운 문제이지만, 어느 정도 해결했다고 생각합니다. Gradio 5에서 꽤 잘 작동하고 있습니다. 기본적으로 서버에서 Gradio 앱이 실행 중이라고 가정했을 때, 다른 사용자가 해당 Gradio 앱을 사용하여 임의의 타사 URL에 접근할 수 없도록 해야 합니다. 그렇게 되면 Gradio 앱을 악용하여 분산 서비스 거부 공격(DoS 공격)을 실행할 수 있기 때문입니다. Gradio 앱이 타사 URL을 호출하도록 허용하는 것도 바람직하지 않습니다. 하지만 동시에 Gradio에서는 타사 URL을 이미지 파일, 이미지 구성 요소 또는 오디오 구성 요소 등의 값으로 전달할 수 있어야 합니다. 음, 이것은 저희가 해결해야 할 문제입니다. 비교적 복잡한 해결책이지만, 저희는 이 기능을 독립적인 라이브러리로 내보내어 더 많은 웹 프레임워크 개발자들이 저희 패치와 솔루션을 자신의 애플리케이션에서 사용할 수 있도록 하는 방안을 고려하고 있습니다. 네, 공유 링크를 사용하여 Gradio를 배포할 때는 어떻게 될까요? 제가 방금 언급한 여러 가지 사항들이 이 시나리오에도 적용됩니다. 예를 들어 XSS 공격 같은 것들이죠. 공유 링크에는 몇 가지 문제점이 더 있습니다. 공유 링크를 생성하면 로컬에서 Gradio 앱이 실행되고, Gradio 서버가 로컬 컴퓨터에 연결을 설정한 다음, 이 공용 링크를 외부로 공유하게 됩니다. 문제는 이 연결이 안전하지 않다는 것입니다. SSL을 사용하지 않는다고 할 수 있겠죠. 따라서 누군가가 이 트래픽을 엿보고 컴퓨터와 Gradio 서버 간에 오가는 메시지를 읽거나 가로챌 수 있습니다. 예를 들어 카페의 공용 Wi-Fi 같은 곳에서 말이죠. 그래서 저희는 이 문제를 해결하기 위해 FRP 클라이언트의 새로운 버전을 개발했습니다. FRP는 Fast River Proxy의 약자입니다. 여기서 이 연결을 설정하는 데 사용되는 방법과 더불어, 심각하지는 않지만 이 연결의 보안을 강화하는 데 도움이 되는 몇 가지 다른 작업도 수행합니다. 마지막으로, 공급망 취약점 중 하나인 GitHub Actions에 대해 이야기하겠습니다. 오른쪽에 있는 비교적 간단한 문제부터 시작하겠습니다. GitHub Actions가 특정 버전으로 고정되도록 하는 것입니다. GitHub Actions 개발자가 자신의 GitHub Actions를 변경하여 CI에서 실행되는 작업에 영향을 미치거나 잠재적으로 비밀 정보 등을 유출하는 것을 방지하고 싶습니다. 그래서 모든 것이 고정되어 있으며, grub과 같은 도구를 사용하여 이 상태를 유지합니다. 그리고 GitHub Actions와 관련된 매우 심각한 보안 취약점이 있는데, GitHub Actions를 사용하는 많은 사람들이 모르고 있는 것 같습니다. 이는 GitHub를 통해 보고된 내용입니다. 실행하면 다음과 같은 문제가 발생합니다. 기여된 PR에 대한 모든 것, 예를 들어 오픈 소스 저장소가 있고 기여를 받지 않는다고 가정해 보겠습니다. 물론 기여를 수락했지만 해당 저장소에서 CI를 실행하고 테스트를 통과하는지 확인하고 싶을 수 있습니다. 일부 테스트에는 토큰이 사용될 수 있습니다. 타사 개발자가 토큰을 사용하여 임의로 실행하지 못하도록 매우 주의하더라도, 실행된 시스템 의 메모리를 덤프하여 메모리 에 저장된 비밀 정보를 유출할 수 있습니다. 매우 복잡한 문제 이지만 우려되는 부분입니다. 그래서 저희는 전체 CI 파이프라인을 재검토했습니다. 특히 저희 팀의 Get Up Handle PNG WN Pete에게 큰 감사를 드립니다. 그는 CI를 리팩토링하여 이러한 문제가 더 이상 발생하지 않도록 훌륭하게 작업했습니다. 이 문제는 저희가 해결했으며, Gradio 버전을 업그레이드할 필요는 없습니다. 이는 저희 CI에서 처리하는 부분입니다. 요약하자면, Gradio 애플리케이션은 로컬에서 실행되고 배포됩니다. 공유 공간이나 Share L과 공유되는 공간은 특정 보안 취약점에 취약합니다. Gradio 4 PointX 또는 Gradio 5 이전 버전을 사용하는 경우 이러한 문제가 발생할 수 있습니다. 결론적으로, 이러한 모든 보안 문제는 Gradio 5에서 수정되었고, 추가적인 검증을 거쳤습니다. 수정된 버전에 대한 검토도 진행했습니다. 또한, 이러한 문제가 재발하지 않도록 단위 테스트, 보안 테스트, 퍼징 테스트, 정적 코드 분석 테스트 등 다양한 테스트를 추가했습니다. 물론 보안은 항상 지속적인 노력이 필요한 부분입니다. 알려진 모든 취약점을 패치할 수는 있지만, 나중에 새로운 보안 문제가 발견될 가능성을 완전히 배제할 수는 없습니다. 따라서 앞으로도 보안 커뮤니티와 협력하여 발생하는 모든 문제를 해결해 나갈 것입니다.
