## 스크립트

Now that Noc has generated the topology, let's switch to the canvas tab. The tool provides two canvas views, the logical canvas and physical canvas. The logical canvas presents a compact diagram style view of micro architecture components and their connections. It focuses on the logical topology rather than physical implementation. So it does not display the actual locations of the components. This view makes it easier to understand the overall connectivity and to modify micro architecture parameters. The physical canvas provides a more detailed view of the micro architecture. It shows the physical locations of the components and their connections. This view is intended for physical optimization tasks such as relocating micro architecture components, adjusting the floor plan, improving time enclosure, or addressing other physical design constraints. Let's begin with the logical canvas. We can expand the right hand panel by clicking this arrow. Here you will find the different editors and viewers. At the top is the canvas visualizations pen. The canvas is made of different layers or networks. You can only edit one network at a time which you select in the edit network field. However, you can display multiple networks simultaneously by selecting them in the visible networks field. Before making any changes, make sure you selected the correct network to edit. If you can't see a component that you expect to be there, it is usually because the corresponding network is not currently visible. For example, we can't see the MCN in the current view, but as soon as we make the Chai network visible, they appear. Select any component on the canvas to display its properties in the property editor on the right. For example, let's click on as zero. The property editor now displays the configuration for this interface. You can expand each section to view additional microarchitecture parameters and modify them. Before making any changes, it is recommended that you create a checkpoint. This allows you to restore the current design state if necessary. To create a checkpoint, go file and then click create checkpoint. The tool prompts you to save a YAML file in your project directory. Enter a name for the checkpoint and then click create checkpoint. The checkpoint is now saved. Now let's modify one of the ASN micro architecture parameters. Expand ASN interface parameters in the property editor. For this example, assume that an additional retiming stage is required on the read response channel on packet tracker path in order to meet timing. So let's enable address register one to break the timing path. Select this option. Then click update to save the changes. Adding the aggress register increases the roundtrip latency. To compensate for this additional latency, let's increase the channel credits for the read response channel. To do this, select the connection between asne0ero and the routter. In the property editor, click connection parameters to open the configuration dialogue. Increase the read response channel credits by one. Then click update to save the changes. You can use the same approach to modify other parts of the noisy generated topology and further optimize the design for your implementation requirements. Once you finish, don't forget to save the configuration. Now let's look at the physical canvas. This view is similar to the floor plan tab we used during the nose configuration. The difference is that now it's populated with the micro architecture components and the endpoint interfaces are rooted. For this demonstration, let's assume that DSU is located far away from the MCN. To help mid timing, we will insert device credited slice DCS into the Chai network. Before adding DCS, we need to select CHI in the edit network field on the right panel. Next, let's expand design process micro architecture in the left panel. This section provides the micro architecture flows for the Chai network along with the components that you can add to the design. One of these components is the device credited slice DCS which you can drag onto the canvas. But before placing the DCS, let's remove the existing connection between the CDB and call. Select the connection. Then click remove connection in the connection editor. Now let's drag the DCS onto the canvas and assign it to the appropriate clock domain. Next, use the connector tool on the canvas toolbar to connect the CDB to DCS and then connect the DCS to the cal. Notice that these connections are displayed as dashed lines rather than solid lines. Dashed lines indicate that the logical connection exist but the routting has not yet been assigned. To assign the rooting, open the root editor next to the property editor. Select the Chai network and click refresh roots. The roots between DSU and the CDIS are marked with a yellow assigned status indicating that rooting still needs to be assigned. Compared to this, other routes which are already assigned are shown with the green status. You can assign each route manually by selecting it and choosing one of the available root candidates. Alternatively, click auto assign to allow the tool assign the roots automatically. You can also run the root analyze tool from the toolbar which I mentioned at the beginning of the video to achieve the same results more easily. Finally, validate the micro architecture by clicking microarchc to run the micro architecture design rule check. The design passes the validation. So, we are ready to move on to the next page.
