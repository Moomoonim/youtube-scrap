## 스크립트

Hello, welcome to a guide to Custom Hardware Development using dynamic PL reload within AMD’s Embedded Development Framework.&nbsp; This How-To video is based on and compatible with the Embedded Common Platform Configurable Example Design (CED) which is the Vivado design used to create the EDF BSP’s, the EDF pre-built OSPI firmware and EDF Linux Disk images. The video will begin by accessing and compiling an EDF compatible Vivado base project targeting the VEK385 board. This base design can be found in the AMD hardware platform GitHub repository. Next, a child project will be created based on this base project and the NoC solution file from the base project will be extracted and imported into the child design so that an identical NoC configuration will be used to ensure compatibility. A new custom IP will then be added to the block design so that the PL is modified, allowing LED control to come from the DIP switches. The child project will then be built, and the design compatibility will be compared to the base project. After the compatibility is verified, an XSA will be generated. The System Device Tree will then be extracted from the XSA using SDTGen utility, and a PL firmware bundle will be created. Last, the firmware bundle will be copied to the running VEK385 board running EDF Linux, and the new PL will be loaded and tested to ensure it is functioning properly. The custom hardware development flow or the Vivado CED flow starts with creating the new Vivado design based on the base design which is the Embedded Common Platform Configurable Example Design. This new child project is then modified and/or extended by adding new RTL blocks/IPs as per the requirement. Dynamic PL Reload using Segmented Configuration is used to implement application-specific incremental hardware design updates within the EDF framework. Segmented Configuration refers to booting the PS first and deferring the PL firmware to boost the Linux boot-time. The deferred PL firmware allows the Programmable Logic to be reconfigured while maintaining the existing Processor System and NoC configuration. The base hardware design is sourced from the Embedded Common Platform Configurable Example Design (CED) and is integrated in the boot firmware and Linux image. The Processor System and NoC defined in the base hardware design remain unchanged to ensure compatibility when loading the new PL PDI. A modified child hardware design is created to implement new PL logic. This results in a PL-specific firmware bundle containing only the PL PDI and device tree overlay. This firmware is loaded at Linux run-time via dfx-mgr-client. Consistency between the base hardware design and the child configuration is maintained by importing the NoC solution from the Golden Project and validating compatibility using pr_verify. Once the new updated child hardware design is ready, it is implemented to generate XSA. The system device tree is extracted from the XSA and a PL firmware bundle is created, which is then deployed back to the running VEK385 board running EDF Linux, and the new PL will be loaded and tested to ensure it is functioning properly. This approach enables custom hardware development without regenerating the base system image or modifying the EDF platform. Only the PL domain is updated. First, let’s look at an overview of how PL Reload for Segmented Configuration works. The segmented configuration approach enables users to delay delivery of the PL PDI image. Moreover, users can dynamically reload the configuration of the PL on the fly, changing the functionality of the design in the PL domain. This effectively provides a simplified entry point to a Dynamic Function eXchange (DFX)-like solution without requiring the use of a full DFX design flow within the Vivado Design Suite. However, it is important to establish consistency between multiple runs so that the NoC usage and interfaces match.&nbsp; To ensure consistency between implementation runs and their corresponding PDI images, the NoC solution is locked and then can be exported from one run and imported into another. The recommended approach to establish consistency from one project to the next is to create a "golden“ project and spawn all new variations from this source. This ensures the same processing system (PS) domain consistency, from the top-level block design name to NoC IP configuration and NoC connectivity. If designers expect to modify the NoC usage within the PL domain (either entirely in the PL domain, or the PL NMUs connecting to the PS NSUs), it is advised to separate this "dynamic" portion of the NoC into one or more unique NoC IP instances. This allows the PS NoC to more easily remain untouched from one run/project to the next.&nbsp; When a design is complete and is routed, first, lock all the NoC path segments that are tagged with the initial_boot property as well as all the segments connecting the PS domain to the PL. Then, export the NoC solution from a routed design checkpoint and write it as an NCR file using the write_noc_solution command. To replicate the NoC solution, read in the NCR file by setting the NOC_SOLUTION_FILE option within the Implementation Run Properties. This option calls the read_noc_solution Tcl command prior to running place_design to apply the NoC solution from the initial run.&nbsp; When the second design image is completely implemented, run the pr_verify command, which will confirm that the NoC solutions are identical and the PL images can be interchanged. This must be done directly in the Tcl Console to identify the two routed checkpoints to compare.&nbsp; To follow along, ensure that Vivado is installed on your machine. This video will be using Vivado 2025.1 on a Linux machine. A VEK385 running EDF Linux will also be needed. For assistance booting a VEK385 using the EDF Linux BSP Disk Image and OSPI boot firmware, please refer to the Getting Started with AMD Embedded Development Framework (EDF) Using Prebuilt Images&nbsp;video. Let’s begin the demo by compiling the base CED project. The CEDs can be found on the AMD GitHub in the “amd-yocto-hw-platforms" repository. Note that if you are using the Vitis Extensible Platform and the default PL payloads, there is no need to re-compile since the base NoC Solution File .ncr file is shipped with Vivado. Clone this GitHUb repository with the branch for Vivado 2025.1 into your working Linux directory. Next, navigate into VEK385_base directory. Here, a Makefile along with helper scripts exist to assist in the compilation of the CED project.&nbsp; Before running, the environment must be sourced with the Vivado version that the CED is from. To do this, run source, then the path to your Vivado installation, settings64.sh. Now, the project can be compiled. To do so, run “make xsa” Once the process is finished, open the Vivado project. After route_design in implementation, the NoC solution file was automatically created. To see its directory, look at the impl_1 properties. Take note of this directory, since it will be needed in the child project. Let’s create a child project based on the CED BaseProject so that an IP can be created and added to the design to showcase the full Dynamic PL Reload Functionality. .In the Vivado GUI, navigate to file, project, save as. Enter a name and specify the location you wish to store the project. Open the new project if it does not open automatically. Navigate to the Tcl console and run the set_property &lt;NOC_SOLUTION_FILE&gt; command as shown here and specify the path for the NoC Solution file from the base project to import the NoC configuration data to this new project. This is necessary to ensure consistency between implementation runs and their corresponding PDI images. Now that the NoC solution file is imported, the design can be modified. In the current design, the LEDs are being directly controlled by software through the AXI interface. A new PL payload will now be added by creating a new IP block to allow the LEDs to be controlled by the DIP switches on the VEK385 instead. It is important that the PS and NoC settings aren’t edited since this may break compatibility with the prebuilt boot.pdi and/or the prebuilt EDF images, which are based on the EDF specifications. If PS settings are edited, this moves into a full-custom flow, requiring re-generation of the EDF Linux image and update of the boot.pdi. Now create a custom new IP and add it to modify the existing PL. To do so, create a new project for the VEK385. You can change the name and save location, but this project will just be used for IP creation, so they are not important. Once the new project opens, add a design source titled dip_control. In the module, allow for the input of the DIP switch to drive the output of the LEDs as seen. Note that this is just an example of how you can add an IP. Feel free to use your own custom module or PL modifications. To create and package the IP, go to tools, create and package IP. Package the current project and include a repo directory of your choice. In the new interface, go to ports and interfaces to create custom interfaces that are compatible with the peripheral gpio pins in the base project.&nbsp; First, create a master pin for the LED output. Select the compatible interface domain “gpio_rtl” under the I/O interfaces. In the port mapping tab, connect the “tri_o” to the “LED_tri_o”. Now, repeat this process for the DIP input in monitor mode. Set the interface to “gpio_rtl”, and map the “TRI_I” port to the “DIP_tri_i" port in the port mapping. To finalize the IP, go to review and package and package the IP. This will add it to your IP catalog. Back in the child project, the IP repository that the new IP was saved in must be added so that it can be accessed. Navigate to the settings &gt; IP &gt; repository and add the directory.&nbsp; The IP can now be added. Open the block design and find the gpio_led and gpio_dip external interface pins on the right-hand side. Enlarge the area. Remove the connection between the axi_gpio_0 block’s GPIO port and the gpio_led external interface. Right click blank space, and select “Add IP”. Search for the “dip_control” IP that was created. Connect the created dip_control block’s LED port to the gpio_led external interface. Next, connect the DIP port on the dip_control block to the connection from axi_gpio_2 block and gpio_dip external interface. Last, connect the clock and reset pins to the AXI clock and reset connections into the other AXI interfaces. Once everything is connected, the PL addition is now complete, and the design can be compiled. Run synthesis, implementation, and generate the device image for the design. This will all happen sequentially when selecting “Generate Device Image” Once the design runs are all complete and the device image has been generated, the validity and design compatibility can now be tested using the pr_verify Tcl command. It compares the NoC routing that was captured in design checkpoint files during design generation.&nbsp; To do this, navigate to the Tcl console in the Vivado GUI and compare the routed dcp designs from both projects Run the “pr_verify” command with -initial option pointing to the base design routed dcp and the -additional option pointing to the child design routed dcp as shown here. After pr_verify finishes its run and it shows no errors, the firmware bundle from the child project can now be generated.&nbsp; First, the XSA must be exported from the Vivado project with the Include bitstream option enabled and save this to the location that can be easily accessed. Next, leave the Vivado GUI and navigate back to the directory where the project resides in the command line. First, extract the system device tree from the exported hardware XSA from the Vivado child project. This can be done using the SDTGen utility. To use this tool, Vivado must be sourced in the directory if it is not already. Next, to get into the SDTGen interface, run “sdtgen”. Specific SDT parameters can now be entered to configure the device tree generated. set_dt_param -dir my_sdt creates a directory in which your system device tree will be saved. set_dt_param -board_dts versal2-vek385-revA defines the target board that will be used. The target board used here is the VEK385. set_dt_param –xsa ./child_project.xsa will attach your Vivado project hardware to the system device tree. To make sure there is a proper handoff between device trees, run set_dt_param -zocl enable. To generate the system device tree, run generate_sdt. Once complete, the system device tree is now generated and stored in the my_sdt directory. To leave the SDT environment, type exit. Let’s now create the Firmware Bundle of the generated SDT to enable dfx-mgr-client to manage multiple PL Payloads and configure the PL from Linux. The firmware bundle is a directory containing a device tree overlay (.dtbo), PL payload (.pdi), and .json file (dfx-mgr-client configuration file). Create a directory to contain the files in the firmware bundle and copy in the source pld.pdi file. Next, create a shell.json file in the firmware bundle directory. To do this, run “nano child-fw/shell.json” Add the shell type as XRT_FLAT and num_slots as 1 wrapped within curly brackets. Next, use Lopper to create the Linux Device Tree from the System Device Tree. To do this, run the lopper command as shown here by giving the paths to the sdt and overlay files. Last, use Device Tree Compiler to create the device tree overlay .dtbo file. To do this, run “dtc -I dts -O dtb -o child-fw/pl.dtbo child-fw/pl.dtsi”. You now have a firmware bundle directory that can be transferred to the running system for use. Copy this firmware bundle to the VEK385 board’s home directory that is running EDF Linux. Once the new directory is copied to the board, it must be moved into the proper location so that it can be treated as a firmware bundle. The easiest way to do this is to copy the directory with the super user privileges and the –r flag to the /lib/firmware/xilinx directory. To confirm that the firmware bundle was added successfully, run “sudo dfx-mgr-client –listPackage" to see the available packages listed out. In here, the bundle from&nbsp;the EDF CED design as well as the newly added child project exist.&nbsp; To load the firmware bundle, run “sudo dfx-mgr-client –load child-fw".&nbsp; You should see that the bundle was successfully loaded and is now running on the board. To confirm, try adjusting the DIP switch positions on SW7 and see the resulting output on the 4 LEDs. Then, a child project was created based on the base project and a new IP was added to the block design to modify the PL, allowing LED control to come from the DIP switches. The child project was then compiled, and the design compatibility was compared to the base project. Last, the firmware bundle was copied to the VEK385 board running EDF Linux, and the new PL was loaded and tested to ensure it was functioning properly.
