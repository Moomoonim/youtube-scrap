## 스크립트

WWDC에서 스위프트 UI를 소개한 문구입니다. 일단 한번 믿어보기로 하였습니다. 더닝 크루거 이펙트라고 경험과 자신감과의 상관관계를 나타낸 그래프입니다. 제 스위프트 UI 경험은 극히 초반 단계였기 때문에 자신감이 가파르게 높아진 것도 한목했습니다. 다행히 스위프트 UR이 적용하고 QA를 거쳐 큰 문제 없이 배포할 수 있었습니다. 비리 통신을 통해 출입문을 열 수 있었고 모든 출입문에 적용해 보았습니다. 실제로 iOS 13 미만 단말을 쓰는 크로가 있었는데 iOS 13으로 업데이트해 달라 요청이기도 하였습니다. UI를 구현하 있어서 스위프트 UI와 UI 킷의 차이점은 무엇이 있을까요? 제가 첫 번째로 느낀 점은 레이아웃 사고 방식의 변화였습니다. UR 정확히는 오토레이엇의 경우를 먼저 살펴보도록 하겠습니다. 특정 뷰의 중심에서 슈퍼브나 주변 뷰들과의 관계를 정의하는 방식으로 레이아웃을 구현해 나갑니다. 안쪽에서 바깥쪽으로 컨스트레인트를 할당해 나가는 방식인 것이죠. 반면 스위프트 UI에서는 특정 뷰에 포함된 서브뷰들을 배치해 나가는 방식입니다. 시점이 오토레어과는 다르게 바깥쪽에서 안쪽으로 향하게 됩니다.이 때문에 같은 디자인 가이드를 받아도 시점의 방향이 반대로 흐르기 때문에 오토 레이아웃에 익숙한 상태에서는 스위프트 UI로 구현하기가 어색할 수 있습니다. 하지만 이마저도 익숙해지면 더할 없이 편한 방식으로 받아들여집니다. 예시를 살펴보도록 하겠습니다. 화면에 노란색 사각형이 그려져 있는데요. 이걸 UI 키만 사용한다면 어떻게 구현해야 되겠다고 생각되시나요? 바로 노란색 사각형의 탑과 리딩에 컨스트레인트를 할당해야겠다고 생각될 것입니다. 서드 파티를 활용하지 않고 코드로만 작성한다면 많은 분들이 이처럼 구현할 것입니다. 스위프트 UI 코드를 살펴보도록 하겠습니다. 시점이 밖에서 안으로 흐른다고 하였죠. 노란 사각형의 탑과 리딩에 마진을 주는 방식이 아닌이를 포함하는 뷰에 패딩을 주어야 합니다. 그리고 스페이스를 활용하여 여백을 채우는 방식으로 노란색 사각형의 위치를 맞추게 됩니다. 스페이스어의 영역은 실제로 점선과 같지 않고 포함된 엑시스에 따라 높이는 제로이고 너만 있거나 너비만 있고 높이가 제로일 수 있습니다. A스택이나 H스택에 포함되지 않으면 높이와 너비가 둘 다 존재하면서 꽉 채우는 형태가 될 것입니다. LOC 기준으로 볼 때 어떠신가요? 스위프트 UI를 사용했을 때 코드양이 상당히 줄어든 것이 느껴지시나요? 이번엔 조금 더 극단적인 예시를 살펴보도록 하겠습니다. 노란 사각형이 정중앙에 배치되는 경우입니다. UI을 사용할 경우 LOC는 큰 변화가 없습니다. 탑과 리딩을 주었던 코드가 센터 X와 센터 Y의 컨스트인트를 할당해 줄 뿐이죠. 스위프트 UI 코드를 보면 정말 짧은 걸 볼 수 있습니다. 왜냐하면 스위프트 UI의 뷰는 기본값이 중앙이기 때문입니다.이 부분도 익숙해져야 하는 부분 중 하나입니다. 그렇다면 실제 화면 구현에서는 어떨까요? 실제 모바일 출입 카드 앱의 로그인 화면 코드입니다. 이미지, 타이틀, 디스크립션, 로그인 버튼으로 화면이 구성되어져 있습니다. 이처럼 X코드에서도 프리뷰를 통해 코드와 URL을 바로 확인할 수 있는데요. 실시간으로 적용되는 프리뷰를 보며 구현을 하니 작업이 매우 수월했습니다. 이런 식으로 각 요소들을 컴퓨티드 프로퍼티로 분리시킬 수 있습니다. 로그인 버튼 또한 컴퓨티드 프로퍼티로 분리해 보았습니다. 하지만 이런 방식만 가능한 건 아닙니다. 이처럼 구조체를 새로 정의할 수도 있습니다. 애플은 이와 같이 뷰를 분리시키는 걸 권장하고 있습니다. 같은 파일에 두지 않고 파일을 새로 만들어 분리시키는 것도 하나의 방법입니다. 제이 적절하게 잘 분리시켜 사용하도록 코딩 컨벤션을 마련하는 것도 좋겠다 생각하였습니다. 그런데 화면상의 버튼은 디자인이 적용되어 있는데 이에 해당하는 모디파이어들은 보이지가 않습니다. 바로 버튼 스타일을 따로 정의하였기 때문입니다. 이처럼 자주 사용하는 스타일들을 버튼 스타일 프로토콜을 어댑트하여 따로 정의해 두면 편하게 디자인을 적용시킬 수 있습니다. 버튼 외에도 토글, 피커, 텍스트 필드 등 해당 스타일들을 따로 정의할 수 있는 프로토콜이 존재합니다. 어려웠던 부분을 공유하자면 WWDC 19 영상을 통해 처음 접하고 적용을 시작하였는데 정식 버전에서는 베타 때의 용어와 달라진 점이 있어 혼동이 있었습니다. 초기 단계이기에 레퍼런스가 적은 부분도 어느 정도 어려움으로 작용했습니다. 순수 스위프트 UI 앱을 개발해 보자라고 시작하였지만 사실상 불가능했습니다. 스위프트 UI에서 제공하지 않는 컴포넌트들은 UI 뷰 레프리젠터블 프로토콜을 어댑트한 뷰를 새로 정의하여 UI키 기반으로 구현해야 했습니다. 예를 들어서 UI 액티비티 인디케이터 뷰를 사용하기 위해서 UI뷰 레프리젠터블을 어댑트한 액티비티 인디케이터 뷰를 새로 정의하였습니다. UI 액티비티 인디케이터 뷰스턴스를 생성하는 메이크 UI 뷰 메소드와 뷰를 갱신해 주는 업데이트 UI 뷰 메소드를 구현하면 됩니다. 참고로 iOS 14로 업데이트한다면 따로 구현할 필요 없이 스위프트 UI 컴포넌트인 프로그레스 뷰를 사용하면 됩니다. 웹뷰를 보여 줄 필요가 있어서 WK 웹뷰도 따로 정의하였습니다. 보시는 것처럼 델리게이트 처리가 필요할 경우 네티드 클래스로 코디네이터를 구현하여 해결할 수 있었습니다. 스위프트 UI의 첫 번째 버전을 사용하다 보니 가장 힘든 점은 역시 버그였습니다. 제가 겪은 버그 현상 중 일부를 공유하고자 합니다. 첫 번째는 돌아올 수 없는 내비게이션 내비게이션 링크 버그입니다. 코드는 매우 간단합니다. 내비게이션 바에 내비게이션 링크가 포함되어 있는 형태입니다. 내비게이션 링크를 누르면 세컨 뷰로 이동하게 되고 백 버튼을 눌러 돌아올 경우 크래시가 나게 됩니다.이 현상은 iOS 13.2에서만 2에서만 나타나고 있었습니다.이 문제는 UI 호스팅 컨트롤러 단위로 화면을 이동시키거나 OS 업데이트를 유도하는 방식으로 문제를 해결할 수 있었습니다. 두 번째 케이스의 코드는 전과 동일합니다. 다만 OS 버전만 13.35로 3로 올렸습니다.이 경우에는 백 버튼을 이용해 돌아왔을 경우 크래시는 나지 않지만 다시 세컨비로 이동되지 않습니다. 다행히 시뮬레이터에서만 해당 현상이 나타나고 있어서 실기기 이슈는 없었습니다. 다음은 1회용 시트입니다. 직전 케이스와 비슷한 모양인데요. 내비게이션 바에 버튼이 포함되어 있고 이즈비저블 스테이트 값을 변경해 주면서 모달뷰를 여닫는 형태입니다. 세컨 뷰에서는 닫기 버튼을 누를 경우 바인딩되어 있는 이즈비저블 값에 퍼스를 할당하며 모달비를 닿도록 구현되어 있습니다. 그런데 한 번 여닫고 나면 다시 열리지가 않습니다. 그래서 앱을 종류하고 다시 킨 후 드래그에서 모달비를 닫으면 문제가 없어서 모달비에는 닿기 버튼을 제공하지 않는 방식으로 해결할 수 있었습니다.이 외에도 내비게이션 링크의 초기값이 비활성으로 되어 있거나 특정 환경에서 토글 버튼이 동작하지 않는 등 자잘한 버그들이 존재하였습니다. 이런 부분들은 마이너 버전 업데이트가 되면서 점점 개선되었습니다. 올해 WWDC에서는 iOS 14가 소개되었는데요. 스위프트 UI에도 대대적인 업데이트가 있었습니다. 만약 iOS 14로 업데이트 된다면 어떤 변화가 있는지 간략히 살펴보도록 하겠습니다. iOS 13에서 사용 가능한 컴포넌트들입니다. 그리고 iOS 14에서 새로 추가된 컴포넌트들입니다. 한 눈에 보기에도 적지 않다는 것을 알 수 있는데요. 인상 깊은 컴포넌트들 몇 가지를 살펴보도록 하겠습니다. 예를 들어 V스택이나 H스택에서 포로 다수의 데이터를 보여 주어야 할 때 기존에는 화면에 보이지 않는 영역의 뷰까지 모두 생성하였지만 레이즈 HD 스택이나 레이즈 V스택에 임배드시키면 화면에 보이는 부분만 뷰를 생성하게 됩니다. iOS 13에서 싱글 컬럼이 아닌 컬렉션 뷰를 그리기 위해서는 구현 방법이 꽤나 까다로웠습니다. iOS 14에서는 그리드 컴퍼넌트들이 추가되면서 플렉서블한 컬렉션 뷰를 쉽게 구현할 방법이 생겼습니다. 아직 스위프트 UI를 망설리고 계신가요? 조금만 더 망설어 보면 어떨까요? 만약 최소 지원 버전이 iOS 13이 되었다면 부분 적용을 하되 사용성에 문제가 되는 버그들이 없는지 버전로 잘 테스트해야 할 것입니다. 만약 순수 스위프트 UI앱 개발을 지향한다면 아무래도 최소 지원 버전은 높을수록 좋겠죠. iOS 14에 업데이트된 내용만 보더라도 말이죠. 스위프트 UI가 사용자 인터페이스를 구현하는데 혁신적인 방법인 건 사실입니다. 또한 읽고 작성하기 쉬운 코드는 높은 생산성을 만들어 냈습니다. 도입은 신중이 고려하되 당장 학습을 시작하는 건 어떨까요? 이상 발표를 마치도록 하겠습니다. 감사합니다.
