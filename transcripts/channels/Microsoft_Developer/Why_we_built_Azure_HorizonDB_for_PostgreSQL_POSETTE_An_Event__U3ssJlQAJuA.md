## 스크립트

안녕하세요 여러분, 저는 마이크로소프트의 제품 관리자 딩딩 루입니다. POSETTE 2026에 오신 것을 환영합니다. 오늘은 "Azure HorizonDB를 개발한 이유"라는 주제로 발표를 준비했습니다. 개발자 또는 DBA이시면 서 Azure HorizonDB가 어떤 추가적인 이점을 제공하는지 궁금하시다면, 이 발표에 꼭 참여하시길 바랍니다. 좋습니다. 이제 Azure HorizonDB for Postgres를 개발한 이유를 자세히 살펴보겠습니다. 마이크로소프트는 이미 약 5년 전에 정식 출시된 Azure Database for PostgreSQL이라는 PostgreSQL 서비스를 제공하고 있습니다 . 이 서비스는 매우 인기 있는 데이터베이스 서비스 이며, OpenAI와 같은 많은 대형 고객사에서 사용하고 있습니다. 그렇다면 왜 또 다른 PostgreSQL 데이터베이스를 개발했을까요? 지난 몇 년간 Azure Database for PostgreSQL을 운영하면서 고객들이 비용 효율성을 높이고, 필요에 따라 워크로드를 확장하고, 다운타임을 최소화하기 위해 트래픽이 급증할 때에도 일관된 성능이나 예측 가능한 지연 시간을 원한다는 것을 알게 되었습니다 . 이러한 모든 점들을 고려하여, 저희는 PostgreSQL을 Azure에서 더 효율적으로 실행할 수 있도록 수정하고, 동시에 Azure가 PostgreSQL과 더 잘 연동되도록 개선하여 고객의 모든 요구 사항을 충족할 수 있는 새로운 PostgreSQL 데이터베이스인 Azure HorizonDB를 구축하고자 했습니다 . 두 데이터베이스를 비교해 보면, Azure Database for PostgreSQL은 기본적으로 오픈 소스 PostgreSQL을 기반으로 약 20가지 정도의 변경 사항을 적용하여 Azure VM에서 호스팅하는 방식입니다. 관리형 오픈 소스 PostgreSQL을 찾고 있다면 이 제품이 적합합니다. Azure HorizonDB는 Azure와 PostgreSQL의 호환성을 높이기 위해 다른 설계 및 아키텍처를 사용하지만 , 여전히 99.9% PostgreSQL을 기반으로 합니다. HorizonDB를 개발하기 위해 PostgreSQL을 수정할 때 매우 정밀한 접근 방식을 취했습니다. 따라서 최고 수준의 가용성, 성능 및 확장성을 원한다면 Azure HorizonDB가 좋은 선택입니다. 또한 엔터프라이즈급 보안을 제공하며 Azure 개발 에코시스템과의 풍부한 통합 기능을 지원합니다. VS Code 확장 프로그램인 Copilot을 통해 데이터베이스 AI 환경을 제공하는 AI 지원 기능을 사용할 수 있습니다 . 또한 ETL 작업 없이 Fabric OneLake로 데이터를 복제하여 거의 실시간으로 분석할 수 있도록 Fabric과 통합됩니다 . 이제 HorizonDB 아키텍처를 살펴보겠습니다. HorizonDB는 데이터베이스를 로그로 간주하고 컴퓨팅과 스토리지를 분리하는 개념을 기반으로 구축되어 컴퓨팅과 스토리지를 독립적으로 확장할 수 있습니다. 가장 아래 계층은 모든 트랜잭션 로그와 데이터 페이지를 저장하는 Azure Blob Storage입니다. 따라서 이는 데이터의 기록 시스템이며 기본적으로 영역 복원력을 제공합니다. 복원력을 높이기 위해 별도의 작업을 수행할 필요가 없습니다. 그 위에 두 개의 스토리지 플릿을 구축했습니다. 하나는 트랜잭션 로그를 저장하는 공유 WAL 스토리지이고, 다른 하나는 PostgreSQL 데이터 페이지를 저장하는 공유 데이터 스토리지입니다. 여기서 '공유'란 모든 컴퓨팅 노드가 WAL 스토리지와 데이터 스토리지 플릿 모두에 액세스할 수 있음을 의미합니다 . 컴퓨팅 계층의 경우, HorizonDB 클러스터는 읽기/쓰기 엔드포인트를 갖춘 기본 서버 하나와 읽기 전용 엔드포인트를 갖춘 최대 15개의 읽기 가능한 고가용성(HA) 복제본을 지원합니다. 이 복제본들은 자동으로 로드 밸런싱 됩니다. 기본 서버와 복제본은 상태 비저장 방식이므로, 데이터가 컴퓨팅 노드가 아닌 스토리지 계층에 저장되기 때문에 서버 전체에 장애가 발생하더라도 데이터는 손실되지 않습니다 . 컴퓨팅 노드에 저장되는 유일한 데이터는 성능 향상을 위한 캐싱 계층 역할을 하는 SSD 캐시입니다. 컴퓨팅과 스토리지의 분리 덕분에 체크포인트 또는 페이지 쓰기와 같이 리소스 사용량이 많은 PostgreSQL 백그라운드 프로세스를 스토리지 계층으로 옮길 수 있습니다 . 이렇게 하면 이러한 프로세스가 디스크 I/O 및 네트워크 I/O와 같은 리소스를 실제 워크로드 와 경쟁하지 않게 됩니다 . 마지막으로 한 가지 더 말씀드리고 싶은 것은, 전체 스토리지 계층과 일부 PostgreSQL 확장 기능은 Rust로 구축되었다는 점입니다. Rust는 C 언어가 1970년대에 만들어진 것과 비교하면 비교적 새로운 시스템 언어로, 대략 10년 정도밖에 되지 않았습니다. Rust는 메모리 안전성과 데이터 경쟁 없는 동시성 지원으로 잘 알려져 있습니다. C나 C++로는 메모리 손상이나 버퍼 오버플로를 피하기가 매우 어렵습니다. Azure에서는 데이터베이스 나 성능에 중요한 서비스를 Rust로 구축하는 추세입니다 . 따라서 Rust를 사용하여 HorizonDB를 구축하는 것은 미래를 대비하는 데 있어 이미 한 발 앞서 나가는 것 입니다. 이제 개요를 살펴보았 으니 좀 더 자세히 알아보겠습니다. 먼저 공유 WAL 스토리지와 그 이점에 대해 살펴보겠습니다. 왼쪽은 기본 서버와 대기 서버로 구성된 고가용성(HA) PostgreSQL의 일반적인 구성입니다. 로그는 로그 전송(log shipping)을 통해 기본 서버에서 대기 서버로 동기적으로 복제됩니다. 트랜잭션을 커밋하려면 PostgreSQL은 다음과 같은 4단계를 순차적으로 거쳐야 합니다. 1단계: 로그를 기본 서버의 로컬 디스크에 기록합니다. 2 단계: 로그를 보조 서버로 전송합니다. 3단계 : 보조 서버가 로그를 자체 로컬 디스크에 기록합니다. 4단계: 보조 서버가 기본 서버에 확인 응답을 보냅니다. 이 4단계가 모두 합쳐져 트랜잭션 커밋 지연 시간이 발생합니다. 또한, 요즘에는 네트워크 연결 디스크(NAD)를 사용하는 것이 일반적이므로, 이로 인해 지연 시간에 추가적인 네트워크 홉이 발생합니다. 오른쪽의 HorizonDB는 기본적으로 영역 복원력이 있는 공유 WAL 스토리지를 사용합니다. 로그를 커밋할 때 세 개의 가용 영역을 한 번만 거치면 됩니다. 대기 서버는 기본 서버와 전혀 상호 작용할 필요가 없습니다. 공유 WAL 스토리지에서 직접 로그를 가져올 수 있습니다. 이는 복제본이 많을 때 매우 효율적입니다. 각 복제본은 독립적으로 작동하며, 기본 서버와 통신하거나 장애 조치 중에 기본 서버가 변경될 때 기본 서버에 다시 연결할 필요가 없습니다 . 이러한 설계를 통해 트랜잭션 커밋에 필요한 홉 수가 줄어들어 성능 향상을 얻을 수 있습니다. 또한 기본 서버와 복제본을 분리하여 안정성을 높일 수 있습니다. 그렇다면 왜 이러한 공유 WAL 스토리지 서비스를 직접 구축해야 할까요? 기존 관리형 디스크를 사용하면 되지 않을까요? 우리가 원하는 것은 크기가 작은 테일 로그, 즉 자주 사용되는 로그만 저장하는 것입니다 . 그리고 자주 사용되지 않는 로그는 Azure Blob Storage와 같은 저렴한 스토리지로 오프로드하면 됩니다. 우리는 영역 이중화, 낮은 지연 시간, 그리고 비용 효율성도 필요로 합니다. 또한, 다른 Azure 서비스에서 재사용할 수 있는 범용 서비스로서 WAL 스토리지 서비스를 구축하고자 합니다. 이러한 모든 요구 사항을 고려할 때, 관리형 디스크는 적합하지 않습니다. 예를 들어, Azure Ultra Disk는 낮은 지연 시간을 제공하지만 영역 이중화를 지원하지 않습니다. 게다가 최소 4GB의 용량이 필요하기 때문에 우리의 목적에는 상당히 비쌉니다. 따라서 이러한 모든 요구 사항을 바탕으로, 우리는 의도적으로 추가 전용 쓰기와 낮고 예측 가능한 쓰기 지연 시간에 최적화되고, 자주 읽히는 로그의 끝부분만 저장하며, 오래된 WAL은 Blob 스토리지에 아카이빙할 수 있는 WAL 스토리지를 구축했습니다. 이제 공유 WAL 스토리지 서비스를 소개했으니, 쓰기 수명 주기 와 재실행 및 업데이트 페이지가 어떻게 작동하는지 살펴보겠습니다 . 지금까지는 공유 데이터 스토리지 플릿에 대해서는 다루지 않았습니다. 크기가 작은 로그와 달리 데이터는 매우 클 수 있으며 디스크 하나에 모두 저장할 수 없습니다. 그래서 저희는 데이터 스토리지 플릿의 여러 노드에 데이터를 분산 저장하는 것입니다. 쓰기 트랜잭션이 기본 서버에 도달하면 로그는 공유 WAL 스토리지에 저장되고 트랜잭션이 커밋됩니다. WAL 스토리지와 데이터 스토리지 사이에 있는 WAL 필터링 서비스는 트랜잭션 로그 스트림을 받아 헤더를 열고 이 로그가 어떤 페이지를 업데이트할지 확인한 후, 업데이트할 페이지가 있는 샤드에만 로그를 전송합니다. 이는 모든 데이터 스토리지 샤드가 네트워크를 통해 모든 로그를 가져온 다음 해당 샤드의 페이지와 관련 없는 로그의 99%를 버리는 방식보다 훨씬 효율적입니다. 공유 WAL 스토리지와 데이터 스토리지를 사용하고 기본 서버가 아닌 다른 스토리지 계층에서 WAL 필터링을 수행함으로써 모든 트랜잭션 커밋, 로그 강화, 로그 재실행, 복제본 읽기, 공유 데이터 스토리지의 데이터, WAL 스토리지, Azure Blob Storage로의 WAL 아카이브 등의 작업을 효율적으로 처리할 수 있습니다 . 이 모든 프로세스는 비동기 프로세스입니다. PostgreSQL은 어떤 단계도 조정하거나 특정 단계가 완료될 때까지 기다릴 필요가 없습니다. 공유 WAL과 공유 데이터 저장소 설계의 또 다른 이점은 장애 조치입니다. HorizonDB의 장애 조치 작동 방식을 살펴보기 전에 오픈 소스 PostgreSQL의 장애 조치 작동 방식에 대한 배경 설명을 드리겠습니다. 장애 조치는 먼저 기본 서버를 감지합니다 . 하트비트가 누락되면 장애로 간주하고, Patroni 또는 이와 유사한 합의 프로토콜에 따라 리더를 선출합니다. 그런 다음 대기 서버를 선출하고 새로운 기본 서버로 승격시킵니다. 이 모든 단계는 신속하게 수행될 수 있지만, 문제는 이전 기본 서버가 다시 연결되어 재참여를 시도할 때 발생합니다. 이전 기본 서버는 로컬 디스크에 자체 로그 복사본을 가지고 있으며, 로그가 분기되었을 가능성이 매우 높습니다. 이를 해결하기 위해 PostgreSQL은 리와인드 작업을 실행해야 합니다. 이는 기본 서버가 정상적으로 종료된 경우에도 필요한 추가 단계입니다. 최악의 경우는 기본 서버가 정상적으로 종료되지 않은 경우입니다. 기본 서버는 자체 로컬 디스크와 자체 데이터를 가지고 있다는 점을 기억하세요. 만약 모든 데이터가 손실된다면 어떻게 될까요? PostgreSQL은 스냅샷을 사용하여 다시 초기화해야 합니다. 이러한 추가 단계들 때문에 장애 복구가 더 어려워지고 오류 발생 가능성이 높아집니다. 또한, 장애 조치와 복구 사이의 시간 간격이 길어질 수 있습니다. HorizonDB의 공유 아키텍처에서는 기본 노드와 대기 노드가 상태를 유지 하지 않으며 로그나 데이터의 자체 복사본을 보관하지 않습니다. 따라서 기본 노드 장애 감지, 대기 노드 선택, 대기 노드를 새로운 기본 노드로 승격시키는 첫 세 단계는 오픈 소스 PostgreSQL과 동일합니다. 차이점은 이전 기본 노드가 다시 연결될 때 자체 로컬 데이터 복사본이 없으므로 공유 WAL 스토리지에서 직접 읽어온다는 것입니다. 필요에 따라 스냅샷을 사용하여 되돌리거나 다시 초기화할 필요가 없습니다. 따라서 장애 조치 복구가 훨씬 빠르고 안정적 이며 다운타임 시간도 짧습니다. 지금까지 HorizonDB에서 쓰기 작업이 어떻게 작동하는지 살펴보았으니, 이제 읽기 작업이 어떻게 작동하는지 살펴보겠습니다. Horizon의 모든 노드(기본 노드든 복제 노드든)에는 NVMe 디스크로 구성된 로컬 SSD 캐시가 있습니다. 이 디스크는 속도가 매우 빠릅니다. 따라서 읽기 요청 시 SSD 캐시에 저장할 수 있는 데이터 세트를 요청하면 지연 시간은 마이크로초 단위입니다. 읽기 쿼리에서 SSD 캐시에 저장할 수 없는 더 많은 데이터가 필요한 경우에만 GetPage API 호출을 통해 공유 데이터 스토리지에 필요한 페이지를 가져옵니다 . 이 경우에도 지연 시간은 여전히 ​​수 밀리초 이내입니다. 이제 선택지가 생겼습니다. 대부분의 읽기 쿼리가 소량의 데이터만 처리하고 해당 데이터가 SSD 캐시에 저장될 수 있다면, 콜드 데이터는 Azure Blob Storage와 같은 저렴한 스토리지 에 저장할 수 있습니다 . 하지만 처리해야 할 데이터 세트가 SSD 캐시 용량보다 크다면, 최적화된 성능을 얻기 위해 더 큰 SSD 캐시 용량으로 컴퓨팅 크기를 업그레이드할 수 있습니다 . 지금까지 WAL 스토리지와 쓰기 및 읽기 트랜잭션 작동 방식에 대해 살펴보았습니다. 이제 데이터 페이지 저장 방식을 살펴보겠습니다. HorizonDB는 PostgreSQL의 데이터 페이지에 대한 논리적 뷰를 변경하지 않습니다. PostgreSQL은 여전히 ​​1GB 세그먼트 파일과 통신하는 것으로 인식합니다. 하지만 내부적으로는 파일을 샤딩하여 데이터 스토리지 플릿 과 최종적으로 내구성이 뛰어난 Azure Blob Storage에 저장합니다. 기본적으로 데이터 스토리지 플릿은 Azure Blob Storage 위에 구축된 캐시 이며, 리두 로그를 실행할 수 있습니다. 복원력을 제공하기 위해 데이터 스토리지 플릿은 각 샤드의 복사본을 가용 영역 전체에 복제합니다. 이렇게 하면 컴퓨팅 노드가 동일한 영역에 있는 샤드에서 페이지 복사본을 요청할 수 있으므로 지연 시간을 줄일 수 있습니다. 효율적인 데이터 스토리지에 대해 이야기해 보겠습니다. 데이터베이스가 연결된 디스크를 스토리지로 사용하는 경우, 데이터 증가에 대비 하여 스토리지 크기를 미리 프로비저닝해야 합니다 . 디스크 크기가 데이터 크기에 맞지 않으면 나중에 수동으로 크기를 늘리거나 줄여야 합니다. HorizonDB를 사용하면 이러한 작업을 전혀 할 필요가 없습니다. HorizonDB는 데이터 증가에 따라 자동으로 확장되거나 축소되도록 설계되었기 때문입니다. HorizonDB 는 데이터를 매우 효율적으로 샤딩합니다. 데이터가 증가하여 샤드를 추가해야 할 경우, 일관성 해싱을 실행하여 적절한 Blob을 찾고 데이터를 대량으로 읽어 Blob에 저장하기 만 하면 됩니다 . Azure Page Blob은 업데이트 가능하므로 데이터를 쉽게 삽입할 수 있습니다. Azure Blob Storage의 또 다른 장점은 빠른 시점 복원입니다. Azure Blob Storage는 스냅샷도 지원하며, 일반 스냅샷과 동일하게 작동합니다. 이는 매우 유용한 기능입니다. 따라서 시점 복원을 지원하는 것이 훨씬 쉬워집니다. 증분 스냅샷 목록에서 원하는 시점의 스냅샷을 선택하고, 해당 시점의 일관된 상태로 되돌리기 위해 일부 로그를 다시 작성하기만 하면 됩니다. 지금까지 컴퓨팅과 스토리지를 분리한 HorizonDB 아키텍처, WAL 스토리지를 구축한 이유, 그리고 Azure Blob Storage 사용의 이점에 대해 살펴보았습니다.
