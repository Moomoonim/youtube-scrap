JSON 파일 내부를 살펴보면 대략 이런 구조입니다. 맨 위로 올라가면 구조를 볼 수 있는데, API의 모든 경로를 담고 있는 `paths`라는 객체 목록이 있고, 인증 체계를 설명하는 `security`라는 객체가 있습니다. 그리고 유용한 정보 섹션이 있는데, 이 두 부분은 그다지 중요하지 않아서 무시하겠습니다. 그 다음에는 ` tags` 목록이 있는데, 이게 정말 유용한 부분입니다. 왜냐하면 이런 식으로 구성되기 때문입니다. 다시 돌아가 보면 이 항목들이 태그로 존재하는 것을 볼 수 있습니다. 즉, 여기에 있는 항목들이 오픈 API 사양의 태그가 되는 것입니다. 흥미로운 점은 오픈 API 사양에서 검색 기능을 구축하는 것이 비교적 간단하면 좋겠다는 것입니다. 왜냐하면 찾고자 하는 것을 모르는 경우 이 검색창이 항상 잘 작동하는 것은 아니기 때문입니다. 예를 들어 " 그룹 내 검색"이라고 입력하면, 오, 이 검색창은 꽤 잘 작동합니다. 와, 이건 향상된 오픈 API 사양 검색창 같네요. 확인하기 전에 미리 살펴봤어야 했는데. 어쨌든 꽤 괜찮습니다. 검색 기능이 잘 작동하네요. 예를 들어 트리브(treeve)의 경우 실제로는 그렇지 않습니다. 동일한 검색 기능을 가지고 있지만, 저는 이 기능을 어떻게 향상시키거나 벡터 검색과 연결하여 래그 감사(rag audit)를 수행할 수 있는지 설명하는 데 정말 관심이 있었습니다. 그리고 제가 여기서 강조하고 싶은 것은 바로 이 부분입니다. 쿼드런트(Quadrant)에는 그룹(groups)이라는 매우 흥미로운 기능이 있습니다. 한 번에 여러 지점을 검색하여 단일 경로만 검색하는 대신 그룹 지향적인 방식으로 결과를 반환할 수 있습니다. 개방형 API 사양에서 이는 매우 흥미로운 기능입니다. 각 태그의 개별 경로를 살펴보면서 태그를 검색할 수 있다는 의미이기 때문입니다. 쿼드런트와 같은 시스템 없이는 구축하기 매우 어려운 기능입니다. PG 벡터 검색이나 얼굴 인식 또는 US 검색과 같은 무차별 대입 방식과 비교했을 때 쿼드런트의 주요 기능 중 하나라고 생각합니다. 제가 목표로 했던 것은 특히 쿼드런트의 개방형 API 사양을 사용하여 제가 하려는 작업에 가장 적합한 엔드포인트가 무엇인지 파악하는 것이었습니다. 이 예제에서는 BUN이라는 JavaScript 스크립팅 런타임을 사용했습니다. 저는 BUN을 매우 좋아하는데, 성능이 뛰어나고 사용하기도 간편해서 만족스럽습니다. 먼저 JSON 형식으로 Quadrant 오픈 API 사양을 불러온 다음, Treeve 내부에 있는 몇 가지 요소를 가져옵니다. Treeve는 내부적으로 Quadrant를 사용하여 많은 기능을 제공하며, 이 예제에서도 같은 방식으로 진행합니다. Treeve SDK 클라이언트 패키지에서 몇 가지를 가져오고, 환경 변수를 몇 개 인스턴스화하고, Treeve API에 대한 구성을 설정합니다. 이제 흥미로운 부분이 나옵니다. Quadrant 오픈 API JSON 사양에서 태그 배열을 가져와서 각 태그를 순회하며 이미 그룹이 생성되었는지 확인합니다. 이미 생성되었다면 아무 작업도 하지 않고, 생성되지 않았다면 각 태그에 대한 그룹을 생성합니다. 이렇게 그룹을 생성하는 이유는 개별 지점을 생성할 때 각 경로를 해당 그룹에 삽입할 수 있도록 하기 위함입니다. 자, 이제 모든 그룹 생성이 완료되었고, 다음 단계로 넘어갑니다. 다음 단계에서는 각 경로, 즉 개별 API 경로를 순회합니다. 각 경로에 대해 요약, 설명, 그리고 POST, GET, PUT, DELETE 등의 API 메서드가 포함된 태그를 가져옵니다. 그런 다음 Treeve에서 각 경로에 대한 포인트를 생성하는데, 이를 청크라고 부릅니다. 마치 RAG 용어처럼 각 경로에 대해 청크를 생성하고, 해당 태그와 그룹 추적 ID(요청 본문 키)를 포함시키면 자동으로 관련 그룹에 추가됩니다. 여기에 몇 가지 TR 캐치가 있지만, 이게 전체 스크립트입니다. Treeve와 Quadrant 같은 도구를 사용하면 오픈 API 사양을 기반으로 검색 기능을 구축하는 것이 매우 간단합니다. 여기서 강조하고 싶은 점은 그룹 기반 시스템을 사용하는 것이 얼마나 훌륭한지입니다. Quadrant를 예로 들어 전자상거래 스토어를 생각해 보세요. 어떤 상품은 여러 색상이 있을 수 있습니다. 운동화의 빨간색, 흰색, 파란색 버전 등이 있겠죠. 사용자가 검색할 때 단순히 신발만 찾는 것이 아니라, 원하는 색상도 함께 찾고 싶을 겁니다. 이 신발과 그룹을 사용하면 쿼드런트 내에서 이 작업을 수행할 수 있습니다. 각 색상을 개별 포인트로 배치하거나, 트리 월드 청크를 특정 그룹에 넣을 수 있기 때문입니다. 그러면 누군가 검색할 때 해당 그룹 의 맨 위에 관련 색상이 표시됩니다. 정말 멋지고 훌륭합니다. 실행 방법도 매우 간단합니다. 전체 데이터 세트를 업데이트하려면 다시 실행하면 됩니다. 그러면 쿼드런트에서 제공하는 모든 경로에 대한 관련 청크가 모두 생성됩니다. 이 실험을 따라 해보고 싶거나 관심 있는 분들을 위해 GitHub에 오픈 소스 프로젝트( rbo)를 만들었습니다. 여기를 확대해서 github.com/dfloincopai-search에서 참조할 수 있습니다.
