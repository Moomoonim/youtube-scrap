## 스크립트

Flink 애플리케이션을 재시작하거나 다운타임 없이 비즈니스 로직 매개변수와 필터 조건을 변경할 수 있다면 얼마나 좋을까요? 정말 멋지지 않나요? Aache Link를 사용하여 실시간 게임 리더보드 애플리케이션을 구축하는 비디오 시리즈의 네 번째 파트에 오신 것을 환영합니다. 총 5개의 에피소드로 구성된 이 시리즈에서는 데이터 수집, 보강, 시각화에 이르기까지 스트리밍 아키텍처의 모든 부분을 배우게 됩니다. 또한 테스트용 제어 채널, 지연 도착 데이터 처리, 정확한 도착 시간 처리, 온디맨드 데이터 재생과 같은 고급 분석 기술도 배우게 됩니다. 지난 비디오에서는 Grafana 리더보드에 결과를 저장하고 시각화하는 작업을 완료했습니다. 처음 오신 분들은 첫 번째 비디오를 시청하시는 것을 강력히 추천합니다. 이번 비디오에서는 재시작이나 다운타임 없이 애플리케이션에 매개변수 변경 사항을 즉시 적용할 수 있는 제어 채널 방식을 설명합니다. 제어 채널 기법을 위해 구성 정보를 저장하는 Kinesis 데이터 스트림을 하나 더 추가할 예정입니다. 예를 들어, 테이블 A 에서 A열의 값이 50인 조건을 선택하는 쿼리를 실행해야 한다고 가정해 보겠습니다. 이 값 50은 동적으로 변하는 값입니다. 이를 외부에 저장한다고 가정해 보겠습니다. 구성 채널에서 유사한 이벤트가 발생하여 구성 테이블의 값과 해당 값의 업데이트를 제공한다고 생각해 보세요. 예를 들어, 시간 T1에 첫 번째 열의 값이 100이라고 가정해 보겠습니다. 그리고 시간이 흐른 후, 예를 들어 일주일, 한 달 또는 1 년 후에 비즈니스 로직이 변경되어 이 외부화된 매개변수 값을 100에서 300으로 업데이트해야 한다고 가정해 보겠습니다. 이 경우 Flink SQL 쿼리에서 50이라는 값을 다음과 같은 SELECT 쿼리로 대체해야 합니다. 보시다시피 이 SELECT 쿼리는 기본적으로 구성 테이블에서 최신 값을 선택하여 필터 조건에 사용합니다. 이 방식의 장점은 구성 채널 또는 구성 스트림에서 새로운 구성이 제공될 때 재시작 없이 애플리케이션에 즉시 적용된다는 것입니다. 구성 또는 제어 채널 기술의 응용 분야는 무엇일까요? 첫째, A/B 테스트 또는 섀도우 테스트입니다. 둘째, 비즈니스 로직에 따라 코드 브랜드 치즈를 동적으로 변경할 수 있는 기능 스위칭입니다. 셋째, 앞에서 본 예시처럼 V 절에 적용하는 것과 같은 매개변수 업데이트입니다. 마지막으로 적응 알고리즘에 사용할 수 있습니다. 머신 러닝 기반 알고리즘을 사용하여 파라미터를 업데이트하거나, 애플리케이션 자체도 파라미터를 지속적으로 푸시하여 업데이트할 수 있습니다. 그럼 구성 채널의 코드가 어떻게 생겼는지 살펴보겠습니다. 보시다시피 저는 이미 4번 브랜치에 있습니다. 만약 여러분이 4번 브랜치가 아니라면 GitHub에서 동적 구성 설정 브랜치를 선택하고 체크아웃하면 다음과 같은 코드를 볼 수 있습니다. 4부에서 추가된 내용은 다음과 같습니다. 첫째, Kinesis 데이터 스트림인 'config'라는 새로운 스트림이 추가되었습니다. 둘째, 이벤트를 게시하는 역할을 하는 Lambda 함수인 데이터 생성기가 추가되었습니다. 이 Lambda 함수는 입력값을 그대로 전달하는 패스스루 함수이므로, 입력값은 Kinesis 데이터 스트림으로 그대로 전달됩니다. 이제 배포를 진행해 보겠습니다. 저는 이미 인프라 폴더에 있으므로 `cdk deploy H`를 입력하고 Enter 키를 누릅니다. 배포가 완료되면 변경 사항을 묻는 메시지가 나타나는데, ' 예'를 선택합니다. 질문이 있으시면 댓글에 남겨주세요. 답변해 드리겠습니다. 지금까지 구성 채널 활용 방법에 대해 알아보았으니, 이제 실습을 진행해 보겠습니다. 새 스트림을 배포하고 노트북에서 제어 채널 로직을 적용합니다. CD c 태그가 배포되면 플링 서비스 관리로 이동하여 노트북을 엽니다. 이제 config라는 새 테이블을 추가해야 합니다. 평소처럼 kindness 데이터 스트림을 참조하는 표준 테이블입니다. 지역을 변경한 다음 이 쿼리를 사용하여 시간 내림차순으로 정렬된 최상위 레코드를 선택하여 Lambda 함수에서 이벤트를 푸시할 때 변경 사항을 확인할 수 있습니다. 이 쿼리의 목적은 보드를 필터링하는 것입니다. 플레이어 테이블에서 EAS 보드 열이 어떻게 생겼는지 살펴보겠습니다. 기본적으로 0 또는 1의 두 값인 정수입니다. 1은 보드를 의미하고 0은 실제 플레이어를 의미합니다. 따라서 플레이어만 남기고 게임 에서 모든 보드를 필터링하는 것이 목표입니다. 다시 config 테이블로 돌아가서 이 경우 리더보드 V2라는 새 버전을 사용할 수 있습니다. 이는 기본적으로 리더보드 뷰 1과 완전히 동일하며 뷰로 등록할 수도 있습니다. 여기서는 섀도우 테스트 또는 A/B 테스트 개념을 사용할 것입니다. 즉, 방해 없이 리더보드를 새로 만들어서 기존 버전에 영향을 주지 않고 새 버전을 병렬로 테스트해 보겠습니다. 리더보드 V2라는 이름의 새 리더보드를 생성할 예정입니다. 다양한 작업 및 쿼리 작성에 대한 자세한 내용은 다음 링크를 참조하세요. 이전 슬라이드에서 설명드린 것처럼 보드를 필터링하는 방법을 보여드리겠습니다. 이제 Lambda에서 구성 이벤트를 푸시하는 방법을 보여드리겠습니다. CloudFormation의 출력 탭으로 이동하면 새 URL인 '구성 게시 Lambda URL'이 표시됩니다. 이 URL을 클릭하면 Lambda 콘솔로 이동하여 Kesis 데이터 스트림에 이벤트를 푸시하는 Lambda 함수가 열립니다. 예제 이벤트를 복사합니다. 기본적으로 이벤트를 푸시할 스트림 과 데이터를 지정합니다. 이 예에서는 ISB 0을 필터링하려고 합니다. 이 이벤트가 표시됩니다. 이 이벤트를 복사하고 테스트 탭으로 이동합니다. 여기서는 JSON을 간단히 교체하겠습니다. 이벤트에 원하는 이름을 지정 하고 나중에 사용할 수 있도록 저장할 수 있습니다. 저는 저장하지 않고 테스트를 클릭합니다. 그러면 이 레코드가 구성 스트림에 푸시됩니다. 성공 메시지와 함께 샤드도 표시됩니다. 데이터가 푸시되었음을 확인하는 ID 및 기타 정보가 출력됩니다. 단, 이 방법은 애플리케이션이 실행 중인 상태에서 사용해야 한다는 점을 유념해야 합니다. 따라서 먼저 쿼리를 실행하여 애플리케이션이 정상적으로 작동하고, Fling 대시보드가 ​​표시되며, 데이터가 원활하게 흐르고 있는지, 더 이상 레코드가 유입되지 않고 애플리케이션이 안정적인 상태인지 확인해야 합니다. 이 시점에 게시자에서 구성을 푸시하여 변경 사항을 적용하고 새 구성을 활성화하여 데이터를 전송할 수 있습니다. 이 비디오에서는 컨트롤 채널 방법을 사용하여 실시간 애플리케이션의 매개변수 및 구성을 업데이트하는 것뿐만 아니라 섀도우 테스트, 기능 전환, 동적 필터 또는 머신러닝 기반 애플리케이션 튜닝에도 활용하는 방법을 배웠습니다. 다음 비디오에서는 지연 데이터 도착, 데이터 중복 방지, 아카이빙 및 온디맨드 재생과 같은 일반적인 스트리밍 분석 문제를 해결하는 방법을 설명하겠습니다. 그때 뵙겠습니다.
