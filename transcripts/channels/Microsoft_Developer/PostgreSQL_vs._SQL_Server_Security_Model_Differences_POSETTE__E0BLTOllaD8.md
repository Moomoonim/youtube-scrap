## 스크립트

안녕하세요, 저는 타이옵 알리입니다. SQL Server와 PostgreSQL의 보안 모델 차이점에 대해 이야기해 보겠습니다. 이 강연은 저처럼 SQL Server 개발자에서 PostgreSQL DBA로 전향한 분들을 위한 것으로 , 두 데이터베이스 플랫폼의 보안 모델 차이점을 비교 분석해 볼 예정입니다 . 자, 그럼 PostgreSQL과 SQL Server의 보안 모델 차이점을 살펴보겠습니다. 시간 관계상 제 소개는 생략하겠지만 , 왼쪽 하단에 있는 연락처를 꼭 기억해 두시기 바랍니다 . 강연 후 질문이나 궁금한 점이 있으시면 언제든지 연락 주세요 . 반드시 답변해 드리겠습니다. 본격적인 기술적인 내용에 들어가기 전에, 앞서 말씀드린 것처럼 이 강연은 PostgreSQL DBA로 전향한 분들을 위한 것입니다. SQL Server와 PostgreSQL을 비교 분석한 슬라이드를 준비했습니다. SQL Server 슬라이드보다는 PostgreSQL 슬라이드 에 더 많은 시간을 할애하겠지만 , 참고 자료로 활용하겠습니다. 이 라이브 스트림을 시청하고 계신다면, 저는 지금 디스코드에 있습니다. 거기에 있을 거예요. 발표가 끝난 후에도 거기서 기다리고 있을 테니 질문이나 의견을 주시면 감사하겠습니다. 어떤 종류의 토론이나 피드백이든, 기꺼이 답변해 드리겠습니다. 자 , 그럼 여러분이 같은 내용을 이해하고 있는지 확인해 봅시다 . 말씀드렸듯이, 여러분 중에는 아마도 의도치 않게 포스트그레스 DBA가 되신 분들도 있고, 포스트그레스를 사용하지 않지만 현재 관계형 데이터베이스 중에서 가장 빠르게 성장하는 데이터베이스 중 하나이기 때문에 관심을 갖고 계신 분들도 있을 겁니다 . 인증이란 무엇일까요? 포스트그레스든 SQL Server든, 인증은 '내가 누구인지'를 확인하는 것입니다. 내가 Taiob이라고 말하는 것이 맞을까요? 내가 정말 Taiob일까요? 다른 사람들은 어떻게 확인할까요? 신분증이나 여권이 있듯이 , 인증에서는 로그인 비밀번호, 관리 ID, 패스키를 통해 확인합니다. 흥미로운 점은 제가 마이크로소프트 웨비나를 듣고 있었는데, 곧 에이전트, 봇 등에 대해 들어보셨을 텐데, 이러한 것들이 마이크로소프트 엔트라(Microsoft Entra)에서 고유한 ID를 갖게 될 것이라고 했습니다. 그리고 우리는 데이터베이스 시스템 내에서 이러한 에이전트에 대한 권한을 관리해야 할 것입니다. 이것이 바로 인증(Authentication)입니다. 그렇다면 권한 부여(Authorization)는 무엇일까요? 예를 들어, 제가 당신의 집에 방문하거나 호텔에 갈 수 있도록 인증을 받았다고 가정해 보겠습니다. 저는 정문으로 들어갈 수는 있지만, 호텔의 모든 객실에 들어갈 수 있을까요? 아마 아닐 겁니다. 제가 예약한 객실은 한두 개뿐이고, 제 키로 해당 객실에만 들어갈 수 있기 때문입니다. 이것이 바로 권한 부여입니다. 데이터베이스에 접근하거나, PostgreSQL 서버 또는 클러스터에 접근할 수는 있지만 , 그 안에서 무엇을 할 수 있을까요? 어떤 데이터베이스에 접근할 수 있을까요? 그리고 그 데이터베이스 안에서 무엇을 할 수 있을까요? 이것이 바로 권한 부여로 정의됩니다. SQL Server 로그인에 대해서는 방금 설명드렸듯이, 우리 모두 잘 알고 있을 것입니다. Azure SQL Database와 포함된 사용자 개념 때문에 이 개념이 다소 모호해질 수 있다는 점은 이해 하지만, 로그인과 사용자 라는 기존 개념을 중심으로 살펴보겠습니다. 로그인은 서버 수준에서, 사용자는 데이터베이스 수준에서 존재하며, 각 로그인은 각 데이터베이스의 사용자에 매핑됩니다. SQL Server에서는 사용자에게 권한 또는 인증을 부여합니다 . 최근에는 관리 ID와 같은 Entra 객체가 등장하면서 이러한 개념들이 다소 모호해질 수 있지만, PostgreSQL과의 비교를 위해 기존 개념을 유지하겠습니다. 또 다른 중요한 개념은 스키마입니다. 스키마는 데이터베이스 내의 논리적 경계입니다. 스키마를 사용하는 이유는 다양합니다. 기능적인 이유일 수도 있고, 여러 클라이언트가 있거나 다양한 작업을 동일한 데이터베이스 에 저장해야 하는 경우처럼 여러 요소를 분리하기 위한 목적일 수도 있습니다 . 또한 스키마는 보안 경계 역할도 합니다. 스키마를 기반으로 보안을 설계할 수 있습니다. 그리고 나중에 좀 더 자세히 이야기해 볼 내용들이 있는데, 그때 몇 가지를 더 보여드리겠습니다. 슈퍼유저. SQL Server에 익숙하신 분들은 SA 또는 sysadmin이라는 용어를 아실 겁니다. 이는 마스터 키를 가지고 있다는 의미입니다. 호텔에 비유하자면, 호텔 관리자나 책임자는 비상시에 모든 객실에 출입할 수 있는 권한을 가지고 있는 것과 같습니다. SQL Server에서 슈퍼유저는 SA라고 부릅니다. Linux에 root 사용자가 있듯이 , PostgreSQL에도 postgres라는 슈퍼유저가 있습니다. 이 슈퍼유저는 무엇이든 할 수 있습니다. 슈퍼유저가 생성되면 PostgreSQL 클러스터에 로그인할 수 있는지 여부 외에는 다른 검사를 거치지 않고 , PostgreSQL 클러스터 내에서 필요한 모든 권한을 자동으로 부여받습니다 . SQL Server 역할. SQL Server에서 역할은 권한의 모음입니다. DB 데이터 읽기/쓰기 관리자, 대량 관리자, 백업 관리자, 보안 관리자 등이 있습니다. 이 역할의 구성원은 서버 또는 데이터베이스 수준에서 특정 작업을 수행할 수 있습니다. 그리고 사용자 정의 데이터베이스 역할이나 서버 역할과 같은 사용자 지정 역할을 만들 수도 있습니다. 그런 다음 다른 사람들을 이러한 역할의 멤버로 지정할 수 있습니다. 애플리케이션 역할이라는 것도 있는데, 여기서는 자세히 다루지 않겠습니다. 관심 있으시면 온라인 서적을 찾아보세요. 데이터베이스 수준에서 작동하는 역할입니다. 여기까지는 SQL Server에 대한 내용입니다. PostgreSQL에서는 역할에 대해 좀 더 자세히 다룰 것입니다. 이 강연에서 꼭 기억해야 할 네 가지 중요한 사항이 있습니다 . SQL Server 환경에서 PostgreSQL로 넘어오신 분들은 이 네 가지를 명확히 이해하지 못하면 어려움을 겪을 것입니다. 첫 번째는 역할입니다. SQL Server에서 간략하게 언급했지만, PostgreSQL의 역할에 대해서도 이야기해 보겠습니다 . 두 번째는 객체 소유권입니다. 객체 소유자는 해당 객체에 대한 최고 관리자와 같은 역할을 합니다. 이는 완전히 다른 개념이므로 객체 소유권을 제대로 이해해야 합니다. 그렇지 않으면 PostgreSQL에서 다른 역할에 권한을 부여할 때 어려움을 겪을 수 있습니다 . 그리고 상속이라는 것도 있습니다. SQL Server에서도 상속이 있는데, SQL Server에서 특정 역할의 구성원이면 해당 역할의 모든 권한을 자동으로 상속받습니다. PostgreSQL에서는 상속이 좀 더 세분화되어 있습니다. 이 점을 이해하는 것이 중요합니다. 또한 기본 권한 과 기본 권한을 수정하는 방법에 대해서도 이야기할 것입니다 . 대규모 PostgreSQL 클러스터에서 권한을 관리하려면 이 부분을 반드시 이해해야 합니다 . SQL Server 와는 완전히 다른 방식으로 작동하기 때문입니다. 기본 권한이 무엇인지 , 어떻게 수정하는지 이해하지 못하면 금방 문제가 발생할 수 있습니다. SQL Server에서 클러스터라고 하면 Windows Server 장애 조치 클러스터 또는 장애 조치 클러스터 인스턴스를 의미합니다. 즉, 하나 이상의 머신이 묶여 클러스터를 구성하는 것입니다. 하지만 PostgreSQL에서는 완전히 다릅니다. PostgreSQL에서 클러스터라고 하면 단일 PostgreSQL 엔진 과 그 엔진 안에 있는 데이터베이스 모음을 의미하며 , 이 모든 데이터베이스는 하나의 데이터 디렉터리에 있습니다. 그래서 SQL Server 호스트와 마찬가지로 하나의 호스트에 여러 개의 PostgreSQL 클러스터를 가질 수 있습니다 . 기본 인스턴스 하나와 여러 개의 명명된 인스턴스를 가질 수 있죠. 하지만 PostgreSQL에서는 명명된 인스턴스라고 부르지 않고 그냥 3개 또는 4개의 PostgreSQL 클러스터가 있다고 합니다. 여기서 중요한 점은 PostgreSQL 클러스터는 SQL Server 인스턴스와 동일하며, SQL Server 클러스터처럼 여러 호스트를 묶어서 구성하는 것이 아니라는 점입니다 . PostgreSQL 역할 에 대해서도 이야기해 보겠습니다. SQL Server에서는 서버 수준 역할과 데이터베이스 수준 역할에 대해 이야기했지만, PostgreSQL에서는 역할이 완전히 다릅니다. 역할은 클러스터 수준에서만 존재합니다. SQL Server에서 알고 있는 모든 로그인, 모든 사용자, 모든 그룹은 PostgreSQL에서는 모두 역할입니다. 역할은 클러스터 수준에서 생성되지만, 권한은 데이터베이스 수준에서 부여됩니다. 따라서 데이터베이스 A에 테이블을 생성할 수 있는 역할을 가질 수 있습니다. 하지만 권한이 다르기 때문에 데이터베이스 E에 테이블을 생성할 수 없습니다. 각 데이터베이스마다 권한을 별도로 부여해야 합니다. 포스트그레스에서는 사용자를 생성할 수 있는데, 이는 사실 역할을 생성하는 별칭입니다. 마찬가지로 그룹을 생성할 수도 있는데, 이 또한 역할을 생성하는 별칭입니다. 따라서 사용자는 로그인할 수 있지만 그룹은 로그인할 수 없습니다. 여기서 말하는 그룹( 역할의 별칭)은 SQL Server의 서버 레벨 역할이나 데이터베이스 역할 과 같은 방식으로 사용할 수 있습니다 . 이러한 그룹을 생성한 후 여러 권한을 할당하고 다른 역할에 해당 역할의 멤버십을 부여 하면 권한이 상속됩니다. 포스트그레스는 'Just-In-Time Access'라는 매우 영리한 기능을 구현했습니다 . 특정 사용자에게 짧은 시간 동안만 액세스 권한을 부여하고 싶을 때, 포스트그레스의 상속 구현 방식은 이러한 목적을 달성하는 데 매우 유용한 기능입니다. 그렇다면 사용자가 아닌 역할은 어떤 권한을 가져야 할까요? 기본적으로 공용 역할에서 일부 권한을 부여받습니다. 버전 15에서 중요한 변경 사항이 있었습니다. 이전에는 모든 역할이 공용 역할에 개체를 생성할 수 있었지만, 버전 15 이후에는 더 이상 불가능합니다 . 공용 권한은 이미 부여되어 있으며 , 필요에 따라 수정하거나 모든 역할에 너무 많은 권한이 부여된다고 생각되면 언제든지 제어할 수 있습니다. 역할은 사용자가 직접 부여한 권한 과 상속받은 권한을 모두 갖게 됩니다. 따라서 이 세 가지를 합치면 데이터베이스 내에서 역할이 가질 수 있는 총 권한이 결정됩니다 . Microsoft SQL Server는 2단계 권한 구조를 가지고 있으며, 이전에도 언급했습니다. Azure SQL Database의 경우처럼 예외적인 경우도 있지만, 일반적으로 로그인을 통해 접근 권한을 얻고, 데이터베이스 별로 권한을 관리하는 사용자가 있습니다.
