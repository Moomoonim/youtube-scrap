ID가 캐시에 존재하면 캐시 데이터를 반환하여 DynamoDB 작업을 방지합니다. 하지만 ID가 없으면 데이터를 가져와 처리한 후 캐시에 저장하고 결과를 반환합니다. 따라서 이 구현의 의도는 데이터베이스 호출과 처리 시간을 줄이기 위해 자주 액세스하는 데이터를 캐싱하는 것이어서 좋아 보일 수 있습니다. 그러나 이 구현에는 Python의 기본 인수 처리 방식 때문에 치명적인 결함이 있습니다. Python에서 기본 인수는 함수가 호출될 때가 아니라 정의될 때 평가됩니다. 즉, 모든 함수가 사용자 이름, 캐시 및 설정에 대해 동일한 딕셔너리 객체를 공유하게 되어 Lambda 환경에서 예상치 못한 동작이 발생합니다. 이제 다른 예제를 살펴보겠습니다. 이 시뮬레이션은 Lambda 컨테이너에서 시간이 지남에 따라 메모리 사용량이 어떻게 증가하는지 보여줍니다. 첫 번째 호출에서 함수는 사용자에 대한 캐시 항목을 생성합니다. 중요한 점은 Lambda가 이후 호출을 위해 컨테이너의 캐시를 유지한다는 것입니다. 따라서 100명의 다른 사용자를 처리할 때 각 호출은 동일한 캐시를 딕셔너리에 추가합니다. 새로운 컨테이너를 생성하면 메모리 사용량이 사용자마다 선형적으로 증가하지만, 이 메모리는 호출 사이에 해제되지 않습니다. 따라서 컨테이너는 AWS가 컨테이너를 재활용하기로 결정할 때까지 과도하게 커진 상태를 유지하며, 경우에 따라 몇 시간 후에 재활용될 수도 있습니다. 자, 이제 다른 예제를 살펴보고 Lambda 동시성에 대해 더 자세히 알아보겠습니다. 이 코드는 Lambda 동시성에서 또 다른 사소한 문제를 보여줍니다. 함수가 여러 동시 요청을 받으면 AWS는 이를 처리하기 위해 별도의 컨테이너를 생성하고, 각 컨테이너는 자체 Python 인터프리터를 사용하므로 기본 인수 의 자체 버전을 갖게 됩니다. 즉, 사용자는 요청을 처리하는 컨테이너에 따라 다른 결과를 얻을 수 있습니다. 한 컨테이너는 캐시에 최신 데이터를 가지고 있는 반면 다른 컨테이너는 오래된 데이터를 가지고 있어 일관되지 않은 사용자 경험을 초래할 수 있습니다. 이는 바람직하지 않습니다. 이제 문제가 발생하는 방식을 살펴보았으니, 이러한 예제를 어떻게 해결할 수 있는지 살펴보겠습니다. 다음 예제에서 자세히 다루겠습니다. 이 구현은 일반적인 Python 관용구를 사용하여 기본 인수 문제를 해결합니다. 즉, `enter` 대신 `enter`를 사용합니다. 딕셔너리의 기본값으로 nonone을 사용하므로, 이 함수가 실행될 때 인수가 non인지 확인하고 필요한 경우 새 딕셔너리를 초기화합니다. 이렇게 하면 각 함수 호출 시 캐시와 딕셔너리 설정의 최신 복사본을 얻을 수 있으므로 동작이 예측 가능해집니다. 따라서 애플리케이션 간에 공유되는 상태가 없고, 리그도 없으며, 동시 실행으로 인한 혼란도 없습니다. 마지막으로, AWS Lambda Power Tools를 사용한 모니터링 예제를 살펴보겠습니다. 이 모니터링 구현은 AWS Lambda 모범 사례 구현 프로세스를 크게 간소화하는 유틸리티 라이브러리인 AWS Lambda Power Tools를 사용합니다. 코드는 Python 데코레이터를 사용하여 메트릭을 자동으로 로깅하고 실행을 추적합니다. 이 데코레이터를 살펴보면 메트릭을 확인할 수 있습니다. 로고 메트릭 데코레이터는 모든 사용자 지정 메트릭이 클라우드워치로 전송되도록 합니다. 다음으로 추적 기능이 있습니다. ` Capture Lambda Handler` 데코레이터는 분산 추적 기능을 추가하여 모든 Lambda 함수의 엔드 투 엔드 실행 흐름을 이해하는 데 도움을 줍니다. 이제 Lambda 함수의 기본 인수에 숨겨진 위험성을 이해했으니, 조치를 취할 차례입니다. 첫째, 기존 Lambda 함수에서 이러한 패턴을 검토하세요. 현재 비용 낭비의 원인이 될 수 있습니다. 둘째, 제가 보여드린 ABS Lambda Power TSE를 사용하여 적절한 모니터링을 구현하세요. 마지막으로, abls YouTube 채널을 구독하고 좋아요를 눌러주세요. 시청해 주셔서 감사합니다. 즐거운 코딩 되세요!
