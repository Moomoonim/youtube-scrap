## 스크립트

Emu 서비스를 원하는 용량인 두 개의 워커로 확장하기 위해 ECS 타겟을 추가했습니다. ECS 타겟은 Emu 자체를 위한 것이고, 앱 자동 스케일링 정책도 있습니다. EC2 자동 스케일링 기능과 동일한 API는 아니지만 개념은 유사하며 ECS에서도 작동합니다. 이제 워커들이 정상적으로 가동되면, 이 ECS 서비스에 자동 스케일링 정책이 적용됩니다. 이 정책은 구성에서 확인할 수 있으며, 아래로 스크롤하면 CPU 사용률 정책이 적용되어 ECS 서비스의 평균 CPU 사용률을 25%로 추적하고 있는 것을 볼 수 있습니다. 이러한 설정은 참조 아키텍처의 최종 사용자가 조정할 수 있도록 제공하는 일종의 조정 요소입니다. 서비스 전체의 평균 CPU 사용률 25%라는 값에 동의하지 않을 수도 있지만, 저는 이 값이 큐에 작업이 많이 쌓여 있고 처리가 필요하다는 것을 Emu에 알리는 데 유용한 기준점이라고 생각합니다. 추가 워커를 가동하는 방식입니다. 예를 들어 Pelican이 큐에 엄청난 양의 메시지를 로드할 때, AOS 정책에 따라 Emu 워커 알람이 발생하면, 해당 워커가 알람 상태로 전환되어 25개, 30개, 또는 40개의 Emu 워커를 추가로 가동합니다. 그러면 이 워커들이 즉시 큐를 매우 빠르게 처리하기 시작합니다. 물론 다른 방법도 있습니다. 정책을 사용하는 것을 선호할 수도 있는데, 이는 추후 설명이나 다른 곳에서 다룰 수 있습니다. 정책을 사용하면 각 ECS 워커가 큐에서 처리해야 할 백로그를 정확하게 계산할 수 있습니다. Pelican에도 정책이 연결되어 있으며, 현재 하나의 알람은 정상 상태( 트리거되지 않음)이고 다른 하나는 데이터 부족 상태입니다. 하지만 알람 신호를 보낼 만큼 충분한 데이터 포인트가 확보되면 알람 상태로 전환되고, 자동 스케일 인/스케일 아웃 동작이 나타납니다. ECS에서 EM 서비스의 워커 수를 현재 코드상 최대 용량으로 설정된 40~50개까지 늘리려고 합니다. 기다리는 동안 코드에서 이 부분이 어디에 정의되어 있는지 보여드리겠습니다. 파일 맨 아래로 스크롤하면 컨테이너 인자 등을 포함한 ECS 프런트엔드 서비스 구성 부분을 볼 수 있습니다. 이 서비스는 많은 작업을 처리하지 않기 때문에 CPU와 메모리 사용량이 상대적으로 낮습니다. 하지만 더 아래로 스크롤하면 Pelican 서비스 자체는 더 많은 리소스를 사용하고, EMU도 마찬가지로 대부분의 작업을 처리하기 때문에 가장 많은 리소스를 사용합니다. 여기서 ECS Target은 EMU 워커의 자동 확장 동작을 정의합니다. 즉, EMU 워커가 동시에 50개 이상 실행되지 않도록 제한하고 최소 용량을 2개로 설정하는 것입니다. 현재 AWS 계정에서 두 개의 프로세스가 실행 중입니다. 대규모 처리를 수행하는 경우 이 값을 150, 250 등으로 늘리는 것이 좋습니다. 대부분의 AWS 계정은 기본적으로 ECS Fargate를 통해 동시에 실행할 수 있는 vCPU(가상 CPU) 할당량이 낮게 설정되어 있다는 점에 유의해야 합니다. 따라서 50개 이상의 Emu 워커 또는 추가 Pelican 워커를 실행하거나 대규모 사용 사례를 수행하는 경우, 가장 먼저 해야 할 일 중 하나는 AWS 계정에 ECS Fargate에서 동시에 실행할 수 있는 vCPU 할당량 증가 요청을 제출하는 것입니다. 이는 대규모 사용 사례를 수행하는 사용자에게 중요한 참고 사항입니다. 기본적으로 이것은 Emu의 CPU 사용률 정책이며, 목표 값을 25로 설정한 이유는 인위적으로 낮게 설정하는 것이 아니라 의미 있게 낮게 유지하기 위한 것입니다. 큐에 충분한 작업이 쌓이면 즉시 작업을 시작하고 추가 Emu 워커를 빠르게 생성하여 큐 결과를 신속하게 처리합니다. 또한 스케일 인/쿨다운 및 스케일 아웃 쿨다운 값을 조정할 수 있는데, 이는 스케일 인 또는 스케일 아웃 이벤트 후 자동 스케일링 서비스가 다음 스케일 아웃 이벤트를 시도할 수 있는 속도를 설정합니다. 예를 들어 큐에 작업이 많은 경우 이 값을 낮게 유지하면 자동 스케일링 서비스가 워커를 더 빠른 최대치로 늘릴 수 있습니다. 제가 이렇게 구성한 이유 중 하나가 바로 이 때문입니다. 좋은 점은 전체 아키텍처가 이 코드에 정의되어 있으므로 배포한 사람은 누구나 여기에 와서 이 값을 조정하고 `palumi up`을 실행하여 원하는 수정된 동작을 얻을 수 있다는 것입니다. 이는 매우 편리합니다. 또한 Emu 자동 스케일링 구성 외에도 Pelican에도 유사한 자동 스케일링 동작이 있다는 점에 유의해야 합니다. 값은 다르지만 Pelican은 Postgress에서 레코드를 선택하거나 Postgress에서 변경된 레코드를 수신하여 큐에 배치하기 때문입니다. Queue는 Emu처럼 모든 것을 임베딩으로 변환하고 API 호출을 통해 업서트할 때처럼 컴퓨팅 집약적인 처리를 하지 않습니다. 따라서 Pelican의 자동 스케일링 정책은 약간 다르게 조정된다는 점에 유의하세요. 하지만 모든 것이 코드로 되어 있기 때문에 원하는 대로 수정할 수 있습니다. 자, 잠깐만요, 배포가 완료되었습니다. 이번에는 평소보다 조금 더 빨리 완료되었네요. 14분 35 초가 걸렸습니다. 제가 여기서 잠깐 비켜서 잘 보이도록 하겠습니다. 전체 배포 과정은 처음부터 끝까지 14 분 35초가 걸렸습니다. 이제 계정을 살펴보고 실행 중인 항목을 확인해 보겠습니다. ECS 클러스터가 모두 실행 중이며 각 클러스터에는 하나의 서비스와 두 개의 워커가 실행되고 있습니다. 이는 기본적으로 바람직한 상태입니다. 시스템이 처음 시작될 때는 처리해야 할 작업이 많지 않기 때문입니다. 또한 안정적인 상태에서는 비용을 절감하기 위해 워커 수를 줄이는 것이 좋습니다. 큐에 작업량이 엄청나게 늘어나거나 데이터 부트스트래핑 초기화 프로세스가 진행되는 경우(이 부분은 후속 영상에서 간단히 설명드리겠습니다) 자동 스케일링이 필요합니다. Emu 워커 서비스에서 보여드린 것처럼 Pelican 서비스에도 자동 스케일링 정책이 설정되어 있어 필요에 따라 크기를 조절할 수 있습니다. 이제 RDS에 접속해 보면 중앙 RDS 데이터베이스가 정상적으로 실행 중이고, 부하가 크지 않으며, Pelican이 직접 연결되어 있어 원활한 연결을 확인할 수 있습니다. 이것이 바로 RDS 데이터베이스입니다. 프런트엔드 ECS 서비스도 확인해 보겠습니다. 프런트엔드 서비스는 공용 서브넷에서 실행되며, 로드 밸런서가 연결되어 있습니다. 로드 밸런서에 직접 접속하면 UI와 앱 환경이 표시되고 샘플 제품도 확인할 수 있습니다. 이제 시맨틱 검색을 시작해 보겠습니다. 14분과 12분 만에 정상적으로 배포되는 것처럼, 또 다른 중요한 부분은 큐잉입니다. SQS로 이동하면 두 개의 큐를 찾을 수 있습니다. 첫 번째 큐(CU)는 데드 레터 큐(Dead Letter CU)입니다. 이는 처음에 처리할 수 없었던 메시지를 위한 것입니다. 작업 큐에서 메시지가 " Flight" 상태라는 것은 Emu가 메시지를 읽고 처리 중이라는 의미입니다. Emu는 Pelican을 통해 메시지를 처리하지만, 오류로 인해 제대로 처리되지 않았거나 주소가 지정되지 않은 경우 데드 레터 큐로 이동합니다. 데드 레터 큐에는 연결된 SNS 주제가 있어 이메일이나 문자를 통해 구독할 수 있습니다. 따라서 필요한 경우 중요한 작업 처리에 실패했다는 업데이트를 받을 수 있습니다. 이것으로 배포 방법을 보여주는 첫 번째 비디오는 끝입니다. 도움이 되었기를 바랍니다. 다음 비디오에서는 점프 호스트를 실행하여 직접 상호 작용하는 방법을 설명하겠습니다. 계속해서 시청해 주세요. 음, 프라이빗 서브넷에서 실행되는 리소스, 예를 들어 RDS 인스턴스나 마이크로서비스 등이 있습니다. 그리고 시스템 아키텍처, 기능, 데이터 흐름에 대해서는 다음 영상에서 더 자세히 설명드리겠습니다. 시청해 주셔서 감사합니다.
