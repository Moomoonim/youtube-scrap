Postgres 데이터베이스용 MCP 구축에 대해 더 자세히 알아보려면 저와 함께해 주세요. 저는 파이썬 개발자들이 새로운 기술을 활용하여 개발할 수 있도록 돕는 일을 하고 있으며, 지난 1년 동안 MCP에 집중해 왔습니다. MCP 는 가장 주목받는 신기술이자 생성형 AI 업계에서 가장 먼저 채택된 표준 기술이며 , 많은 사람들이 큰 관심을 보이고 있습니다. Postgres 사용자 여러분께 MCP에 대해 이야기할 수 있게 되어 기쁩니다. 자, 그럼 제가 GitHub Copilot을 사용해서 질문하는 간단한 데모를 보여드리겠습니다 . 질문은 "제가 사는 엘 세리토에서 4월에 어떤 벌들이 활동하고 있나요?" 입니다 . GitHub Copilot 에이전트는 Opus 4.6을 사용해서 이 질문에 대한 답을 찾습니다. 그리고 MCP 서버를 찾아서 쿼리를 통해 답변을 얻을 수 있다는 것을 알게 됩니다. 그래서 "좋아, 이 MCP 서버를 사용해서 데이터베이스를 쿼리할 수 있겠군."이라고 생각합니다. 쿼리를 실행하고, 벌과 관찰에 대한 여러 행을 받아 "가장 많은 그룹은 호박벌입니다."라고 알려줍니다. 저도 지금 창밖을 보면 정원 곳곳에 호박벌이 있는 것을 볼 수 있으니, 이 말이 맞다는 것을 확인할 수 있습니다 . 이것은 에이전트를 MCP 서버에 연결하여 질문에 대한 답을 얻고 작업을 완료하는 방법을 보여주는 예시입니다 . 그럼 MCP가 무엇인지 궁금하시죠? 네, 맞습니다. MCP는 모델 컨텍스트 프로토콜(Model Context Protocol)의 약자로, AI 앱과 에이전트가 외부 도구 및 데이터 소스에서 컨텍스트를 가져오는 방법을 정의하는 개방형 프로토콜입니다. 이 프로토콜은 Anthropic Games에서 처음 제안되었지만, 이후 널리 채택되었고 현재는 Linux Foundation의 일부입니다. 따라서 완전한 개방형 프로토콜이라고 할 수 있습니다. MCP 이전에는 AI 앱과 에이전트를 다양한 데이터 소스와 통합하려면 사용자 지정 통합 기능을 개발해야 했습니다. 하지만 이제 MCP 덕분에 각 데이터 소스 앞에 MCP 서버를 설치하기만 하면 공통 프로토콜을 통해 정보를 가져올 수 있습니다. 이러한 데이터 소스 중 하나로 PostgreSQL 데이터베이스를 예로 들 수 있는데, 이제 이를 자세히 살펴보겠습니다. 방금 시연한 MCP 서버를 직접 구축해 보겠습니다. PostgreSQL 데이터베이스 위에 MCP 서버를 구축하는 다양한 방법을 확인할 수 있습니다 . 한쪽 극단에는 에이전트가 전체 SQL 문을 작성 하고 해당 쿼리 전체를 데이터베이스로 전송할 수 있는 탐색 서버가 있습니다 . 이 경우 LLM과 에이전트에 상당한 신뢰를 두어야 하지만, 그만큼 위험도 큽니다. 다른 극단에는 완전한 SQL 문을 사용할 필요가 없는, 형식이 정해진 제약 조건이 있는 도구를 사용하는 보다 운영적인 서버가 있습니다. 그리고 그 중간에도 여러 옵션이 있습니다. 오늘은 이러한 전체적인 발전 과정을 살펴보겠습니다. 먼저 자유 형식 SQL부터 시작해 보겠습니다. 자유 형식 SQL 은 최대의 유연성을 제공하지만, 동시에 최대의 위험을 수반합니다. 다음은 간소화된 Python MCP 서버 코드입니다. 저는 Python에서 MCP 서버를 구축하는 데 FastMCP라는 패키지를 선호하는데, 이 패키지는 매우 인기 있는 패키지입니다. 그리고 서버에 두 가지 도구를 정의합니다. 첫 번째는 데이터베이스 스키마를 가져오는 도구입니다. 이 도구를 호출하면 스키마를 가져오는 SQL 문을 실행하고 그 결과를 문자열로 반환하도록 정의합니다. 그다음 도구는 SQL 쿼리, 어떤 SQL 쿼리 든 입력받아 데이터베이스 연결에 대해 해당 SQL 쿼리를 실행합니다. SQL 쿼리는 SELECT일 수도 있고, INSERT, UPDATE, DELETE일 수도 있습니다. 데이터베이스에서 실행할 수 있는 쿼리에는 여러 가지 옵션이 있습니다. 그래서 실제로 어떻게 작동하는지는 데모에서 이미 보셨던 것과 같습니다. 에이전트가 먼저 "좋아요, 이 데이터베이스의 스키마를 찾고, 어떤 테이블이 있고 어떤 열이 있는지 확인하기 위해 스키마 도구를 호출하겠습니다 ."라고 말합니다 . 그런 다음 해당 테이블에 대해 SQL을 실행하여 필요한 답변을 얻습니다. 이 시스템은 잘 작동했고 제 질문에 대한 답을 얻을 수 있어서 좋았습니다. 하지만 이 서버에는 몇 가지 분명한 문제가 있습니다. 첫 번째는 스키마 도구입니다. 스키마 전체를 덤프합니다. 이 경우에는 테이블이 5개, 열이 60개밖에 없는 작은 데모 데이터베이스이기 때문에 큰 문제는 아닙니다 . 하지만 실제 데이터베이스에서는 테이블이 수백 개, 열이 수천 개에 달할 수 있고 , 스키마가 너무 커지면 LLM이 제대로 작동하지 못할 것입니다. 우리는 너무 많은 정보를 봤는데, 그중 대부분은 필요하지 않고 LLM의 컨텍스트 창을 초과할 수도 있습니다. LLM은 컨텍스트 창이 제한되어 있기 때문입니다. 따라서 전체 스키마를 덤프하는 이러한 도구를 항상 사용할 수는 없습니다. 대신 점진적인 스키마 검색을 사용할 수 있습니다. 예를 들어, `list_tables()` 도구를 사용하면 테이블 이름만 가져올 수 있습니다. 각 테이블을 설명할 수도 있습니다. 그리고 `describe_table()` 도구를 사용하면 특정 테이블의 열을 가져올 수 있습니다 . 이러한 도구를 에이전트에 제공하면 에이전트는 먼저 `list_tables()`를 호출하여 사용할 수 있는 모든 테이블을 확인합니다. 그런 다음 필요한 테이블에 대해서만 `describe_table()`를 호출합니다. 이 경우 종 테이블과 관찰 테이블을 설명하고 각 테이블의 열을 가져옵니다. 보시 다시피 필요한 스키마 정보를 얻기 위해 한 번의 호출이 아닌 세 번의 호출이 필요했습니다 . 그래서 전체적인 호출 횟수가 증가했습니다. 따라서 이러한 점진적 스키마 검색 도구 로 전환하는 것이 항상 이득은 아닐 수 있습니다. 하지만 스키마 규모가 매우 큰 경우에는 에이전트가 현재 질문에 답하는 데 필요한 스키마 정보를 검색할 수 있도록 하는 방법으로 고려해 볼 만합니다 . 정말 큰 문제는 안전장치가 없는 변경입니다. 실수로 업데이트하거나 삭제하기가 너무 쉽습니다. 예를 들어, 사용자가 "꿀벌 관찰 데이터 중 품질 등급이 낮은 것이 몇 개나 있나요?" 라고 묻자, "아, 사실, 그것들을 삭제해 주세요." 라고 답했습니다. 사용자는 실제로 삭제를 원하는 것처럼 보이지만, 너무 가볍게 말하는 것입니다 . 그래서 Opus 4.6은 "잠깐만요, 거의 2만 개의 행을 삭제하시겠습니까?" 라고 묻습니다 . 상당히 중요한 문제인 거죠. 그리고 사용자는 "잠깐, 내가 정말 이걸 해야 하나? 음, 너무 많은 것 같은데." 라고 생각할 수도 있습니다. 하지만 Gemini 2.5는 그냥 바로 삭제해 버립니다. 묻지도 않고 말이죠. 그냥 바로 삭제합니다. Opus는 이렇게 많은 행을 삭제하는 것이 중요하기 때문에 확인 메시지를 표시해 주는 점에서 좀 더 나은 것 같습니다 . 하지만 여기서 중요한 점은, 도구가 삭제 기능을 제공한다면, 어떤 에이전트나 모델이 그 삭제 작업을 수행할 것이라는 사실입니다. 따라서 모델의 안전성에만 의존할 수는 없습니다. 도구 자체를 안전하게 만들어야 합니다. 그렇죠? 그리고 우리가 살펴볼 것은 바로 도구를 안전하게 만드는 방법입니다. 한 가지 방법은 읽기 전용 SQL을 강제하는 것입니다. SELECT 문만 허용하는 거죠. 안전한 SELECT 문만 허용하는 겁니다. 다음은 읽기 전용 SQL 도구의 코드입니다. 맨 위에 readOnlyHint라는 표시가 있는데, 이는 해당 도구가 읽기 전용임을 나타냅니다. 이 도구는 먼저 SQL 문이 SELECT 문인지 확인한 다음, 해당 문을 실행하고 너무 많은 행을 가져오지 않도록 특정 제한을 둡니다 . 따라서 여기에는 몇 가지 흥미로운 점이 있는데, 곧 자세히 살펴보겠습니다. 이제 실제로 이 에이전트를 사용해 보면, 에이전트에서 MCP 서버를 사용하여 복잡한 SELECT 쿼리를 전송하고 실행한 후 응답을 받을 수 있음을 확인할 수 있습니다 . 따라서 이 도구를 사용하여 앞서 제기했던 질문에 대한 답을 여전히 얻을 수 있습니다. 그렇다면 읽기 전용을 어떻게 강제할까요? 첫 번째는 readOnlyHint를 사용하는 것입니다. MCP 도구에서 readOnlyHint가 true로 설정된 것을 보셨을 겁니다. 이는 MCP 사양에 있는 기능으로, 도구의 작동 방식을 설명하기 위해 데코레이터를 사용할 수 있도록 합니다. readOnly, 멱등성, 파괴성 등이 있습니다. 이 경우 "이 도구는 읽기 전용이지만, 단지 힌트일 뿐입니다."라고 지정하는 것 입니다. MCP 클라이언트는 이 힌트를 활용하여 도구의 렌더링 방식이나 승인 방식을 변경할 수 있습니다. 하지만 이는 UI에만 사용되는 힌트일 뿐, 계약이 아닙니다. 확실한 보장은 아닙니다. 도구를 읽기 전용으로 지정했더라도 실제로는 읽기 전용이 아닌 작업을 허용할 수도 있습니다. 따라서 MCP 서버 개발자인 우리는 도구가 실제로 읽기 전용인지 확인해야 합니다. 만약 읽기 전용 여부가 중요하다면 말이죠. 어떻게 확인할 수 있을까요? 우선 SQL 유효성 검사를 하는 함수가 있습니다. 이 함수는 라이브러리를 사용하여 SQL 문을 추상 구문 트리(AST)로 파싱한 다음, 하나의 문만 있어야 하고 여러 문이 있으면 안 되는지, 그리고 그 문은 반드시 SELECT 문이어야 하며 INSERT, DELETE, UPDATE 등은 안 되는지 확인합니다 . 이렇게 하면 많은 잠재적인 쿼리를 차단할 수 있습니다 . 유효하지 않은 SQL 문, 이처럼 여러 문이 포함된 쿼리, DELETE 문은 확실히 차단하고 SELECT 문은 통과시킵니다 . 자, 이것이 읽기 전용을 강제하는 첫 번째 시도입니다. 다음으로 할 일은 데이터베이스 수준에서 읽기 전용을 강제하는 것인데 , 이것이 정말 중요합니다. 연결을 설정할 때 "이 연결에서는 default_transaction_read_only = ON"으로 설정하면 됩니다. 이렇게 하면 읽기 전용 작업만 수행할 수 있게 됩니다. 더 나아가, 읽기 전용 역할을 만들어서 쿼리를 보낼 때마다 사용할 수도 있습니다. 이 역할은 특정 데이터베이스의 특정 스키마에 대해서만 SELECT 작업을 수행할 수 있도록 권한을 부여합니다. 이 두 가지 방법을 결합하면 데이터베이스 수준에서 읽기 전용을 강력하게 강제할 수 있습니다 . 이렇게 하면 INSERT, DROP, DELETE 작업은 물론 이고, 이전 파서에서는 차단되지 않았던 까다로운 작업도 차단할 수 있습니다. 바로 CTE(공통 테이블 표현식)인데, WITH blah blah blah blah... SELECT FROM 으로 시작하는 구문입니다 . 파서는 통과했을지 몰라도 데이터베이스 수준의 제한 때문에 차단될 겁니다. 하지만 우리가 원하는 SELECT 문은 여전히 ​​통과시키고 있죠. 에이전트가 여기서 DELETE 작업을 보내려고 하면 "이건 허용되지 않습니다. 할 수 없어요." 라는 오류 응답을 받게 됩니다. 그리고 " 로컬에서 실행해 보세요."와 같은 제안을 하죠. 우리가 원하는 경험은 에이전트가 "아, 이건 안 되겠구나."라고 깨닫고 사용자에게 더 자세한 정보를 제공하는 것입니다. SQL을 안전하게 만들려면 여러 계층의 보호 장치가 필요하다는 것을 알 수 있습니다 . 4단계 보호 장치를 사용하는 이유는 매우 복잡한 SQL 쿼리를 만들 수 있고, 그중 일부는 여러 계층을 통과할 수 있기 때문 입니다. 그래서 WITH 문은 파서는 통과했지만 다행히 데이터베이스 제한 때문에 차단된 겁니다. 이제 이 부분이 흥미롭네요.
