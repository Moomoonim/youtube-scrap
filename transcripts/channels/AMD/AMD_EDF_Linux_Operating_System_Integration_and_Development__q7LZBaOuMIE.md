## 스크립트

Hello, welcome to AMD EDF Linux Operating System integration and development using the AMD embedded development framework how-to video. Here, you will use a prebuilt Yocto Project framework to generate the EDF Linux disk images and artifacts used in the “Getting Started with the AMD EDF” and “Developing Software with the AMD EDF” videos. The OS developer builds custom images to meet system or application needs, ranging from simple Linux builds to complex setups with hypervisors, containers, or multiple domains. This includes low-level components like PMU, PLM, PSM firmware, U-Boot, and Arm Trusted Firmware. The Yocto Project provides the environment to create these custom, heterogeneous boot and OS images. This video begins by demonstrating the necessary steps required for setting up and configuring the Yocto Project environment. Then, you will create a single-stage EDF Linux disk image for VEK280 board, which is based on the Versal AI Edge Series. And you will also generate a multistage EDF Linux disk image, including the OSPI binary image required for VEK385 board, which is based on the Versal AI Edge Series Gen 2. Note that if the board you are working with is a production board, it will be pre-programed with an OSPI image. Finally, you will configure a QEMU environment and run the emulation on QEMU. You will also build and install a customized SDK for cross-development of your application. This video assumes you are using a supported operating system for the Yocto Project environment. At this stage, basic to advanced Yocto Project knowledge is required depending on the task you want to perform. Please refer to the “Yocto Project Basics” video for learning more about the Yocto Project environment. Here you will use the Repo tool, which is a tool chosen by AMD to be the tool for EDF flows to manage multiple git repositories. First, you will configure Git with your username and email and then set up the Yocto Project environment. The Operating System Integration and Development flow for AMD Versal devices demonstrated in this video is also available in text form in the “Operating System Integration and Development” Wiki page. Let's begin the demonstration by setting up the Yocto Project build environment. This guide assumes that the build host shell is bash, not csh or dash, and the OS is supported by Yocto Project. Configure your git identity. Use your identity, do not follow these commands word for word. Run “git config --global user.email” followed by your email. Then, set your name with “git config --global user.name” followed by your name. Confirm this configuration using “git config –list“. Download and install the repo tool using “curl”, which will help you to setup all the necessary repositories for EDF. Use the command “curl https://storage.googleapis.com/git-repo-downloads/repo &gt; repo”. Ensure that the downloaded binary is executable by using “chmod a+x”. Then, create and add repo to your “bin” directory. Ensure that this “bin” directory is appended to your PATH variable using “PATH=~/bin:$PATH”. Create a directory for the EDF project and navigate into it. Now, clone the Yocto Project meta layer source using “repo init”. Use the latest EDF version tag when pointing to the Yocto Project manifest; here it is version 25.05. Fetch by using “repo sync”. This may take a few seconds. When done, set up your build environment by sourcing the edf-init-build-env script. If you are on an NFS-based build host system, modify the “build/conf/local.conf” configuration file and add a “TMPDIR” variable pointing to a temporary directory. When the environment is fully set up, it is time to begin generating the files necessary for booting the device. A single stage boot image will be generated for the AMD Versal AI Edge Series VEK280 so that the necessary files are created to successfully boot via a properly partitioned SD card. First, the binary boot file must be generated. To do this, run “MACHINE=versal-vek280-sdt-seg bitbake xilinx-bootbin". This command uses the VEK280 board layer to run the xilinx-bootbin recipe. When completed, generate the SD Wic. To do this, run “MACHINE=amd-cortexa72-common bitbake edf-linux-disk-image". This command uses the Arm Cortex A72 meta layer to run the Bitbake edf-linux-disk-image recipe. After completion, all required files are created and exist in the “tmp, deploy, images” directory. If you used the default tmp directory, it is created and accessible from the build directory. The GUI is used to verify the boot.bin was generated properly by looking in the “versal-vek280-sdt-seg" directory. Here, you can find the boot.bin file. It should be approximately 3 to 4 MB if you were following this exact build. Next, to ensure that the EDF Linux Common Disk Image .wic file was properly created, look in the “amd-cortexa72-common" directory. Here, you can find the edf-linux-disk-image-amd- cortexa72-common.rootfs.wic file. It should be approximately 9 to 10 GB if you followed this exact build. After verifying that files were successfully generated, the SD card .wic file must be partitioned to add the bootloader. To do this, first confirm that the content of the EFI partition of the .wic file is empty by running the “wic ls” command on it with “:1” attached to the end of it. Make sure there are no files attached. Now, copy the boot.bin into the efi partition of the wic image by running “wic cp, the boot.bin file, then the .wic file with :1 at the end to indicate the efi partition”. List the .wic file’s EFI partition out again to confirm that the boot.bin was successfully added. This partitioned .wic file can then be flashed onto an SD card and used to boot a single stage bootloader board like the VEK280. Now, images and binaries for a Versal AI Edge Series Gen 2 VEK385 will be built. The VEK385 follows a multistage boot process by default. This means an OSPI binary image that contains boot firmware and boot images is created for the first stage boot loader, then a Common EDF Linux disk image is created for the next stage of the full OS image boot. These files can again be generated using the “bitbake” command attached to a recipe. Note that production boards are shipped with the OSPI populated, but this process must be followed if the firmware bundles that affect the initial boot were modified. Let's generate the board specific OSPI binary image containing the boot firmware. To do this, run “MACHINE=versal-2ve-2vm-vek385-sdt-seg bitbake edf-ospi". This command uses the VEK385 board layer to run bitbake’s edf-ospi recipe. This command can take roughly 30 minutes to an hour or longer depending on the performance of the build host PC. Once completed, let’s generate the Common EDF Linux disk image (SD WIC). To do this, run “MACHINE=amd-cortexa78-mali-common bitbake edf-linux-disk-image". This command uses the Arm Cortex A78 meta layer to run the Bitbake edf-linux-disk-image recipe. Again, this command can take 30 minutes to an hour or longer depending on how powerful your build host is. After completion, both required files are now created and exist in the “tmp, deploy, images” directory. If you use the default tmp directory, it is created and accessible from the build directory. To verify the OSPI boot file was generated, look in the “versal-2ve-2vm-vek385-sdt-seg" directory. Here, you can find the edf-versal-2ve-2vm-vek385-sdt-seg-.bin file. It should be approximately 270 MB If you were following this exact build. Next, to ensure that the SD Wic file was properly created, look in the “amd-cortexa78-mali-common" directory. Here, you can find the edf-linux-disk-image-amd- cortexa78-mali-common.rootfs.wic file. It should be approximately 9 to 10 GB if you followed this exact build. These OSPI and SD card WIC images can now be flashed and used to boot a VEK385. Refer to the “Getting Started with AMD EDF” video for more information. Quick Emulator, or QEMU, can be used to simulate the generated OSPI and WIC images. Create a directory and copy the versal-2ve-2vm-vek385-sdt-seg board and amd-cortexa78-mali- common images to this new directory. Use the bundled qemuboot-tool to merge the two images as can be seen on screen. This is required since to run the QEMU, only one config file is accepted rather than the two that are created through the build. This can be done with the command “./yocto/edf/sources/meta-xilinx/meta-xilinx-core/scripts/qemuboot-tool load tmp/deploy/images/vek385-common-qemu-images/BOOT -versal-2ve-2vm-vek385-sdt-seg.qemuboot.conf remove image_link_name remove images/edf-linux-disk-image-amd-cortexa78- mali-common.rootfs.qemuboot.conf &gt; tmp /deploy/images/vek385-common-qemu- images/vek385-common-combined.qemuboot.conf”. Once done, verify the contents of the file using the cat command. Launch the QEMU boot instance using the command “runqemu combined.qemuboot.conf nographic slirp”. The QEMU instance will boot up using the images. Log in using the default username “amd-edf” and set up your password when prompted. Explore the running system by listing out the programmable logic (PL) firmware files included by running “dfx-mgr-client –listPackage“. Exit QEMU typing Ctrl+A and then “X”. In the “Developing Software with AMD EDF video”, we used the prebuilt EDF SDK to compile and deploy an “hello world” application. However, we noted that this SDK was not extensible, and adding new packages means that a new SDK will need to be built. This process begins by first modifying the SDK recipe in the “meta-edf-app-sdk.bb” file found in the directory “/yocto/edf/sources/meta-amd-edf/recipes-core/meta/”. Append recipes to the TOOLCHAIN_TARGET_TASK list Now, build the SDK using MACHINE=amd-cortexa 78-mali-common bitbake meta-edf-app-sdk. The resulting SDK install script will be placed in the “tmp/deploy/sdk” directory. To run the sdk, execute the generated script in the tmp directory. Enter the target directory when prompted. Once completed, the sdk was successfully installed. In this video, the necessary steps for configuring the Yocto Project environment were shown. Next, an EDF Linux disk image for an AMD Versal AI Edge Series VEK280 board and an OSPI binary and EDF Linux disk image for a Versal AI Edge Series Gen 2 VEK385 board was generated through a series of Yocto Project commands and recipes. Then, we used the files created for the VEK385 to boot and simulate the board using QEMU. Lastly, an SDK for application cross-development was built and installed.
