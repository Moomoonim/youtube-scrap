Let's look at what makes AKS such a strong fit for self-hosting Postgres. It all starts with the virtual machines. Your node pool choices help shape the performance of the workload. General purpose D series machines can handle most workloads. Memory Optimize E-Series help with heavy caching. Storage optimized families like LSV-3 or LSV-4 bring local NVME, which cuts latency for write-heavy clusters. Azure Boost removes extra virtualization overhead by offloading networking and storage to the dedicated hardware. On supportive VM types, that means steadier low latency, which matters for features like SY and transaction commits. AKS keeps the Kubernetes control plane managed and patched. You shape the worker node pools, add autoscaling, and plug into Azure Identity, Networking, and Observability services. It's a balance. Kubernetes orchestrates the pods, while Azure handles the node lifecycle, identity, and networking. - Our reference architecture uses a multi-zone AKS cluster with three Postgres pods managed by CloudNativePG, a popular open-source Postgres operator. We designate one pod as the primary and use the two other as synchronous replicas. An Azure Load Balancer sits in front of the read and write traffic. Azure-managed Prometheus and Grafana provide metrics dashboards. For backups, the operator streams data to Azure Blob Storage using workload identities, so there are no static credentials. Now, let's talk about storage. Storage can have a big impact on performance. Premium SSD and premium SSD v2 discs both deliver high performance and low latency. Premium SSD v2 provides the most flexibility and value, allowing you to independently configure capacity, IOPS, and throughput, making it ideal for workloads that need a strong balance of price and performance. Azure Container Storage with local NVME drives reaches sub-millisecond latency for write-heavy or the most IO-intensive scenarios. Just remember that local NVME is tied to the VM. We recommend having a backup system to Azure Blob Storage so a node pool recycle doesn't cost you data. CloudNativePG pairs with Barman to send WAL archives and snapshots to Blob Storage over that managed identity. Remember, if you plan to rely on NVME for ultra low latency, make sure the VM family ships with local and VME devices, such as L-Series machines. CloudNativePG is what keeps day-to-day operations manageable. We install the operator in its own namespace. From there, a single custom resource spells out replica counts, backup targets, TLS, and maintenance windows. The operator handles rolling failovers, keeps replicas spread across zones, and manages connections so the cluster rides out node drains. - After the cluster's live, day two operations start with checking the status of the database. That quick check shows which pod is primary, where the replicas sit, and the current log sequence numbers. Because we schedule across multiple zones, the database keeps running, even if a zone goes dark. When you need more detail, CNPG also lets you vol a full snapshot of the cluster's health. It calls out replication, storage assignments, and the conditions the operator is tracking. Use it when something feels off and you want a structured report before diving into logs. If you're investigating storage or throughput, you can stream the Postgres logs from whichever pod currently owns the primary role, so you can watch checkpoint activity, autovacuum behavior, or slow queries without guessing which pod to connect to. For replica health, we can surface your existing base backups and WAL archives. You can confirm when the last backup ran, where it landed in Blob Storage, and whether the retention policy is being enforced. For disaster recovery, Barman takes care of the scheduled snapshots and WAL archiving straight into Azure Blob Storage. One command triggers an on-demand backup, and each run lands with a clean timestamp. Workload Identity supplies the credentials, so there are no secrets to rotate.
