Analytic DB for MySQL은 컴퓨팅과 스토리지가 분리되어 있고 다양한 오픈 데이터 레이크링크 형식을 지원하는 통합 온라인 분석 엔진으로 설계되었습니다. 이 솔루션은 기존 OLTP 데이터베이스, NoSQL 솔루션 및 로그 저장소를 포함한 다양한 데이터 소스 수집 파이프라인과의 원활한 통합을 제공합니다. 또한 QuickBI 및 Tableau와 같은 다양한 BI 보고 및 시각화 도구를 지원합니다 . 알리바바 클라우드 서비스를 통해 MySQL용 분석 데이터베이스에 접근하고 관리할 수 있는 강력한 데이터 개발 도구를 제공하며, 여기에는 데이터 관리 시스템(DMS)도 포함됩니다 . DMS를 사용하면 SQL 개발을 수행하고, 작업을 오케스트레이션하고, 데이터 수명 주기를 원활하게 관리할 수 있습니다. Analytic DB for MySQL은 MySQL 프로토콜을 기본적으로 지원하며 MySQL 버전 5.6, 5.7 및 8.0과의 호환성을 유지합니다. 즉, 내 SQL 데이터베이스의 데이터 형식을 문제없이 정렬할 수 있다는 뜻입니다. 또한 온라인 DDL 및 실시간 기본 키 삭제 및 업데이트 작업과 같은 온라인 분석을 위한 사용자 친화적인 기능도 포함되어 있습니다. 기본적으로 Analytic DB for MySQL은 높은 동시성을 요구하는 실시간 쿼리, 임시 탐색, 오프라인 ETL 작업 등을 효과적으로 처리하는 올인원 SQL 분석 플랫폼입니다. 이 시스템은 CPU와 GPU 컴퓨팅 기능을 모두 제공하며, AI 분석 시나리오에서 학습 및 추론에 최적화된 솔루션을 제공합니다 . Analytic DB for MySQL은 하이브리드 아키텍처를 통해 네이티브 데이터베이스 엔진과 오픈 소스 Spark 엔진을 결합하여 사용자가 분석 작업에 따라 필요에 따라 엔진을 전환할 수 있도록 합니다. 스토리지 측면에서 이 플랫폼은 자동 핫/콜드 데이터 계층화 및 효율적인 콜드 데이터 수집을 지원하는 고성능 자체 개발 컬럼형 스토리지를 갖추고 있습니다. 이 시스템은 Hoodie, Delta Lake, Iceberg 및 Payon Analytical DB for MySQL을 포함한 인기 있는 레이크 형식과 호환되며, 컴퓨팅 및 스토리지 분리 아키텍처를 따라 온라인 분석과 오프라인 컴퓨팅 기능을 모두 지원합니다. 각 계층의 컴퓨팅 및 스토리지 기능은 독립적인 탄력성을 갖습니다. 내부 스토리지 엔진은 실시간 원자적 업데이트 및 삭제를 지원하며, 스토리지 계층에는 상태 비저장 원격 데이터 읽기를 지원하는 SDK가 포함되어 있습니다. 자, 이제 오늘의 주요 주제인 서버리스에 집중해 보겠습니다. 먼저 제가 개발한 SQL 기반 분석 데이터베이스의 서버리스 개발 과정을 간략하게 설명드리겠습니다. 초기에 우리는 컴퓨팅 및 스토리지 분리와 비즈니스 격리를 가능하게 하기 위해 기존 MPP 아키텍처 내에 리소스 그룹을 도입했습니다. 리소스 그룹은 Snowflake의 가상 웨어하우스와 유사하게 작동하여 독립적인 사업 부서가 컴퓨팅 탄력성을 확보할 수 있도록 합니다. 이러한 리소스 그룹을 기반으로, 우리는 대화형 쿼리를 위한 대규모 병렬 처리 MPP 실행 모드 와 배치 처리를 위한 대량 동기 병렬 BSP 실행 모델을 개발했습니다 . 이러한 실행 모드는 특정 비즈니스 요구 사항을 충족하도록 맞춤 설계되었습니다 . MPP 실행 모드의 경우 멀티클러스터 확장을 구현했으며, BSP 실행 모드는 온디맨드 확장을 특징으로 합니다. 최신 커널 버전에서는 이러한 실행 모드와 탄력성 전략을 일관된 프레임워크로 통합하고 리소스 그룹 격리를 도입하여 리소스 그룹 내 노드 격리를 강화했습니다. 이제 사용자는 단일 스토리지 기반에 여러 리소스 그룹을 생성할 수 있으며 , 각 그룹은 서로 다른 SQL 계정에 연결되어 다양한 비즈니스의 컴퓨팅 워크로드를 효과적으로 분리할 수 있습니다 . 리소스 그룹 노드는 상태를 저장하지 않으므로 신속한 수동 확장이 가능하며, 대화형 처리와 배치 처리 모두를 지원하는 유연한 시간 기반 탄력성 정책을 적용할 수 있습니다. MPP 및 BSP 실행 모드의 구체적인 내용을 살펴보겠습니다 . MPPP 모드는 모든 실행 작업을 동시에 예약하여 리소스 활용률과 메모리 효율성을 극대화하므로 빠른 응답 시간이 필요한 짧은 쿼리에 이상적입니다 . 하지만 복잡한 ETL 시나리오에서는 MPP 모드가 클러스터 성능에 상당한 부담을 주어 OOM 예외가 발생할 수 있습니다. 반대로 BSP 실행 모드는 SQL 실행을 여러 단계로 분리합니다. 디스크에 셔플 데이터를 임시로 저장하면서 작업을 순차적으로 실행합니다 . 이는 실행 중 최대 메모리 사용량을 크게 줄여줍니다 .
