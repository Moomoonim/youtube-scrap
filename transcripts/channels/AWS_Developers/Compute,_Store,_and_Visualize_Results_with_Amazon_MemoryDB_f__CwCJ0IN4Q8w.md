Radius는 키와 값을 저장할 수 있는 인메모리 데이터베이스로, 업계 전반에서 매우 널리 사용되고 있습니다. 캐싱 목적과 데이터를 빠르게 로드하고 검색해야 하는 모든 상황에서 매우 유용하게 사용될 수 있기 때문에 실시간 분석 분야에서 널리 적용됩니다. 특히 저희와 같은 실시간 분석 사용 사례에서는 radis의 정렬된 세트(Sorted Set)라는 데이터 구조를 활용할 수 있다는 점에서 더욱 중요합니다. 이 구조는 이벤트 수집 시 자동으로 정렬해 줍니다. 첫 번째 작업인 `zc by`를 예로 들어 보겠습니다. ` zc by player 3 and 50`이라는 쿼리가 radis에 전송되었다고 가정해 봅시다. 플레이어 이름과 총 거리에 대한 키 값이 이미 radis에 저장되어 있다고 하면, ` zc by 50` 작업이 실행되는 즉시 radis에서는 두 가지 작업이 수행됩니다. 첫째, 총 거리가 50만큼 증가합니다. 둘째, 이 효과가 순위표 재정렬에 반영되어 순위가 정렬됩니다. 따라서 플레이어 6이 2위로, 플레이어 3이 1위로 이동한 것을 볼 수 있습니다. 이제 다른 작업인 `z add`를 살펴보겠습니다. ` z add GT Player 11`이라는 쿼리를 radis에 전송하면 어떻게 될까요? 이 경우 200이라는 값이 있다고 가정해 보겠습니다. Radius에는 이미 플레이어별 속도 순위표가 저장되어 있습니다. 이때 플레이어 11의 최고 속도가 100에서 200으로 변경되었다고 가정하고 쿼리를 실행합니다. 그러면 Radius는 속도를 100에서 200으로 업데이트하고 자동으로 데이터를 재구성합니다. 이제 플레이어 11이 선두를 차지한 새로운 순위표를 볼 수 있습니다. 하지만 이 쿼리에서 GT 연산을 사용하기 때문에, 예를 들어 속도를 180으로 업데이트한다고 하면 어떻게 될까요? 180은 200보다 작으므로 Radius는 아무런 연산도 수행하지 않습니다. Radius에 저장된 데이터가 이미 200보다 크기 때문에 Radius는 쿼리를 실행하지도 않고 업데이트도 하지 않습니다. AWS에서 Radius 데이터베이스를 호스팅하는 방법에는 Elastic Cache 와 Amazon Memory DB4 Radius 두 가지 옵션이 있습니다. Elastic Cache는 데이터를 메모리에 저장하는 반면, Memory DB는 영구적으로 저장됩니다. 따라서 영구 저장이 중요한 경우에는 Memory DB를 선택할 수 있습니다. 순위표 사용 사례에서 이 부분을 살펴보겠습니다. Amazon Memory DB를 사용하여 지금까지 구축한 아키텍처는 다음과 같습니다. 데이터베이스를 연결하고 Enrich 스트림을 만들었습니다. 이제 Lambda 함수가 쿼리를 읽고 Redis에서 실행한 다음 Grafana에서 시각화하는 데 사용되는 Kinesis 데이터 스트림을 새로 추가하겠습니다. 소스 코드에서 볼 수 있듯이, 2부에서는 네트워킹과 노트북을 이미 생성했습니다. 3부에서는 Kinesis 데이터 스트림인 Results Stream과 Memory DB Sync라는 새로운 구조를 만들 것입니다. Memory DB Sync는 두 가지를 결합한 것으로, 첫 번째는 Redis용 Memory DB 이고 두 번째는 결과 테이블에 푸시한 명령을 Redis용 Memory DB에 동기화하는 함수입니다. Grafana를 열면 두 부분이 있습니다. 첫 번째는 Grafana에 로그인하는 데 필요한 사용자 이름과 비밀번호가 포함된 Secret이고, 두 번째는 Grafana 서버를 호스팅하는 EC2 인스턴스입니다. 원한다면 Grafana 관리자를 사용할 수도 있지만, 간단하게 설명하기 위해 EC2 인스턴스를 사용했습니다. 쿼리가 성공적으로 실행된 후에는 반드시 일시 중지해야 합니다. 한 번에 하나의 쿼리만 실행할 수 있기 때문입니다. 다음은 조인에 관한 내용입니다. 이벤트 테이블과 플레이어 ID를 조인해 보겠습니다. 시스템 시간을 이벤트 시간으로, 시간대를 플레이어 ID를 기준으로 지정하는 구문을 사용할 수 있습니다. 데이터를 조인하면 출력에서 시스템 시간을 기준으로 조인된
