## 스크립트

이 과정의 첫 번째 부분에서는 HL을 사용하여 가중치 및 B 모델 레지스트리와 웹훅을 이용한 자동화 실행 방법을 배웠습니다. 이번 강의에서는 Kubernetes Launch를 사용하여 자동화를 실행하는 다른 방법을 살펴보겠습니다. 먼저, Docker 큐와 평가 스크립트를 실행할 간단한 Docker 이미지를 사용하는 가장 간단한 설정을 사용하겠습니다. 하지만 향후 강의에서는 Kubernetes 클러스터 또는 분산 컴퓨팅 환경에서 작업을 실행하는 매우 강력한 개념인 Launch에 대해 더 자세히 배우게 될 것입니다. Launch는 간단한 자동화를 넘어 훨씬 더 많은 가치를 제공합니다. 다시 한번, 매우 간단한 사용 사례부터 시작해 보겠습니다. 먼저 평가 스크립트를 실행할 Docker 이미지를 생성해 보겠습니다. 이 Docker 파일은 매우 간단한 Python 환경을 제공하며, 평가에 필요한 구성 요소를 설치한 다음 방금 살펴본 평가 스크립트를 실행합니다. 자, 이 명령어를 복사해서 Docker 이미지를 만들어 보겠습니다. 이미지가 생성되었으니 이제 이 이미지를 이용해서 Weight Sys Launch Job을 만들 수 있습니다. Weight Sys에서 Job은 Weights and Bias를 통해 실행할 수 있는 템플릿과 같습니다. 이 템플릿을 사용하여 실험을 실행하고, 평가를 수행하고, 파이썬으로 할 수 있는 거의 모든 작업을 Weight Sys Job으로도 할 수 있습니다. Was&amp;B CLI 명령어를 사용해서 Job을 생성해 보겠습니다. Was&amp; B Run 명령어를 사용하면 실행 시에도 Job을 생성하고 코드를 로그에 기록할 수 있습니다. 그런 다음 Was&amp; B Launch 명령어를 사용해서 Job을 복제할 수도 있습니다. 이제 Was&amp;B CLI를 사용해서 Job을 생성해 보겠습니다. 보시다시피, 이 명령어는 이미지 유형의 Docker Job을 생성하고 있습니다. 이렇게 하면 프로젝트에 Job이 생성됩니다. 이제 프로젝트로 이동해서 방금 생성한 Job을 살펴보겠습니다. WBUUS 프로젝트에 Job이 생성되어 있는 것을 볼 수 있습니다. 여기 작업 목록이 있는데, 이게 바로 평가 작업입니다. 방금 생성한 거라 아직 실행된 작업이 없죠. 클릭하면 확장할 수 있고, 네, 이 작업을 실행할 수 있습니다. 하지만 작업을 실행하려면 작업이 실행될 수 있는 컴퓨팅 자원이 필요하죠. 이게 바로 실행 큐의 개념입니다. 다시 설명으로 돌아가서 실행 큐를 생성해야 합니다. 이 큐는 어떤 환경에서든 실행할 수 있지만, 간단하게 제 MacBook에서 실행되는 큐를 만들어 보겠습니다. 이렇게 하면 Weights &amp; Bies 서버에서 제 로컬 컴퓨터에서 실행되는 작업을 트리거할 수 있습니다. 이를 위해 ' 실행' 메뉴로 이동해서 엔티티에 새 Docker 큐를 생성해야 합니다. 이 경우에는 Review C 엔티티에서 작업하고 있지만, 팀이나 개인 엔티티에서 작업할 수도 있습니다. 다시 Review C로 돌아가서 ' 실행' 메뉴로 이동하고 새 큐를 생성해 보겠습니다. 이 큐는 이 엔티티에서 실행될 것입니다. 이 큐의 이름을 '실행'이라고 하겠습니다. Q 평가를 위해 Docker 컨테이너를 사용할 것입니다. 여기서 설정해야 할 한 가지는, 그리고 이는 rmy에서도 확인할 수 있듯이, 평가 작업을 실행하는 환경에서 OpenAI API 키 변수에 접근할 수 있도록 해야 한다는 것입니다. 왜냐하면 gp4 API를 호출하는 데 필요하기 때문입니다. 따라서 이 환경 변수를 여기에 전달하고, 로컬 환경에서 제대로 가져오는지 확인하겠습니다. 여기에 이 ​​변수를 입력하고 Q를 생성해 보겠습니다. 이제 Q가 생성되었지만, 활성 에이전트가 없기 때문에 실행되지 않고 있습니다. 즉, 이 Q에서 작업을 가져와 수신하는 컴퓨팅 리소스가 없습니다. 이제 에이전트를 추가하는 것이 좋겠습니다. 여기에 " 이 Q를 사용하여 에이전트를 시작합니다"라는 명령어가 있습니다. 이 명령어를 복사하여 터미널로 돌아가서 여기에 입력하겠습니다. 이제 이 환경에서 에이전트를 시작해 보겠습니다. 보시다시피, 지금 에이전트가 실행 중이고 평가 큐에서 작업을 가져오고 있습니다. 현재 이 큐에는 작업이 전송되지 않았기 때문에 실행 중인 작업이 없습니다. 자동화를 설정하기 전에 작업을 테스트하는 것이 좋습니다. 작업으로 돌아가서, 저희의 작은 랩 작업 공간으로 돌아가 보겠습니다. 작업 목록에는 평가 작업이 있고, 이제 이 작업을 실행할 수 있습니다. 평가 큐를 선택하겠습니다. 방금 생성한 Docker 큐입니다. 보시다시피 조직에서 사용 가능한 Kubernetes 클러스터를 사용할 수도 있지만, 간단하게 진행하기 위해 Kubernetes는 이 평가 스크립트를 실행하는 데 필요하지 않습니다. 작업 우선 순위를 조정하고, 큐 구성을 변경하고, 대상 프로젝트를 변경할 수 있습니다. 모든 설정이 올바른 것 같습니다. 이제 작업을 실행해 보겠습니다. 터미널을 확인해 보면 에이전트가 큐에서 작업을 가져왔고, 실행 중인 것을 볼 수 있습니다. 평가 스크립트를 실행하고 ' candidate'라는 이름의 아티팩트가 없으면 실패합니다. 아, 그러고 보니 평가 스크립트를 실행하기 전에 방금 학습시킨 모델을 모델 레지스트리로 옮기고 'candidate' 태그를 지정해야 합니다. 실행 작업이 이 태그를 필요로 하기 때문입니다. 다시 프로젝트로 돌아가 보겠습니다. Weights and Bias에서 최근 실행 기록을 확인할 수 있습니다. 특히 저는 후보 모델에 접근할 수 없어서 실패한 평가 작업을 보고 싶습니다. 이제 학습 실행 기록에 집중해 보겠습니다. 필터를 추가하고 작업 유형을 ' 학습'으로 선택하면 1시간 전에 완료된 실험이 표시됩니다. 이 작업은 우리가 실행한 것입니다. 학습 지표를 살펴보겠습니다. 학습 손실과 거래 손실은 단일 단계로 고정되어 있습니다. 음, 그 이유는 이 모델을 아주 오랫동안 실행하지 않았기 때문입니다. 하지만 여기에서 평가 결과를 확인할 수 있고, 아티팩트로 이동하면 모델 아티팩트가 보일 것입니다. 이제 이 모델을 레지스트리에 추가할 시간인 것 같습니다. 작은 명령어 llm에 추가해 보겠습니다. 이 모델은 10억 달러 규모의 10억 개 매개변수를 가진 모델로, 명령어를 기반으로 미세 조정 중입니다. 후보 값을 지정하고 레지스트리에 연결해 보겠습니다. 레지스트리에서 모델을 확인해 보면 후보 값과 함께 추가된 모델을 볼 수 있습니다. 기준선도 있는지 확인해 보겠습니다. 네, 이미 모델이 있습니다. 이 모델 레지스트리에 추가된 첫 번째 학습 모델에 기준선이 있습니다. 이제 자동화를 다시 실행하기에 좋은 시점인 것 같습니다. 이번에는 모든 것이 잘 작동하기를 바랍니다. 프로젝트와 작업으로 돌아가서 다시 실행해 보겠습니다. 보시다시피... 자, 이번이 두 번째 실행이므로 가장 최근 실행에서 설정을 복제할 수 있습니다. 기본 설정이 몇 가지 있는데, 여기에 표시됩니다. 일부 설정을 조정할 수 있지만, 지금은 그대로 두겠습니다. 여기서는 아무것도 변경하지 않겠습니다. 다시 Docker Cube 평가를 선택하고 우선 순위를 중간으로 설정한 다음 작업을 시작하겠습니다. 콘솔로 돌아가면 에이전트가 작업을 감지하고 실행 중인 것을 확인할 수 있습니다. 후보 선호도 점수는 0.04로, 아주 약간의 개선이 있지만 기준선과 매우 유사합니다. 평가는 가중치 및 편향에 기록됩니다. 방금 가중치 및 편향에서 Lou 작업을 트리거했는데, 이는 수동으로 수행한 것입니다. 다음 강의에서는 동일한 작업을 모델 레지스트리 자동화를 통해 수행하는 방법을 알아보겠습니다.
